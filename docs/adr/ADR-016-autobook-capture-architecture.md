# ADR-016 自动记账的采集与解析架构（无障碍服务 + 通知监听双通道）

**状态：** 已采纳（2026-10-13）
**范围：** 第二十一轮 REQ-83（T21-1…T21-9），属 **L3 变更**（新增数据模型、新增两项系统设置页授权、新增采集组件与一端点候选）
**关联文档：** `docs/APP-CONTEXT.md` §2.4（非目标收窄）；`docs/product/non-goals.md`；`docs/legal/privacy-policy-v1.md` §2.4（自动记账读取范围）；`docs/legal/accessibility-disclosure.md`（无障碍用途说明）；`docs/architecture/security.md`（采集原文的日志禁令）；`docs/architecture/data-model.md`（`auto_captures` 表）；`docs/architecture/ai-architecture.md`（文本解析入口）；`docs/architecture/ai-agent-architecture.md` §4.7；`docs/product/principles.md`（PR-2 / PR-3）

> **为什么需要一份 ADR：** 这个能力同时动到**四条对外可核对的承诺**——① `APP-CONTEXT.md` 的「当前非目标」曾把「自动抓取流水」**写成不做**；② 隐私政策 §2.3 写着「不收集其他应用的使用数据」，而两条采集通道读的**都是其他 App 的内容**；③ 无障碍服务在中国软件行业协会 2025-04 标准与 Google Play 政策下是**需要显著披露与用途限定**的高敏授权；④ PR-2「永不产生用户不知情的账目」是硬约束而非参考。这四条里任何一条被后来的实现者**重新推导一遍**，都可能推出不同的结论（尤其是「为什么不直接读短信」与「为什么不用悬浮窗」——这两个是市面产品的默认做法）。把取舍写死在这里，是防止同一问题被反复推翻的唯一手段。

## 背景

### 诉求

用户原话：「给 aozora 新增一个自动记账功能……探索一下市面上安卓环境下的 app 都怎么实现自动记账功能，然后对需求尽可能的探究和挖掘找出一个效果较为理想且稳定的方案」。拆成四个子诉求：①**支付发生后不用手动记**；②**效果理想**（金额准、商户认得出、分类选得对）；③**稳定**（不因第三方改版失败、不被省电策略杀掉、不漏记不重记）；④**方案有调研依据**。

**同日澄清（2026-10-13）**：「修改一下，**可以通过无障碍服务这个渠道来实现自动记账的功能**」。→ 首版「第一版明确不做无障碍」的取向作废，采集层改为**双通道**。

### 市面调研结论（2026-10-13，安卓环境）

| 通道 | 代表产品 | 能拿到什么 | 硬伤 |
|---|---|---|---|
| **无障碍服务** `AccessibilityService` | 钱迹、一木、iCost、小星、小花、指尖管家 | **金额 + 商户/对方 + 时间 + 订单号 + 收支方向**（信息最全）；不依赖用户的通知设置 | 依赖第三方页面文案与结构，**改版即可能失效**；审核与合规成本；`FLAG_SECURE` / 支付保护页读不到 |
| **通知监听** `NotificationListenerService` | 记花、chaoxi-jizhang、小星（银行短信靠通知而非 `READ_SMS`） | 通知标题与正文；**不随第三方 UI 改版失效**；`<uses-permission>` 零新增 | 部分通知**不含商户名**；用户关掉该来源的通知就收不到 |
| 读取短信 `READ_SMS` | 早期方案 | 银行短信格式稳定 | `READ_SMS` 仅默认短信应用可申请，第三方上架严审；**与本仓库隐私政策直接冲突** |
| 截图 / 分享识别 | iCost、飞鸭 | 零权限风险 | 需用户**主动**分享，不「自动」 |
| 账单文件导入 | 几乎所有记账 App | 平台原始账，权威 | 需定期手动导出，实时性差 |
| 系统级 / 官方 API | 小米钱包（已终止内测） | 体验最好 | **第三方不可得** |
| Xposed / Hook | 开源 AutoAccounting | 数据最细 | 需 root / LSPosed，受众极小，属注入第三方进程 |

**三条结论：**

1. **没有任何单一通道能同时做到「全自动 + 稳定 + 合规」**——市面产品的真实形态一律是**多通道组合 + 待确认/补录**，没有例外；效果最好的那批清一色是「无障碍（拿全字段）+ 通知（补漏、免 UI 依赖）」。
2. **两条通道的失效面几乎不重叠**，这是双通道能成立的根本原因：无障碍怕 UI 改版、怕支付保护，但不依赖用户的通知设置；通知不随 UI 改版失效，但缺商户名、且用户关通知就收不到。**二者互补 → 互为兜底**，比单独任何一条都稳。
3. **代价是明确的、必须写进口径的两条**：无障碍带来**审核与维护成本**，通知带来**覆盖率上限**——**都不许宣传成「100% 自动」**。

### 真正的问题形态

两条通道产出的**都是文本**（无障碍按行拼装页面可见文本，通知取标题 + 正文）。这决定了本方案的形状：**它们可以汇入同一套解析层**，不必为无障碍单独造一条解析链。也因此**去重必须做在文本层**——同一个页面会高频抖动（`TYPE_WINDOW_CONTENT_CHANGED`）、同一条通知会重复回调（`onNotificationPosted`），而两条通道还会**同时抓到同一笔**。

## 备选方案

| 方案 | 做法 | 结论 |
|---|---|---|
| **A. 只做通知监听** | 单通道 | **否决。** 通知缺商户名 → 分类准确率有硬上限；用户关掉该来源的通知就完全失效，没有第二条防线 |
| **B. 只做无障碍** | 单通道 | **否决。** 第三方改版即失效，且**没有任何兜底**——这正是市面产品被一次改版打垮的形态 |
| **C. 无障碍 + 悬浮窗弹确认** | 市面常见组合 | **否决。** 悬浮窗要 `SYSTEM_ALERT_WINDOW`（高危权限）。本产品**用已有的 `POST_NOTIFICATIONS` 通知触达**替代：少一个高危权限，UX 不减 |
| **D. 无障碍 + 通知前后台常驻** | 引入前台服务保活 | **否决。** 本仓既定取向是「网络不进后台服务、不引入前台服务」；两条通道都是**系统托管服务**（由系统在授权后自行拉起），不需要自造保活 |
| **E. 无障碍（只读）+ 通知监听，共用一张表与一套解析** | 双通道 + 三级去重 | **采纳** |

## 决策

### 决策 1：采集通道 = 无障碍服务（只读）+ 通知监听，两条并行

**通道一（主）无障碍服务**：唯一能拿到「商户名 + 订单号」的通道，且不依赖用户的通知设置。**通道二（并行）通知监听**：不随 App 改版失效，覆盖微信 / 支付宝 / 云闪付 / 银行 App / 银行短信的**通知**。

**通道关系**：并行采集，同笔去重后**取信息最全的一份**（无障碍 > 通知）。两条通道产出的都是文本，因此**汇入同一套解析层**。

### 决策 2：仍然禁止的四项采集手段

| 不做 | 理由 |
|---|---|
| **读取短信**（`READ_SMS` / `SMS_RECEIVED`） | 第三方上架基本不可得；**且与隐私政策正面冲突**。银行短信的**通知**由通知监听覆盖，**不需要**短信权限——这是关键区分 |
| **悬浮窗**（`SYSTEM_ALERT_WINDOW`） | 市面无障碍方案普遍要它来弹确认窗；本产品**用已有 `POST_NOTIFICATIONS` 通知触达**替代（「已记一笔 ¥32 · 星巴克 · 点击确认」） |
| **Xposed / Hook** | 需 root / LSPosed，受众极小，且属注入第三方进程 |
| **自动操作第三方 App** | 见决策 3 |

**可被守住的自证量**：`AndroidManifest.xml` 的 `<uses-permission>` 集合**逐条不变**——两条通道都靠 `<service>` + `android:permission` 声明、授权在系统设置页，**都不走 `<uses-permission>`**。该集合由 `SecurityConfigTest.kt` 的反向断言钉住（不得出现 `READ_SMS` / `SYSTEM_ALERT_WINDOW`）。

### 决策 3：无障碍服务**只读不写**（本轮的合规分界线）

`AccessibilityService` **只订阅窗口事件 + 读取节点文本**，**禁止调用任何 `performAction`**（`ACTION_CLICK` / `ACTION_SET_TEXT` / 手势派发一律禁止）。

这是「读屏记账」与「AI 智能体操作第三方 App」的分界线——2025 软协标准与不正当竞争判例的落点都在后者。守护方式三处：**配置 XML 不声明 `canPerformGestures`**；`SecurityConfigTest.kt` 加反向断言；用例层面**断言服务代码中不存在 `performAction` 调用**。

### 决策 4：采集层只做「预筛 + 落库」，不做网络、不做解析

两条通道的过滤都是**纯函数**（`AccessibilityFilter` / `NotificationFilter`），判定在设备内完成。对齐本仓「网络不进后台服务」的既有取向，也避免在系统回调里阻塞。

★ **两条通道共同的红线：非支付类内容当场丢弃，不落库、不上行。** 无障碍通道的风险更高（它会看到整个页面的文本），故它还多一条：**只在用户选定来源的支付 / 账单相关页面上工作，其他页面连文本都不拼装**。两个过滤器都需守护用例，且**反向验证**（打回缺陷形态确认用例变红）。

### 决策 5：新增 `auto_captures` 表（Room v11 → v12），三级去重

「一条被捕获、尚未解析/确认的原始事件」有独立生命周期（captured → parsed → pending_confirm → committed / ignored / failed）、需要**去重键唯一索引**、需要**原文留档**，且**双通道写同一张表**（靠 `sourceChannel` 区分）。`pending_mutations`（装已定型的写操作）语义不符，**不得挪用**。迁移走 `MIGRATION_11_12`，**不开启 `fallbackToDestructiveMigration`**。

**去重分三级（定死）：**

| 级 | 判据 | 处置 |
|---|---|---|
| **L1 同通道同事件** | `dedupeKey = hash(sourceChannel + sourcePackage + 事件 key/postTime + 归一化文本)` | **唯一索引 + 自动丢弃**。★ 这一级在无障碍通道上是**必需的**——`TYPE_WINDOW_CONTENT_CHANGED` 在页面上高频抖动，不按事件去重必然重复入账 |
| **L2 跨通道同笔** | `mergeKey = hash(方向 + 金额分 + 分钟级时间桶)` 命中**且**（两边都无商户名 **或** 商户名相同） | **合并为一条**（`mergedInto` 留痕），保留信息最全的那份，标 `multi_source`。**两条通道同时抓到同一笔 = 两个独立来源印证**，这是允许自动合并的依据 |
| **L3 同额但不可判定** | 商户名不同 / 时间窗外的同额 | **不合并**，只标「疑似与其他一笔重复」的**提示**。同额消费是日常（两杯 18 元咖啡），**自动合并会吃掉真实账目** |

★ **合并只解决「不重复入账」，不改变「要不要问用户」**——合并后仍按置信度走，且**在待确认箱与交易详情里可见来源数**（不静默）。

### 决策 6：幂等键一律确定性生成，**禁止任何 LLM 参与**

`dedupeKey` / `mergeKey` 都是**确定性 hash**（通道、包名、时间、金额、归一化文本的纯函数）。本仓已有惨痛先例——**LLM 生成 UUID 当幂等键 → 照抄训练示例值 → 撞键 → 静默丢弃**（T18 收口实证）。任何「让模型给这笔账编个 id」的形态**一律禁止**。

### 决策 7：解析层 = 本地规则（离线兜底）+ 服务端模型（主），入口判据先行

- **本地规则**（`LocalCaptureParser`，纯函数 + 模板）：输入统一是文本，两条通道**共用同一套模板**（微信支付页/通知、支付宝页/通知、云闪付、银行 App、银行短信各若干条），**离线可用**。
- **服务端**：**判据先行**——先用既有 `/ai/interpret` 直接喂真实文本取一轮命中率实测，**够用就不新增端点**（最小改动）；不够才新增 `POST /ai/parse-notification`（复用 v1 proposal 骨架与 `_render_categories_section` 分类注入面，提示词独立）。无论走哪条，**都计入 `ai_usage`**，guest 日配额照常生效。
- ★ 提示词必须显式处理四类「**不是消费**」的语义——**退款 / 转账（含信用卡还款）/ 理财基金买入 / 红包收发**（否则会把这些记成消费，污染收支统计）。
- **商户记忆**第一期**不开新表**：用 `auto_captures` 表内同 `merchantKey` 的已 `committed` 记录回查上次分类。★ 无障碍通道让这条真正可用——通知常常拿不到商户名，无障碍拿得到。

**为什么不在 agent loop 里做**：自动记账的解析是**单轮、无工具、无多步推理**的文本结构化，接进 loop 只会平白付出编排与上下文成本；写库仍走既有 `Repository.enqueueInsert` + 确认门，PR-2 不放松。

### 决策 8：入账策略沿用 PR-2，不新造卡片类型

**高置信快速通道自动入账（立即可见 + 可撤销）；低置信 / 缺字段 → 待确认箱。** PR-2 原文即此口径（`docs/product/principles.md:10`），**自动记账只是新增提案来源**，不改 v1/v2 提案与确认卡的既有形状。

### 决策 9：默认关闭 + 两类授权各自独立 + 「设置页授权」形态

**默认关闭、用户显式开启**——「永不产生用户不知情的账目」的延伸：**不知情就不该开始**。

无障碍与通知**是两种授权、两个目标**，各自独立（只授一个也应有可用的一半能力），且**都不是运行时权限**：无障碍只能用 `AccessibilityManager.getEnabledAccessibilityServiceList()` 判定 + 跳 `Settings.ACTION_ACCESSIBILITY_SETTINGS`；通知只能用 `NotificationManagerCompat.getEnabledListenerPackages()` 判定 + 跳 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`。**不得**试图用运行时权限弹窗走这两条路（那条路只会产出一个永远 `DENIED` 的假状态）。UI 每类给**三种态**：未授权 / 已授权 / 已授权但服务被系统或用户停用。

### 决策 10：用户可见文案的诚实口径

**禁止**「100% 自动」「绝不遗漏」。对用户只有两句是对的：「**支付类通知到了、或在支付页上，就会自动记**」+「**没记上的可以一键补**」——与 T20-9「回执文案不得说谎」同一种纪律。

## 后果

### 残余与责任人

1. **无障碍规则有持续维护成本**：依赖微信 / 支付宝的页面文案与结构，对方改版可能导致规则失效，须持续适配。登记 R-PROD-58。
2. **通知通道的覆盖率不可控**：用户可关闭该来源通知 → 就收不到。登记 R-PROD-59。
3. **跨通道同额只能提示、不自动合并**（L3）：这是刻意的（自动合并会吃掉真实账目），代价是用户偶尔会看到「疑似重复」提示。登记 R-PROD-60。
4. **商户名缺失时分类准确率有上限**：通知通道常见此情形。登记 R-PROD-61。
5. **侧载授权门槛**：Android 13+ 侧载应用授予无障碍需先在应用详情页「允许受限设置」（Android 15+ 更严），直接影响走查步骤与用户引导。登记 R-PROD-62。
6. **`FLAG_SECURE` / 支付保护页读不到**：系统限制，无法绕过，须在真机上确认微信/支付宝支付结果页在支付保护开启与否两种状态下的可读性（T21-4 取数）。
7. **隐私政策的版本面**：`docs/legal/privacy-policy-v1.md` 是版本化 + 与 `UserConsent` 绑定的一致同意面，本轮只做**内容修订**（不改版本号与文件名，避免与客户端 `POLICY_VERSION = 'v1'` 脱节）；**客户端内联副本** `app/src/features/legal/LegalPage.tsx` 的同步归后续 UI 卡（T21-7 面）。登记 R-PROD-63。
8. **合规物料是上架前置**：`docs/legal/accessibility-disclosure.md` 与两份商店申报口径随本 ADR 一并落笔；**不得先写码后补合规**。
9. **风险册正文**：本卡只登记编号占位（R-PROD-58…63），正文由 T21-9 收口统一落笔。
