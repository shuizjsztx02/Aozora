# ADR-010 设备能力通道的服务端协议与 loop 暂停/恢复

**状态：** 已采纳（2026-09-19）
**范围：** M7 T-M7-05e（P4，批次 2；服务端侧，客户端执行器归 05f）
**关联文档：** `docs/architecture/ai-agent-architecture.md`（§4.3 设备能力通道、§4.4 Loop 不变式、§6.2 事件类型表、§8.1 事件类型、§8.4 部署前提、§12.2 未决 #4）、`docs/architecture/ai-architecture.md`（设备能力通道协议小节）、`server/src/modules/ai/devices.py`、`docs/APP-CONTEXT.md` §12 `D-PROD-16`

> **为什么需要一份 ADR：** 05e 是**第一个跨进程的双向通道**——此前所有 SSE 事件都是服务端单向下发，客户端的上行全部是「另起一次普通 HTTP 请求」（输入、确认卡、分叉）。设备通道的「需结果」类要求**同一个 Turn 在服务端挂起、被一次上行唤醒后接着跑**，这引入了三个此前不存在的取舍：暂停态存在哪里、上行端点如何鉴权与收敛、以及挂起期间的边界（超时/取消）算工具失败还是算回合终止。这三件事同时被 05f 与后续所有设备能力依赖，取舍必须固化。

## 背景

### 现状：三条影响结论的硬事实

| # | 事实 | 依据 |
|---|---|---|
| 1 | **`device_request` 是八类 SSE 事件里唯一没有生产者的一类**，`stream.py` 明写「无生产者——设备能力通道归 P2」 | `stream.py:34,72`（本卡顺手改正为 P4） |
| 2 | **生产是单 worker 部署**，会话状态可用进程内 + DB 持久化；内存限流字典同样是单实例假设 | `server/Dockerfile:52`（无 `--workers`）、`service.py` 的限流字典注释、架构 §8.4 |
| 3 | **客户端既有的设备类桥命令已全部就位**（权限 / 语音 / 图片 / 分享 / 触感 / 提醒 / 小组件 / 图标 / 主题背景），但触发它们的是**本地表单路径**（`use-assistant` 的直接桥调用），不是服务端 loop | 架构 §3.2 映射表；`BridgeProtocol.kt`；02g 的 SSE 通道 |

### 问题的真正形态

架构 §3.2 把十三个域全部映射为「对话可完成」，其中标**设备**的项（提醒 / 小组件 / 权限 / 语音 / 图片 / 分享 / 触感 / 图标）**永远无法上云**：它们只能在用户设备上执行。服务端 loop 要触达它们，必须有一条「服务端下指令 → 客户端执行 → 结果按需回传」的通道。**「按需」是这条通道的设计核心**：分享文本、刷新小组件、触感反馈的结果不影响后续推理，为它们引入一次往返与一份挂起态纯属浪费；而权限申请、语音转写、图片选择的结果是任务继续的必要输入。

## 备选方案

| 方案 | 内容 | 评估 |
|---|---|---|
| **A. 全部走「需结果」**（下发即挂起，一律等回传） | 所有设备指令都挂起等回传 | **否决。** 单向类（触感 / 刷新小组件 / 分享）的结果没有任何下游消费者，挂起只会让每一轮白等一次回传；且客户端任何一个这类调用没回报（用户划走了分享面板），回合就多停一个超时窗 |
| **B. 全部走「单向」**（下发后不管结果） | 设备指令只下发，结果不进 loop | **否决。** 权限被拒 / 用户取消选图 / 语音转写失败都是**必须让模型知道**的结果——不知道它会对用户谎报「已经帮你选好了」 |
| **C. 分两类 + 需结果类进程内挂起**（**采纳**） | 单向：下发即继续；需结果：挂起 → 上行回传 → 恢复。挂起态放**进程内注册表**（单 worker 前提） | 与架构 §4.3 的分法一致；挂起态的生命周期**就是一次 Turn**（秒级到分钟级），不值得为它建表；单 worker 已是本项目的既定部署前提（事实 2） |
| **D. 需结果类落库（设备请求表 + 轮询）** | 设备请求与结果各写一行，loop 轮询或重启后恢复 | **否决。** 引入一张新表 + 迁移 + 状态机 + 恢复语义，代价远超收益：断连本来就走「连接级取消」，用户重发即可；而跨进程恢复一个**正在对话中**的 Turn，本项目的 agent 路径从未承诺（04b 的恢复是「按 conversation_id 重开一轮」，不是续跑一个挂起中的 Turn） |

## 决策

### 决策 1：两类协议按架构 §4.3 落地，`device_request` 载荷即完整信封

单向（`kind="one_way"`）与需结果（`kind="result"`）两类共用一个帧与一套载荷：

```json
{
  "request_id": "dev-<uuid4>",     // 需结果类的回传凭据（单向也给，便于客户端去重与留档）
  "step": 3,                        // 1 起的 Step 序号，与其它事件的 step 同源（步骤卡分组）
  "kind": "one_way" | "result",
  "capability": "image.pick",       // 协议层能力名（见决策 6）
  "payload": { ... },               // 已过服务端 schema 校验的参数（只含模型给的原始参数）
  "timeout_seconds": 120            // 仅 result 类：客户端据此提醒用户，服务端按同一值收敛
}
```

### 决策 2：需结果的挂起态是**进程内注册表**，不落库

`devices.DeviceChannel`：`request_id → Future`，随 Turn 生随 Turn 灭；`wait()` 内部套超时，`finally` 一律注销条目。**不在 DB 建表**（见方案 D）。单 worker 是既定前提（事实 2），与 02f 的会话配额、04d 的保留期任务同一取向。

**代价（已知并接受，已建项 R-PROD-34）：** ①`--workers > 1` 时回传可能落到另一个进程 → 挂起请求等满超时窗才收敛（不会错写数据，只是慢）；②进程重启（部署、reload）会让挂起请求直接消失，客户端的上行拿到 404 —— 客户端按「这一次设备操作作废」处理即可（用户重说一遍的成本）。

### 决策 3：上行端点 `POST /ai/device-result`，**404 覆盖三种「回不去」的情形**

请求体 `{request_id, status, data?}`，`status ∈ {ok, denied, unavailable, failed}`；回 `{accepted: true}`。

- **不存在 / 已回传 / 已超时 → 同一个 404 `device_request_not_found`**（三者不可分辨）。理由与 03a 的会话端点同构：①**重试安全**——客户端在弱网下重发一次回传，不该被当成错误弹给用户；②**不泄漏存在性**——别人的 request_id 与已不存在的 request_id 得到同一个答案。
- **归属按 `user_id` 校验**（挂起时记下，回传时比对），别人的请求 id 一律 404，**不是 403**（403 等于承认「这个 id 存在但不是你的」）。
- **不要求 `conversation_id`**：挂起条目自己知道它属于哪个会话与用户，多一个由客户端上报的字段就多一条需要交叉校验的输入。

### 决策 4：设备失败是**工具级结果**，不新增 `StopReason`

超时 / 拒绝 / 不可用 / 失败四种收敛都作为**配对的 tool 结果**（安全枚举码）回喂模型——它据此向用户解释，回合照常往下走（架构 §11.1 的「一次工具调用失败不整体降级」）。**`StopReason` 不新增取值**：设备失败不是「任务终结」，把它做成终止原因会造出一个客户端必须渲染、而 `_wrap_up` 又无事可交代的状态。取消与断连沿用既有路径（连接级取消，`CANCELLED` 在 `/ai/agent` 上仍不可达——04b 的定案不变）。

### 决策 5：`device_request` 的**日志事件仍不接生产者**

架构 §6.2 的日志事件 `device_request` 保持「无生产者」。理由：设备指令的下发与结果**已经**由 Surface 事件留档了——模型的那次 `tool_call` 与配对的 tool 结果消息（`{"status":"sent"}` / `{"status":"ok",...}` / 错误码）都在日志里，再写一条结构性事件是把同一件事记两遍，而它没有任何消费方（投影 A 不收、投影 B 无渲染路径、投影 C 的审计要的是「谁在什么时候让设备做了什么」，tool 结果已足够）。

### 决策 6：`capability` 是**协议层能力名**，不与桥命令表耦合

设备工具单列一份服务端目录（`devices.py` 的 `DEVICE_TOOLS`），**不进 `tools.py` 的工具注册表**：设备工具没有 DB handler、执行体在客户端、执行语义分两类，与「服务端直连 DB」的工具是两套。工具名沿用 provider 的字符集约束（**下划线**，点号会让 provider 直接 400——02c 收口实测），协议字段 `capability` 用点号（它只出现在 SSE 帧与上行回传里，不过 provider）。

**能力名 → 桥命令的映射归客户端（05f 的分派表）**，可能是一对多：`voice.transcribe` 在桥上是一对（`voice.startRecording` → 用户停止 → `voice.stopRecording` 回文本），协议层只看成一个能力。服务端因此不需要知道客户端命令表的形状。

### 决策 7：开关 `ai_device_channel_enabled` 默认 **false**

开启前，loop **不注入**设备工具（模型看不到它们，行为与 P1 逐字相同）。理由：设备能力要被执行，得有客户端执行器（05f）——在那之前让模型调用一个没人应答的能力，会让回合白等一个超时窗，用户看到的是「卡住两分钟然后说没做成」。默认关闭同时保证 P4 其余卡与全部既有用例的基线不变（与 02g 的 `ai_agent_enabled` 同一取向）。

### 决策 8：回传数据**不设大小上限**

与读工具的结果同口径（读工具本来就整块账本数据回喂）。设备侧该做的是**不把大对象塞进回传**（图片走既有 `attachments/upload` 链路，只回 `attachmentId` 之类的小引用），这是 05f 的分派责任，不是服务端的截断问题——截断一个结构化结果只会让模型拿到半截数据。
