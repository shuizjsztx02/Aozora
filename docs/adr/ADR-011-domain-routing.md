# ADR-011 域路由：选择注入哪些工具域

**状态：** 已采纳（2026-09-20）
**范围：** M7 T-M7-05g（P4，批次 5）
**关联文档：** `docs/architecture/ai-agent-architecture.md`（§7.2 域分组、§8.1 事件类型、§12.2 未决 #2 与「易混淆点」）、`server/src/modules/ai/routing.py`、`server/src/modules/ai/agent.py`、`server/src/modules/ai/stream.py`、`docs/risk-register.md`（R-PROD-17）、`docs/APP-CONTEXT.md` §12 `D-PROD-17`

> **为什么需要一份 ADR：** 架构 §12.2 在 P1 就把「域路由归 P4」定死了，但**只定了时机、没定形态**。05g 领取时工具集已到 54 个 / 14 域（05b/05c/05d），而架构 §7.2 的经验上限是「单域 5–8 个」——**每一轮注入 54 个工具**这件事本身违反了自己写下的判据。落地形态有三个真正开放的问题：**用什么判据选域**（规则还是模型）、**判错时往哪边倒**（多注入还是少注入）、**它是否与入口推理分级共用一套实现**（架构 §12.2 特意标注的易混淆点）。这三件事被后续所有新域依赖，取舍必须固化。

## 背景

### 现状：三条影响结论的硬事实

| # | 事实 | 依据 |
|---|---|---|
| 1 | **`tools_for_domains(domains, contract_version=...)` 早已是注入入口**，P1 就按域过滤，只是每次调用都传 `DOMAINS`（全量） | `server/src/modules/ai/tools.py`；架构 §7.2 |
| 2 | **`phase: routing` 在协议里已定义但无生产者**；客户端（03c）已按「一行占位文案」渲染它，**不需要改一行客户端代码** | `stream.py:30` 原注释「属域路由，P4 才有」；`StepCardStream.tsx` 的 `ROUTING_PLACEHOLDER` |
| 3 | **注入面按轮变化是安全的**：`AgentLoop` 的 `_advertised`（可执行集合）与 provider 载荷同源，收窄即隔离——模型报出域外工具名只会拿到一条可纠正的 `tool_unavailable` | `agent.py` 的 `_inject`；`test_only_advertised_tools_can_execute`（02d 就立过这条边界） |

### 问题的真正形态

不是「能不能选域」，而是**每一轮注入 54 个工具要付两份代价**：

1. **准确率**（R-PROD-17）：工具越多，模型在同域近义工具之间越容易挑错；
2. **上下文成本**：工具 JSON 是 prompt 里最大的一块。实测（2026-09-20）**全量 55 个工具 = 32,418 字符**，而它在**每一个 Step** 里都要重发一遍（深档任务 5–7 步）。

同时有一个**必须避免的失败**：漏注入 = 能力消失。用户说得出的话，模型必须做得到——「这个我做不了」比「多显示几个工具」严重得多。

## 备选方案

| 方案 | 内容 | 评估 |
|---|---|---|
| **A. 不动**（继续全量注入） | 保持 `tools_for_domains(DOMAINS)` | **否决。** 与 §7.2 自相矛盾（域分组的唯一目的是「由预路由选择注入哪些域」），且上下文成本随域数线性上涨——每加一个域，**所有**轮次都变贵 |
| **B. 轻量模型分类器**（多一次小模型调用判域） | 每轮先问一次分类模型「这句话属于哪些域」 | **否决。** ①**给每一轮加一次模型调用**——记账 App 的绝大多数输入是简单输入（架构 §12.2 已定第 2 项：快路径由 loop 自然产生，步数即复杂度），这笔钱正好花在最不该花的地方；②它自己会错，错了还要兜底，于是仍要写一套规则；③多一次网络往返意味着多一个失败点与一个超时预算项 |
| **C. 规则词表**（**采纳**） | 手写中文信号 → 域；命中即收窄，未命中退回全量 | 确定性、零成本、可解释、**可离线量**（误路由率/漏注入率能跑出来而不是估出来）。代价是词表要维护，且覆盖度靠实测——记为 R-PROD-17 的残余 |
| **D. 规则 + 模型兜底**（规则没命中时再问模型） | C 加一层 fallback 分类调用 | **否决。** 只在「没命中」时调用看起来便宜，但「没命中」恰恰是**最不确定**的输入（闲聊、指代、新说法）——在最不确定的地方引入一次模型调用，换来的通常还是「不知道」，而全量注入已经是一个正确的答案 |

## 决策

### 决策 1：规则词表，**不额外调用模型**；判据只有本轮用户输入

`routing.route_domains(text) -> RoutingDecision`：同步纯函数，一次子串扫描，零 IO。

**不看历史**是刻意的：① 指代性追问（「那改成 6000 吧」）本来就命中不了信号 → 兜底全量，能力不受影响；② 拿历史来路由会让决策变成**非确定**（同一句话在不同会话里路由到不同域），而它换来的只是「少注入几个域」。

### 决策 2：**判错时一律多注入**——未命中 = 全量

两边的代价不对称（见「问题的真正形态」），因此误差方向定死在「能力优先」：

| 情形 | 结果 | 代价 |
|---|---|---|
| 命中（`matched=True`） | 只注入命中的域 | 若命中偏窄 → 见决策 3 的跨域信号 |
| **未命中（`matched=False`）** | **注入全部域**（= P1 的注入面） | 只有上下文成本，**没有能力损失** |

`matched` 一并进帧与日志：生产上 `matched=False` 的比例就是**词表覆盖率**的观测量。

### 决策 3：一个信号可以指向**多个域**——近义工具跨域时必须都给

`transaction_summary`（记账域）与 `stats_monthly`（分析域）在「这个月花了多少」这类输入上**都是正确答案**；只给一域就是一次漏注入。因此词表里 `花了 / 支出 / 收入 / 收支 / 消费` 同时指向 `transaction` 与 `analysis`。

这是本方案里唯一「放宽精确度换能力」的机制，也是 18/58 例「多给域」的主要来源——**它们不是错域，是刻意共享**。

### 决策 4：`phase: routing` 帧，**`step` 恒为 0**

载荷：`{phase: "routing", step: 0, domains: [...], matched: bool}`。

`step=0` 是**协议层的取值决定渲染结果**：客户端按 `step` 把同类帧归并进同一条，用 1 会被紧随其后的 `thinking` 覆盖，03c 预留的那行「正在理解你的需求…」就永远不出现。帧的整份生命周期只在**流式期间**（收尾后步骤卡整份释放），因此它不违反 §9.1「简单任务无步骤展示」——那条约束说的是**收尾后**的气泡。

### 决策 5：通知落在**第一个 Step 的入口**，不在 `run()` 里

决策本身在 `run()`（与 `classify_reasoning` 同一处、两件事各算各的），但**发帧**推迟到第一个 Step 入口、`step_started` 之前。理由有二：① 帧序因此是 `routing` → `thinking`，与「域选择不属于任何 Step」一致；② `run()` 里紧接着还有一次用户输入的落库（一次 DB 往返），在那里发帧会让客户端在「这一轮真的开始跑了」之前先收到一个 phase 帧——真实链路上有两条用例正是靠「第一个 phase 帧 ≈ 模型请求已在飞」这个时序性判断的（`test_frames_are_sent_while_the_turn_is_still_running` / `test_disconnect_cancels_the_turn...`）。

### 决策 6：显式 `tools=` **跳过路由**，且不发 `routed` 回调

`AgentLoop(tools=...)` 是调用方已经决定注入面的入口（用例的精确复现、探针的对照组）。那时没有做过选择，因此既不收窄也不发帧——「没有做过的决定不要报出来」。

### 决策 7：词表完整性由**用例**守护，不在导入期报错

`unrouteable_domains() == ∅`（每个域至少有一个信号）由用例钉住，范式同 `stream.TOOL_PROGRESS` 的「每个工具都要有步骤卡文案」。**模块级 `raise` 被明确否决**：它会让整个服务端起不来，爆炸半径远大于「新域暂时路由不到」；而它要防的只是配置疏漏——漏配的真实后果是该域只能靠兜底注入，功能不消失。

> **这条决策在施工中就被验证过**：05g 与 05i（产品帮助域）并行推进时，05i 在 `tools.py` 加了第 15 个域，而词表还没补——导入期 `raise` 的版本让**整个测试套件**报错（十个测试模块 ERROR），换成用例守护后，失败被精确地限制在一条用例上。

### 决策 8：**不设开关**，域路由默认生效

与 `ai_device_channel_enabled`（05e，默认 false）的取向**相反**，原因也相反：设备通道当时默认关闭是因为**客户端执行器不存在**（开了就是白等超时）；域路由不需要客户端做任何事（03c 的占位已就位），且**兜底路径就是 P1 的行为**——最坏情况（词表全不命中）与升级前逐字相同。

**回退方式**＝ 把 `route_domains` 的返回值固定成 `DOMAINS`（一行），或按决策 6 显式传 `tools`；无数据迁移、无契约文件替换、无客户端改动。

## 实测（2026-09-20，`probe_tool_selection.py`）

**离线口径**（`--offline`，58 条用例，零模型调用）：

| 指标 | 值 | 说明 |
|---|---|---|
| **漏注入** | **0 / 58** | 每条用例的「期望工具」所属域都在路由结果里（唯一不可接受的形态） |
| 误路由（多给域） | 18 / 58 | 其中绝大多数是决策 3 的刻意共享，**没有一条是「错域」** |
| 兜底（全量） | 0 / 58 | 用例集全是领域内的输入——**闲聊/指代不在这个集合里**，它们走兜底（另有用例钉住） |
| 平均注入 | 1.4 域 / 6.8 工具 | 全量是 14 域 / 54 工具 |

**上下文成本**（同一口径下的注入面字符数）：全量 55 个工具 = **32,418 字符**；路由后平均 **4,982 字符**（**−85%**，最深的一次 11,793、最浅 519）。这份载荷在**每个 Step** 都要重发。

**真实调用**（58 例，**同一个会话内两臂对跑**，模型 deepseek-flash）：

| 口径 | 路由臂（平均注入 1.4 域） | 对照组（全量 55 个工具） |
|---|---|---|
| 首调命中 | **40/58 = 69%** | **40/58 = 69%** |
| 两步内命中 | **53/58 = 91%** | **53/58 = 91%** |
| 分组 | 05b 19/27、05c 12/20、05d 9/11 | 05b 19/27、05c 11/20、05d 10/11 |

**逐例比对更直白：58 例里 52 例的实际工具序列逐字相同**；8 例不同，且方向两边各有（4 例路由臂首调更准、4 例对照组更准或更省一步），汇总指标因此完全一致。

> **这个结果要说清：域路由没有提高准确率。** R-PROD-17 当初的假设是「工具集过大降低选择准确率」，而实测显示 54 个工具时模型的选择已经很稳（三轮抽样只错过 1 次），**收窄到 7 个工具并没有让它更准**。它买到的是另外两样东西：**每步 prompt 小 85%**，以及**步骤卡上可见的域选择**。
>
> 「域越小越准」（05d 组的 91% 曾是这个判断的证据）在这一轮**没有被复现**：两臂在 05d 组分别是 9/11 与 10/11，在噪声内。那条读数的成因更像是「05d 的五个域各只有 2–3 个工具、近义面天然窄」，而不是「注入面小」——**域切得细**与**注入面窄**是两件事，本轮把它们的区别量出来了。

## 已知残余

| # | 残余 | 归属 |
|---|---|---|
| 1 | **词表是手写的**：覆盖度靠实测，新说法（尤其口语化/长句）会静默退化成全量注入——用户无感，只有 `matched=False` 的比例能在生产上观察 | R-PROD-17；生产统计 |
| 2 | **误路由 18/58**：多给域只损失上下文，但它把「域是注入单位」的收益摊薄了一部分 | 可继续收词；不建议为此牺牲决策 2/3 |
| 3 | **指代性追问一律全量**（决策 1 的直接代价）：多轮会话里「那就改成 6000 吧」这类输入永远拿不到收窄收益 | 刻意；改法（拿历史路由）会引入非确定性 |
| 4 | **词表随域增长**：新增域必须同时补词，否则该域只能靠兜底注入（用例会红着提示） | 每张新域卡的收尾清单 |
| 5 | **`help`（05i）的词已经在词表里占位**：那一组信号是**问法**而不是名词，误注入面比别组大（「支持」「能不能」等泛问句） | 05i 落地时复核 |
