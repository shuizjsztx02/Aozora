# ADR-008 会话正文的跨设备呈现方式

**状态：** 已采纳（2026-09-19，经账户所有者确认）
**范围：** M7 T-M7-04e（P3，决策门）
**关联文档：** `docs/architecture/ai-agent-architecture.md`（§6.1 / §6.2 / §12.2 未决 #6）、`docs/architecture/ai-architecture.md`（会话管理端点与客户端接入）、`docs/APP-CONTEXT.md` §12 `D-PROD-14`、`docs/adr/ADR-006-ai-agent-architecture.md`（编排位置）、`docs/adr/ADR-007-deepseek-provider.md`（日志记录完整对话）

> **触发条件：** 架构 §12.2「未决问题」第 6 项——**会话正文是否跨设备同步**（摘要已定同步，正文待定）。P3 计划把该项落为决策门卡 04e：先出决策、经账户所有者确认，再按结论落地。

## 背景

### 现状：三条影响结论的硬事实

| # | 事实 | 依据 |
|---|---|---|
| 1 | **「摘要同步」今天没有可同步的东西。** `AIConversation.summary` 列存在，但**没有任何生产者**，也不出现在任何 API schema 里 | `server/src/models/ai.py:85`（列定义）；全仓无写入点；`schemas.py` 无该字段 |
| 2 | **协议面已经齐了。** `GET /ai/conversations/{id}/events?after_seq=` 返回**全部事件**（不做 Surface 过滤，带 `turn`/`seq`/`type`/`data`）；桥命令 `conversation.events` 已交付（桥计数 83），客户端 `fetchConversationEvents()` 已有真实调用点 | `modules/ai/routes.py`（`conversation_events`）、`modules/ai/conversation.py:338`（`events()`）、`AozoraBridge.kt:1437`、`use-assistant-stream.ts`（`catchUp`） |
| 3 | **客户端投影缓存是 localStorage 的派生缓存。** `aozora-assistant-chat`，登出即清（`clear()`）；`AssistantMessage` 只有 `{id, role, text, proposal…}`——**不含步骤卡片** | `platform/store/assistant-chat-store.ts`、`use-assistant.ts:111` |

### 问题的真正形态

P2（03d）交付后，同一账号在**两台设备上看到的是同一份会话列表**（服务端权威），但点开一条在别的设备上产生的会话，消息区是空的——那台设备没有它的投影缓存。

### 备选方案

| 方案 | 内容 | 评估 |
|---|---|---|
| **A. 仅摘要同步** | 服务端摘要进同步面，客户端投影缓存不跨设备 | **今天等于什么都不做**：摘要无生产者（事实 1），归 04c；且摘要只是「超窗轮次被 `replace` 替换」的压缩产物，即便 04c 落地，对「打开旧会话看见内容」也几乎不提供正文。代价：把同一个问题推迟到 04c 之后再答一次 |
| **B. 正文做成同步实体** | 卡面原文：客户端投影缓存「降级为同步实体，接入现有 sync 模块，增量，不新协议」，并定义冲突策略 | **不建议。** 会话正文的权威在服务端（§6.2 事件日志＝事实来源、§6.3 服务端持有会话状态），客户端投影是**派生数据**。把派生数据提升为同步实体＝给一份不产生新事实的数据造第二个写入者，凭空引入一套冲突消解。而且它接入不了「现有 sync 模块」：那是 Kotlin/Room 层（8 类实体白名单、乐观并发、`cursor` 增量），而投影缓存是 WebView 的 localStorage——跨这一层要新增实体类型、服务端模型、迁移与推送规则，成本远超收益 |
| **C. 正文按需重建**（**采纳**） | 切到本机无投影的服务端会话时，调**已有的** `conversation.events` 拉日志、投影成消息列表；有缓存时按游标增量补齐尾部 | 零新协议、零新端点、零服务端改动；服务端始终唯一权威，因此**不存在冲突策略**；与 §6.2「投影 B 由日志派生」的模型自洽 |
| **D. 不同步** | 本卡退化为文档 + 行为说明 | 保留了「同一账号在不同设备上是同一批空壳会话」这一已交付的割裂 |

## 决策

### 决策 1：正文跨设备**按需重建**，不做双向同步实体（方案 C）

**客户端从不把投影写回服务端。** 于是冲突策略这个议题**不存在**——它不是「被简化了」，而是问题本身消失了：只有一个写入者（服务端的事件日志），客户端只读。

**落地形态：** 新模块 `app/src/features/assistant/history-projection.ts`（纯函数，事件 → 消息列表）＋ `use-conversations.ts` 的切换路径（拉取与合并）。桥命令 04b 已交付，本卡**只消费**。

### 决策 2：三条刷新规则，起点是**落盘的日志游标**

`assistant-chat-store` 升 v3，新增 `cursors: Record<桶键, seq>`——「本地这条投影已覆盖到日志的哪一行」。**缺省 = 未知**，未知只有一种处置：不做增量。

| # | 状态 | 动作 |
|---|---|---|
| ① | 本机**无**该会话的投影 | **全量重建**（不带 `after_seq`）。这就是「换设备后打开旧会话」的路径 |
| ② | 有投影且**游标已知** | 从游标**增量补齐**尾部，**本地已有的消息一条不动** |
| ③ | 有投影但**游标未知** | **原样保留，不拉取** |

规则 ② 之所以是「追加」而不是「替换」：重建只认得正文，本地缓存里还有**日志里没有的东西**——历史只读记账卡、离线轮的中断标注。拿重建结果顶替它等于每切一次会话就抹掉一次卡片。

规则 ③ 的「未知」有明确来源：**04e 之前落盘的存量桶**（反推不出日志位置），以及**用户取消过的会话**——服务端在断连取消时**不写任何日志事件**（`CancelledError` 不被 `except Exception` 捕获），但那一轮**已落库的部分**确实在游标之后，而本机那半截气泡是流的拼接、反推不出对应哪一行。推进会漏、不推进会重，唯一安全的选择是放弃增量。两条都会**自愈**：下一次正常收尾写下 `done.seq`，游标就回来了。

**游标的写入点（只有三处）：** 一轮正常收尾（`done.seq`，经投影的 `logCursor` 交接字段）、一次成功的事件拉取（重建 / 增量补齐 / 断连续读）、失败收尾（续读已把游标推到日志的真实位置）。**只前进不回退**——乱序到达的并发拉取不该把游标往回拨。

### 决策 3：重建的能力边界写清楚，不假装完整

**能重建：** 用户与助手的**正文**（`user` / `assistant` Surface 事件），外加失败轮的**中断标注**（`error` 事件，与实时路径共用同一份文案 `INTERRUPTED_TURN_NOTE`）。

**重建不出：**

- **历史只读记账卡** —— 提案的日志留档是 `approval_request` / `approval_result` 事件，而它们**当前没有生产者**（04a 把该生产者记在「谁要做『从日志重建确认卡』谁接」名下，未指派）。缓解即规则 ②③：**本地有投影就不重建**，本机看过的卡片不会因为刷新而消失。
- **步骤卡片** —— 不明显写进损失项：`AssistantMessage` 里本来就没有它，**同一条会话在本机重新载入（localStorage 出来的那份）同样没有**。重建与原生的保真度是一致的。

这条边界是采纳方案 C 时**明确接受**的代价，不是遗留的疏漏。若将来要让重建侧也出记账卡，正确的入口是把 `approval_request` / `approval_result` 的**生产者**接上（写路径侧的事，不是读路径侧的事）。

### 决策 4：明确不做的事

- **不改协议、不加端点、不动服务端。** 本卡是**纯客户端 + 文档**的改动面。
- **不做摘要同步**（方案 A 排除）：摘要的生成与注入归 **04c**；本 ADR 只回答「正文怎么呈现」。
- **不引入设备维度**：P2 的登出粒度结论（`ai-architecture.md`「登出粒度」）保持不变。
- **不改保留期口径**（04d）与写路径安全门（02e）。
- **不做离线正文**：断网时读本机缓存，缓存没有就是没有（与既有降级一致）。

## 后果

**收益：** 同一账号跨设备打开旧会话能看见正文；服务端保持唯一权威，投影永远可丢弃、可重建；客户端的 `localStorage` 缓存降级为**纯加速层**（丢了只是慢一次）。

**成本与已知残余**（均已建项或明确接受）：

| # | 残余 | 影响 | 出路 |
|---|---|---|---|
| 1 | 重建结果里**没有历史只读记账卡** | 在**没缓存过的设备**上打开旧会话，只看得见正文 | 接 `approval_request` 生产者；未指派，P4 收口时若无需求则关闭 |
| 2 | 取消过的会话**不做增量**（游标置未知） | 该会话在下次正常收尾前看不到别的设备写的轮次 | 自愈；若将来要在取消后补拉，需服务端在取消路径留可观测位置 |
| 3 | 升级前的**存量桶不做增量** | 同上 | 自愈（下一轮 `done.seq`） |
| 4 | 事件端点**没有分页** | 极长会话的全量重建响应偏大 | `after_seq` 已在，真需要时加分页；30 天保留期是天然上界 |
| 5 | 别的设备**正在跑**的一轮会被拉到半截 | 该轮正文不全，下一轮补齐 | 可接受（与服务端「逐事件落库」的既定语义一致） |

**回退方式：** 本卡不改协议、不改服务端、**不改已落盘的数据结构语义**（store 的 v3 只多一个字段）。回退 = 撤掉 `use-conversations.ts` 的拉取分支即可，`cursors` 字段留着无害（是纯增量字段，旧代码忽略它）。迁移是**向后兼容的一次性**：v2 → v3 只补一个空 `cursors`，v1 → v3 走既有链路。

**验证：** `assistant-history-projection.test.ts`（纯变换 11 例）、`assistant-conversations.test.tsx` 的「跨设备正文重建」9 例（三条规则各一例 + 拉取失败/空日志/旧 APK/迟到批次）、`assistant-chat-store.test.ts` 的「日志游标」6 例（只前进、抹成未知、登出/删除/404 三处清理、v2→v3 迁移）。
