## 1. 为什么升级

### 1.1 当前架构的三个天花板

当前 AI 链路是**单发制**：一次用户输入 → 一次 `/ai/interpret` → 一个 intent → 一个动作。

| 天花板 | 表现 | 根因 |
|---|---|---|
| **单发制** | 无法完成"先查上月预算再改"这类多步任务 | 一次请求只承载一个动作，无循环 |
| **枚举制** | 每新增一个表单能力都要改 prompt 主体白名单 | 能力靠在巨型 prompt 中枚举 intent/op |
| **无上下文** | 二次澄清、补充说明、指代（"改成 500"）全部失效 | `AIInterpretRequest` 只有 `input`+`context`，无 history 字段；`render_messages_with_context` 只构造 `[system, user]` 两条消息 |

第三项是用户可直接感知的缺陷：模型每次看到的都是孤立一句话，无法理解"回答上一轮的追问"。

### 1.2 目标

**用户通过一个对话框，完成 App 内所有已有功能**——不只是记账，而是设置预算、修改账本、账户设置、设置存钱、查询账单、收支分析、新建角色、设置定时记账、提醒、导出、账号管理等全部表单操作。且新增功能**不需要改动 prompt 主体**。

对标产品：**DeepSeek App 的对话框**。

## 2. 标杆分析：DeepSeek 模式

### 2.1 三条核心特征

| 特征 | 说明 |
|---|---|
| **服务端 Agent Loop** | 模型推理、工具执行、循环编排全部在服务端。客户端发一次请求，服务端跑完整个 loop |
| **SSE 流式推送** | 一次长连接，服务端把中间步骤（思考中 → 调用工具 → 工具结果 → 生成中）流式推给客户端 |
| **客户端瘦渲染** | 客户端只做 UI + 流式渲染 + 本地会话存储，**零 agent 逻辑** |

这带来三个关键好处：

- **能力更新不发版**——agent 逻辑与工具全在服务端，热更新即可
- **UX 好**——一次连接而非多次往返，中间步骤全程可见
- **风控与成本统一**——配额、审计、限流在服务端一处收口

> ️ **可信度声明：** DeepSeek App 的官方技术架构**无公开资料**。「loop 在服务端」是基于「联网搜索、文件解析等工具在云端」的**推断，非官方确认**。本架构采用服务端 loop 的理由见 §2.2 与 §4.3，不依赖于对 DeepSeek 内部实现的复刻。

### 2.2 关键规律：Loop 跟着工具走

| 产品类型 | 工具位置 | Loop 位置 | 例子 |
|---|---|---|---|
| 对话类 AI App | 云端（搜索、代码执行、文件解析） | **服务端**（推断） | DeepSeek、豆包、ChatGPT |
| 编码类 Agent | 本地（文件系统、shell） | **客户端**（已确认） | Claude Code、Cursor、Codex CLI |
| **Aozora** | **云端为主 + 设备能力在客户端** | **服务端 loop + 设备通道** | 本架构 §4.3 |

Aozora 的数据是「云端权威 + 本地副本」（`D-PROD-03`），设备能力（权限/提醒/分享/语音）在客户端。因此目标架构是**服务端 loop 为主 + 设备能力通道为辅**（见 §4.3）——这是数据分布决定的，而非对某个产品的模仿。

### 2.3 参考实现：DeepSeek Harness（DSH）

**已核实事实**（多源交叉验证）：DeepSeek 于 **2026-08-13** 开源 **DeepSeek Harness**，MIT 协议，CLI 名 `dsh`，仓库 `github.com/deepseek-ai/deepseek-harness`。官方公式 **`Agent = Model + Harness`**。**当前为 Developer Preview，官方明确不建议生产使用。**

**架构：Cordis 微内核 + 一切皆插件。** 内核只做插件加载/卸载、依赖管理与事件分发，**不实现任何 agent 能力**——模型适配器、工具集、会话、沙箱、存储、主循环、调度、UI 全部是插件。四种模式：标准 / **PTC（程序化工具调用）** / 极简 / 创造。

**四处可直接借鉴的设计**（§4.4、§6.2、§7.4、§9 已吸收）：

| 设计 | 内容 | 对 Aozora 的价值 |
|---|---|---|
| **Session V3 事件日志** | 会话存为 append-only 事件日志；模型看到的 messages 只是**从日志派生的投影**；压缩用 replace（原文仍在日志） | 直接升级 `AIConversation` 设计（§6.2） |
| **审批四值** | `allowed-once` / `rejected` / `cancelled` / `unavailable`，**只有 `allowed-once` 放行**，不确定时倾向拒绝 | 比现有确认卡更严谨（§7.4） |
| **Turn / Step 分层** | Turn = 一次用户交互周期；Step = 一次模型请求 + 工具执行 | 解决中途插话与取消收敛（§4.4） |
| **退出条件硬边界** | 防「永不停止 / 假完成 / 半途而废」 | 对应 R-PROD-16（§4.4） |

**采纳建议：** DSH 为预览版且接口高速迭代，**不作为依赖引入，仅作为设计参考**。PTC 模式值得关注，暂不采用。

## 4. 目标架构

### 4.1 总览

```
┌─ 客户端（瘦渲染 + 设备能力执行器）─────────────────────┐
│  流式渲染        SSE 事件消费与展示（含中间步骤）        │
│  会话列表        多会话管理（对标 DeepSeek）             │
│  设备能力执行器   接收设备指令 → 调 bridge → 回报结果     │
│  确认卡          服务端推「待确认」事件时渲染            │
│  离线兜底        本地 NLU（仅记账，现有，不变）           │
│  ✗ 不含 agent loop / 工具选择 / 上下文编排               │
└─────────────────────────────────────────────────────────┘
        ↕ SSE 下行（流式）  +  HTTP 上行（每轮输入/工具结果）
┌─ 服务端（Agent Host）──────────────────────────────────┐
│  Agent Loop      模型 ↔ 工具 多轮循环                    │
│  工具注册表      业务 API 全量 + 设备工具描述             │
│  工具执行器      服务端工具直连 DB；设备工具经 SSE 下发    │
│  上下文          会话历史 + 摘要（AIConversation）        │
│  安全边界        ActionProposal 校验 + 确认门 + 审计      │
│  密钥 / 配额 / 限流 / prompt 热更新                      │
└─────────────────────────────────────────────────────────┘
```

### 4.2 分层职责

| 层 | 职责 | 不做 |
|---|---|---|
| 客户端 | 流式渲染、会话列表、设备能力执行、离线兜底 | agent loop、工具选择、上下文编排 |
| 服务端 | loop 编排、工具执行、上下文管理、配额审计 | 直接操作用户设备；信任模型输出的 ID |
| 安全层 | ActionProposal 校验、确认门、TOCTOU 重校验 | 信任模型输出的任何 ID 或金额 |
| 设备通道 | 执行设备类工具（提醒/权限/分享/语音等） | 参与 agent 推理 |

### 4.3 设备能力通道（关键设计）

部分能力**本质上只能在客户端执行**：权限申请、语音录制、图片选择、分享、触感、提醒调度、小组件刷新、图标选择。

设计原则：**按是否需要结果回传分两类**。

| 类型 | 例子 | 处理方式 |
|---|---|---|
| **单向指令** | 刷新小组件、触感反馈、分享文本 | 服务端 loop 产出设备指令 → SSE 下发 → 客户端执行 → **不回传**（结果不影响后续推理） |
| **需结果** | 权限申请、语音转写、图片选择 | 服务端 loop **暂停** → SSE 下发请求 → 客户端执行 → HTTP 上行回传结果 → loop 继续 |

这条通道让「对话完成全部功能」在服务端 loop 架构下成为可能——包括那些永远无法上云的能力。

### 4.4 Loop 结构

**Turn / Step 两层**（借鉴 DSH `ReactLoopAgent` 的已验证结构）：

```
Turn  = 一次用户交互周期（可含多个 Step，以「模型不再调用工具且无新输入」结束）
  └─ Step = 一次模型请求 + 工具执行
```

主循环形态：`while (await turn())`。

**四条跨请求不变式**（实现时必须成立）：

| # | 不变式 | 违反后果 |
|---|---|---|
| 1 | 工具调用与结果必须**配对** | 模型看到孤立的调用或结果，推理错乱 |
| 2 | 用户中途输入必须进入**正确的下一步** | 输入丢失或错位到已完成的 Step |
| 3 | 取消请求必须**收敛到一致状态** | 半执行的事务、悬挂的确认卡 |
| 4 | 会话历史必须**可恢复与分叉** | 断连后无法续跑 |

**退出条件必须含硬边界**——只以「任务达成」为退出条件会导致三类失败（DSH 总结为「永不停止 / 假完成 / 半途而废」）。Aozora 的硬边界：

| 边界 | 值（初始，待实测） |
|---|---|
| 单 Turn 最大 Step 数 | 8 |
| 单 Turn 最大写操作数 | 5 |
| 单 Turn 最大工具调用数 | 20 |
| 连续无进展 Step（无新工具调用、无新信息） | 2 |

任一触发即**优雅终止**：向用户说明已完成的步骤与未完成的部分，不静默失败。

### 4.5 设备能力通道小结

设备能力通道（§4.3）使服务端 loop 能触达永远无法上云的能力（权限、语音、分享、触感、提醒、小组件）。它是 Aozora 相对纯对话类产品（DeepSeek）的**架构增项**，也是「覆盖 App 全部功能」的必要条件。

## 5. 前提工作：实体上云

服务端 loop 要求服务端能访问全部数据。以下三个实体**当前仅在客户端 Room**，必须先上云：

| 实体 | 现状 | 上云所需 |
|---|---|---|
| `savings`（存钱目标） | 仅本地，不同步 | 建表 + 迁移 + 同步接入 |
| `scheduled`（定时记账） | 仅本地，不同步 | 建表 + 迁移 + 同步接入 |
| `personas`（聊天角色） | 仅本地，不同步 | 建表 + 迁移 + 同步接入 |

**这不是为 agent 付的额外成本**：`D-PROD-03` 已确认「云端权威，Room 本地副本」，多设备、备份、换机恢复本来就需要它们上云。agent 化只是让这件事有了更早的时间点。

现有同步模块（`server/src/modules/sync/`）可直接增量接入，不需要新协议。

## 6. 上下文与会话管理

### 6.1 多会话（对标 DeepSeek）

| 项 | 现状 | 目标 |
|---|---|---|
| 会话数 | 单会话（`assistant-chat-store`，200 条上限） | **多会话列表**（新建/切换/重命名/删除） |
| 存储 | 客户端 localStorage | 客户端本地 + 服务端 `AIConversation` 摘要 |
| 跨设备 | 无 | 摘要可同步（正文可选） |

### 6.2 会话存储：事件日志 + 派生投影

**核心设计（借鉴 DSH Session V3）：会话不是「聊天记录」，而是 append-only 的事件日志；模型看到的 messages 只是从日志派生的一个投影。**

```
SessionEvent 日志（事实来源，append-only）
   ├─ 投影 A：模型上下文（只含 Surface 事件，受 token 预算约束）
   ├─ 投影 B：UI 展示（全部事件，含步骤卡片、工具结果）
   └─ 投影 C：审计与回放（全量，含配额与安全事件）
```

| 项 | 设计 |
|---|---|
| 事件结构 | `type` / `seq`（单调递增）/ `time` / `data` / `ignorable` |
| 事件类型 | 用户输入、模型回复、工具调用、工具结果、审批请求、审批结果、设备指令、错误、摘要替换 |
| **进入模型上下文** | 仅「Surface 事件」子集；结构性事件（如 UI 状态、设备指令回执）**不占 token** |
| **压缩** | 用 `replace` 操作把长历史替换为摘要——**原文仍留在日志中**，不丢失 |
| 恢复与分叉 | 同一事件流支持断连恢复、会话分叉、回放（支撑 §4.4 不变式 3、4） |
| 存储位置 | 服务端（`AIConversation` 扩展）；客户端只缓存投影 B |

**为什么这个模型优于「存聊天记录」：**

- **可恢复**——断连后从 `seq` 续跑，不依赖客户端重传历史
- **可分叉**——用户「回到某轮重说」不需要复制消息数组
- **省 token**——只有 Surface 事件进上下文，UI 状态与回执不占预算
- **压缩无损**——摘要替换后原文仍可审计、可回溯

**与现有代码的衔接：** `AIConversation` 表已存在（含 `summary` 字段）；需新增事件日志表（或 JSONL 列）。`assistant-chat-store` 降级为投影 B 的客户端缓存。

### 6.3 上下文窗口

| 项 | 设计 |
|---|---|
| 传递方式 | 服务端持有会话状态，客户端只传 `conversation_id` + 本轮输入 |
| 窗口 | 最近 N 轮原文（N 待实测，初始 8） |
| 压缩 | 超出窗口的轮次经 `replace` 事件替换为摘要（原文保留在日志） |
| 反幻觉 | 历史与摘要只含自然语言，**不得出现 UUID / 内部 ID** |

**服务端持有会话状态**是服务端 loop 模式的关键——客户端不重传历史，更省流量、更安全、更容易做摘要。

### 6.4 Token 预算

| 项 | 上限 | 超限降级 |
|---|---|---|
| 单轮输入 | 500 字符（现状不变） | 拒绝 |
| 历史窗口 | 按 N 轮 + 字符双限 | 丢最早轮次（保留于日志） |
| 摘要 | 800 字符 | 使用上一版摘要 |
| 工具定义 | 按域分组注入（§7.2） | 减少域 |

## 7. 工具系统

### 7.1 工具注册表

**服务端持有工具清单**（与客户端 Host 方案的关键区别）：

| 来源 | 生成方式 |
|---|---|
| 服务端业务 API | 从 FastAPI 路由 + Pydantic schema 生成 |
| 设备工具 | 手写描述（数量有限，稳定），执行体在客户端 |
| 分析工具 | `/stats/*`、`/ai/report` 封装 |

**description 是模型可见的唯一语义来源**，自动生成后必须人工审核。

### 7.2 域分组

工具数超过 10-15 个会显著降低模型选择准确率。按域分组，每域 5-8 个（域见 §3.2），由预路由选择注入了哪些域的工具。

### 7.3 读工具与写工具

| 类型 | 执行 | 结果去向 |
|---|---|---|
| **读工具** | loop 内直接执行 | tool result 喂回模型，继续 loop |
| **写工具** | **不直接执行**，产出 ActionProposal | loop 挂起 → 用户确认 → 执行 → 结果回喂 |

### 7.4 写操作安全边界（不变）

```
模型 tool_call 参数
  → 组装 ActionProposal（名→id 服务端确定性解析）
  → 校验（Schema + 账本上下文）
  → 确认卡（低置信/高风险强制）
  → 执行（TOCTOU 重校验）
```

**铁律三条（agent 化不放松）：**
1. 模型永不输出 UUID——名→id 由确定性代码解析
2. 金额与统计永远由确定性代码计算
3. 写库必须经校验与确认门

**审批结果四值**（借鉴 DSH 审批模型，比二值确认更严谨）：

| 结果 | 含义 | 后续 |
|---|---|---|
| `allowed-once` | 用户明确同意本次 | **唯一放行值**；执行后即失效，不产生长期授权 |
| `rejected` | 用户拒绝 | loop 收到拒绝理由，可调整方案重提 |
| `cancelled` | 用户中止整个任务 | 优雅终止（§4.4），说明已完成部分 |
| `unavailable` | 无法取得授权（超时/离线/界面不可用） | **视为拒绝**，不执行 |

**设计原则：不确定时倾向拒绝。** 只有 `allowed-once` 放行——没有「默认同意」「记住选择」这类隐式授权。

**审批不只是安全机制，也是人机交接点**：用户在此刻看到 agent 的完整意图，可以纠正理解偏差。这使审批卡同时承担「安全门」与「纠偏点」两个角色。

**服务端 loop 的额外收益**：工具与数据同在服务端，校验与执行可合并为一次事务，TOCTOU 窗口消失。

## 8. 流式协议设计

### 8.1 事件类型

SSE 下行事件（`text/event-stream`）：

| 事件 | 载荷 | 客户端行为 |
|---|---|---|
| `phase` | 阶段标识（thinking / routing / tool_calling） | 显示进行中状态 |
| `tool_call` | 工具名 + 人类可读描述（"正在查询预算…"） | 显示步骤卡片 |
| `tool_result` | 摘要（不含原始数据） | 更新步骤卡片为完成 |
| `confirm` | 提案摘要（ActionProposal 预览） | 渲染确认卡 |
| `device_request` | 设备指令（需结果类） | 执行并上行回传 |
| `delta` | 助手回复增量文本 | 流式渲染 |
| `done` | 结束标记（含 usage） | 收尾 |
| `error` | 错误码（安全枚举） | 按降级契约处理 |

### 8.2 通道实现（技术可行性已确认）

```
WebView (JS)  ←─桥事件推送─  Kotlin 层  ←──SSE──  服务端
                                  │
                            OkHttp EventSource
```

- **Kotlin 层**：用 `okhttp-sse` 的 `EventSourceListener` 接收 SSE（OkHttp 4.12 已在依赖，仅需加 `okhttp-sse:4.12.0`）
- **转发**：复用现有桥事件推送机制（`onPermissionResult` 的「命令返回 pending + 事件推送结果」模式，`native-bridge.ts:497`）
- **上行**：用户输入、确认、设备工具结果为普通 HTTP（复用 `ai.*` 命令族）
- **Token**：沿用 ADR-003——Bearer token 全程不出 Kotlin 层

**不依赖 WebView 的 fetch streaming 支持**（minSdk 26 / targetSdk 36，但走桥转发更稳且与现有架构一致）。

### 8.3 超时与打断

| 项 | 设计 |
|---|---|
| 单步超时 | 沿用 12 s 慢速提示（显示当前步骤）/ 25 s 单步取消 |
| 整体 | 不设总时长上限，由多步构成，用户可见进度 |
| 打断 | 客户端可随时取消 → 上行 cancel → 服务端终止 loop |
| 断连 | SSE 断开 → 客户端提示；loop 状态在服务端可恢复（按 conversation_id） |

## 9. 交互设计（对标 DeepSeek）

### 9.1 统一智能模式（无模式选择）

DeepSeek App 于 2026-09-10 将「快速 / 专家 / 识图」三模式**合并为统一智能模式**——由系统自动分析输入判断场景与难度，自动决定是否开启深度思考与联网搜索。**用户不需要理解或选择模式。**

Aozora 对应设计：

| 用户侧 | 系统侧 |
|---|---|
| 只有一个输入框，无模式开关 | 自动判定：简单意图走快路径（单发），复合任务走 agent loop |
| 不感知"快路径/慢路径" | 路径切换对用户透明（§11 的升级判据） |
| 步骤可见（长任务时） | 简单任务无步骤展示，直接给结果 |

**原则：复杂度对用户不可见。** 用户说"记一笔 12 块"和说"帮我把上个月的预算改成 3000"应该是同一个输入框。

### 9.2 交互对照

| 场景 | DeepSeek 做法 | Aozora 设计 |
|---|---|---|
| 中间步骤 | 思考过程折叠区、"搜索中"状态 | 步骤卡片流（"正在查询预算…"→"已读取 3 条"），可折叠 |
| 需确认 | 无（对话即执行） | **确认卡**（写操作与高风险强制，见 §7.4 四值审批） |
| 失败 | 显示错误 + 重试 | 按降级契约：重试 → 快路径 → 本地 NLU；优雅终止时说明已完成部分 |
| 打断 | 停止生成按钮 | 取消按钮 → 终止 loop（§4.4 不变式 3：收敛到一致状态） |
| 会话管理 | 侧边栏会话列表、文件树预览 | 会话列表（新建/切换/重命名/删除）；后续可扩展"任务产物"侧栏 |
| 语音 | 语音对话，**支持中途打断** | 复用现有 Vosk 语音；打断语义同"取消" |
| 文件/图片 | 图片、PDF、Word 上传 | 现有图片记账链路（`/ai/parse-image`）扩展到对话内上传 |

**安全优先的差异点**：DeepSeek 是消费级对话（无副作用），Aozora 的写操作有真实财务后果，因此**确认卡不能省**。这是有意的产品差异，不是架构妥协。

## 10. 迁移路径

| 期 | 内容 | 交付后的能力 | 独立价值 |
|---|---|---|---|
| **P0** | 三实体上云（`savings` / `scheduled` / `personas`）：建表 + 迁移 + 接入现有同步 | 服务端数据完整，loop 才可能 | **数据可靠性**——多设备、备份、换机恢复本就需要 |
| **P1** | 服务端 Agent Loop + 工具层 + SSE 流式通道 + 基础会话状态 | 多步任务、**多轮澄清（当前痛点）**、步骤可见 | 核心能力升级 |
| **P2** | 客户端瘦渲染重构 + 多会话管理 | 对标 DeepSeek 的观感：流式渲染、会话列表 | UX 升级 |
| **P3** | 会话事件日志（完整形态）+ 摘要压缩 | 断连恢复、会话分叉、压缩无损、审计 | 可靠性 + 成本控制 |
| **P4** | 域路由 + Skill 封装 + 设备能力通道 | **全功能覆盖**（含设备类能力）、扩展性 | 目标达成 |

**顺序理由：**

- **P0 必须最先**——服务端 loop 够不到本地数据，这是硬前提；且 P0 的价值独立于 agent（数据可靠性）
- **P1 带 SSE**——loop 的中间步骤必须可见，否则多步任务变成"长转圈"；SSE 与 loop 是同一交付
- **P2 再瘦客户端**——先让服务端能力可用，再重构客户端；期间客户端可用非流式降级（等待完整结果）
- **P3 完整化会话**——P1 的基础会话状态已够多轮澄清；事件日志的恢复/分叉能力可后置
- **P4 收口覆盖度**——设备能力通道需要前面的 loop + SSE 就位

**回退保护：** 每期结束时代理旧链路仍可用（§11），任一期出问题可单独回退。

## 11. 兼容、回退与灰度

### 11.1 回退链

```
服务端 agent loop 失败 → 单发 /ai/interpret（快路径） → 本地规则 NLU
```

各期均可独立回退：P1 出问题 → 关闭 agent 开关，回到单发链路；P2 出问题 → 客户端回退旧渲染（服务端能力保留）。

### 11.2 兼容

| 项 | 策略 |
|---|---|
| 旧客户端 | 不调 `/ai/agent`，走现有 `/ai/interpret`，行为不变 |
| ActionProposal | 升 v2 覆盖全量 CRUD；v1 契约与校验器保持可用 |
| 降级契约 | 503/429 语义不变，客户端回退路径不变 |
| 桥版本 | 新增 `ai.agent` / `ai.cancel` 命令与事件，只增不改 |
| 本地实体 | 上云后本地 Room 保留为副本（离线可读），写入走同步 |

### 11.3 灰度

- agent 路径由服务端开关 + 客户端开关双层控制
- 关闭时完全回落到现有单发链路
- 按用户分批放量，观察任务完成率、回退率与 token 成本

## 12. 风险与未决问题

### 12.1 风险

| ID | 风险 | 缓解 |
|---|---|---|
| R-PROD-15 | 多轮 token 成本成倍上升 | 配额「每会话轮数 + token」双限；域分组控制工具定义开销；事件日志只让 Surface 事件进上下文 |
| R-PROD-16 | Loop 失控（永不停止 / 假完成 / 半途而废）与超时 | 退出条件硬边界（§4.4）；单步 12 s/25 s 独立计时；优雅终止须说明已完成部分 |
| R-PROD-17 | 工具集过大导致选择准确率下降 | 域分组 + 预路由 |
| R-PROD-18 | 三实体上云引入同步冲突/数据丢失 | 复用现有 sync 协议与对账不变量测试；迁移用旧版本 fixture；灰度先读后写 |
| R-PROD-19 | SSE 长连接在弱网/后台中断 | 断连重试 + 按 `conversation_id` 恢复状态 + 客户端明确提示 |
| R-PROD-14（既有） | 写操作绕过服务端审计 | **本架构显著缓解**：写操作回到服务端执行路径 |
| R-PROD-20 | 服务端持有会话日志的隐私边界 | 摘要与日志含用户自然语言；复用 `D-PROD-08` 删除等待期与保留策略；登出清理（现有 `SecurityPage.doLogout` 模式） |

### 12.2 未决问题

1. 历史窗口 N 的具体取值（初始 8，需实测调优）
2. 预路由实现（规则 / 轻量模型 / 混合）
3. 摘要压缩触发条件（轮数 vs token vs 时间）
4. 设备工具「需结果」类的最小集合（哪些必须回传）
5. 会话日志的存储形态（独立表 vs JSONL 列 vs 对象存储）与保留期
6. 会话正文是否跨设备同步（摘要已定同步，正文待定）
7. 是否需要 PTC（程序化工具调用）范式的部分特性（DSH 四种模式之一）
