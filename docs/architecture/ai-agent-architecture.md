## 1. 为什么升级

### 1.1 当前架构的三个天花板

当前 AI 链路是**单发制**：一次用户输入 → 一次 `/ai/interpret` → 一个 intent → 一个动作。

| 天花板 | 表现 | 根因 |
|---|---|---|
| **单发制** | 无法完成"先查上月预算再改"这类多步任务 | 一次请求只承载一个动作，无循环 |
| **枚举制** | 每新增一个表单能力都要改 prompt 主体白名单 | 能力靠在巨型 prompt 中枚举 intent/op |
| **无上下文** | 二次澄清、补充说明、指代（"改成 500"）全部失效 | `AIInterpretRequest` 只有 `input`+`context`，无 history 字段；`render_messages_with_context` 只构造 `[system, user]` 两条消息 |

第三项是用户可直接感知的缺陷：模型每次看到的都是孤立一句话，无法理解"回答上一轮的追问"。

### 1.2 目标

**用户通过一个对话框，完成 App 内所有已有功能**——不只是记账，而是设置预算、修改账本、账户设置、设置存钱、查询账单、收支分析、新建角色、设置定时记账、提醒、导出、账号管理等全部表单操作。且新增功能**不需要改动 prompt 主体**。

对标产品：**DeepSeek App 的对话框**。

## 2. 标杆分析：DeepSeek 模式

### 2.1 三条核心特征

| 特征 | 说明 |
|---|---|
| **服务端 Agent Loop** | 模型推理、工具执行、循环编排全部在服务端。客户端发一次请求，服务端跑完整个 loop |
| **SSE 流式推送** | 一次长连接，服务端把中间步骤（思考中 → 调用工具 → 工具结果 → 生成中）流式推给客户端 |
| **客户端瘦渲染** | 客户端只做 UI + 流式渲染 + 本地会话存储，**零 agent 逻辑** |

这带来三个关键好处：

- **能力更新不发版**——agent 逻辑与工具全在服务端，热更新即可
- **UX 好**——一次连接而非多次往返，中间步骤全程可见
- **风控与成本统一**——配额、审计、限流在服务端一处收口

> ️ **可信度声明：** DeepSeek App 的官方技术架构**无公开资料**。「loop 在服务端」是基于「联网搜索、文件解析等工具在云端」的**推断，非官方确认**。本架构采用服务端 loop 的理由见 §2.2 与 §4.3，不依赖于对 DeepSeek 内部实现的复刻。

### 2.2 关键规律：Loop 跟着工具走

| 产品类型 | 工具位置 | Loop 位置 | 例子 |
|---|---|---|---|
| 对话类 AI App | 云端（搜索、代码执行、文件解析） | **服务端**（推断） | DeepSeek、豆包、ChatGPT |
| 编码类 Agent | 本地（文件系统、shell） | **客户端**（已确认） | Claude Code、Cursor、Codex CLI |
| **Aozora** | **云端为主 + 设备能力在客户端** | **服务端 loop + 设备通道** | 本架构 §4.3 |

Aozora 的数据是「云端权威 + 本地副本」（`D-PROD-03`），设备能力（权限/图片/分享/触感/小组件）在客户端。因此目标架构是**服务端 loop 为主 + 设备能力通道为辅**（见 §4.3）——这是数据分布决定的，而非对某个产品的模仿。

### 2.3 参考实现：DeepSeek Harness（DSH）

**已核实事实**（多源交叉验证）：DeepSeek 于 **2026-08-13** 开源 **DeepSeek Harness**，MIT 协议，CLI 名 `dsh`，仓库 `github.com/deepseek-ai/deepseek-harness`。官方公式 **`Agent = Model + Harness`**。**当前为 Developer Preview，官方明确不建议生产使用。**

**架构：Cordis 微内核 + 一切皆插件。** 内核只做插件加载/卸载、依赖管理与事件分发，**不实现任何 agent 能力**——模型适配器、工具集、会话、沙箱、存储、主循环、调度、UI 全部是插件。四种模式：标准 / **PTC（程序化工具调用）** / 极简 / 创造。

**四处可直接借鉴的设计**（§4.4、§6.2、§7.4、§9 已吸收）：

| 设计 | 内容 | 对 Aozora 的价值 |
|---|---|---|
| **Session V3 事件日志** | 会话存为 append-only 事件日志；模型看到的 messages 只是**从日志派生的投影**；压缩用 replace（原文仍在日志） | 直接升级 `AIConversation` 设计（§6.2） |
| **审批四值** | `allowed-once` / `rejected` / `cancelled` / `unavailable`，**只有 `allowed-once` 放行**，不确定时倾向拒绝 | 比现有确认卡更严谨（§7.4） |
| **Turn / Step 分层** | Turn = 一次用户交互周期；Step = 一次模型请求 + 工具执行 | 解决中途插话与取消收敛（§4.4） |
| **退出条件硬边界** | 防「永不停止 / 假完成 / 半途而废」 | 对应 R-PROD-16（§4.4） |

**采纳建议：** DSH 为预览版且接口高速迭代，**不作为依赖引入，仅作为设计参考**。PTC 模式值得关注，暂不采用。

## 4. 目标架构

### 4.1 总览

```
┌─ 客户端（瘦渲染 + 设备能力执行器）─────────────────────┐
│  流式渲染        SSE 事件消费与展示（含中间步骤）        │
│  会话列表        多会话管理（对标 DeepSeek）             │
│  设备能力执行器   接收设备指令 → 调 bridge → 回报结果     │
│  确认卡          服务端推「待确认」事件时渲染            │
│  离线兜底        本地 NLU（仅记账，现有，不变）           │
│  ✗ 不含 agent loop / 工具选择 / 上下文编排               │
└─────────────────────────────────────────────────────────┘
        ↕ SSE 下行（流式）  +  HTTP 上行（每轮输入/工具结果）
┌─ 服务端（Agent Host）──────────────────────────────────┐
│  Agent Loop      模型 ↔ 工具 多轮循环                    │
│  工具注册表      业务 API 全量 + 设备工具描述             │
│  工具执行器      服务端工具直连 DB；设备工具经 SSE 下发    │
│  上下文          会话历史 + 摘要（AIConversation）        │
│  安全边界        ActionProposal 校验 + 确认门 + 审计      │
│  密钥 / 配额 / 限流 / prompt 热更新                      │
└─────────────────────────────────────────────────────────┘
```

### 4.2 分层职责

| 层 | 职责 | 不做 |
|---|---|---|
| 客户端 | 流式渲染、会话列表、设备能力执行、离线兜底 | agent loop、工具选择、上下文编排 |
| 服务端 | loop 编排、工具执行、上下文管理、配额审计 | 直接操作用户设备；信任模型输出的 ID |
| 安全层 | ActionProposal 校验、确认门、TOCTOU 重校验 | 信任模型输出的任何 ID 或金额 |
| 设备通道 | 执行设备类工具（提醒/权限/分享/图片等） | 参与 agent 推理 |

### 4.3 设备能力通道（关键设计）

部分能力**本质上只能在客户端执行**：权限申请、图片选择、分享、触感、提醒调度、小组件刷新、图标选择。

设计原则：**按是否需要结果回传分两类**。

| 类型 | 例子 | 处理方式 |
|---|---|---|
| **单向指令** | 刷新小组件、触感反馈、分享文本 | 服务端 loop 产出设备指令 → SSE 下发 → 客户端执行 → **不回传**（结果不影响后续推理） |
| **需结果** | 权限申请、图片选择 | 服务端 loop **暂停** → SSE 下发请求 → 客户端执行 → HTTP 上行回传结果 → loop 继续 |

这条通道让「对话完成全部功能」在服务端 loop 架构下成为可能——包括那些永远无法上云的能力。

**落地状态（2026-09-19，T-M7-05e）：** **服务端侧已就位**——`device_request` 有了首个生产者，两类协议按上表落地（`server/src/modules/ai/devices.py` 的能力目录 + `agent.py` 的挂起/恢复 + `routes.py` 的上行端点 `POST /ai/device-result`）。协议细节见 `ai-architecture.md`「设备能力通道协议」；取舍（挂起态进程内、404 覆盖四种回不去的情形、超时是工具级结果而非 `StopReason`）见 `ADR-010`。

**闸门：** `AI_DEVICE_CHANNEL_ENABLED` 默认 **false**——客户端执行器（05f）就位前不注入设备能力（否则模型会调用一个没人应答的能力，白等一个超时窗）。**客户端执行器与「能力名 → 桥命令」的分派表归 05f**。

**服务端目录（5 个能力）：** 单向 `haptic.feedback` / `widget.refresh` / `share.text`；需结果 `permissions.request` / `image.pick`（`voice.transcribe` 已随 REQ-75 下架，见 `ADR-015`）。**提醒（`reminder.*`）不在其中**——它是写工具（写用户的提醒配置、要过审批门，进 `tools.py` 的注册表），执行体在设备上属于**执行位置**的分派问题（05f），不是本通道的「设备指令」。

### 4.4 Loop 结构

**Turn / Step 两层**（借鉴 DSH `ReactLoopAgent` 的已验证结构）：

```
Turn  = 一次用户交互周期（可含多个 Step，以「模型不再调用工具且无新输入」结束）
  └─ Step = 一次模型请求 + 工具执行
```

主循环形态：`while (await turn())`。

**四条跨请求不变式**（实现时必须成立）：

| # | 不变式 | 违反后果 |
|---|---|---|
| 1 | 工具调用与结果必须**配对** | 模型看到孤立的调用或结果，推理错乱 |
| 2 | 用户中途输入必须进入**正确的下一步** | 输入丢失或错位到已完成的 Step |
| 3 | 取消请求必须**收敛到一致状态** | 半执行的事务、悬挂的确认卡 |
| 4 | 会话历史必须**可恢复与分叉** | 断连后无法续跑 |

> **不变式 1 的四道防线**（T-M7-04b 起）：① loop 给每个 `tool_calls` 条目都回一条配对结果（含未知工具 / 预算用尽）；② **落库批的边界＝配对组的边界**——带 `tool_calls` 的 assistant 消息与它的全部结果同批同提交，断连不会留下悬空的调用；③ `history()` 按 `turn` 整取 + 读侧裁掉可能半截的尾巴（`_paired_prefix_len`）；④ 分叉切点向下取整到最近的完整组。前三道在写 / 读路径上各有用例，第四道在分叉端点上有用例。

**退出条件必须含硬边界**——只以「任务达成」为退出条件会导致三类失败（DSH 总结为「永不停止 / 假完成 / 半途而废」）。Aozora 的硬边界：

| 边界 | 值（初始，待实测） |
|---|---|
| 单 Turn 最大 Step 数 | 8 |
| 单 Turn 最大写操作数 | 5 |
| 单 Turn 最大工具调用数 | 20 |
| 连续无进展 Step（无新工具调用、无新信息） | 2 |

任一触发即**优雅终止**：向用户说明已完成的步骤与未完成的部分，不静默失败。

### 4.5 设备能力通道小结

设备能力通道（§4.3）使服务端 loop 能触达永远无法上云的能力（权限、图片、分享、触感、提醒、小组件）。它是 Aozora 相对纯对话类产品（DeepSeek）的**架构增项**，也是「覆盖 App 全部功能」的必要条件。

|---|---|---|---|
| **agent 路径**（`/ai/agent`，多步 loop） | **DeepSeek** | `deepseek-flash`（V4.1-Flash） | OpenAI 兼容，base URL `https://api.deepseek.com`；1M 上下文、tool calls、thinking 可控 |
| **快路径**（`/ai/interpret` 等，单发） | DashScope | `qwen3.7-flash` | **不变**——其 prompt 为逐轮调优，换模型属独立工作 |

两者由既有的 `LLMProvider` Protocol（`provider.py`）承载，新增实现不改调用方。

**推理分级（取代二值开关）：**

| 档位 | 触发条件 | thinking | `reasoning_effort` |
|---|---|---|---|
| **快** | 简单意图：记账、查询、闲聊 | `disabled` | — |
| **中** | 单步但需理解：编辑、删除、配置 | `enabled` | `low` |
| **深** | 多步 / 复合任务 | `enabled` | `high` |

- **入口判定用规则**，不额外调用 LLM（那会多一次往返，与省时的初衷相悖）。
- **loop 内升级：Step 数即复杂度证据**——若进入第 2 个 Step，说明任务实际比入口判断的复杂，后续步骤自动升级到「深」档。这让入口分类的准确率不再是硬约束。
- ⚠️ `deepseek-flash` 的 thinking **默认开启**，「快」档必须**显式传 `disabled`**，不能靠省略参数。

**为什么这个方案能同时保住效果与耗时：** 原 provider 的 `enable_thinking` 只有开/关，开了会击穿单步预算（实测 20–24 s），关了多步规划质量不足——二值开关无法折中。三档 + Step 升级把「付多少推理成本」变成可按任务调节的量。

**`reasoning_content` 回传（2026-09-18 多轮真实探针校准）：** 官方文档称「请求含 `tools` 时，多轮必须回传前序轮次的 `reasoning_content`，否则返回 **400**」。带历史的多轮探针把这条收窄成一条**可执行规则**：**thinking 模式**的请求里，历史中**每条 assistant 消息都必须带 `reasoning_content` 这个键**——**空串可以通过**，缺键才被拒（提示该字段在 thinking 模式下必须回传）；thinking `disabled` 的请求不要求该键。02a 的单发初测曾得出「不回传亦返回 200」，与带历史的多轮结论不同——**按「assistant 消息始终带该键」实现即可两者兼顾**。完整矩阵（含孤立 `role:"tool"` 消息被拒一行）见 `docs/milestones/T-M7-02-P1-implementation-plan.md` §五（02d）。**实现：** `messages` 原样透传，loop 保存 `ProviderResult.reasoning_content` 并在下一轮带回，且 assistant 消息**始终**带该键（无推理时空串）——`server/src/modules/ai/provider.py` 的 `DeepSeekProvider` 与 `agent.py` 分别承担两层。

**成本影响：** `deepseek-flash` 的输入 cache hit 单价为 $0.003/1M（cache miss $0.15/1M，差 50 倍）。agent loop 每轮重发历史与工具定义，命中缓存后近乎免费——这是 R-PROD-15（多轮 token 成本）的主要缓解手段。

## 6. 上下文与会话管理

### 6.1 多会话（对标 DeepSeek）

| 项 | 现状 | 目标 |
|---|---|---|
| 会话数 | 单会话（`assistant-chat-store`，200 条上限） | **多会话列表**（新建/切换/重命名/删除） |
| 存储 | 客户端 localStorage | 客户端本地 + 服务端 `AIConversation` 摘要 |
| 跨设备 | 无 | **正文按需重建**（T-M7-04e）：切到本机无投影的服务端会话时从事件日志重建；有投影则按游标增量补齐。不做双向同步实体，见 `ADR-008` |

### 6.2 会话存储：事件日志 + 派生投影

**核心设计（借鉴 DSH Session V3）：会话不是「聊天记录」，而是 append-only 的事件日志；模型看到的 messages 只是从日志派生的一个投影。**

```
SessionEvent 日志（事实来源，append-only）
   ├─ 投影 A：模型上下文（只含 Surface 事件，受 token 预算约束）
   ├─ 投影 B：UI 展示（全部事件，含步骤卡片、工具结果）
   └─ 投影 C：审计与回放（全量，含配额与安全事件）
```

| 项 | 设计 |
|---|---|
| 事件结构 | `type` / `seq`（单调递增）/ `time` / `data` / `ignorable` |
| 事件类型 | 见下方「事件类型全集与 Surface 子集」——**单一来源常量在 `server/src/modules/ai/conversation.py`** |
| **进入模型上下文** | 仅「Surface 事件」子集；结构性事件（如 UI 状态、设备指令回执）**不占 token** |
| **压缩** | 用 `replace` 操作把长历史替换为摘要——**原文仍留在日志中**，不丢失。T-M7-04c 落地：触发条件＝**窗口溢出**（不另立 token / 时间尺子，见 §12.2 未决 #3 的闭环）；摘要在轮末 `done` **之后**生成（不占用户等待），产出＝一条 `replace` 事件 + `AIConversation.summary` 列 |
| **写入粒度** | **逐事件**（T-M7-04b）：loop 每产出一个**落库批**就写一次、提交一次，批的边界＝配对组的边界（带 `tool_calls` 的 assistant 消息与它的全部结果同批）。断连留在日志里的因此永远是完整的组，「半截落库」在结构上不可能 |
| 恢复与分叉 | 同一事件流支持断连恢复、会话分叉、回放（支撑 §4.4 不变式 3、4）。T-M7-04b 落地：恢复＝带同一个 `conversation_id` 再跑一轮（`history()` 即入口，尾部保证干净）+ 客户端按 `after_seq` 增量续读；分叉＝`POST /ai/conversations/{id}/fork`，切点向下取整到完整配对组 |
| **保留期** | 事件正文**30 天**到期物理删除（T-M7-04d），**按整轮删**以保住不变式 1；只删事件行，**不动会话索引行与 `ai_usage`**（配额基座）。口径见 `security.md`「会话事件日志的保留期」 |
| 存储位置 | 服务端（`AIConversation` 扩展）；客户端只缓存投影 B |
| **投影 B 的跨设备重建** | 客户端投影是**派生数据**，因此**按需重建**而不是同步实体（T-M7-04e，`ADR-008`）：无投影 → 全量重建；有投影且**日志游标**已知 → 增量补齐尾部（本地消息一条不动）；游标未知 → 原样保留。客户端**从不把投影写回**服务端，冲突策略这一议题因此不存在。重建只认得正文——历史只读记账卡不在其中（`approval_request` 生产者未接），规则二/三使本机看过的卡片不被抹掉 |

**为什么这个模型优于「存聊天记录」：**

- **可恢复**——断连后从 `seq` 续跑，不依赖客户端重传历史（04b：`GET …/events?after_seq=` + 带同一个 `conversation_id` 再跑一轮；被中断那一轮**已经跑完的步骤都在**）
- **可分叉**——用户「回到某轮重说」不需要复制消息数组（04b：客户端只报一个 `seq`，前缀由服务端从日志复制）
- **省 token**——只有 Surface 事件进上下文，UI 状态与回执不占预算
- **压缩无损**——摘要替换后原文仍可审计、可回溯

**事件类型全集与 Surface 子集（T-M7-04a 定稿）。** 事件分两档：**Surface 事件**一一对应 loop 消息流里的一条消息（`data` 就是那条 API 消息字典），是唯一进投影 A 的一档；**结构性事件**是「发生过什么」的留档，只进投影 B（UI）与投影 C（审计）。读侧的白名单常量是 `SURFACE_EVENT_TYPES`（`conversation.py`），`history()` 只投它；写入时按**同一常量**派生 `ignorable` 列，两者的一致性由测试钉死。

| 语义 | `type` 值 | 进投影 A | 生产者 |
|---|---|---|---|
| 用户输入 | `user` | ✅ | `TurnWriter`（loop 的落库批，04b 起逐事件） |
| 模型回复 / 工具调用 | `assistant` | ✅ | 同上。**`tool_calls` 挂在同一条消息的 `data` 里，不另立事件**——一条事件＝一条消息，重组回 API 载荷零歧义；§4.4 不变式 1（调用与结果配对）也因此绑在同一条消息上 |
| 工具结果 | `tool` | ✅ | 同上。**与它对应的那条 `assistant` 同批落库**（批＝配对组） |
| 审批请求 | `approval_request` | ❌ | 待接（04a 只给写入口） |
| 审批结果 | `approval_result` | ❌ | 待接 |
| 设备指令 | `device_request` | ❌ | **不接生产者（05e 决策，`ADR-010` 决策 5）**：设备指令的下发与结果由 Surface 事件留档——模型的那次 `tool_call` 与配对的 tool 结果消息（`{"status":"sent"}` / `{"status":"ok",…}` / 错误码）都在日志里，再写一条结构性事件是把同一件事记两遍，且没有任何消费方 |
| 错误 | `error` | ❌ | `stream._record_failure`（04b）——失败轮收尾：一条事件说明这一轮为什么停在半路，载荷只有安全枚举码与固定文案 |
| 摘要替换 | `replace` | ❌ | `ConversationService.summarize_overflow`（04c）——窗口之外那段历史的压缩；载荷 `summary` / `upto_turn` / `turns`，**原文一行不删** |
| 配额 | `quota` | ❌ | `record_turn`——每轮一条用量事件，**与消息同轮** |
| 安全 | `security` | ❌ | **不接生产者**（04d 的访问面审计结论）——读取面按授权校验 + HTTP 层脱敏留痕覆盖，记录进会话日志只会让日志自我放大；理由见 `security.md`「读取面访问审计」 |

**与 §8.1 的 SSE 八类是两套独立枚举。** 有同名值（`error` / `device_request`），但一个是下行协议帧、一个是日志行——**不得互相赋值或复用枚举类**；`confirm` 帧对应的日志类型是 `approval_request`，不是 `confirm`。

**列宽：** `type` 为 `varchar(32)`。04a 实测（PG 17.11）：`varchar(16)` 按字符数计，全集里最长的 `approval_request` 恰为 16 字符——**顶格、零余量**，17 字符即被拒（`StringDataRightTruncationError`），故加倍留余量。

**与现有代码的衔接：** `AIConversation` 表已存在（含 `summary` 字段）；需新增事件日志表（或 JSONL 列）。`assistant-chat-store` 降级为投影 B 的客户端缓存。

### 6.3 上下文窗口

| 项 | 设计 |
|---|---|
| 传递方式 | 服务端持有会话状态，客户端只传 `conversation_id` + 本轮输入 |
| 窗口 | 最近 N 轮原文（N 待实测，初始 8）。**复核结论（04c）**：维持 8，实测依据见 §12.2 未决 #2 |
| 压缩 | 超出窗口的轮次经 `replace` 事件替换为摘要（原文保留在日志）。**触发＝窗口溢出**——与窗口同一把尺子，不另立 token / 时间判据。摘要在轮末生成，经**系统提示**的一段注入（不是 messages 里的一条），从下一轮起生效（T-M7-04c） |
| 反幻觉 | 历史与摘要只含自然语言，**不得出现 UUID / 内部 ID**（04c：输入侧不喂工具消息、输出侧整条校验，两道都在） |

**服务端持有会话状态**是服务端 loop 模式的关键——客户端不重传历史，更省流量、更安全、更容易做摘要。

### 6.4 Token 预算

| 项 | 上限 | 超限降级 |
|---|---|---|
| 单轮输入 | 500 字符（现状不变） | 拒绝 |
| 历史窗口 | 按 N 轮 + 字符双限 | 丢最早轮次（保留于日志） |
| 摘要 | 800 字符（`AI_AGENT_SUMMARY_CHARS`） | 使用上一版摘要——**整条退回、不截断**；首次压缩没有上一版即不压缩（04c） |
| 工具定义 | 按域分组注入（§7.2） | 减少域 |
| 域知识（Skill，§7.5） | 单条正文 400 字符 / 一次注入合计 1200 字符（05h） | **整条不进**（不截断）；单条上限在导入期拦 |

> **摘要这一行的执行口径（T-M7-04c）：** 「使用上一版摘要」在代码里就是**什么都不写** —— 超限的、空的、含内部 ID 的摘要一律整条退回，`replace` 事件与 `summary` 列都不动，上一版原样留着。不截断是因为半句摘要会被下一轮当成事实，比没有更糟。摘要的字符上限与窗口的字符上限（`AI_AGENT_HISTORY_CHARS`）量的是**两件事**（窗口之外 vs 窗口之内），不是同一个上限的两种写法。

### 7.2 域分组

`help` 一域**（产品帮助检索，**在 §3.2 的表外**——那张表列的是「读写用户数据」的功能面，
而「这个 App 怎么用」是横切问题，见下）。当前 **15 域 / 55 个工具**：

| 域 | 工具数 | 内容 |
|---|---|---|
| `transaction` | 7 | 增（单条 / 批量）、改、删、列、最近、汇总 |

| `account` | 5 | 增 / 改 / 归档、列、余额 |
| `book` | 5 | 增 / 改 / 删、列、详情 |
| `budget` | 8 | 五个读 + **设总预算 / 设分类预算 / 删预算**（05c，**正好到上限**） |
| `savings` | 4 | **增 / 改（含存入）/ 归档**、列（05c） |
| `scheduled` | 4 | **增 / 改（含暂停）/ 归档**、列（05c） |
| `persona` | 5 | **增 / 改 / 归档 / 切换当前角色**、列（05c） |
| `meta` | 1 | 默认项（执行位置＝设备，见 §3.2 订正） |
| `analysis` | 2 | 月度事实总览（含预算执行 / 最大单笔 / 近 6 期趋势）、区间趋势（05d，读） |

| `help` | 1 | **产品帮助检索**（05i，读；语料与检索在 `help.py`，**表外追加**，见下） |

> **`help` 域为什么在 §3.2 的表外（T-M7-05i，2026-09-20）：** §3.2 那张表回答的是
> 「App 已有的**数据功能**怎么映射成 Agent 工具」，而帮助检索不读写任何用户数据——
> 它回答的是「这个 App 怎么用」。它因此有两个与表内各行不同的性质：① **横切**：
> 每一轮都可能被问到，不属于任何一类数据；② **信号是问法而不是名词**（域路由
> `routing._SIGNALS` 里它那一组是「怎么用 / 在哪 / 支持」这类问句形态，而其它组
> 都是「预算 / 账本 / 分类」这类名词）。**范围是刻意收窄的**：只有产品帮助，
> **理财知识（外部行情 / 产品 / 收益数据检索）本卡显式砍掉、不做**；语料只写
> 当前实现里真实存在的功能与入口（不写「即将支持」这类承诺），它随实现漂移的
> 风险登记为 R-PROD-40。

**`budget` 域到上限（8/8）这件事本身是一个信号**：05d 的分析域或后续新增的预算类工具不能再并进来，只能新开域——域是注入单位，超过 8 就该考虑拆而不是塞。05d 的五个新域**都远低于上限**（2–3 个），这是刻意的：域在 05g 的域路由里是**注入单位**，小域让路由切得更准。

**域切分的判据是「模型在同一时刻要在这几个工具里挑一个」**——`transaction_update` 与 `account_update` 分属两域，是因为预路由可以只注入其中一域（05g），而它们各自的近义工具（`transaction_add` / `transaction_delete`）必须同域才谈得上准确率。

**域也是「v1 车道」的过滤单位**：v1 客户端只注入 `V1_LANE_OPS`（记账）对应的写工具，读工具与车道无关（见 `ai-architecture.md` 的「服务端接线」）。

**域路由（T-M7-05g 落地，2026-09-20）：** 按**词表**选域（`server/src/modules/ai/routing.py`），命中即只注入被选中的域，**没命中就注入全部域**（= P1 的注入面）。取舍与方案对比见 `ADR-011`，要点：

- **不额外调用模型**（§12.2 已定第 2 项的口径：简单输入的快路径由 loop 自然产生）；决策必须在第一个模型请求**之前**完成——`tools` 载荷发出去就收不回来。
- **误差方向是「宁可多注入」**：漏注入＝能力消失（模型只能说「这个我做不了」），误注入＝选择面变宽。因此闲聊、指代性追问（「那改成 6000 吧」）这类命中不了信号的输入**一律退回全量**。
- **域路由与入口推理分级是两件事**（`agent.classify_reasoning` 决定推理**开销**）：两者在 `run()` 里各算各的，判据与产物都不共享。
- **`tools_for_domains(domains, contract_version=...)` 就是注入入口**：路由只决定第一个参数，契约车道过滤（05b）原样生效；设备能力（05e）不在域里，任何路由结果都带上。
- 实测口径与数据点见 `risk-register.md` 的 **R-PROD-17**（离线：漏注入 0/58、误路由 18/58、平均注入 1.4 域 / 6.8 工具）。

### 7.3 读工具与写工具

| 类型 | 执行 | 结果去向 |
|---|---|---|
| **读工具** | loop 内直接执行 | tool result 喂回模型，继续 loop |
| **写工具** | **不直接执行**，产出 ActionProposal | 按审批策略挂起或放行（见 §7.4）→ 执行 → 结果回喂 |

### 7.4 写操作安全边界（不变）

```
模型 tool_call 参数
  → 组装 ActionProposal（名→id 服务端确定性解析）
  → 校验（Schema + 账本上下文）
  → 确认卡（风险 medium / high，或低置信 / 多步时强制）
  → 执行（TOCTOU 重校验）
```

**铁律三条（agent 化不放松）：**
1. 模型永不输出 UUID——名→id 由确定性代码解析
2. 金额与统计永远由确定性代码计算
3. 写库必须经校验与确认门

**审批结果四值**（借鉴 DSH 审批模型，比二值确认更严谨）：

| 结果 | 含义 | 后续 |
|---|---|---|
| `allowed-once` | 用户明确同意本次 | **唯一放行值**；执行后即失效，不产生长期授权 |
| `rejected` | 用户拒绝 | loop 收到拒绝理由，可调整方案重提 |
| `cancelled` | 用户中止整个任务 | 优雅终止（§4.4），说明已完成部分 |
| `unavailable` | 无法取得授权（超时/离线/界面不可用） | **视为拒绝**，不执行 |

**设计原则：不确定时倾向拒绝。** 只有 `allowed-once` 放行——没有「默认同意」「记住选择」这类隐式授权。

**审批不只是安全机制，也是人机交接点**：用户在此刻看到 agent 的完整意图，可以纠正理解偏差。这使审批卡同时承担「安全门」与「纠偏点」两个角色。

**服务端 loop 的额外收益**：工具与数据同在服务端，校验与执行可合并为一次事务，TOCTOU 窗口消失。

**审批触发策略（2026-09-18 定型；2026-09-28 REQ-78 扩档）**：写工具一律产出 ActionProposal，但**是否强制确认取决于两件事**——这个 op **做什么**（风险分级），以及这一轮**模型有多稳**（步数与置信度）：

| 任务形态 | 策略 |
|---|---|
| 单 Step 完成 | 沿用现有策略——confidence ≥ 0.9 自动执行 + 撤销窗（PR-2「高置信快速通道」）；低置信 / 中风险 / 高风险出确认卡 |
| **多步 loop（≥2 Step）** | **写操作一律强制确认** |
| **风险分级（REQ-78 / T20-3）** | 每个 op 带 `Tool.risk`（`low` / `medium` / `high`）；`medium` 与 `high` **一律强制确认，不看步数与置信度** |

四条理由的实现是 `agent.confirm_reason(*, step, confidence, op)`，**顺序即优先级**：
`high_risk` → `medium_risk` → `multi_step` → `low_confidence`。风险两级判「做什么」
（后果的形状），后两条判「模型自己有多稳」——两类正交，同时命中时报前者。

**逐 op 的完整名单不在这里**：那是 `docs/product/ai-confirmation-policy.md`
（61 条：56 个工具 + 5 个设备能力，含理由与处置），本节的表只讲**形态**。风险维度
的落点是注册表（`tools.Tool.risk`），`HIGH_RISK_OPS` 从它派生——**这三处不许各写
一份**（R-PROD-47「同一把尺子有三层」的同族陷阱），对账由
`tests/test_ai_confirmation_policy.py` 强制。

风险分级的判据（原文见 `Tool.risk` 的 docstring）：`low` = 新增类写 / 查询类 /
可一键改回的设置项（**不碰用户已有的数据行**）；`medium` = 改动或删除用户既有数据
（交易 / 预算 / 账户 / 账本 / 分类 / 定时 / 角色 / 余额），以及导出域与隐私域的写；
`high` = 后果**不可通过 App 内的任何操作挽回**——注销账号（7 天冷静期之后数据永久
删除）与删账本（连同其中全部流水）。**它不靠「会写库」判定**——写库的 op 有三十多个
——所以不能用一个通用的置信度阈值冒充。**05d 的工具在它之外还带 `warnings`**（置信度
因此降到 0.8），两条判据构成双保险：任一条被将来的改动放松，另一条仍拦得住。

理由：若所有写操作都强制确认，会击穿 PR-2 的快速通道体验；若多步任务也自动执行，则「先查预算再改预算」这类任务失去人工复核点——而多步场景下模型连续写库的累积风险高于单发。这是 §7.3 与 §7.4 此前表述张力的收敛。

### 7.5 域知识：按需加载的 Skill（T-M7-05h）

工具 `description` 只讲「这个工具能做什么」（§7.1），**跨工具的规则**（「『以后每月自动记房租』要建规则，不要顺手记一笔」）没有落点：写进某个工具的文案就是在讲别的工具的事，写进系统提示则是每一轮都要付的常驻成本——而记账 App 的绝大多数输入是「一句话记一笔」，PR-2 的 12 s / 25 s SLO 就在那条路上。

**Skill ＝ 一段服务端持有的域知识，绑定一到多个工具域，域命中才进系统提示。**

| 加载来源 | 规则 | 生效时机 |
|---|---|---|
| **收窄的注入面**（前瞻式） | 本轮注入面比**本车道**全部域小 → 带上这些域里有 Skill 的那些 | **第一个 Step 就在** |
| **实际用过的域**（懒加载） | 本轮有工具调用落在某域 → 带上它的域知识 | **下一个 Step 起** |
| 全量注入 | **不带任何 Skill** | ——「所有域都可能」等于没有命中 |

- **注入面是关键的可观察量**：05g 的域路由收窄它、显式 `tools=` 覆盖它。本卡不 import 路由，只读注入面——路由与显式覆盖一落地，前瞻式命中自动生效（零接线）。
- **未命中时 Skill 段本身与 05b–05d 逐字相同**（`render_skill_section(())` 返回 `""`，`test_ai_skills.py` 的金标用例钉住），因此**本机制**对快路径的 prompt 与 token 成本零影响。**这不等于「整个系统提示恒定」**——T20-6 在提示主体加过三条分类规则（+501 tokens / +3.6%，常驻），见 `docs/review/T20-6-delivery-2026-09-28.md` §3.4 的 token 实测与 R-PROD-54。
- **预算**：单条正文 ≤400 字符、一次注入合计 ≤1200 字符（与 §6.4 同一把尺子）；超限**整条不进**（不截断——半句规则的语义可能正好反过来）。单条上限在**导入期**就拦。
- **实测**（2026-09-20，`deepseek-flash`，真实调用）：域知识本身 **+144 tokens / 286 字符**；不命中 **0**（**仅指域知识这一段**，提示主体成本另计，见上一条）；同一轮收窄注入把 `prompt_tokens` 从 4888 降到 879（那是域路由的收益，与本卡成本分开报）。
- **位置与落库面**：追加在系统提示尾部（摘要段与现有对象段之后）；只替换 `messages[0]`，**不进事件日志**（system 消息从 P1 起就不在增量里）。

实现：`server/src/modules/ai/skills.py`（注册表 + 命中 + 渲染 + 导入期校验）、`agent.AgentLoop._load_skills`（两个来源的并集与系统提示重建）、`scripts/probe_skill_budget.py`（token 实测）。取舍与残余见 `ADR-012` 与 R-PROD-39。

## 8. 流式协议设计

### 8.1 事件类型

SSE 下行事件（`text/event-stream`）：

| 事件 | 载荷 | 客户端行为 |
|---|---|---|
| `phase` | 阶段标识（thinking / routing / tool_calling）。`routing`（T-M7-05g）在第一个 Step 入口发一次：载荷另有 `domains`（这一轮注入的域）与 `matched`（是否命中词表），**`step` 恒为 0** | 显示进行中状态（`routing` 步在 03c 的步骤卡上是「正在理解你的需求…」） |
| `tool_call` | 工具名 + 人类可读描述（"正在查询预算…"） | 显示步骤卡片 |
| `tool_result` | 摘要（不含原始数据） | 更新步骤卡片为完成 |
| `confirm` | 提案摘要（ActionProposal 预览） | 渲染确认卡 |
| `device_request` | 设备指令：`request_id`（需结果类的回传凭据）、`kind`（one_way / result）、`capability`、`payload`、`timeout_seconds`（仅 result）。**两类共用这一个帧**——客户端按 `kind` 决定要不要上行回传（T-M7-05e，字段表见 `ai-architecture.md` 与 `stream.py`） | 单向：执行；需结果：执行并 `POST /ai/device-result` 上行回传 |
| `delta` | 助手回复增量文本（**含推理通道**，见 §8.5） | 流式渲染 |
| `done` | 结束标记（含 usage、`conversation_id`、`stop_reason`、提案与执行回执、**`seq`**＝本轮结束时的事件序号——断连续读的游标，T-M7-04b） | 收尾 |
| `error` | 错误码（安全枚举） | 按降级契约处理 |

### 8.2 通道实现（技术可行性已确认）

```
WebView (JS)  ←─桥事件推送─  Kotlin 层  ←──SSE──  服务端
                                  │
                            OkHttp EventSource
```

- **Kotlin 层**：用 `okhttp-sse` 的 `EventSourceListener` 接收 SSE（OkHttp 4.12 已在依赖，仅需加 `okhttp-sse:4.12.0`）
- **转发**：复用现有桥事件推送机制（`onPermissionResult` 的「命令返回 pending + 事件推送结果」模式，`native-bridge.ts:497`）
- **上行**：用户输入、确认、设备工具结果为普通 HTTP（复用 `ai.*` 命令族）
- **Token**：沿用 ADR-003——Bearer token 全程不出 Kotlin 层

**不依赖 WebView 的 fetch streaming 支持**（minSdk 26 / targetSdk 36，但走桥转发更稳且与现有架构一致）。

### 8.3 超时与打断

| 项 | 设计 |
|---|---|
| 单步超时 | 12 s 慢速提示（显示当前步骤）/ 25 s 单步取消。**流式下两端计的都是「静默时长」**——即「多久没收到任何数据」，不是「这一步总共跑了多久」。见下方说明 |
| 整体 | 不设总时长上限，由多步构成，用户可见进度 |
| 打断 | 客户端可随时取消 → 上行 cancel → 服务端终止 loop |
| 断连 | SSE 断开 → 客户端提示；loop 状态在服务端可恢复（按 conversation_id） |

> **与服务端单步超时的口径一致（2026-09-19 明确）：** 服务的 `ai_agent_step_timeout_seconds`（20 s）在流式下由 httpx 的 read timeout 承担，语义同样是「两个数据块之间最多等 20 s」而非「整步 20 s」。两侧同口径是有意的：**一个在稳定输出的长回答不该被掐掉**——非流式下「总时长」是唯一可用的判据，流式下「静默」才是真正该判的异常。客户端实现（T-M7-02h）据此设 OkHttp 的 read timeout，**不要**用 `callTimeout`。

> **取消的服务端可观测形态（2026-09-19，T-M7-03e 定案；T-M7-04b 复审维持）：保持「断连即取消」。** **P2 把取消做成主动交互（「停止生成」；当时还有一个「语音打断」入口，REQ-75 后已不复存在，见 §9.2）后，`StopReason.CANCELLED` **仍不可达**——不新增取消端点、不发取消帧：① 服务端已把断连实现为连接级取消（工作协程被取消、未提交的那一批回滚，02g）；② 加显式取消通道要动已冻结的桥命令表与 `/ai/agent` 协议，而取消的用户已经离开，多一次模型往返或一条事件没有价值（02d 决策 8）；③ 真正需要服务端可观测的是**断连恢复**。客户端凭本地 `canceled` 标志收敛，并把它与被动中断（`unavailable`）**分成两个状态**：前者「已取消」，后者「连接中断」+ 重连入口（见 §9.2 与 `ai-architecture.md` 的「客户端确认门」一节）。
>
> **T-M7-04b 的复审结论：分两级。** `CANCELLED` 在 **loop 层可达**（显式 `cancel()`；以及审批四值的 `cancelled`——用户中止整个任务时置位取消标志，下一个 Step 入口收敛）；在**生产入口 `/ai/agent` 不可达**，且这是刻意的，不是遗漏：那条路径上没有 approver（确认卡走既有 v2 卡链路），而断连走的是取消任务本身——loop 的 Step 入口检查点根本不会被走到，客户端连一个 `done` 帧都收不到。**04b 的逐事件落库没有重新打开它**：断连时能留下的只是**已经产出的事件**（§6.2 的落库批），与「loop 自己收敛到 `CANCELLED`」是两回事。可达性的两级各有用例钉住（`tests/test_ai_conversation_resume.py::TestCancelledReachability`）。若要让它生产可达，需要的是**服务端可观测的取消信号**（显式端点或上行帧），那要改已冻结的桥命令表——按 ③ 的价值判断不做。

> **与 `APP-CONTEXT §10.3` 的关系（2026-09-18 明确）：** 该节「25 秒远端超时并降级」描述的是**快路径**（单发）SLO，不可直接套用到 agent 路径——一轮 loop 含多次模型调用，串行耗时必然超出 25 s。agent 路径的计时单位改为**单步**：单步 25 s 静默超时并取消，整体不设上限，由步骤可见性与用户取消权兜底。快路径保持 12 s / 25 s 不变。

### 8.4 部署与运行前提（2026-09-18 补充）

以下四项目前**均未就位**，是 P1 落地的前置条件，此前未在文档中记录：

| 项 | 现状 | 要求 |
|---|---|---|
| **nginx 缓冲** | 服务器实际部署（`/usr/local/nginx/conf.d/api.conf`，2026-09-18 实地核对）**无** `proxy_buffering off`；nginx 默认 `proxy_buffering on` 会把 SSE 事件**攒批下发**，中间步骤实时性归零 | 在服务器 **`/usr/local/nginx/conf.d/api.conf`** 增 `proxy_buffering off` / `proxy_cache off`，并允许 `X-Accel-Buffering: no` 透传，**并同步更新仓库副本 `infra/deploy/prod/nginx/api.conf`**（该副本即服务器那份的等价内容）。见下方说明 |

另注：生产为**单 worker** 部署（`server/Dockerfile:52` 无 `--workers`），会话状态可用进程内 + DB 持久化；现有内存限流字典（`service.py:64`）同样是单实例假设，其注释已声明多实例须换 Redis。**设备通道的挂起表同属这一族**（`devices.DeviceChannel`，T-M7-05e）：需结果类的挂起态生命期就是一次 Turn，因此放进程内；多 worker 时上行回传可能落到另一个进程（挂起请求等满超时窗才收敛，不会错写数据），进程重启则直接丢掉挂起请求（客户端拿到 404，按「这次设备操作作废」处理）。见 `ADR-010` 决策 2 与 R-PROD-34。

### 8.5 增量粒度与推理通道（2026-09-19 补充）

T-M7-02g 交付时 loop 仍是**非流式**的，`delta` 在助手文本产出的那一刻整段送出（一轮一帧），实时性由 `tool_call` / `tool_result` 的步骤可见性承担。**T-M7-02g-2 起改为 token 级**：provider 的流式增量逐片送出，同一套帧格式（§8.1 的八类事件一个不变）。

**两个通道。** `delta` 的载荷带 `channel` 字段区分内容来源：

| `channel` | 内容 | 客户端行为 |
|---|---|---|
| `content` | 助手正文（`ProviderResult.content`） | 正常渲染为回复 |
| `reasoning` | 推理内容（DeepSeek 的 `reasoning_content`） | **灰字折叠区**，对标 DeepSeek App 的「深度思考」 |

载荷形状：`{"text": "<增量>", "channel": "content" \| "reasoning", "step": <1 起的 Step 序号>}`。`reasoning` 通道是**纯增量字段**，P2 之前的客户端可以整条忽略（不渲染即可，不影响正文）。

**为什么推理增量必须送（而不是只送正文）。** `deepseek-flash` 的真实探针（2026-09-19，三档形态各一次真调用）显示：推理增量**先于**正文增量到达，且量大——深档带工具那一步 0.45 s 就有推理、全程 524 字符推理对 **0 字符正文**。而 02d 实测深档单步 5–7 s，那一步的时间几乎全花在推理上。**只转发正文增量的话，最需要「有反应」的那一步仍然长时间静默，收益接近于零。**

**服务端合并窗（100 ms）。** 实测帧粒度约 **4 字符/帧**（单步 138–164 帧），一轮三步就是 400–500 帧；直连透传会把客户端桥调用量推高一个数量级。帧泵把**同一通道、同一 Step** 的增量在 100 ms 内并成一帧再发：帧数降一个数量级，而首帧延迟最多只多这一窗。**合并放在服务端**而非客户端——架构的立场是客户端瘦渲染（§2.1），一处解决对所有客户端生效。合并只改帧的**分法**，不改内容：把一帧内的若干 `delta` 顺序拼接，与不合并时逐帧拼接的结果逐字节相同。

**收尾文案不流式。** 撞硬边界时的收尾请求（§4.4 的优雅终止）仍走非流式：它是一次机械交代，没有流式的必要；更要紧的是收尾请求失败时会退回确定性兜底文案——若它也流式，客户端会看到「半截模型输出 + 兜底文案」拼在一起。收尾文本产出后作为**一帧** `delta` 送出（此时正文通道已经收口）。

**中途失败的半截文本（客户端契约）。** `error` 帧到达时气泡里可能已经有文本。**客户端保留已渲染的半截文本并标注本轮失败，不清空。** 理由：已经显示给用户的内容突然消失，比「看到一半 + 一句失败提示」更糟；这也与 §4.4「优雅终止须说明已完成部分」同一口径。**T-M7-04b 起本轮已经产出的部分会落库**（逐事件落库：用户输入、每个跑完的配对组、收尾文案各成一批），因此重新打开会话时**这一轮跑完的步骤都在**，并有一条 `error` 事件说明它停在半路。**仍不在日志里的只有正在生成的那一段正文**——它还没产出，无从落库；客户端按上面的契约保留它并标错。断连恢复入口见 §6.2。

**失败那一步的 token 拿不回来。** usage 在流式响应的**尾块**，流中断即无——失败步骤的用量记不上（与非流式失败「无响应体 = 无 usage」同口径，不是回归）。**已经完成的步骤**的用量照常计入（每步结束时即上报）。真实频率与成本低估幅度待 02g/02i 接通后统计（R-PROD-15）。

> **⚠️ 服务器实际形态（2026-09-18 实地只读核对 + 当日文档对齐）：** A 机 nginx 是**源码编译**安装（`/usr/local/nginx`，1.16.1，由 `/etc/init.d/nginx` 托管），**不存在 `/etc/nginx`**；站点配置在 `/usr/local/nginx/conf.d/`（`api.conf` + `ups.conf`），监听 **80**，路径前缀 **`/aozora-api/`**——该前缀由应用层 `SharedProxyPrefixMiddleware`（`server/src/main.py`，提交 `dc05b1c`）剥离，nginx 原样透传（对应用例见 `server/tests/test_main.py::TestSharedProxyPrefix`）。upstream 指向 A 机自身 eth0 内网 IP `192.168.44.13:18080`，再到 `aozora-api-test` 容器。仓库原先按 `/etc/nginx` + 8081 的设计稿从未落地，**已于当日按实况统一**：仓库改以 `api.conf` + `ups.conf` 承载实际部署副本，`aozora-prod.conf.template` 保留为未落地的生产设计稿。完整记录、已知风险（`location /` 敞开、upstream 走 DHCP IP、无访问日志等）与一处磁盘/运行态漂移见 `infra/deploy/prod/nginx/DEPLOYED.md`——**任何 nginx 相关改动都以该文件为准**。

## 9. 交互设计（对标 DeepSeek）

### 9.1 统一智能模式（无模式选择）

DeepSeek App 于 2026-09-10 将「快速 / 专家 / 识图」三模式**合并为统一智能模式**——由系统自动分析输入判断场景与难度，自动决定是否开启深度思考与联网搜索。**用户不需要理解或选择模式。**

Aozora 对应设计：

| 用户侧 | 系统侧 |
|---|---|
| 只有一个输入框，无模式开关 | 自动判定：简单意图走快路径（单发），复合任务走 agent loop |
| 不感知"快路径/慢路径" | 路径切换对用户透明（§11 的升级判据） |
| 步骤可见（长任务时） | 简单任务无步骤展示，直接给结果 |

**原则：复杂度对用户不可见。** 用户说"记一笔 12 块"和说"帮我把上个月的预算改成 3000"应该是同一个输入框。

### 9.2 交互对照

| 场景 | DeepSeek 做法 | Aozora 设计 |
|---|---|---|
| 中间步骤 | 思考过程折叠区、"搜索中"状态 | 步骤卡片流（"正在查询预算…"→"已读取 3 条"），可折叠 |
| 需确认 | 无（对话即执行） | **确认卡**（写操作与高风险强制，见 §7.4 四值审批） |
| 失败 | 显示错误 + 重试 | 按降级契约：重试 → 快路径 → 本地 NLU；优雅终止时说明已完成部分 |
| 打断 | 停止生成按钮 | 取消按钮 → 终止 loop（§4.4 不变式 3：收敛到一致状态） |
| 会话管理 | 侧边栏会话列表、文件树预览 | 会话列表（新建/切换/重命名/删除）；后续可扩展"任务产物"侧栏 |
| 语音 | 语音对话，**支持中途打断** | **产品侧不内置**（REQ-75 移除离线语音）：交由系统输入法自带的语音转文字，因此也没有「语音打断」这条语义 |

**打断与中断的落地（T-M7-03e）：** 「取消按钮」= 流式期间输入位的**「停止生成」**（`ai.cancel` → 关 SSE → 服务端按断连取消）；这是**唯一的取消入口**（REQ-75 移除语音后，原先「录音键按下先取消再录音」那条同语义路径不复存在）。**「取消」是用户主动、断连是被动**——两者在 UI 上不合并成一个状态：前者就说「已取消」，后者说「连接中断，本轮未完成」并给**重连入口**（R-PROD-19；P2 的恢复手段是原样重发，按 `conversation_id` + `seq` 续跑归 P3 的 04b）。确认卡的动作**只在收尾后启用**（`done.proposals` 是权威清单），四值口径见 `ai-architecture.md` 的「客户端确认门」一节。
| 文件/图片 | 图片、PDF、Word 上传 | 现有图片记账链路（`/ai/parse-image`）扩展到对话内上传 |

**安全优先的差异点**：DeepSeek 是消费级对话（无副作用），Aozora 的写操作有真实财务后果，因此**确认卡不能省**。这是有意的产品差异，不是架构妥协。

## 10. 迁移路径

| 期 | 内容 | 交付后的能力 | 独立价值 |
|---|---|---|---|
| **P0** | 三实体上云（`savings` / `scheduled` / `personas`）：建表 + 迁移 + 接入现有同步 | 服务端数据完整，loop 才可能 | **数据可靠性**——多设备、备份、换机恢复本就需要 |
| **P1** | 服务端 Agent Loop + 工具层 + SSE 流式通道 + 基础会话状态；**客户端最小接通**（SSE 接收 + 桥事件转发 + 终态按既有 v2 intent 分发渲染） | 多步任务、**多轮澄清（当前痛点）** | 核心能力升级 |
| **P2** | 客户端瘦渲染重构 + 步骤卡片流 + 多会话管理 + 统一智能模式 | 对标 DeepSeek 的观感：流式渲染、步骤可见、会话列表 | UX 升级 |
| **P3** | 会话事件日志（完整形态）+ 摘要压缩 | 断连恢复、会话分叉、压缩无损、审计 | 可靠性 + 成本控制 |
| **P4** | 域路由 + Skill 封装 + 设备能力通道 | **全功能覆盖**（含设备类能力）、扩展性 | 目标达成 |

**顺序理由：**

- **P0 必须最先**——服务端 loop 够不到本地数据，这是硬前提；且 P0 的价值独立于 agent（数据可靠性）
- **P1 带 SSE**——loop 的中间步骤必须**可推送**，否则多步任务变成"长转圈"；SSE 与 loop 是同一交付
- **P2 再瘦客户端**——P1 交付通道并做**最小消费**（终态走既有 v2 intent 分发，用户感知为"思考完毕展开卡"）；流式气泡、步骤卡片流、多会话等**观感**归 P2
- **P3 完整化会话**——P1 的基础会话状态已够多轮澄清；事件日志的恢复/分叉能力可后置
- **P4 收口覆盖度**——设备能力通道需要前面的 loop + SSE 就位

> **2026-09-18 定型：** P1 / P2 的边界原表述存在内部张力——「SSE 与 loop 是同一交付」（要求 P1 带通道）与「P2 期间客户端可用非流式降级」（暗示 P1 不接通道）并存。现统一为：**P1 = 服务端能力闭环 + 客户端最小接通；P2 = 观感与结构**。P1 的客户端交付底线是"端到端可验证"，上限是"不做观感打磨"。
>
> **P1 的实施拆解**见 `docs/milestones/production-execution-plan.md` T-M7-02（02a–02i 九张子卡）。其中 **02a 是 go/no-go 闸门**：`qwen3.7-flash` 的 tool calling / thinking / stream 组合实测若不支持，loop 需退回「文本 JSON 工具调用」（§7 相应修订）。
>
> **P2 / P3 / P4 的实施拆解（2026-09-19 拆定）：** 三期的子卡拆分已定稿，逐卡职责边界、批次与并行切分点见各自的实施推进计划——P2 `docs/milestones/T-M7-03-P2-implementation-plan.md`（03a–03e）、P3 `docs/milestones/T-M7-04-P3-implementation-plan.md`（04a–04e）、P4 `docs/milestones/T-M7-05-P4-implementation-plan.md`（05a–05i）。**跨期唯一的安全切分点：** P4 的 **05a（ActionProposal v2 契约）** 与 **05e 的设备通道协议部分**不依赖 P2 / P3，可提前开工——契约晚改等于已实现的工具返工。

**回退保护：** 每期结束时代理旧链路仍可用（§11），任一期出问题可单独回退。
