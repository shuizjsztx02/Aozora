## 二、设计决策与落地

### 2.1 配置 XML（`res/xml/accessibility_service_config.xml`）

三条红线守在这里（ADR-016 决策 3 / 5）：

1. **只订阅窗口类事件**：`typeWindowStateChanged|typeWindowContentChanged`。不订阅按键、触摸、通知——配置 XML 里 `accessibilityEventTypes` 已限定，由系统强制。
2. **`canRetrieveWindowContent="true"`**（必须，否则拿不到节点文本）。
3. ★★★ **不声明 `canPerformGestures`**：配置 XML 里**没有**这个属性，`SecurityConfigTest.accessibilityServiceConfig_doesNotDeclareCanPerformGestures` 守住。

**一处刻意选择**：`notificationTimeout="500"` 节流。`TYPE_WINDOW_CONTENT_CHANGED` 在一个页面上会高频触发（每次 UI 刷新都回调一次），500ms 节流是成本最低的第一道防抖，真正的防抖靠服务内的内存签名（见 §2.3）。

**另一处刻意选择**：**不写 `packageNames`**。用户的来源集合会变化（T21-7 的「从已安装应用添加」），XML 是静态的写不了动态集合。包名判定在 `AutoBookAccessibilityService` 内按 `AutoBookRepository.sourcePackages()` 运行时过滤，与通知通道形态一致。

**关于 `android:isAccessibilityTool`**：本卡**未加**。Google Play 上架时要求 API 33+ 在 `<service>` 标签上声明 `android:isAccessibilityTool="false"`（我们不是辅助工具），但这是 Google Play 专用的上架前置，国内商店不管；且该属性加在 `<service>` 标签而非配置 XML。登记为已知限制（§五.3），由 T21-9 在 Google Play 上架准备时处理。

### 2.2 `AutoBookAccessibilityService.kt`

形态与 `AutoBookNotificationListener` 对齐（`ADR-016` 决策 1 通道关系），但事件模型不同——无障碍服务订阅的是**事件流**而不是通知，需要自己处理页面抖动：

| 处理 | 内容 |
| --- | --- |
| `TYPE_WINDOW_STATE_CHANGED` | 记录 `currentPageKey = pkg\|activityClass`；清除旧页面签名（避免不同页面复用同一 key）。**不落行**——页面还没渲染完，文本往往不全 |
| `TYPE_WINDOW_CONTENT_CHANGED` | 拼文本 → 内存签名防抖 → 过滤 → 落库 |
| `eventIdentity` | = `currentPageKey`（`pkg\|activityClass`），**不带分钟桶**——同一页面多次触发 → 同一 L1 键 → L1 自动丢弃（配合 `DedupeKeys.l1Key` 的分钟桶 + 归一化文本） |
| `postedAt` | 取 `event.eventTime`（系统给的事件时间戳，UTC ms），取不到时 fallback `System.currentTimeMillis()` |

★ **只读不写的三道守护**（ADR-016 决策 3）：

1. 配置 XML 不声明 `canPerformGestures`（§2.1）；
2. `SecurityConfigTest.accessibilityServiceSource_doesNotCallPerformAction`——grep 式反向断言，源码里不得出现 `performAction(`；
3. 本卡自审：代码里**没有任何 `performAction` 调用**，包括 `AccessibilityNodeInfo.performAction` 与 `this.performAction`。

### 2.3 内存签名防抖（关键设计）

★ **两层防抖**（`TYPE_WINDOW_CONTENT_CHANGED` 在页面上高频触发）：

1. **内存签名**（本对象内）：`ConcurrentHashMap<pageKey, hash(归一化文本)>`，文本没变就直接跳过，**根本不走到 DB**；
2. **L1 去重**（`DedupeKeys` + Room 唯一索引）：即使同一页面的文本微变（秒级刷新导致金额显示变化），L1 的分钟桶 + 归一化文本仍能把它合并为同一行。

两层共同挡住抖动：内存层挡 99% 的重复（避免无谓 DB 写入），DB 层兜住跨进程重启的残差。**T21-3 的 `DedupeKeys.l1Key` 注释里点名的「T21-4 侧的页面签名防抖」就是本卡实现的这条**。

### 2.4 `AccessibilityFilter.kt`

与 `NotificationFilter` 形态完全对齐（输出同一个 `Decision` 形状），但**常量独立定义**。

**为什么常量独立而不是共用**：红线 #7「不顺手重构卡外文件」——`NotificationFilter` 是 T21-3 独占的文件，本卡修改它会越过文件边界。两条通道的关键词集事实上相同（支付成功 / 到账 / 退款 / 验证码 / 广告），但归属的过滤器不同，语义上分开更清楚。

**一处复用**：`NotificationFilter.extractAmountCents` 是公开纯函数，金额提取的数学与货币标记是通道无关的，直接调用避免重复代码。

**支出事件词表一处刻意选择**：刻意**不加** `付款金额` / `支付金额`——它们是金额修饰词（商品详情页也有），不是事件词。如果加入，测试用例 `amountAndOrderNumber_withoutEventWord_isRejected` 会**变绿**——这正是"品牌词/修饰词误判方向"的缺陷形态。

### 2.5 `strings.xml` 显著披露

无障碍 label 与 description 的口径对齐 `docs/legal/accessibility-disclosure.md`（T21-1 的合规物料）。用户在系统「无障碍」页看到的就是这几句话——**读什么 / 不读什么 / 不操作什么 / 能撤销吗** 一次讲清楚。

★ 这一行是本 App 在无障碍授权链路里**唯一能说的话**，口径以 `docs/legal/privacy-policy-v1.md §2.4` 与 `accessibility-disclosure.md` 为准。

### 2.6 `AndroidManifest.xml` 追加无障碍 `<service>`

与通知 `<service>` 同形态：
- `android:exported="true"`
- `android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE"`
- `<intent-filter>` 带 `android.accessibilityservice.AccessibilityService`
- `<meta-data android:name="android.accessibilityservice" android:resource="@xml/accessibility_service_config"/>`

★ **`<uses-permission>` 集合逐条不变**——`SecurityConfigTest.manifest_usesPermissionSetIsUnchangedByAutobook` 的 `expectedUsesPermissions` 集合无需改动（本卡未新增任何 `<uses-permission>`）。

### 3.2 反向验证（`AI协作稳定性守则.md` §3.2）

把「页面像支付页」的判据打回缺陷形态，三条变异用例确认用例本身守得住：

1. **品牌词-only 变异**：去掉事件词，只留品牌词 `微信支付 ¥32.00` → 用例断言**拒绝**。如果未来有人把 EXPENSE_EVENT 加宽到包含品牌词，用例会变红。
2. **金额+订单号变异**：保留金额与订单号，去掉事件词 → 用例断言**拒绝**。这是「商品详情页误识别为支付页」的根因。
3. **聊天+金额形态变异**：聊天文本里出现 `¥32.00` → 用例断言**拒绝**。这是「聊天页误识别为支付页」的根因。

### 3.3 `performAction` grep 式守护

`SecurityConfigTest.accessibilityServiceSource_doesNotCallPerformAction` 直接读 `AutoBookAccessibilityService.kt` 源文件，断言 `performAction(` 字面不存在。**任何未来加入的写操作**（即使是 `AccessibilityNodeInfo.ACTION_FOCUS` 这种看似无害的）都会让这条用例变红，迫使他显式决定要不要打破只读承诺。

## 五、已知限制（交 T21-9 收口落笔）

1. **Android 13+ 侧载授予无障碍需先在应用详情页「允许受限设置」**（Android 15+ 更严）——直接影响走查步骤与用户引导。T21-7 的权限引导须显式覆盖这条（登记为 R-PROD-62 候选，T21-9 落笔）。
2. **`FLAG_SECURE` / 支付保护页读不到**——必须在真机上确认微信/支付宝的支付结果页在常见机型的支付保护开启与否两种状态下是否可读。**本卡未做真机取证**，defer 到 T21-9 收口现场取证（决策 #18 ② / 决策 #19 ④）。
3. **商店审核**——国内商店须做无障碍权限申报（钱迹 / iCost / 小星记账均有在架先例，口径可参考），Google Play 须声明 `isAccessibilityTool="false"` 并做显著披露。**本卡未加该属性**，理由见 §2.1。
4. **无障碍规则的第三方改版维护成本**：依赖微信 / 支付宝的页面文案与结构，对方改版可能导致规则失效。本卡的 `AccessibilityFilter` 关键词集是**粗筛**（支付成功/扣款/到账这种**极稳定**的事件词），改版成本主要在「页面文本拼接」的形态识别上——登记 R-PROD-58（T21-9 落笔）。
5. **同一 activity class 下跨笔支付且文本相似时的 L1 误合并**：例如两笔「支付成功 ¥32」在同一个 `PayResultActivity`，L1 键相同会被视为同一事件。第一版已知限制，登记 R-PROD-5x（T21-9 落笔），后续轮次若证明真实影响可考虑引入订单号解析（属于 T21-6 解析层的活）。
