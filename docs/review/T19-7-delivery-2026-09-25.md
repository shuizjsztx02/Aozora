## 三、包体对照（用户诉求的量化核验）

### 3.1 读数的可信口径（本卡的一处方法学发现）

**`app/build/outputs/apk/debug/app-debug.apk` 的文件大小不可直接采信**：Gradle 增量打包（zipflinger）会在 zip 条目之间留下空洞，形成稀疏文件——本卡实测该文件 `ls` 报 128 MiB 而其 zip 内容只有 6.3 MiB，条目 `header_offset` 最大值达 134,157,744 而内容总和仅 6.59 MB。**首次测量因此得到「只减 4 MiB」的假读数**。

正确做法：**删除 APK 后重新 `assembleDebug`**（强制 `packageDebug` 重新执行），得到非稀疏文件；或直接用 zip 内容口径（`compress_size` 求和）读数。本卡的最终读数两者一致。

### 3.2 对照表

| 口径 | 移除前 | 移除后 | 差值 |
| --- | --- | --- | --- |
| APK 文件大小（干净重建） | 138,600,240 B（132.18 MiB） | **6,673,237 B（6.36 MiB）** | −131,927,003 B（−125.82 MiB，**−95.2%**） |
| APK zip 内容（`compress_size` 求和） | 134,009,756 B | 6,586,247 B | −127,423,509 B（−121.51 MiB，−95.1%） |

> 两个口径的差值（−131.9 MB vs −127.4 MB）来自「移除前」那份 APK 自身也含约 4.5 MB 稀疏空洞，是产物侧的噪声、不是内容差异。**归因以内容口径为准**。

### 3.3 降幅的构成（逐条目取证）

| 组成 | 原始大小 | APK 内占用 |
| --- | --- | --- |
| `assets/vosk-model-small-cn/`（28 条目） | 136,584,542 B（130.24 MiB；`du -sh` = 131 MB） | 89,855,044 B（85.69 MiB，deflate 压缩后） |
| `libvosk.so` × 4 ABI（arm64-v8a 8,862,928 / armeabi-v7a 8,279,808 / x86 9,670,916 / x86_64 9,678,912） | 36,492,564 B | 36,492,564 B（**stored，不压缩**） |
| `libjnidispatch.so` × 7 ABI（arm64-v8a / armeabi / armeabi-v7a / mips / mips64 / x86 / x86_64） | 944,852 B | 944,852 B（stored） |
| **合计在 APK 内占用** | | **127,292,460 B（121.40 MiB）** |

内容口径降幅 127,423,509 B 与该合计 127,292,460 B 差 131 KB（中央目录 / 签名块随条目数变化的正常差异）——**降幅完全由语音链路解释，无残余项**。

> **与卡面预期的两处出入（如实记录）**：①卡面写「assets −131 MB」指的是**磁盘目录大小**（131 MB），APK 内是**压缩后的 85.69 MiB**，两者不可混用；②卡面写「native libs −3 ABI × 2 库」，实测是 **`libvosk.so` 4 ABI + `libjnidispatch.so` 7 ABI = 11 个条目**（`build.gradle.kts` 未配 `abiFilters`，AAR 自带的全部 ABI 都进了包）。

### 3.4 仓库根那份副本

`.gitignore` 的两行分别是 `app/src/main/assets/vosk-model-small-cn/` 与 `src/main/assets/vosk-model-small-cn/`。后者是一个**误放在仓库根的 131 MB 同名副本**（该目录树内除 vosk 模型别无他物，实测 `find src -type f | grep -v vosk` 为空）。**删掉忽略条目的同时必须删掉它**，否则它立刻从「被忽略」变成 131 MB 的未跟踪目录（实测：只删忽略行的瞬间 `git status` 就冒出 `?? src/`）。

## 六、设计决策（在卡面既定口径内落地，无新增决策）

1. **`usePermissions` 的 `canRecord` 随语音一起删**（`use-permissions.ts`）：它的唯一消费方就是 `AssistantPage` 的 mic 授权流。`PermissionStatusData` 的 `canRecordAudio` 与 `PermissionType` 的 `RECORD_AUDIO` 同步删除——三者是同一份词汇表的三处，改一处就失配。**保留** `canCamera` / `canGallery` / `shouldGuideSettings`（`ImagePickerSheet` 在用）。
2. **`device-executor` 的 `deferred` 结局删掉**：它唯一的生产者就是 `voice.transcribe` 分支，留在类型里就是一条永不产生的死分支（守则 4.3「单一实现判据」的反面）。
3. **`use-assistant` 的 `handleDeviceRequest` 收敛为一行委托**：语音分支删掉后「能力名 → 执行器」不再有例外，原本为语音写的「同一时刻只等一次语音输入 → 后来者按 `unavailable` 结算」也随之删除——那段逻辑的存在理由（人的动作没法排队）随语音消失。
4. **`AssistantPage` 的「语音打断」交互随之下架**：`handleMicClick` 里「流式期间开口即打断本轮生成」的语义（架构 §9.2）没有别的入口，`streaming` 期间的中止仍由输入区的「停止」按钮承担。这正是 T19-9 要写进 `risk-register.md` 的 R-PROD-19 措辞项（决策 #14）。

## 九、推送与远端 CI 实况
