# T18-7 · 记账联动账户余额（REQ-70）— 交付记录

**日期：** 2026-09-23 | **轮次：** 第十八轮 T18-7 | **基线 HEAD：** `d360988`（main）

**上游依据：** `docs/人工测试和需求变更-v2.md` REQ-70（用户第 5 项诉求）+ T18-7 卡 + `docs/adr/ADR-013`（余额=存量字段）

**一句话：** 记一笔钱时，被选中的账户余额在同一次事务里跟着动；编辑、换账户、软删、撤销删除、AI 记账、定时记账六条路径全都被同一处实现覆盖，入队的是**余额绝对值**而非增量。

## 一、范围与非目标

**做：** REQ-70 卡面五项 —— ①三方法同事务联动 + 同事务入队 account upsert（绝对值）；②编辑/换账户重算；③定时引擎联动；④服务端 `proposal_ops` 的 transaction 系列联动；⑤五条不变量守护用例。

**非目标（明确不做）：** 不改交易金额与 `Money` 链路；不为负余额发明新样式（沿用 `Math.abs` + 手拼负号口径）；不做按月余额快照；不动预算聚合；不改服务端 `statistics` 口径（仍按交易算，不读余额）；不做多币种；不动 `pickDefaultAccount`、`account.archive` 语义。

**一处对卡面的扩面（有意，需理由）：** 卡面只提 `transaction_add/update/delete`，实际把 **`undo_delete_transaction`（REST 撤销删除）** 也接上了联动 —— 它是**可达的真实入口**（`POST /transactions/{id}/undo` 有路由有服务方法），软删已回补而撤销不回补会让「软删 → 撤销」这一来一回凭空吃掉一笔钱。同一条不变量不能只在半边成立。

## 二、跨端契约：余额符号（本卡新引入）

```
收入（type=income） → 账户余额 +amountCents
支出（type=expense） → 账户余额 −amountCents
```

落点两处，**逐字同式**，各有用例钉住：

| 端 | 实现 | 守护用例 |
|---|---|---|
| 客户端 | `db/Repository.kt` 私有 `balanceDelta(type, amountCents)` | `RepositoryTransactionBalanceLinkTest`（20 例） |
| 服务端 | `transactions/service.py` 模块级 `balance_delta(tx_type, amount_cents)` | `test_transaction_balance_link.py::TestBalanceDeltaContract` |

这是**隐性契约**（不像桥命令计数那样有显式清单），所以两处各设一防，任一端改符号都会被自己的板抓住 —— 单边设防等于没设防（守则 3.1）。

## 三、实现要点

### 3.1 客户端：联动落在 `Repository`，前端零改动

三条写入路径（`insertTransaction` / `updateTransaction` / `softDeleteTransaction`）在**既有事务内**调用同一私有方法 `applyBalanceDelta(accountId, delta)`：读账户 → `copy(balanceCents + delta, version + 1)` → `accountDao().update` → 入队 `OP_UPDATE` mutation（payload = `accountToJson(全字段)`，`expectedVersion = 变更前版本`）。

**卡面列的前端文件一个都没改**（`QuickEntrySheet.tsx` / `TxEditSheet.tsx` / `use-assistant.ts` 全零改动）。理由：前端所有交易写入都经桥的 `transaction.insert` / `transaction.update` / `transaction.softDelete` 三个命令，落点全在这三个 Repository 方法上 —— 联动放这里，**QuickEntrySheet、TxEditSheet、聊天卡替换写、DetailPage 删除、定时引擎五条调用方路径自动全覆盖**。卡面说「TxEditSheet 与聊天卡替换写两条路径都要覆盖，这是本卡最容易漏的地方」，落点选对之后这条风险结构性消失，而不是靠记得两处都写。

`updateTransaction` 的重算按「同账户取净差额 / 换账户两侧分别处理」：

```kotlin
if (current.accountId == tx.accountId) {
    tx.accountId?.let { applyBalanceDelta(it, newSigned - oldSigned) }
} else {
    current.accountId?.let { applyBalanceDelta(it, -oldSigned) }   // 旧账户回补
    tx.accountId?.let { applyBalanceDelta(it, newSigned) }          // 新账户加计
}
```

### 3.2 客户端：绝对值入队（幂等铁律）

`accountToJson` 写的恒是**新余额本身**，不是 delta。于是同一条 mutation 重放（离线队列重试 / pull-push 重放）只是把同一个值再写一次，**不产生任何累积**。这是决策 #4 一直以来的口径（T18-5 已把 `balanceCents` 放进 payload），本卡只是让**记账路径**开始生产它。

### 3.3 服务端：联动是单点实现，sync change 由调用方登记

按稳定性守则 4.3 的判据自查（「同一业务概念，仓库里有几处实现？」），服务端把联动收敛成**一处**：

- `TransactionService._apply_balance_deltas(user_id, deltas)` 是唯一的余额改动点，REST 路由与 AI 执行面都经本类的写方法进来；
- 五个写方法（`create_transaction` / `create_transaction_batch` / `update_transaction` / `delete_transaction` / `undo_delete_transaction`）各自构造 delta 字典后调用它；
- **batch 按账户聚合**：同一账户的多笔先求和再一次性应用，否则一个批次里同一账户会被叠加多次、`version` 也会被多加几次；
- 符号只从 `balance_delta` 取，联动处绝不另算一遍。

**sync change 的登记留在调用方**（`proposal_ops._execute_transaction_update/_delete` 与 `service.execute_proposal` 的记账分支），新增导出辅助 `register_balance_account_changes(db, user_id=..., account_ids=[...])`。这是**刻意的分工**而不是漏做：

- 与交易自身的登记同一分工（`_register_change` 一直由执行体调）——「改了什么」由 service 负责，「让设备看得见」由执行面负责；
- **REST 路径不登 sync change 是既有性质**（它整条链路都不参与设备同步）。若把登记塞进 service，REST 记一笔会突然让设备 pull 到一个余额变化、却 pull 不到那笔交易 —— 引入一种新的不一致。本卡不改变这条边界。

换账户时**旧账户也要登记**（它被回补了，同样变了），所以 `_execute_transaction_update` 在调用 `update_transaction` **之前**先取 `old_account_id`。

### 3.4 联动失败的静默跳过（一条明确的策略，不是防御性代码）

账户查不到 → 跳过联动，记账照常成功。这不是「不可能场景的错误处理」，而是**优先级表态**：联动是记账的附属效果，一笔合法流水不该因为附属效果失败而写不进去。归档账户**照样联动**（查询不过滤 `archived_at`）—— 余额是事实，归档只是不再可选。

## 七、已知限制与挂账

### 7.1 R-PROD-43（本卡新增，登记于本文件）

**多设备并发下的余额覆盖。** 余额是**存量字段**，上行恒为**绝对值** —— 于是两台设备各自记账时，各自的「本地余额」都不知道对方那一笔，后 push 的一方会把先 push 的一方的结果整个覆盖掉（丢一笔的增量）。服务端 AI 侧同理：设备离线期间 AI 在服务端改了余额，设备上线后若本地已有活跃 account mutation，pull 会跳过该账户的合并（既有保护），两边就此分叉。

这是 ADR-013 决策 #2 选择存量字段的**已知代价**，换来的是幂等（绝对值可重放）与可手动校准。现有缓解是 pull 的「仍有活跃 mutation 的实体跳过合并」，它避免了**本地被覆盖**，但没有解决**服务端侧无仲裁**这一半。

**真机多设备并发与离线→联网余额一致性 → T18-9 收口验收项。** 长期方案（余额改为「交易现算净额 + 手动校准量」的派生表示，决策 #3 已为 `account_balances` 工具统一口径）属独立决策，不在本卡。

按 §3 冲突矩阵，`docs/risk-register.md` 由 **T18-9 统一落笔**，本卡只在此描述。
