## 二、缺陷形态（复核入库结论，无新增发现）

生产者是 Kotlin 六处兜底赋值，消费者是 `CategoryIcon`「icon 非空即原样文本渲染」：

| 落点 | 旧兜底 | 触发条件 |
| --- | --- | --- |
| `db/Repository.kt:1849` `serverChangeMapToBook` | `"default"` | 服务端 `book.icon` 为 NULL（bootstrap / pull） |
| `db/Repository.kt:1878` `serverChangeMapToAccount` | `"default"` | 同上（**AI 走 v2 车道新建账户最典型**：工具只在模型给了 icon 时才写进 payload） |
| `sync/SyncModels.kt:56` `toBook` | `"default"` | pull 的 change 载荷缺 icon |
| `sync/SyncModels.kt:80` `toAccount` | `"default"` | 同上 |
| `bridge/AozoraBridge.kt:415` `handleBookInsert` | `"book"` | JS 不传 icon 键 |
| `bridge/AozoraBridge.kt:530` `handleAccountInsert` | `"account"` | JS 不传 icon 键 |

两处复核（与卡面一致）：

- `handleBookUpdate` / `handleAccountUpdate` 走 `BridgePayload.optionalString(...) ?: current.icon`，**没有裸词兜底** —— 故卡面 ② 只点两处 `insert` 是正确的。
- **服务端侧无裸词**：`server/src` 全文搜 `"default"` 为 0 命中；`server/src/models/ledger.py:59/:126` 两列均 `nullable=True`、无默认值。「服务端保持 NULL 语义、兜底留在客户端」成立。

## 三、设计决策：存量走**渲染层容错**，不做回填迁移

卡面 ③ 给了二选一。**选渲染层容错**，三条理由：

1. **回填迁移在数值上不可行**：本轮决策 #1 规定「Room v10 → v11，收口核验 = `schemas/…/11.json` 存在且**只此一个新版本**」—— 为回填再加 v12 直接违反收口核验。
2. **折进已提交的 `MIGRATION_10_11` 也不行**：它对**已经升到 v11** 的设备不生效（本机模拟器/真机经 T18-5 / T18-8 的设备验证后均已过 11），而那正是要看效果的地方。
3. **回填只治本机，容错治全链路**：裸词**可以存在于服务端** —— 一台还带着中毒行的客户端把 `"default"` push 上行（push 侧本轮刻意不改），服务端 `icon` 列就存下这个词，再下发给**其它设备**。回填只修当前设备的本地行；容错对本地存量、服务端存量、新落库三种来源一律生效。

**实现**：`CategoryIcon.tsx` 里一个 `PLACEHOLDER_ICONS = new Set(['default','book','account'])`，命中即视同「未设置」，落 `fallback`（或名映射回退）。

**精确匹配小写三词、不做大小写归一**：`IconPicker` 的「自定义图标」文本框上限正是 4 字符，`book` 是**合法的自定义文本**；放宽匹配会吞掉用户真自定义的图标（用例 `非裸词的自定义文本照旧原样渲染` 钉住这条边界）。

## 六、已知限制与挂账

1. **库内值不会自愈，只有显示层不再中招**（§三的刻意代价）：Room 里那条 `"default"` 仍是 `"default"`，直到该实体下一次被写入（用户选 emoji，或服务端该行变化 → pull 覆盖）。
2. **编辑态仍会把中招值回填进自定义文本框**：`IconPicker.tsx:35` 的 `customValue` 判据是「非照片且不在 emoji 宫格内 → 视为自定义文本」，`"default"` 不在宫格内，故编辑一个中毒实体时那个 ≤4 字符输入框里会显示 `default`（**预览框已走容错、显示 💰**）。卡面 ③ 只点了 `CategoryIcon`，改动清单也未列 `IconPicker`，按「改动不越界」未动。收口时若想一并收掉，只需让 `customValue` 共用同一谓词（一行）。
3. **服务端 `icon` 列可能存着裸词**：push 侧本轮刻意不改，故一台中毒客户端上行即把 `"default"` 存进服务端、再下发给其它设备（那些设备靠本卡的容错显示正常）。**未登记 R-PROD 号** —— 本轮多个并发会话在占号（手册 §2.6 撞号风险），且这属「客户端已兜住的服务端语义」，建议收口时统一决定是否登记。
4. **`EmojiPicker` 的两个 `'✈️'` 重复格（索引 13 / 46）未动**：卡面只点 4 个坏格子，重复项不影响可用性，按外科手术式改动保留。
5. **`Repository.kt` 的两处兜底不在本提交里**：见 §七。

## 七、并发说明（★ HEAD 一度不自洽）

本轮并发会话多（T18-1 / T18-5 已交付；T18-2 + T18-10 在途至本卡交付中途；T18-8 在途）。两件事必须记账：

### 7.1 我的两处 hunk 被并发提交带走，且**带走得不完整 → origin/main 一度编不过**

- 我在 `db/Repository.kt` 的两处兜底改动（`:1849` / `:1878`）**被并发会话的 `372393e`（T18-10）随该文件一并提交** —— 属手册 §2.2「谁先提交谁带走对方的 hunk」的形态，本身正常。
- **但它没有带走本卡新增的 `db/entity/DefaultIcons.kt`**。于是 `372393e` 的 `Repository.kt` 引用了 `com.aozora.app.db.entity.DefaultIcons`，而该类型在 HEAD 里不存在 —— **Kotlin 主源码集必编不过，CI 必红**。
  - 判据（file 级，未跑编译）：`git show HEAD:…/db/Repository.kt | grep -c DefaultIcons` → `2`；`git cat-file -e HEAD:…/db/entity/DefaultIcons.kt` → 不存在。
- 本卡的 `4c7cc21` 补齐该文件后 HEAD 恢复自洽（核对：HEAD 的 `Repository.kt` 引用 2 处、HEAD 的 `DefaultIcons.kt` 存在）。
- **教训（新形态）**：**新增文件与它的引用点跨提交时，先提交的一方会把 HEAD 撕成两半，而本地工作区是绿的**。手册 §2.4 的「本地绿 ≠ HEAD 绿 ≠ CI 绿」，这次是「别人替你把引用提了、新文件留在你这儿」。**若非本卡恰好提交得快，这个红会一直挂到 CI 恢复计费为止（见 §八）。**

### 7.2 环境现象（非代码问题）

- **Gradle 构建目录争用**：首次 `:app:testDebugUnitTest` 因 `apk-for-local-test.ap_` 被另一进程占用而 `FileSystemException` 失败，重试通过；第二次跑完的测试 XML 又被对方的构建清空（`test-results/testDebugUnitTest` 为空），最终以「跑完立刻把 XML 复制到私有目录再聚合」的方式取数。
- **未用隔离树**：手册 §2.3 建议整卡进 `git worktree`；我起了 worktree 后按现场决定放弃该路径，改为「主工作区实现 + 精确路径暂存」。代价即 §5.1 的隔离性边界与本节这两条现象。
