## 一、本轮发现并已修复的两个「规划里不可能生效」的缺陷

这两条都不是"某个功能没做完"，而是**按现有配置，规划中的步骤在物理上无法发生**。
它们的共同特征：单看代码都自洽，只有把「部署形态」与「客户端形态」一起看才暴露。

### 1.1 bootstrap checksum 车道被 05j 撑破 → 已同步的客户端会进同步死循环

**已修：** `ab243a2`（服务端），客户端侧随 05j 数据面一并落地。

- 05j 把偏好项并进 `checksum_v2` 的输入（八类 → 九类）。
- `checksum_v2` 是**已构建客户端**的比对基准：`SyncPayloadMapper.parseBootstrapResponse`
  只解析八类、`BootstrapChecksum.computeV2` 只算八类。
- `_compute_checksum` 对**空列表不产出分段**，所以：
  - 账号没有偏好行 → 两边算出同一个值，**问题完全不可见**；
  - 账号一旦有一行偏好（AI 的 `meta_set` 就会写）→ 服务端 hash 变、客户端算不出
    → `SyncOutcome.RETRYABLE` → **bootstrap 死循环，整条同步链路停摆**。
- `schemas.py` 自己的 docstring 早就写着这条规则（「predates T-M7-01 的客户端不得
  被切到会失配的车道」），05j 违反了它；而 05j 的用例只钉住了"偏好为空时兼容"这一半，
  恰好是问题不可见的那一半。

**修法：** 新增 `checksum_v3`（九类），`checksum_v2` 恢复成八类（与 05j 之前逐字节相同），
客户端按 v3 > v2 > legacy 择高。零破坏。

### 1.2 生产 compose 没有接线 AI Agent 的环境变量

**已修：** `0fc2d38`。

- `docker-compose.prod.yml` 与 `docker-compose.staging.yml` **一个 `AI_AGENT_*` 都没写**。
- 后果：容器里恒为 `config.py` 的默认值 → `AI_AGENT_ENABLED` 永远 false →
  `POST /ai/agent` 恒 404。**「部署到 A 机后真机测 AI Agent」在配置层面不可能发生**，
  而 agent 正是 M7 的交付主体。
- 同批打开 `AI_DEVICE_CHANNEL_ENABLED`（ADR-010 决策 7 把开启时点归 P4 收口，
  05f 的客户端执行器已交付，故此刻打开）。

## 四、本轮对 R-PROD-31 / 37 / 38 的裁决

三项都是 P4 出口标准「功能覆盖清单逐项对话可完成」的阻塞面，且**收敛路径是同一次
客户端工作**——分开做会各留下另一半（R-PROD-37 的原文即警告「别只补一处」）。

### 4.1 裁决：**本轮不开 v2 车道**，R-PROD-31 / 37 转为一张有完整设计的尾卡

**理由（这是一次取舍，不是遗漏）：**

- 客户端**声明的契约版本就是灰度旋钮本身**（服务端
  `AIAgentRequest.proposal_contract_version: Literal[1,2] = 1`，缺省即 v1 车道、
  P1 的 15 个工具、行为逐字不变）。不声明 = 今天不构成任何故障。
- 声明 v2 = 服务端开始产出 **v2 信封**（op 在 `action` 上、参数在 `payload` 里）。
  在客户端渲染面就位**之前**声明，会把**连记账都渲染不出来**——比现状（只有设备
  op 静默无效）更糟。**两者必须同时上线，不能只做一半。**
- 而渲染面是一次**完整卡片级**的改动：确认门 `PendingApproval.proposal` 目前是
  `ActionProposal`（v1 形状，`transactions` 是根字段），v2 提案没有 `transactions`
  → 类型面会外溢到 `commitProposalInternal` / `editProposal` / `writeTransactions` /
  `withResolvedAccounts` / `AssistantPage` 的卡片渲染。改到一半的确认门，正好会
  砸在紧接着的真机联调上。

**本轮**验证过、可直接开工的设计（省掉下一张卡的全部调研）：

| 面 | 现状（已核实） | 还差什么 |
|---|---|---|
| 契约层（客户端） | **已就位**：`ActionProposalV2` 类型、`validateProposalV2`、双读入口 `validateProposalAny`、`V2_OPS`（从 `schema-v2.json` 派生，不另抄一份） | 无 |
| 车道声明 | 未做 | Kotlin `AiGatewayClient.buildAgentRequest` 加一个字段（**TS 侧不用改**——HTTP 请求体由 Kotlin 构造，故不触桥命令计数面） |
| 卡面文案 | 未做，但**成本极低**：`tools.py` 里 **37 处** `"message":` ——**每个 v2 工具都产出一句人类可读的中文**（如「把 2026-09 的整体预算设为 ¥3000」） | 一张通用卡：`message` 作主行 + `warnings` + `payload` 键值对照行 + 确认/拒绝 |
| 服务端执行分派 | **已就位**：`ai.execute` 桥命令在（`BatchConfirmationCard` 仍在用 `executeProposal`），`proposal_ops.EXECUTORS` 28 个执行体 + `transaction_add` | 按 `contractVersion` 分流到 `executeProposal` |
| 设备执行分派 | 未做。`DEVICE_EXECUTED_OPS` 现为 **3 个**（`persona_switch` / `consent_record` / `sync_trigger`）——05j 把 `meta_set` 移回服务端后清单已收窄 | **只是一张映射表，不需要新增桥命令**（已核实三条命令都在 `BridgeProtocol.kt` / `native-bridge.ts` 里）：`persona_switch` → `meta.set(active_persona_id)`；`consent_record` → `consent.record`；`sync_trigger` → `sync.trigger`。故**不触桥命令计数面** |
| `account_deletion_request` | 服务端执行体在，且是唯一 `HIGH_RISK_OPS` | 卡面必须能把「即将发生什么、为什么必须确认」讲清（**卡片是它唯一的用户可见面**） |

### 4.2 R-PROD-38（`reminder_set` 没有工具体）——**本轮同样不补**

它与上面**同一条链**：`reminder_set` 是 v2 注册表成员，补上工具体之后它就是第 4 个
设备执行 op ——而设备执行 op 在客户端没有分派路径，**今天的表现正是 R-PROD-37 的
「确认后显示已记录 0 笔交易」**。05d 当初不越界代做是对的判断，但现在另有一条理由：
**补它的正确时点是和 v2 渲染/分派一起**，否则只是给静默无效的清单再加一行。

架构 §3.2 的「提醒」行因此本轮**显式记为「P4 不做」**（范式见 05i 对理财知识的处理），
并把它并入上面那张尾卡。

### 4.3 下一张卡的边界（已定，可直接领取）

**一张卡、四个面、一次上线**：
① 桥声明 `proposal_contract_version: 2`；
② 通用 v2 确认卡（按 `validateProposalAny` 分流，`message` 主行 + payload 对照）；
③ 执行分派（服务端 op → `ai.execute`；设备 op → 三条**已存在**的桥命令，纯映射表）；
④ `reminder_set` 补三处表态 + 守护用例。

**验收**：把 §三 的三项（R-PROD-31 / 37 / 38）一起关掉；真机上「让 AI 改整体预算」
与「让 AI 设提醒」都能出正确的卡并真的生效。

> **设备自管量永不进工具**：`sync_cursor` / `master_book_id` / `personas_seeded` /
> `budget_carryover_mark` / 迁移标记 / `active_persona_id` / `avatar_uri` /
> `display_name` / `budget_carryover` 一个都不上行，也不可由 AI 改。

### 7.1 「读后不落子」在**记账**面上没有复现（R-PROD-17 残余的读数修正）

05b/05c/05d/05g 四轮抽样都记下同一种形态：模型先调读工具，拿到数据后转为文字回答
而不把写工具调下去，并把残余收窄为「读后不落子」。本轮用**真实 HTTP 链路**（注册 →
建账本 + **分类** → `/ai/agent` → 查 `/transactions` 计数）对同一句 `记一笔 12.5 元的午饭`
连跑 **12 次**：

| 口径 | 结果 |
|---|---|
| 首调即写（`transaction_add`） | **12/12 = 100%** |
| 有写动作（proposals/executions/writes 任一非空） | **12/12 = 100%** |
| 实际落库（流水数真的 +1） | **12/12 = 100%** |
| 工具序列 | 稳定为 `transaction_add → device_haptic → device_widget_refresh` |

**第一次跑同一份脚本时落库是 0/12**——根因不是模型：探针用 `POST /books` 建的是
**裸账本（无分类）**，而记账工具按名字解析分类，于是每一步都回
`unknown_category`（工具结果里明写「请先查询分类清单再使用完全一致的名称」），
模型收到错误后转去查流水，**看起来就像「读后不落子」**。补上分类后即 12/12。

**结论与订正：**

- 「读后不落子」**不是**记账任务的稳定形态；真实链路上记账落子率 100%。
- `probe_tool_selection.py` 的假上下文**是带分类的**（`餐饮/交通/购物/工资`），所以
  那几轮记录的形态**不来自**这个环境缺陷；但那个探针**每例最多两次模型调用**，
  而多步 loop 的真实上限远高于此——**「走半程就停」可能有一部分是探针步数上限的产物**。
  建议后续按本节的真实链路口径复测那 58 例，再决定这条残余的最终描述。
- **一条给产品的新读数**：分类缺失时 AI 不会瞎记，但**用户看到的是「没记上」**——
  错误引导语（「请先查询分类清单」）模型没有照做。是否让这类错误更强制（或在
  系统提示里补执行纪律），与 §四 的尾卡一并裁决。

### 7.2 客户端 agent 闸门与服务端**不对称**（本轮新发现，已开）

`AI_AGENT_CLIENT_ENABLED`（`use-assistant.ts:264`）是**编译期常量、默认 `false`**，
且 `AssistantPage` 没有传 `agentStream` 覆盖它。也就是说：**M7 交付的 agent 路径在
客户端默认不可达**——用户要的「AI 记账 / 查询 / 多步」全部回落 `ai.interpret` 单发链路。

这与收口记录 §1.2 是**同一类不对称**：服务端 compose 已在 `0fc2d38` 接线为默认开，
客户端这一侧却还关着。两者都属「单看代码自洽，把部署形态与客户端形态一起看才暴露」。

**实测对照（同一台模拟器，同一个 APK 其余部分不变）：**

| 客户端闸门 | 表现 |
|---|---|
| `false`（原默认） | 「⚠️ 云端 AI 暂时不可用，操作与查询需要云端可用，本次未改动账本」 |
| `true`（本轮联测开启） | 步骤卡可见（`步骤 · 2 步` / 「正在理解你的需求…」/「已统计这个月的收支…」）+ 正确回答 |

**处置：** 本轮临时置 `true` 以便设备联测（`09ceaa1`），**默认值是否正式翻向待账户所有者裁决**。
翻向的代价是「旧 APK 与新 APK 行为分叉」——但服务端工具注入本来就按客户端声明的契约
版本分流（v1/v2），两条灰度旋钮是独立的，**翻客户端闸门不会改变 v1 车道的注入面**。

### 7.3 404 的误导文案在设备上**真实复现**（R-PROD-20 / T-M7-02 收口段）

模拟器新注册 guest 的本地账本尚未同步到服务端时，每轮 `/ai/agent` 拿到服务端
`404 not_found "Book not found"`（`conversation.py:_verify_book`），而客户端把**任意**
404 折成 `AiError.NotFound` → 桥硬编码 `not_found` + `"Conversation not found"`，
于是界面显示：

> ⚠️ 这条会话已失效（可能已在其它设备删除），已切回本地会话，重发即可继续

**「重发即可继续」是错的**——真实原因是账本不在服务端，**重发永远失败**（本轮实测：
连发 4 次全部同一条提示）。这一时期的所有轮次都停在这个状态，AI 能力一条都测不到。

**根因已定位到具体位置（服务端其实已经分了码，是客户端丢掉了）：**

- 服务端：会话端点回 `404 conversation_not_found`，账本/账户等业务实体回 `404 not_found`
  （`conversation.py:236` vs `:325`）——**两者本来就是不同的 code**；
- 客户端：`AiGatewayClient` 只看 HTTP 状态码（`AiGatewayClient.kt:346` / `:423`），
  丢掉 body 里的 `ErrorResponse.code`；桥再按「404 = 会话失效」硬编码文案
  （`AozoraBridge.kt:1363`）。
- 幂等 404 的白名单实际是**两个** code：`conversation_not_found` 与
  `device_request_not_found`（`device.result` 的「404 等价成功」契约，`AozoraBridge.kt:2466`）。

**处置：本轮不改代码**（改动要跨 `AiGatewayClient` + 桥两处，且要覆盖三条 404 路径的
反向守护；本轮改动面刻意保持在最小）。**升格为 §四 尾卡的一部分**——理由同源：它属
「客户端如何归因服务端错误」这一面，与 v2 渲染/分派同一次成型更省。

### 7.4 「多步强制确认」未出确认卡（R-PROD-27 的现场复现）

用例「先看看这个月餐饮花了多少，再记一笔 50 元的交通」的结果：

> 这个月餐饮花了 **12.50 元**（就那一笔午饭）。**交通 50 元已经记好了**，日期是今天。

外加一张「已记录 1 笔交易」卡。**两件事都做对了，但没有出现确认卡。**

这正是 R-PROD-27 描述的形态：模型在**同一个 Step 内并行**发出「读 + 写」，
写提案产出时 `step` 仍是 1 → 与快路径同待遇 → 自动执行、不出卡。
**本轮的实证把这条从「评估项」变成「已复现」**——误差方向仍是「少一道确认门」而非
「写错数据」（写本身过服务端校验）。

**同一场景的第二次走查里出现了一个反向观察**（对评估这条有影响）：当账本里**已经**
有一笔同日同额的交通时，模型**主动停下征询**——「不过今天已经有一笔 50 元的交通了，
你确定要再记一笔 50 元的吗？**确认下我就记**」，那一轮**没有落库**。
即：**在模型自己识别出风险时，它会在文本层充当确认门**。这说明缺的不是"征询能力"
而是"结构性保证"——确认卡的价值在于**不依赖模型每次都想起来**。评估时值得把这点
一并纳入：收紧并行策略（第二判据）仍然必要，但紧急度低于原先的判断。

### 7.5 v1 车道的**能力边界**被模型正确表达（R-PROD-31 的用户可见面）

用例「把午饭那笔改成 15 元」（v1 车道无 `transaction_update`）：

> 抱歉，我这边**只能新增和查询账目，没法直接修改已有记录**。……（删除功能我也没有，
> 得你在 App 里操作），再让我记一笔 15 元的。要我帮你新记一笔吗？

**如实说明 + 给替代路径**，没有假装成功。这说明 R-PROD-31 的现状（客户端不声明 v2 →
只有 P1 的 15 个工具）在用户面前是**得体的失败**，而不是「静默无效」——与 R-PROD-37
（设备 op 确认后显示「已记录 0 笔交易」）的形态**不同**，后者的严重性更高。

### 7.6 测试环境配方（下次走查直接照做）

本轮踩到的环境问题与解法，全部是**环境**而非产品缺陷：

1. **模拟器网络缺 `VALIDATED` → WorkManager 不跑同步 → 一条都不推**，而首页仍显示
   「✓ 已同步」。`dumpsys connectivity` 里 Capabilities 无 `VALIDATED`；
   `pending_mutations` 全是 `status=pending / retryCount=0 / lastError 空`（= **同步从未尝试过**，
   这是判据）。修法：宿主机起 204 探针 → `settings put global captive_portal_http_url`
   指向它 → 重启 wifi → `ConnectivityService: validation passed` → 积压一次性清零。
2. **客户端 agent 闸门**（§7.2）不翻向时，AI 路径**恒不可达**，且提示是「云端 AI 暂时不可用」。
3. `/ai/agent` 的 book 校验要求**账本在服务端**——同步没跑通时 AI 全链路不可用（§7.3）。
4. 刷新本地服务端后**必须重启 uvicorn**（无 `--reload`），并把 stdout 落盘才看得到
   `POST /ai/agent 200` 与 provider 调用日志。
5. 真机（MIUI）`run-as ... sqlite3` 被拒，客户端落库断言只能在模拟器做。
