## 二、判据先行（卡面 ⑤⑥ 明确要求，两处各出结论）

### 2.1 图片车道（`IMAGE_RECEIPT_PARSE`）：**不改**

**现状核实**：图片车道**确实**注入分类白名单——`service.py:1386-1388` 走 `prompts.get_template(IMAGE_PARSE_TASK)` → `render_image_messages` → `prompts.py:485` 的 `_render_categories_section`，注入 `【用户现有分类名列表】`，规则是「无精确项时选语义最接近的，**完全对不上输出 `""`**」。

**结论：不改，三条理由。**

1. **它与 `LEDGER_PARSE` 是同一族**（同在 `prompts.py` 的 `REGISTRY`，同一套 `_render_categories_section` 机制，同为**客户端执行**的 v1 模板车道）——而决策 #11 定死「本轮**只改 agent 车道**……v1 模板（LEDGER_PARSE）保持不动，并在交付记录里写明两车道行为差异是刻意的」。
2. **它的 `""` 兜底有用例钉住**（`tests/test_image_parse.py:698` 断言 `完全对不上输出 ""`），改它就是改一条既有契约。
3. 「同一件事只有一份规则」在这里的正确解读是**一条车道一份规则**，不是「把两车道的规则合并」：合并必然让其中一条改变行为，而两条车道的行为差异是**有意的**（agent 车道是设备在线时的唯一写路径，且它能追问、能提议；v1 模板只产出一次性提案，留空由客户端兜底更安全）。

**已落一条用例把这个决定钉在代码里**（`test_rules_are_absent_from_the_other_lane`）：它不是「忘了改 v1」，而是防止后人「顺手统一一下」。

### 2.2 记账句是否让 `category_list` 可用（域路由 `routing.py:86-96`）：**不改**

**实测**（`route_domains` 直接调用）：

| 输入 | 结果 | `category_list` 可用？ |
| --- | --- | --- |
| 「记一笔午饭 12 块」 | `matched=True`，**收窄到 transaction 单域** | ✗ |
| 「今天坐地铁花了 6 块」 | `matched=True`，transaction + analysis | ✗ |
| 「打车 25」 | `matched=False` → **兜底全量**（16 域） | ✓ |
| 「同事结婚随了 600 份子钱」 | `matched=False` → 兜底全量 | ✓ |

即**同一类「记一笔」的输入，一半拿得到 `category_list`、一半拿不到**。

**结论：不改，理由是它不影响本需求的达成路径。** 模型选分类靠的是**系统提示尾部的「现有分类」清单**，而那一节的渲染与域路由**完全无关**（`_render_object_section` 读 `ctx.categories_by_kind`，每一轮都在）——`category_list` 只是「查完整清单 / 看父级」的补充手段，注入面本身已经带层级、已经不截断。

**抽样证实了这个判断**：改后「记一笔午饭 12 块」（收窄到 transaction 单域、**没有** `category_list`）3/3 落「餐饮」，与「打车 25」（兜底全量、有 `category_list`）同分。**没有观测到因缺 `category_list` 而落空的情形。**

反过来说，若按 ⑤ 字面给「记一笔」等词加 `DOMAIN_CATEGORY`，代价是**把分类域的 4 个工具常驻进每一轮记账**（选择面变宽 = R-PROD-17 的准确率风险），收益却为零。**不做。**

### 2.3 判据先行的产出：一套可复跑的验收尺子

入库文档实证⑧指出「R-PROD-17 那套抽样全部是**工具选择准确率**，没有一次是『分类选对了没有』」。本卡补上：`server/scripts/probe_category_selection.py`，19 用例分四组（二级 / 一级 / 兜底 / 提议），判据与数字见 §4.3。

## 三、设计决策（实施期定死的，卡面之外）

### 3.1 ★ 注入格式会被**整体抄走**——这是实施中发现并当场修掉的真缺陷

层级渲染的形态是卡面 ① 指定的（`人情社交（职场 / 亲戚 / 借用 / 借出 / 回礼）`）。改后首轮抽样 4 次里出现 **1 次**：

```
transaction_add(categoryName="人情社交（亲戚 / 借出 / 借用 / 回礼 / 职场）")
```

**后果比「选错分类」更重**：`resolve_category` 是逐字匹配 → `ERR_UNKNOWN_CATEGORY` → **这一笔记不进去**（不是记错分类，是写路径失败）。

**修法**（两处，各写一句）：系统提示加「**括号只是标注归属，填的时候只填名字本身，别连括号一起抄。**」；`categoryName` 描述加「（填「人情社交」，不要填「人情社交（亲戚 / 借用）」）」。**改后重跑：零次非法值**（§4.3 的「非法值」检测列全空）。

**没有**采用「放宽服务端解析」这条路——卡面明令「不改 `resolve_category` 的严格匹配」；也没有改注入格式（那是卡面 ① 指定的）。

### 3.2 截断以**一级条目为原子单位**（不是按名字切）

改前是 `sorted(names)[:30]`——按 Unicode 码点切，**成片丢失**。新实现遍历**一级条目**，每个条目的成本 = `1 + len(它的二级)`，超预算就 `break`：

- **不会渲染出半棵树**（父在、子在名单外）：模型对半棵树的推断与整棵树不同——与 `skills.render_skill_section`「半句规则比没有规则更误导」同一取向；
- **第一个条目无条件进**：预算再紧也要让模型看见至少一个合法分类名，否则它被要求「必须选一个」却无路可走；
- 单个父的子树也限长（同一个常量）。

### 3.3 ★ 「必选一个」必须**同时压住「追问」**

改前「必选一个」在 agent 车道**根本不存在**（那条规则只写在 v1 模板的 LEDGER_PARSE 里，而它的兜底恰是「**完全对不上输出 `""`**」——方向相反）。

只写「必须选一个」还不够：实测模型会用**追问**代替选（改前基线里「花了 66，杂七杂八的」→ 不记账，回「这笔我帮你记上，不过『杂七杂八』该归到哪个分类呢」）。**根因是系统提示里两条规则打架**：「信息不够时用一句话问清楚」 vs 「必须选一个分类」。

修法：在分类规则里显式圈定例外——「**也不要为分类追问用户**（用户下一轮自己会改）」。这正是用户原话的语义（「让用户自己修改或者在下一轮对话里下修改需求, 这没关系」）。**兜底组因此从 33% 升到 89%**（§4.3）。

### 3.4 ★ 三条规则写**系统提示**而不是只写 Skill——因为路由不可靠

`skills.py` 的既定口径是「全量注入**不算命中**，不带任何 Skill」（模块头 + `test_full_injection_is_not_a_hit`）。而「打车 25」「同事结婚随了 600 份子钱」这类记账句**命不中任何路由信号** → 兜底全量 → **一条 Skill 都不带**。

把「怎么挑分类」放进 Skill，等于**在最需要它的轮次缺席**。因此三条规则落在系统提示（唯一每一轮都在的可见面），分类域 Skill 管**另一件事**（§3.5）。

**代价是打破 T-M7-05h 立的「未命中时系统提示逐字不变」不变量**——决策 #12 已预告这是必然的，并要求**取 token 实测**（数字见 §4.2）。金标 `_BASELINE_NO_SKILL_PROMPT` 因此有意更新，注释里写明这是「一次有意识的决定」及其理由（金标的作用本来就是让提示主体的改动显形）。**Skill 机制本身的不变量未破**：`render_skill_section(())` 仍返回 `""`。

### 3.5 分类域 Skill 管的是「分类本身怎么维护」，不是「记账时怎么选」

绑 `DOMAIN_CATEGORY`，只在用户**谈分类本身**（建 / 改 / 挂到哪一级）时进：两级结构、建二级用 `parentName`、改已有分类用 `category_update`、记账不合适时**不要顺手 `category_create`**。它是**跨工具**的（`category_create` / `category_update` / `category_list` 三个工具之间），与系统提示的三条**不重复**——各自回答不同场景的问题。

### 3.6 注入面的父子关系建在**名字**上，且「父不可见时子升为一级」

`ToolContext.category_children_by_kind` 是 `kind → 父名 → 子名元组`。三条边界：

- **父必须也在可见集里**才认这条边（父已归档 / 在别的账本时，子按一级独立列出）——**名字不丢**，与 `categories_by_kind` 那条「本账本覆盖全局」同一取向：宁可让名字多出现一次，也不让合法分类名消失（模型看不到的名字就是不可用的能力）。
- **成环时跳过**（`parent_name == name`）。
- 只服务**渲染**：写路径的名字解析仍由 `categories_by_kind` 独占权威，一个字没改。

### 4.2 token 实测（决策 #12「不得以『反正是必要的』为由免测」）

**同一句用户输入（「打车 25」）、同一套工具载荷**，只差本卡的改动，读真实 provider 报的 `prompt_tokens`（`deepseek-flash`）：

| 臂 | 系统提示字符 | `prompt_tokens` |
|---|---|---|
| **改前** | 868 | **14 013** |
| **改后** | 1216 | **14 514** |
| 差额 | +348 | **+501（+3.6%）** |

**口径说明**：这 501 tokens 里含两部分——分类行从 123 → 169 字符（**+46**，那是「餐饮 / 购物 / 转账」等 8 个名字从不可见变可见 + 两处层级括号），以及新规则文案（约 +300 字符，含后来补的「括号只是标注归属」那句，见 §3.1）。基数的 14 013 里绝大部分是 **58 个工具的定义**（工具清单才是这条车道的成本大头）。

**三个成本项分开看**：① 系统提示是**每一轮都付**的（agent 车道）；② 三条规则是**常驻**的（这就是选它而不选 Skill 的代价，§3.4 已论证这个代价必须付）；③ v1 快车道与 `LEDGER_PARSE` / 图片车道**一个字都没动**，token 零变化。

**取值 40 的依据**：不是拍脑袋——`_MAX_PROMPT_OBJECTS` 的语义是「一行里最多渲染多少个名字」。T20-5 的种子是 **支出 28 一级 + 10 二级 = 38 个名字 / 收入 15**。30 会丢 8 个，40 全量可见并留 2 个名字的余量给用户自建。

**抽样口径的两条诚实说明**：① 用例期望对**多解**的输入写成可接受集合（`职场|回礼|亲戚`），集合的取定理由逐条写在脚本里——不是为了凑分数，而是「用户诉求要求的是『别停在宽泛的一级』，而具体落哪个二级本就多解」；② 单次 3 轮仍有波动（±1 条），**上表的数字是 3 轮合计**，绝对值不应当成精确指标，**可靠的是改前 / 改后的方向与量级**。
