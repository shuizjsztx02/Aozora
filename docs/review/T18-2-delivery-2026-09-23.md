### 2.2 证据（真机 / 模拟器 + 服务端行对照）

复现环境：`Pixel_7_API_36` 模拟器上的 debug 包（`AI_AGENT_CLIENT_ENABLED=true`）+ A 机部署实例（`aozora-api-test`，`AI_AGENT_ENABLED=true`，库在 B 机 `aozora_test`）。用 CDP 驱动**真实输入**（壳内 WebView 9222 通道），非页面内直接调桥。

1. **挂起即零写（确认门有效）**——诉求「把备注是『…购物』的那笔金额改成 6 元」第一轮被强制确认挂起：助手文案「我已经把改金额（5 元 → 6 元）的提案提交了，**等你确认后才会生效**」，服务端该行 `amount_cents=500 / version=1` **未变**。
2. **执行后服务端确实写了**——同一诉求第二轮（模型在 Step 1 直接执行，绕过强制确认＝R-PROD-27 的已知形态）收尾时：容器日志 `POST /api/v1/ai/agent 200` → `AI proposal executed`；服务端行 `amount_cents 500 → 600`、**`version 1 → 2`**、`updated_at` 前进。助手文案：「改好了 ✅ …」＋回执行「已记录 1 笔交易」（来自 `done.executions`）。
3. **客户端不刷新（H2 的直接证据）**——执行之后**不重启**：本机 Room 仍是 `amountCents=500 / version=1`；切到明细页仍显示 `5.00`；`sync.getStatus` 的 `lastSyncedAt` 仍为 0（即从没有一轮同步被前端观察到）。
4. **机制层根因**——①写后动作 `bridge.triggerSync()` = 桥命令 `sync.trigger` → `SyncScheduler.enqueue`（WorkManager 一次性任务 + `NetworkType.CONNECTED` 约束），**只入队、不等待**；②三个数据页全仓**零** `visibilitychange`/focus/同步事件订阅（挂载期单次读）。

### 2.3 取证中额外发现并修复的缺陷 A：同步事件通道在真机上是**死的**

`MainActivity.dispatchSyncEvent` 注入的 JS 是**调用函数**的形式：

```js
if (typeof window.__aozoraSyncEvent__ === 'function') window.__aozoraSyncEvent__({state, …})
```

而 `platform/store/sync-store.ts` 的 `initListener` 挂的是 `Object.defineProperty` 的 **getter/setter**（指望原生**赋值**一个对象）——那个 `typeof` 判据在真机上**恒为假**，事件从未到达 store。

- **设备侧直接证据：** 壳内求值 `typeof window.__aozoraSyncEvent__` → `"undefined"`（同一时刻 `typeof window.__aozoraNavigate__` → `"function"`，对照成立）。
- **实际影响：** `SyncBadge` 恒显「已同步」、`AuthLostBanner` 永不出现（两者都订阅同一个 store），且**本卡 ③ 依赖「同步完成」这个信号**——不修则重取订阅无从触发。
- 该缺陷自 `c101afb`（T-M4-02）起存在，此前无任何用例守护（跨层契约少了一处守护＝3.1 节所说的高危形态）。

### 2.4 取证中额外发现并修复的缺陷 B（**本卡第二层根因，P0**）：服务端下行的 transaction 被**静默丢弃**

修好 ②③ 之后在真机上复验，出现了不该有的结果：**真同步跑了（`lastSyncedAt` 前进）、服务端行也确实是 `600 / version 2`，可本地 Room 仍是 `500 / version 1`。** 追下去得到：

1. **表象**：真机日志 `SyncEngine: bootstrap entity count MISMATCH: transactions: expected=4 actual=0` —— 快照里有 4 条交易，一条都没落进 Room。`pending_mutations` 为空（不是「活跃 mutation 跳过合并」那条路）。
2. **根因（跨层契约断裂）**：服务端 `_serialize_entity`（`server/src/modules/sync/service.py`）把 `occurred_at` 出网成 **ISO 8601 字符串**（bootstrap 与 pull 的 change 载荷同一条路径）：
   `"occurred_at": "2026-09-23T09:33:47.687000+00:00"`（实测抓取）。
   而客户端 Room 的时间列是 **epoch 毫秒**，两条 transaction 映射路径却都用裸 `toLongOrNull()`：
   - pull：`sync/SyncModels.kt` 的 `ServerChange.toTransaction()`
   - bootstrap：`db/Repository.kt` 的 `serverChangeMapToTransaction()`
   ISO 字串解析不出 Long → 返回 `null` → 调用方 `?: continue` **静默跳过**，而游标照常推进。
3. **本该用的转换器早就在仓库里**：`SyncPayloadMapper.isoToEpochMillis`（存钱目标、定时规则、persona 都在用），**唯独 transaction 两处漏接**。
4. **为什么此前全绿**：既有 Kotlin 用例的 fixture 用 **epoch 毫秒**喂 payload，与服务端真实出网形态不一致 —— 这条跨层契约**一处守护都没有**（3.1 节的高危形态，又一次）。
5. **影响面**：任何**服务端权威**的交易写都到不了客户端 —— AI 的 v2 服务端执行、跨设备恢复、bootstrap 重建全都受影响。**REQ-67 的用户症状（「AI 说改好了，各处显示都没变」）正是这条 + ②③ 共同造成的**：②③ 让同步「跑起来」，本条决定「跑起来也拿不到」。
6. **落地**：两处 `occurredAt` 改为 `toLongOrNull() ?: isoToEpochMillis(...)`（**epoch 与 ISO 双收**，向后兼容旧服务端/测试 fixture）；新增回归用例 `app/src/test/java/com/aozora/app/sync/ServerTransactionWireFormatTest.kt`，载荷是**从运行中的服务端逐字节抄下来的**，覆盖 pull 与 bootstrap 两条路径。
7. **刻意未动**：`deletedAt` 同为 ISO 出网、同样解析不出，但 `applyBootstrap` 对它有 `check(entity.deletedAt == null)` 断言 —— 一旦正确解析出非空值就会**抛异常**而不是静默跳过。服务端 bootstrap 只返回活跃行，故现状无害；改它需要连同那条断言一起重新论证，**不在本卡范围内**，在此登记。
8. **文件越界说明**：`sync/SyncModels.kt` 与 `db/Repository.kt` 在本轮的冲突矩阵里分别归 T18-4→T18-5 与 T18-4/5/6/7。本卡动它们属**越界**，但卡面 ① 明确要求「据实修对应的那一层」，且不改这两处则本卡的验收（切页即为新值）**不可能达成**。改动是两行、additive、不改变既有调用形态，已在此显式记录以便收口与后续卡 rebase 时核对。

### 2.6 交付期额外发现并修复的缺陷 C（**板级，P0**）：本卡新用例自身让整套 JVM 板挂死

修完 A/B 之后跑 JVM 板，出现与代码逻辑无关的现象：**整套 `:app:testDebugUnitTest` 永久挂起**——第一次跑满 25 分钟、测试 worker 的 CPU 只涨 0.13 s；换工作树、`--max-workers=1`、杀掉并发会话的构建**都不消除**；定向跑单个类也挂。

抓栈定位到唯一卡点：

```
"SDK 33 Main Thread" ... cpu=10750ms elapsed=537s
  - parking to wait for (a kotlinx.coroutines.BlockingCoroutine)
  at kotlinx.coroutines.BlockingCoroutine.joinBlocking(Builders.kt:98)
  at com.aozora.app.AozoraApp.onCreate(AozoraApp.kt:208)     ← runBlocking
  at org.robolectric.android.internal.RoboMonitoringInstrumentation.callApplicationOnCreate
```

链路（逐环节核过源码/依赖，非推测）：

1. 本卡新增的 `ServerTransactionWireFormatTest` 用 `AozoraDatabase.getInstance(RuntimeEnvironment.getApplication())` 取库，并在 `@After` 里 `db.close()`。
2. `AozoraDatabase.getInstance()` 把实例缓存在 `INSTANCE`，**`close()` 后不清空**（`AozoraDatabase.kt:79-88`，`open()`/`createInMemory()` 之外没有清空口）。
3. Robolectric **每个用例都重建 Application** → `AozoraApp.onCreate` 的 `runBlocking { repository.ensureSeedDefaults() … }` 经 `AozoraApp.database`（by lazy）拿到的正是**上一个用例关掉的那个库**。
4. 构建声明 `androidx.room:room-runtime:2.6.1`，**实际解析为 2.7.0**（`./gradlew :app:dependencies` 实测 `2.6.1 -> 2.7.0`，被 WorkManager 提升）。2.7 关闭数据库时会**取消数据库的协程作用域**，而查询任务在该作用域上启动、靠任务自身恢复调用方——作用域已取消 ⇒ 任务永不执行 ⇒ **调用方永久挂起**。
5. 所以「定向跑也挂」是必然的：**同一类里第 2 个用例被自己第 1 个用例的 `tearDown` 污染**。

**对照事实**：`app/src/test/` 下**只有两个**文件用 `AozoraDatabase.getInstance`——本卡的 `ServerTransactionWireFormatTest.kt:67` 与 T18-10 的 `OneTimeCursorResetTest.kt:37`；仓库内**其余 20+ 个** `Repository*Test` 一律 `createInMemory(...)`（新实例，不碰单例）。

**落地**：本卡用例改用 `createInMemory(RuntimeEnvironment.getApplication())`（与既有惯例一致），并在注释里写清「为什么不能用 `getInstance()`」。**修复后同一套用例 1 分 28 秒跑完**（挂死时 >25 分钟未完成）——这就是本条的对照验证。

**刻意未动**：
- 生产侧不在本卡范围内：`getInstance()` 在生产是进程内单例、从不 `close()`，无实际影响；但「`INSTANCE` 不在 `close()` 时清空」确是脆弱点，登记在 §六。
- `OneTimeCursorResetTest.kt`（T18-10 的卡）有**同款缺陷**且同样会让整套板挂死；按「不夹带」纪律，本卡**没有**改它，只在此登记。
