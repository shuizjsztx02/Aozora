## 二、设计决策

### 2.1 `before` 抓在 `service.py`，不穿透 `OpReceipt`

改 / 删类 op 的「旧值」由 `execute_proposal` 在**调用执行器之前**抓（`_snapshot_before`）。
另一条路是让执行器自己抓、随 `OpReceipt` 回带——没走，两条理由：① 执行权威本来就在这一层，
快照必须与「执行前」是同一个瞬间；② `proposal_ops.py` 不在本卡的领地（注册表面是 T20-3 的地盘），
少一层转手就少一处漂移。

`_snapshot_before` **从不报错**：payload 形状不对 / 不是本人的 / 不在本账本，一律 `None`。这三件事
执行器马上要用同一份 payload 再判一次，抢先报只会让同一个错误有两个出口、两套文案。快照是锦上添花
——缺了它卡上少两行，执行该怎么报错还怎么报错。

### 2.2 ★ `before` 带上了 `accountId`（决策点名的六项之外）

决策 #4 定死的是「分类 / 收支 / 金额 / 日期 / 备注 / 账本」六项。交付时**多带了 `accountId`**：
卡的展示口径含账户 chip（`ConfirmationCard` 的 `SnapshotCard` 渲染 `-account`），不带的话历史卡会把
「有账户」显示成「不使用账户」——**少一个键就是一次错误的显示**。键名与 payload 逐字对齐，卡上按字段
比对才成立。

### 2.3 v1 车道**不填**这四个键

响应模型统一带这四个键，v1 走空默认（`action: ""` / `message: ""` / `payload: {}` / `before: null`）。
v1 的信封只有 action + `transactions`（`_v1_envelope`），没有 `message` / `payload` 可回带；补空壳进去
只会让既有契约多三个恒空的键。**值层面 v1 逐字不变**（既有 v1 客户端按字段取值，多出来的空键不影响它；
`handleAiExecute` 原样透传 JSON 串）。用例 `test_v1_receipt_carries_no_card_fields` 钉住这一点。

### 2.4 幂等命中**不带** `before`

`existing` 命中时那次执行已经发生，此刻再查「执行前」只会拿到被改过之后的值——**宁可缺一个键，
也不给一张假的「旧卡」**。`action` / `message` / `payload` 仍从入参 proposal 回带（同一个 proposal 重放，
这三样是同一个值）。

为此把 `lane = validate_proposal_any(proposal)["contractVersion"]` 从「Re-validate 之后」**上移到幂等检查之前**
（纯函数、无副作用）：幂等命中若不带回卡片信息，重放那一次客户端手里又只剩一串 id ——同一只坑，只是发生在
第二次调用上。

### 2.5 分型判据：`LEDGER_OPS` = 记账三 op（决策 #3）

`action ∈ {transaction_add, transaction_update, transaction_delete}` → 业务卡 + 「已记录 N 笔交易」+
撤销窗；其余一律回落通用卡 + 用服务端 `message` 作回执。**`action` 缺席（旧服务端的回执）按记账类处理**：
那时 `/ai/execute` 只会被记账调用，沿用旧文案比新造一个说法更贴近事实。

### 2.6 一轮多次执行 → 多条消息（模型正文只挂第一条）

`done.executions` 是清单，历史渲染循环是 `messages.map(msg => …)`（一条消息一张卡），所以 N 条执行
落成 N 条消息，`text` 只附加在第一条上（它属于整轮，不属于某一次执行）。消息 id 相应改为
`msg_${stamp}_${i}_assistant`（同一毫秒内多条不再撞 key）。

### 2.7 撤销窗：非记账 op **不动**它

改前是无条件 `activeTxIdsRef.current = ids` —— 非记账 op 会把**分类 / 账本的 id** 塞进撤销窗，
下一次撤销就拿它去 `softDeleteTransaction`（R-PROD-50 记的「撤销窗污染」）。现在只在记账类赋值，
非记账时**不动**（不清空也不覆盖）：清空会让用户撤不掉刚记的那笔，指向上一轮记账在 5 秒窗内是正确语义。

## 四、交接给 T20-2 / T20-4

- **数据面已就位**：T20-2 需要的三样都在回执与凭据里——`action`（分型）、`payload`（「新」）、
  `executions[0].before`（「旧」）。`ExecutionEvidence` 已带 `action?` / `before?`（`commitV2Proposal`
  路径与 `done.executions` 路径**都会填**，所以用户确认过的修改卡也有新旧对照）。
- **判据未改**：`AssistantPage` 的历史渲染循环一行未动，`isV2Proposal(p)` + `proposalId !== activeProposal?.proposalId`
  照旧——T20-2 只需在 `V2ConfirmationCard` 内按 `proposal.action` 分支。
- **需要 T20-2 自己取的**：`SnapshotCard` 要的 `categories` / `accounts` / `books` 名单（`V2ConfirmationCard`
  当前不接收），以及从 `ConfirmationCard.tsx` 导出 `SnapshotCard`（卡面 ④ 已授权「只导出，不改其行为」）。
- **通用卡的 payload 块在业务卡上要撤掉**：现在记账卡会同时显示「主行 + payload 键值对照」，
  T20-2 换成业务卡后那一段应只在通用卡分支出现（决策 #3：其余 op 一字不改）。
