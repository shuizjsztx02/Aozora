## 二、复核卡面：四处与实况不符（都是「照卡面做会做错或做空」的地方）

**1. ★ 卡面 ③ 只写「`proposal_ops` 落 icon」——不够，`categories` REST 模块根本不读这一列。**
`CategoryCreate` / `CategoryUpdate` 没有 `icon` 字段、`CategoryRepository.create/update` 也不写它。执行体拿了 `CategoryCreate` / `CategoryUpdate` 去落库，只改 `proposal_ops` 的后果是：**pydantic 直接丢掉这个键**（`extra` 忽略）→ 图标静默不落库——**正是卡面决策 #2 自己点名的 REQ-69 `account_type` 原型**，只不过它这次藏在 REST 模块里，不在卡面的改动清单上。
补这一层是**同批两端化**的要求（决策 #2：「必须同批两端化，不得只改一侧」），且 ADR-014 决策 5 把 REST 面明确划给了 T19-2（「不在服务端 `categories` REST 模块加 icon（**那是 T19-2 的 AI 面**）」）。故本卡补齐 schemas / repository / service 三处，并顺带让 `CategoryResponse` 出 icon——**写进去了就要读得回来**（book / account 的 Response 都带 icon；只收紧写口会让 REST 的读写各说一半）。

**2. 卡面 ④「`authorization.py` 若对 payload 字段有白名单则同步放开」——没有白名单，本卡空改动。**
`_PAYLOAD_ID_FIELDS` 管的是**id 目标**（`category_create` 已有 `bookId` / `parentId` 两条），字段级白名单并不存在（v2 的 payload 形状由工具注册表拥有，契约不复制第二份）。`icon` 不是 id，**授权面无需改动**。把这条「刻意不改」写下来，免得下一位以为漏了。

**3. 卡面 ② 的「v2 payload」就是处理器里的那份草案 dict，契约文件一个字没动。**
`contracts/action-proposal/schema-v2.json` 的 `payload` 是**不校验字段的开放对象**（只校信封），fixtures 里也没有 category 用例——加键无需动契约，四板里的 v2 parity 用例不受影响。

**4. 连带面：探针的假 `category_list` 结果漂了。**
`probe_tool_selection.py` 的 `_FAKE_READS` 自述「形状与真工具一致（键名取自工具处理器）」。读口新增 icon 后，这份假结果就成了**过期的真值**——而它恰好是新能力（模型照着现有风格挑图标）唯一能看到的东西。已补齐（并给几条分类填了真实风格的 emoji）。

## 三、设计决策（四条）

### 3.1 「键缺省 = 不改」三处同口径，AI 路径**不能清空**图标

| 处 | 落法 |
| --- | --- |
| 工具处理器 | `if params.get("icon"): payload["icon"] = ...`（没提就不发这个键） |
| `CategoryUpdate.icon` | `str \| None = None`（与 `name` / `parent_id` 同一局部合并语义） |
| `CategoryRepository.update` | `if icon is not None: category.icon = icon` |

**清空图标只有客户端 sync 的显式 null 一条路**（T19-1 决策 3：`categoryToJson` 显式上行 null 是 IconPicker 的真实操作）。AI 侧刻意不开放清空——模型一句「把图标去掉」若落成 `null`，在服务端 NULL 双语义下（ADR-014 后果 2）本来也传不出去，开放它只会制造一张「说成功但什么都没变」的卡（T18-3 记过的回执说谎形态）。这条进 T19-9 挂账。

### 3.2 建分类时 payload **条件加键**，不是 `icon: None`

既有用例 `test_create_resolves_the_parent_and_defaults_to_the_current_book` 用 `payload ==` **逐字相等**钉着「没提图标时没有这个键」。照 `account_create` 的现成写法（先构 payload、再条件加键）落地，既有断言一字未改即继续成立。`category_create` 的处理器因此从「内联 payload」改成「先构 dict 再加键」——**与同文件的 account/book 两个 create 处理器同形**。

### 3.3 ≤64 有三层，主防线仍在客户端

| 层 | 作用 |
| --- | --- |
| 客户端 `categoryToJson`（T19-1） | **主防线**：照片那种超长值省略键，防整批 push 422 毒丸 |
| 工具 schema `maxLength: 64` | 模型面的形状（超长在**进提案前**降级成 `invalid_arguments`） |
| `CategoryUpdate.icon` 的 pydantic `max_length` | 执行面的兜底：形状不对 → 400 `ai_invalid_payload`，**不是 500**、且一个字节都不写 |

三层的值必须同时是 64——任一放宽，照片 data URI 就会灌进 change 表与每一份 bootstrap 快照（ADR-014 方案 A 被否决的理由）。

### 3.4 读工具出 `icon`，`None` 有语义

`category_list` 的每条分类多一个 `icon` 键，值可能就是 `None`——那是「客户端按名字映射默认 emoji」，**不是「没有图标」**，故不能渲染成空字符串或省略键。模型照着现有风格挑图标的唯一依据就是这份结果。

### 4.2 活体模型（真实 DeepSeek，真实系统提示，车道 v2 / 56 工具，**每句 3 轮**）

`route_domains` + `AgentLoop._system_message()` + `to_openai_tools`，上下文是内存假用户（分类名与假读结果逐字对齐）。**15/15 首调命中**：

| 用户原话 | 模型实际调用（3 轮逐字一致） |
| --- | --- |
| 把交通分类的图标改成 🚗 | `category_update` `{"categoryName":"交通","kind":"expense","icon":"🚗"}` |
