## 二、设计决策与落地

### 2.1 命令命名：方法段用**下划线**（与卡面逐字一致）

四条命令是 `autobook.get_status` / `set_enabled` / `list_captures` / `resolve_capture`——**方法段用下划线**，与本仓既有命令的 camelCase（`sync.getStatus` / `permissions.getStatus`）**不一致**。取卡面而非惯例：**T21-5 卡面与下游两卡（T21-7 设置页 / T21-8 待确认箱）的引用逐字都是下划线**，改回 camelCase 会让下游卡引用失配。此判断写进了 `BridgeProtocol.kt` 与 `bridge-types.ts` 的常量注释（决策 #12）。

### 2.2 `get_status` 的形状与两条授权判定

返回 `{ enabled, accessibilityGranted, notificationGranted, todayCaptureCount, pendingConfirmCount }`（决策 #10 / #12）。

- **两类授权都是「设置页授权」，不是运行时权限**：无障碍查 `AccessibilityManager.getEnabledAccessibilityServiceList()` 里是否有本应用的服务；通知查 `NotificationManagerCompat.getEnabledListenerPackages()` 里是否有本包名。查不到即未授权，**不猜**。两条判定写在 `AozoraBridge` 私有函数里，并**留了交接注释**：T21-7 会把它们收进 `PermissionManager` 的「设置页授权」形态（含「已授权但服务被停用」的第三态），届时此处改为调用它，避免两处实现（`稳定性守则 §4.3`）。★ 本卡不越界改 `PermissionManager.kt`（T21-7 独占）。
- **待确认数按「未被合并」的口径计**（= `list_captures` 的可见集）：L2 合并只留一条可见卡（保留行），被合并行（`mergedInto != null`）是**留痕**，不进待确认箱，也就不该被计入角标——否则角标会比列表多一条。今日捕获数仍取 `countCapturedSince`（"捕获"这件事本身，与状态无关）。

### 2.3 `list_captures`：留痕行不作独立卡片，来源数派生

逐行返回 `parsedJson` / `sourceChannel` / `sourceApp` / `rawText` / `merchantKey` / `status` / `confidence` / `transactionId` + **`sourceCount` / `multiSource`**（= 指向本行的留痕行数 + 1，决策 #5 的 `multi_source` 派生量，不另设列）。**`mergedInto != null` 的行被跳过**：两条通道抓到同一笔是**合并成一卡**（保留行带 `sourceCount`），不是两张卡。

### 2.4 `resolve_capture`：三种处置 + 幂等 + 拒绝

| 处置 | 行为 |
| --- | --- |
| `confirm` | 读 `parsedJson` → 组装普通交易 → `repository.insertTransaction`（与 `pending_mutations` 同事务）→ 标 `committed` + 回填 `transactionId` |
| `confirm_modified` | 同上，但 `overrides`（`categoryId` / `amountCents` / `type` / `note` / `bizDate`）逐字段覆盖解析结果 |
| `ignore` | 标 `ignored`，**零写**（不留半成品账目）；已 `committed` 的拒绝改忽略（否则账目成孤儿） |
| 已是 `committed` 再确认 | **幂等**：回既有 `transactionId`（`alreadyResolved: true`），不再写第二笔 |

**组装交易的三条硬口径**（`buildConfirmedTransaction`）：

1. **来源不得新造枚举**：`source = "nlu_ai"`——必须是服务端 `TxSource` 并集内的既有值（`Repository.insertTransaction` 与 `server/models/ledger.py` 同集）。**库里没有也不许加 `autobook` 这个值**：那是跨端枚举扩列，会把 push 变成 422 毒丸（T11-4 的既有教训）。取 `nlu_ai`：REQ-83 的解析以服务端模型为主（ADR-016 决策 7），流水详情页据此打「AI 记的」徽标。
2. **不猜字段**：缺方向 / 缺金额 / 分类解析不出 / `kind == not_transaction` → 一律 `invalid_input` 明确拒（宁缺毋滥），**不编**一个出来。
3. **复用聊天记账的兜底口径**：`bookId` 取默认账本、`accountId` 兜底默认账户（与 `use-assistant` 同法）；`occurredAt` 取**采集时间**（`postedAt`，比"现在"更准）。

### 2.5 接线：`autoBookDb` 注入（而非从 `syncContext` 反推）

`auto_captures` 的读写入口在 `AutoCaptureDao`，而 `db/` 簇归 T21-3 独占、`Repository` 未暴露其 `db`——桥只能拿到数据库本身。故给 `AozoraBridge` 加一个**可选构造参数 `autoBookDb: AozoraDatabase?`**（与本仓既有的 ~17 个可选注入客户端同形），`MainActivity` 传 `app.database`，JVM 测试传内存库。`AutoBookRepository`（写路径 / 开关，无状态）在 handler 内按需构造。

## 五、已知限制与挂账（交下游）

1. **并发在途（T21-6）**：测量时工作树含 T21-6 未提交文件（§3.1）。本卡提交只带自己的 10 个文件（精确路径暂存），**未夹带**。T21-6 的 `AutoBookEngine` / `LocalCaptureParser` 会与 `resolve_capture` 的落账路径**语义重叠**（都在"把解析结果变成交易"）——建议 T21-6 复用/抽出本卡的 `buildConfirmedTransaction` 形态，避免两处实现（`稳定性守则 §4.3`）。本卡不替 T21-6 决定。
2. **两条授权判定的归属**：本卡就地实现（见 §2.2），T21-7 应收进 `PermissionManager` 并让此处的 `get_status` 改为调用它。**当前无「已授权但服务被停用」第三态**（本卡只能判 granted / not-granted）——归 T21-7 按决策 #10 补齐。
3. **`resolve_capture` 的并发双写**：幂等靠"读 status 再写"，两次**并发**点击仍可能各写一笔（本地单用户 UI、按钮点击后即禁用，风险低）。`AutoCaptureDao.applyResolution` 是无条件更新（DAO 归 T21-3 独占，本卡不能加条件更新）。如需硬保证，交 T21-9 复核或在 `db/` 侧补一条条件推进。
4. **分类名 → id 的匹配**：`resolveCategoryId` 先按「收支方向 + 名字」精确匹配，再退一步只按名字。同名跨方向（极少）时可能取到另一方向的那条——模型输出的分类名本就在当前方向的候选集里（`_render_categories_section`），实测风险低。
5. **`source = nlu_ai` 是折中**：本地规则命中时更准确的 `nlu_local` 细分归 T21-6（本卡拿不到"这条是本地还是服务端解析的"标记；`parsedJson` 无来源位）。
6. **`accountId` 兜底默认账户**：复用聊天记账口径，会让确认的账目**联动账户余额**（REQ-70）。若产品上认为"自动记账不该动余额"，需回来看这一条——本卡按"与聊天记账一致"取默认。
7. **未走真机**：本卡是纯逻辑层（桥 handler），四板 + 反向验证即充分；**两类授权与两条通道的现场投递归 T21-9 收口**（决策 #19）。
8. **`get_status` 的「今日」按设备本地日零点**：跨时区/跨零点行为与 `countCapturedSince` 的既有口径一致，未单独处理。
