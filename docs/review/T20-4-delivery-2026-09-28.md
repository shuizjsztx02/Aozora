## 二、设计决策（卡面之外，实施期定死的）

### 2.1 ★ 下发通道：理由码挂 `ToolOutcome`，不重算（T20-3 交接的落实与**修正**）

T20-3 的交接写的是「需要在 `confirm` 帧与 `done.executions` 回执上加一个字段，那是 `stream.py` + `service.py` 的面」。**前半对、后半不对**：

- **「加字段」判得准**——`proposal` 是 v2 契约信封（`schema-v2.json` 的 `additionalProperties: false`），塞不进新键；`ApprovalRequest.reason` 只活在服务端。
- **但 `stream.py` 自己拿不到那个值**。它只在 `tool_finished(step, name, outcome)` 上有提案，而理由码是 `_handle_proposal` 里的局部变量。**唯一不重算的做法**是让它随产物带出来——落地为 `ToolOutcome.confirm_reason`（tools.py）+ 挂起分支回带（agent.py）+ 帧里透传（stream.py）。
- **明确否决了「在 stream.py 重算」**：`confirm_reason(step, confidence, op)` 是纯函数、三样输入帧里都有，看起来最省事——但那等于**把同一把尺子摆两处**，将来 loop 多一条挂起理由（比如 T20-6 之后的新形态）就会静默漂移：帧上写着 A，loop 实际因为 B 挂起。

顺带修正一处**假前提**：卡面写「风险等级随**提案/回执**下发」，实际**回执那一侧不需要新字段**（见 2.3）。

### 2.2 ★ 设备 op 刻意**不带**理由码

`sync_trigger` / `persona_switch` / `consent_record` / `reminder_set` 的挂起发生在 `_handle_proposal` 的**第一步分流**，理由不是风险而是**能力**（服务端没有它们的存储位置）。`confirm_reason` 对它们算出来的值（`consent_record` 是 `medium_risk`！）是**宣告性的**、不参与它们的挂起判定——带上它，卡片就会说「因为会改动你已有的记录」这种半真的话。故设备分支**不传**。

这一条**第一次写成了假绿用例**：我原先在既有的 `sync_trigger` 用例里加 `assert "confirmReason" not in confirm`，而 `sync_trigger` 是 `low`、`confirm_reason` 本来返回 `None`——把理由硬塞进设备分支，这条断言**照样绿**（探针 C 复现）。改成用 `consent_record`（`medium`）新写一例之后，探针 C 恰好 1 条红（§3.4）。

### 2.3 ★ 「已按低风险直接执行」不靠新字段，靠一条**服务端不变式**

自动执行那条路（`reason is None and executor is not None`）**不产提案、不产 confirm 帧**，T20-1 之后客户端的回执卡是**客户端自己**从 `/ai/execute` 回执组装的（`requiresConfirmation: false`）。而挂起的提案**恒为 `true`**（T-M7-02e 决策 2，`test_multi_step_write_hangs_and_emits_confirm` 逐字钉住）。于是卡片只需要这一条：

> `requiresConfirmation === false` ＋ 有服务端凭据 ＋ 不是设备凭据 → 「已按低风险直接执行」

**为什么不给回执也加 `risk` 字段**（卡面「风险等级随提案/回执下发」的字面读法）：① 那句话的**目的**是「零新增通道」，本卡满足（桥命令恒 83）；② 这一支的「低风险」是**可证的**——能自动执行 ⟹ `confirm_reason` 返回了 `None` ⟹ 该 op 的风险不是 medium/high（后两档永远出卡）；③ 多一个字段要多动 `service.py` / `schemas.py`（T20-1 刚落库的面）与两处回执，换来的信息客户端已经握在手里。**代价写在这里**：若将来有一条「不经确认就执行、但不是低风险」的路，这个推断会失真——那时应当补字段，而不是让卡片继续说这句话。

### 2.4 「说不出来就不说」：三态而非两态

`AssistantMessage.confirmReason` 有**三种值**，卡片只对第一种说话：

| 值 | 来源 | 卡片 |
| --- | --- | --- |
| 理由码字符串 | `confirm` 帧带了 | 出理由行 |
| `null` | 帧里没带（设备 op / 没人可问） | 不出 |
| `undefined` | T20-4 之前落盘的老消息没有这个字段 | 不出 |

**不认识的码也不出**（`REASON_LABELS` 查不到就返回 null）：服务端将来多一档理由时，卡片**安静地少一行**，而不是编一个解释。这与本卡既有的「没凭据就不说已执行」（REQ-67②）是同一口径。

### 2.5 没做的那一条（**挂账，交 T20-7**）

T20-3 交接里还有一句：「设备 op 的 4 条……卡片对它们要自己说明『由设备执行』」。**未做**，两条路都比这一行字贵：

- 认设备 op 要把 `use-assistant` 的 `DEVICE_OP_DISPATCH` 这个**运行期值**导进渲染层——T20-2 已经记过这条约定（渲染代码只从**契约层**取判据，否则七个页面用例的 `vi.mock` 都要补导出，`AssistantPage` 取 `isV2Proposal` 而不从 `use-assistant` 取就是照这条办的）；
- 或者往线协议上再加一个 lane 字段，绕过 T20-3 冻结的四码词汇。

**现状的影响面**：设备 op 的卡照旧出、照旧要确认，只是少一行解释；四条里两条的主行本身就点了设备（`consent_record`「记录**这台设备**的隐私政策同意」/ `sync_trigger`「让**这台设备**立刻同步一次」），执行完成后结果行照旧说「✓ 已在本机执行」。

### 2.6 卡面第 ③ 条：`APP-CONTEXT.md` 确实有一处**过时口径**

§6.2 的流程图里写着「**高置信快速执行 / 低置信确认卡**」——那是 REQ-78 之前的世界（只有置信度一条判据）。已改写为「按风险分级 / 步数 / 置信度出确认卡，或直接执行 / 无效则追问」，并加一段指向成文清单（并写明机器读的那一份在 `Tool.risk`、两处由用例对账）。**只动这一处**，红线两句（§6.1 / §M7）一字未改。
