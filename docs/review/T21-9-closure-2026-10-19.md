## 二、真机回归查出的两处缺陷（本卡的代码改动只有这两处）

### 2.1 ★ 无障碍通道在真实第三方 App 上**零采集**

**现象**：授予无障碍授权、开总开关、把来源包加入集合、在支付结果页停留并滚动——`auto_captures` **一行都没有**。

**定位过程**（用临时探针，取证后已全部移除）：

| 探针 | 结果 | 结论 |
|---|---|---|
| 在 `onAccessibilityEvent` 入口打印 `eventType / pkg / className` | 事件**正常到达**（`type=2048` = `TYPE_WINDOW_CONTENT_CHANGED`，`pkg=com.android.chrome`） | 服务在跑、事件在来 |
| 在 `handleContentChanged` 打印拼好的文本长度 | **一次都没有输出** | 说明在拼文本之前就 `return` 了 |
| 直接遍历 `rootInActiveWindow` 打印节点文本 | `支付结果\|支付成功\|¥32.00\|星巴克咖啡\|付款方式：零钱\|…`（57 字符） | **节点树可读** |
| 同时打印 `event.text?.size` | 恒为 **0**（`evtLen=0`） | **根因**：`AccessibilityEvent.text` 在真实页面上恒为空 |

**根因**：`handleContentChanged` 用 `composeText(e)` 只读 `AccessibilityEvent.getText()`。原实现的注释写着"`AccessibilityEvent.getText()` 已经按节点顺序给出列表"——这个假设**在真机上不成立**（Android 16 / Chrome；事件文本只在部分场景被填充）。

**修法**：改为遍历 `rootInActiveWindow` 的节点树（新增 `collectText`，深度上限 40，`LinkedHashSet` 去重保序），并按 T21-4 卡面原意（"只在用户选定包名且页面判定命中时遍历节点"）把**来源包闸门前移**——不在来源集合里的包**连节点都不遍历**。

**为什么所有用例都绿**：`AccessibilityFilterTest` 测的是纯函数（输入是拼好的文本），根本没覆盖"文本从哪来"；`SecurityConfigTest` 的三道守护守的是"不许写"，不守"读得到"。

**回归守护**：`SecurityConfigTest.accessibilityServiceSource_readsWindowNodesNotOnlyEventText`（断言源码含 `rootInActiveWindow` 与 `getChild(`）。

### 2.2 ★ L2 跨通道合并**静默永不命中**

**现象**：同一笔同时被通知与支付页抓到，两条都各自入账——按设计应该合并为一条。

**定位**：查库发现无障碍行的 `postedAt` 落库后是 **1970-01-01**，通知行是 **2026-10-19**。

**根因**：无障碍用 `e.eventTime` 当 `postedAt`。`AccessibilityEvent.getEventTime()` 是 **`uptimeMillis` 基准**（开机以来的毫秒，本机取证时是开机 197 秒），而通知通道的 `StatusBarNotification.getPostTime()` 是 **epoch 毫秒**。`DedupeKeys.l2Key` 的分钟桶建立在这个时间上 → 两条通道的 `mergeKey` **永远对不上**。

**修法**：无障碍改用 `System.currentTimeMillis()`。

**这条的隐蔽性**：`AutoBookEngineTest` / `DedupeKeysTest` 里两侧都传同一个基准的时间，所以**用例永远绿**；`createdAt`（`System.currentTimeMillis()`）也是对的，只有 `postedAt` 这一列错——不查真机库看不出来。

**修复后现场验证**：同一分钟桶内投「瑞幸咖啡 ¥56.78」通知 + 打开同金额支付页 → 两行 `mergeKey` **同值**（`043a2443`），无障碍行被 `mergedInto` 留痕为 `ignored`，保留行带 `merchantKey=瑞幸咖啡`，**不重复入账**。

### 2.3 补 `isAccessibilityTool="false"`

T21-4 交付记录 §五.3 明确移交本卡处理。按 `docs/legal/accessibility-play-declaration.md` 的口径，声明在 `accessibility_service_config.xml`（`res/xml/` 确实是该属性的合法位置）。守护：`SecurityConfigTest.accessibilityServiceConfig_declaresIsAccessibilityToolFalse`。

## 五、决策 #18 三条系统层 / 审核约束取证

### 5.1 侧载授权门槛（★ 本轮最需要写清的一条）

| 尝试 | 结果 |
|---|---|
| `adb shell settings put secure enabled_accessibility_services <组件>` + `accessibility_enabled 1` | `settings` 读回**有值**，但**系统设置页显示 Off**、`dumpsys accessibility` 的 `Bound services` **为空**、`Crashed services` 也为空——**服务根本没启动**，且**不报任何错** |
| `appops set com.aozora.app ACCESS_RESTRICTED_SETTINGS allow` | 同上，**无效** |
| 走系统设置 UI：Accessibility → 下载的应用 → 「自动记账（只读支付页）」→ 开 → 确认框 **Allow** | **绑定成功**（`Bound services` 出现条目），随后捕获正常 |
| `adb install -r` 更新 APK 后再触发 | 绑定**再次失效**（`Bound services` 变空）；`settings put` 无效，**重启设备**后恢复 |

**结论**：① `settings put` **不能**冒充已授权——用户意图与系统认可不是一回事；② 侧载 / 重装后必须走一次系统设置页（或重启）才真正绑定；③ 这是 R-PROD-62 的正文依据。
