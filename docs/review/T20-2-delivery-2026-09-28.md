## 二、设计决策

### 2.1 ★ 业务卡**只在能忠实渲染时出场**（本卡最重要的一条）

卡面写的是「旧 = **回执** `before`」——`before` 由服务端在**执行前**抓、随回执下发（T20-1 决策 #4），
所以**挂起态（用户还没点确认）的改 / 删卡手里没有旧值**。那时只有一条**增量** payload
（`_build_tx_changes` 只带模型改的那几项），拿它当快照渲染会把「没提到的字段」显示成
「未分类 / 不使用账户」——**少一个键就是一次错误的显示**（T20-1 §2.2 同一条理由，那里说的是 `accountId`）。

所以 `ledgerCard()` 在拿不到 `before` 时**返回 `null`**，卡片回落通用卡（payload 键值对照 +
确认 / 拒绝）——与改前的行为一字不差。设备实测（§3.3 路径 2 / 3 的第一步）就是这个形态。

**红线 4 也把这条路堵死了**：「修改卡的新旧对照必须用服务端下发的 `before`，不得事后从 Room 猜」——
所以这不是偷懒，是本轮定死的口径。**代价**见 §4 第一条。

### 2.2 ★ 修改卡的「新」= `before` 叠 payload 的增量，不是 payload 本身

payload 是**增量**：`{transactionId, version, amountCents}` 这样一条，只有改过的那两项。
直接拿它当快照会缺一半字段（分类 / 日期 / 备注 / 账户全是空的）。所以：

```
after = snapshotOf({ ...before, ...changedFields(payload) }, bookId)
diff  = diffMask(after, old)          // 与 v1 对照区同一份比对口径
```

`changedFields` 只取 `SNAPSHOT_KEYS` 这六个（决策 #4 的六项），把 `transactionId` / `version`
这类**内部标识**挡在外面——它们不该进快照，更不该被当成「字段变了」高亮。

变异探针 2 证明这一步是承重的：把 `after` 换成裸 payload → **恰好那条修改卡用例红**。

### 2.3 高亮复用 v1 的 `diffMask`，只导出不重写

`SnapshotCard` 要一个 `DiffMask`，而掩码是**两侧共用**的（旧卡上改动的字段也标出来，与 v1 一致），
所以两个渲染点必须拿到**同一份**掩码——要么导出 `diffMask`，要么把 8 条比较在客户端再抄一遍。
选了前者（单一事实源；本项目反复记过「同一件事两处各写一份」的坑，见 R-PROD-47 一族）。

副作用：`ConfirmationCard.tsx` 从「只导出组件」变成「又导出函数」，多出一条
`react(only-export-components)` warning。**该规则在仓库里已有 6 处存量**
（`OnboardingPage` / `EmojiPicker` / `ReportsPage`×3 …），oxlint 仍 exit 0；
读数 43 → 44 条 warning，其余 43 条全是存量。**如果这条判为不可接受**，替代方案是把
`CommittedSnapshot` / `DiffMask` / `diffMask` 抽到单独模块（行为零变化），代价是多一个新文件。

### 2.4 预算位**不渲染**（`SnapshotCard.hideBudget`）

`before` 与 payload 都**没有** `includeInBudget` 这一位（决策 #4 的字段集是六项）。
照默认值画就等于对用户说「这笔计入预算」——一个我们并不知道的断言。所以隐藏它：
`hideBudget` 默认 `false`，**v1 的两处调用一字未改**，只有 v2 业务卡传 `true`。
设备实测：业务卡上 `[data-testid$=-budget]` 命中数 **0**（§3.3）。

### 2.5 `transaction_add` 一次多笔 → 逐笔各出一张

`transaction_add_batch` 与 `transaction_add` 共用同一个 `action`（payload 里是 `transactions[]`），
所以记账卡按**数组**渲染。「早饭 12、午饭 25、打车 30」这类一轮多笔的输入不会只显示第一笔。

## 四、发现与已知限制（**交 T20-7 落笔风险册，本卡不碰 `risk-register.md`**）

1. ★ **挂起态看不到旧值——与 REQ-77 ③ 的字面诉求有差距（本卡最该被看见的一条）**。
   用户原话是「**当进行修改删除时**, 也需要弹出一个修改的卡片, 表明新旧版本的修改内容」，
   而「弹出卡片」的那一刻正是**挂起态**（T20-3 之后改 / 删均为 `medium`，一律先问）。
   那一刻客户端手里没有 `before`（它只在执行回执里），所以**用户点确认之前看到的是通用卡**
   （payload 键值对照），新旧对照只在**确认之后**出现。设备实测就是这个时序（§3.3 路径 2）。
   要按字面满足，得让 `before` **随提案**下发（`tools.py` 的 `transaction_update` / `_snapshot_before`
   提前到提案产出时），那是服务端改动、且与决策 #4「服务端在执行前抓」相抵触——**不在本卡领地**，
   登记为取舍。**未擅自绕路**（红线 4 明令不得从 Room 反推）。
2. **预算位在业务卡上不可见**（§2.4）：`before` / payload 都不带这一位，所以业务卡不显示它。
   若产品要它，得先让服务端把 `includeInBudget` 放进快照（同样是服务端改动）。
3. **旧消息仍无 `message` 主行**：树上有一张 T20-1 之前的自动执行卡，`proposal.message` 为空
   （回执那时不带它），业务卡渲染出来只有四行、没有主行——如实反映「那次回执没带话」，
   不做兼容性补齐。
