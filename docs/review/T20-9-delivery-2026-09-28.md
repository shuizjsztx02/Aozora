## 二、设计决策（卡面之外，实施期定死的）

### 2.1 ★ 429 的归因分层：照 T18-1 的 503 先例，**只放行已知子码**

桥以前只按状态码映射，两类 429（`ai_quota_exceeded` = guest 日配额用尽 / 「请求太密」）一律译成 `429` + 「AI rate limit exceeded」。前端的码说不清前因，只能落「连接中断」兜底。

做法与 T18-1 **逐字同构**（那是同一个陷阱的前一个实例）：

| 层 | 动作 |
| --- | --- |
| `AiGatewayClient` | `AiError.RateLimited` 带上服务端 body 的 `code`（同步路径用已有的 `body`；SSE 路径**必须在 `onFailure` 里读**——okhttp-sse 在 `response.use { … }` 内回调，出了那个作用域就没有第二次机会） |
| 桥 | `rateLimitedCodeAndMessage(e, fallbackCode)`：**已知**子码原样透传，其余回落调用方既有的笼统码。未知码**不透传**——前端对未知码会回退原生英文 message，比笼统码更糟（T18-1 的判据） |
| 前端 | `aiRefusalNote(code)`：码 → 整句如实文案；`null` = 不是这一类，照旧 `INTERRUPTED_TURN_NOTE` |

**回落码按 handler 保持原样**（`handleAi*` 用 `429`、图片链路用 `rate_limited`）——不动既有语义面，只加一条分流。

### 2.2 ★ 只放行**配额**一个子码，`ai_rate_limited` 不新增码

服务端的两个 429 码里，桥只为 `ai_quota_exceeded` 放行新码（即服务端自己的码，与 `image_parsing_disabled` 同法）。`ai_rate_limited` **不新增**：笼统的 `429` 已经是那个语义，前端对它的文案也已如实（见 2.3）。这样桥的新增码面 = **1 个字符串**，桥命令面 = **0 变化**（83 不变）。

### 2.3 ★ 「服务端拒绝」与「链路断了」的判据落在**文案**上，而 Ring 入口照旧

限流（缓一会儿就能再发）与配额用尽（今天没额度了）都要换掉「连接中断」，理由同一条：**请求到了服务端、服务端也答了话**——用户的下一步动作不是查网络。

`AI_REFUSAL_ZH` 两个语义、四个码（`ai_quota_exceeded` / `429` / `rate_limited` / `ai_rate_limited`——后三个是同一语义的三种码，`ai_rate_limited` 是服务端的码、桥当前不产出，留着免得下次接线时再来改一遍）。

**重发入口两类都留着**：限流一会儿就恢复，重发有用；配额到顶时重发无害（撞同一句如实文案），而不给入口反而让用户满屏找按钮。**真断连仍用 `INTERRUPTED_TURN_NOTE`**——那句对断连是对的（卡面明确要求）。

### 2.4 ★ 两处文案**同源**，缺一处等于没修

「连接中断」在聊天页出现**两次**：气泡收尾（`settleStream` / `failCloudTurn`）与输入框上方的提示条（`AssistantPage` 的 `interrupted-banner`）。只改气泡的话，用户在同一屏上照样看得见那句谎。故 `InterruptedTurn` 多一个可选 `note`（`undefined` = 既有那句），**气泡与提示条读同一个值**。

### 2.5 ★ 动了卡面没列的 `security.md`（并说明为什么算必须）

卡面 ④ 只列了三份文档。但 `security.md` 的保留期表里，**「为什么不动会话行」那一格的理由原文是「否则会话级双限被清空、用户可刷回满额」**——本卡把双限删了，那条理由当场失效。留着它的后果不是措辞陈旧，而是**下一个读者可能据此去改 `SET NULL`**（一个真实的、方向相反的结论）。

订正方式是加一段带日期的说明，**不覆盖原文**：`SET NULL` **不变**——它现在由上面那条「`ai_usage` 是 guest 日配额基座、审计行必须活得比会话长」支撑（`models/ai.py` 的列注释本来就是这个口径）。同表的「与 §6.3 的窗口 N=8、会话级双限同口径」也把已消失的那半摘掉。

**没动**的陈旧引用（都属**历史快照**，改写即伪造历史）：`production-execution-plan.md` 的 P1 交付清单、`T-M7-ai-agent-issues-2026-09-20.md` 的复盘快照、`ADR-010` 里那句把「02f 的会话配额」当单 worker 同取向的类比。

### 2.6 ★「不得只删」落成可检出的守护，而不是「调某个方法不抛」

删掉判定之后，「正确行为」已经不存在——**断言「`check_quota` 不抛」是自反的**（方法都没了，恒真 ⇒ 假绿，仓里记过的两种形态之一）。故守护拆成两层：

1. **服务层**（`test_ai_conversation.py`）：配置面与判定面**都不存在**（`Settings.model_fields` 里没有那两个名字、`ConversationService` 没有 `check_quota`）——它会在双限被加回来的那一刻变红；
2. **E2E**（`test_agent_stream.py`）：**把超限用量真的造出来**再发一轮，判据是「不再 429」。种子行落在 40 天前，因此**同时**证明了两把尺子是分开的（穿透会话维度、不触发 guest 日配额）。
