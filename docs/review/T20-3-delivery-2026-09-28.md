## 二、设计决策（卡面之外，实施期定死的）

### 2.1 ★ 判定量是 **op** 不是工具名——两处键空间必须合一

卡面第 ② 条写的是 `frozenset(t.name for t in TOOLS if t.risk == "high")`，而 `confirm_reason` 收到的 `op` 是 `canonical_op(tool.proposal_action)`（`_handle_proposal:1668`）。今天两者恰好同名（两个高风险工具名与 op 一致），但**名与 op 一旦分叉，按名查的口径会静默漏掉那个工具**——正是本卡要终结的那类陷阱。

故 `HIGH_RISK_OPS` 从 **`TOOL_RISK_BY_OP`（按 op 建索引）** 派生，`confirm_reason` 的 high 也走同一张表（不再查 `HIGH_RISK_OPS`）；另加一条守护用例钉住「按 op 派生的集合 == 按名派生的集合」，把「今天恰好同名」这件事也变成断言而不是巧合。

顺带定死一条：**两个工具可以共用一个 op**（`transaction_add_batch` 的 `proposal_action` 就是 `transaction_add`）。共用时风险不一致在**导入期** `RuntimeError`，而不是让「先注册的那个」静默赢。

### 2.2 ★ `risk` 字段**不给默认值**

决策 #8 要的是「新增工具漏标即红」。若给 `risk: ToolRisk = "low"`，一个新增的**写**工具漏标就静默降级成 `low` = 悄悄自动执行——恰是本卡要防的方向。无默认值 → 漏标在导入期 `TypeError`；守护用例再遍历一遍，把「有人给它补了个默认值」这条路也堵上。

### 2.3 读工具标注为 `low`，不是漏标

「不为读工具分级」的执行含义是**它们的处置恒为「直接执行」**（读工具不产提案、不过审批门），而不是「字段留空」。字段是必填的，故 22 条读工具逐条标 `low`，并有一条用例钉住「读工具恒 low」（防将来有人把默认值改成 `medium` 让只读指令莫名出卡）。清单文档也收读工具——用户问的是「哪些指令能直接跑」，只读指令同样是指令。

### 2.4 优先级：风险两级在 `multi_step` / `low_confidence` **之前**

风险判「**做什么**」（后果的形状，与模型把握无关），另两条判「**模型自己有多稳**」——两类正交，同时命中时报前者（用户问「为什么这次问我」时，「这个操作会改掉你已有的数据」比「这一步是第 2 步」有用得多）。

对 `low` 的 op **零影响**：`transaction_add` 在两步流程里仍报 `multi_step`、单步高置信下仍是 `None`——记账那条主路径的快路径没被击穿（用例 `test_single_step_high_confidence_executes_without_asking` 与流式的 `test_step_one_write_autoexecutes` 都仍然绿）。

### 2.5 三档判据的落点（逐字写在 `Tool.risk` 的 docstring 里）

**`low`** = 新增类写操作 / 查询类 / **可一键改回的设置项**——共同点是**不碰用户已有的数据行**；**`medium`** = 改动或删除用户既有数据（交易/预算/账户/账本/分类/定时/角色/余额）+ **导出域与隐私域的写**（按域判，不逐 op 再议）；**`high`** = 后果**不可通过 App 内的任何操作挽回**——注销账号、**清空或批量删除语义**、隐私同意撤回。

两处需要说明的取舍（文档「两处刻意取舍」一节也写了）：

- **`feedback_submit` 归 `medium`**：它不改既有数据，按第一把尺子该是 `low`；归 `medium` 是因为第二条判据按**域**判（数据离开 App 与导出同类）。按域判是刻意的——逐 op 再议等于每个新工具都要重新吵一遍边界。
- **设备能力 5 条全 `low`**：`device_share_text`（分享）/ `device_request_permission`（权限）/ `device_pick_image`（选图）的「人工确认」由**系统 UI**（分享面板 / 权限对话框 / 选择器）承担，再叠一张 AI 确认卡是重复询问。`device_haptic` / `device_widget_refresh` 无副作用。

### 2.6 `high` 从一条变两条：`book_delete` 达标

05d 的判据是「不可挽回」，当时只有注销达标。REQ-78 把 high 的第二条语义定死为「**清空或批量删除语义**」——`book_delete` 删掉的账本**连同其中全部流水**一并不可见（`tools.py` 自己的描述就写着「本工具集里破坏性最强的操作之一」「唯一的批量删除语义」），故 BLOCK 它进快路径。`transaction_delete`（软删单笔）与 `scheduled_archive`（已生成记录不受影响）**不达标**，留在 `medium`。

### 2.7 `account_delete` 刻意不进高风险名单

`account_delete` 是 v2 注册表成员但**没有工具产出它**（它的 payload 是一次性删除 token，凭据不进模型上下文；`authorization.py` 对未登记授权规则的 op 一律拒绝）。把它塞进 `HIGH_RISK_OPS` 反而会掩盖「授权面 fail-closed」这件事的独立性。未注册的 op 落回旧口径（fail-open 到步数 / 置信度），有一条用例把这个边界写明。

### 3.2 活体取证（真实 uvicorn + **真实 DeepSeek 模型**，v2 车道）

起 `uvicorn src.main:app`（工作区代码，`127.0.0.1:8013`，dev 库 `native-bills-postgres-1`）→ guest → 账本 → 分类 → 一笔账，然后打**真实端点** `POST /ai/agent`（`proposal_contract_version: 2` = 生产客户端声明的车道，`AiGatewayClient.kt:485`）。**模型是真的**，只有输入是我写的。

抽样三类各一条（卡面验收的「清单文档与真机行为抽样三类一致」）：

| 档 | 输入 | 实测 | 与清单一致 |
|---|---|---|---|
| **low** | 「记一笔 30 块打车」 | 无 `confirm` 帧，`done.executions = ["transaction_add"]` | ✅ 直接执行 |
| **medium** | 「把打车那笔账删掉，直接删不用先查」 | `confirm` 帧 `step=1`、`action="transaction_delete"`、`requiresConfirmation: true`；`done.executions = []` | ✅ 需确认 |
| **high** | 「把「日常」这个账本删掉，直接删」 | `confirm` 帧 `action="book_delete"`、`warnings` 非空（工具自己提示「删除后需要切换账本」）；`done.executions = []` | ✅ 强制确认 |

**medium 那一条是判别性的证据**，逐字如下（模型这一步没有先查，是**单 Step + 高置信**形态）：

```json
{"step": 1,
 "proposal": {"contractVersion": 2, "action": "transaction_delete",
              "payload": {"transactionId": "01a81835-…"},
              "message": "删除一笔支出记录（含「打车」）",
              "warnings": [], "confidence": 1.0,
              "proposalId": "agent-8bb6fd3f…", "requiresConfirmation": true}}
```

`step=1` + `confidence=1.0` + `warnings=[]` + 非设备 op ⇒ **改前 `confirm_reason` 必返回 `None` ⇒ 自动执行**（这条老口径由 `test_single_step_high_confidence_executes_without_asking` 逐字钉住）。改后它挂起出卡，且**那笔账一个字段都没动**：

```
那笔账：id=01a81835-… deleted_at=None note='打车' 金额=3000
done.executions = []      done.proposals = ['transaction_delete']
```

另一轮（模型自己选择先查一次，`step=2`）同样只出卡不执行——那一轮 `multi_step` 本就会拦，故不作判别性证据，仅作对照。

**没做到的那一条（如实记录）：**「真机上点一下卡、账真的被删掉」这一段**未走**——本卡零客户端改动，卡的渲染与提交是 T20-4 / T20-2 的面；而**风险等级目前还没有下发到客户端**（见 §4 第一条），T20-4 落地前真机上也分不出「为什么问我」。本轮真机 USB 亦不可达（T20-1 记录：`adb devices` 掉线，`adb reconnect offline` 无效）。
