## 二、判据先行（卡面第①步：产出结论而非代码）

在 dev 环境（uvicorn + 真实 DeepSeek）复现附件 #147 的场景，**三组实测**：

### 2.1 路由与注入面（`route_domains` 纯函数 + `AgentLoop` 真实系统提示）

| 输入 | 现状域 | `meta_set` 在场？ |
| --- | --- | --- |
| 以后叫我爹 / 以后叫我老板 | `security, reminder` | **否** |
| 帮我改一下我的消费偏好 | `transaction, analysis` | **否** |
| 记住我的记账习惯是月底结算 | `transaction` | **否** |
| 我的说话偏好是温柔一点 | 兜底全量（16 域） | 是 |
| 把我的用户画像清空 | 兜底全量 | 是 |
| 把默认账本设成旅行 | `book, meta` | 是 |

注入面**只由路由决定**（`agent.py:1162` `self._inject(self._default_tools(self._route.domains))`），所以第一类句子上 `meta_set` 是**结构性不可达**的——模型不是不会用，是手里没有。**卡片「模型手里常常没有 `meta_set`」的假设成立。**

### 2.2 模型到底调了什么（真实调用，每档 3 轮）

| 输入 | 现状（3 轮） | 注入 meta 后（现描述） | 注入 meta + 新描述 |
| --- | --- | --- | --- |
| 以后叫我爹 | `auth_update_profile` ×3 | `auth_update_profile` ×3 | **`auth_update_profile` ×3** |
| 我的说话偏好是温柔一点 | `meta_set` ×2 `{"说话偏好": …}` | `meta_set` ×2 中文键 | **`meta_set` ×3 `{"communicationStyle": …}`** |

**两条结论，一条推翻卡片假设：**

1. **卡片 ②+③ 对「说话偏好」这类句子完全有效**：键名从**编造的中文自由词**（`说话偏好` / `说话风格`）变成**正确键名 `communicationStyle`**，命中率 2/3 → 3/3。这正是 REQ-74 症状④（「表单页显示为空而数据其实在库里」）的直接解药。
2. **★ 卡片假设在验收句上被推翻**：卡片决策 #7 期望「并列补 meta → 由模型按语义选」，但实测**注入 meta 之后模型仍一律选 `auth_update_profile`（6/6）**——补路由与改描述都不够。原因是两条语义撞车：`auth_update_profile` 改的是**账号昵称**（`users.nickname`，显示在「账号安全」页），而「如何称呼你」在**用户画像**里（`user_profile.nickname`）。两者都是「怎么叫你」。

### 2.3 据实决定的后续动作（§3.2 的由来，一条实测出来的补法）

`auth_update_profile` 的描述原文写着「用户说『**以后叫我小王**』『把昵称改成…』时用它」——把那句话**原样**指向了账号昵称。收窄它的描述后再测：

| 输入 | 收窄后（3 轮） | 是否误伤 |
| --- | --- | --- |
| 以后叫我爹 / 以后叫我老板 | **`meta_set` ×3**，`{"nickname":"爹"}` ✅ | — |
| 以后称呼我为老板 | `meta_set` ×3 | — |
| **把昵称改成老王 / 我的昵称改成老王** | `auth_update_profile` ×3 | **没有误伤**（真·账号昵称仍走原路） |

**判据**：账号昵称**不进 AI 上下文**（`prompts.py` 只认画像的 `nickname` 标签），所以「以后叫我爹」走 `auth_update_profile` 等于**用户的诉求完全落空**——AI 仍然不会叫他「爹」。这不是风格问题，是功能不成立。

## 三、设计决策

### 3.1 路由只收**复合词**（不写裸「偏好」「习惯」）

画像类信号逐条对应表单的 7 个字段（`职业` / `生活节奏` / `固定支出` / `消费偏好` / `沟通风格` / `说话偏好` / `语气` …），加上 `用户设定` / `画像` / `称呼我` / `叫我`。

**裸泛词刻意不进词表**：信号命中会把输入从兜底全量**收窄**成命中域——「我更偏好用现金」若因「偏好」命中 meta，注入面就只剩 meta，「记账工具被收走」正是模块头明令避免的**漏注入**方向。钉住这条的用例：`test_a_bare_preference_word_does_not_narrow_to_meta`。

**「叫我」是第三条并列，不是搬迁**（决策 #7）：reminder 与 security 各有一条 `叫我`，meta 再加一条——并集语义下三个域都注入。挪走的代价是「提醒我交房租」丢掉 reminder 域。

### 3.2 ★ 补一条卡面没有的改动：收窄 `auth_update_profile` 的描述

依据 §2.2/§2.3 的实测。改动本身极小（只改描述文本，不动参数、不动 op、不动执行体），**同在本卡独占的 `tools.py` 文件面内**，且带回归对照（「把昵称改成老王」仍走 `auth_update_profile`）。

> **交接给 T19-9**：这条是「两个『称呼』撞车」的**描述级**解法。真正的产品口径（账号昵称与 AI 称呼是否应该合并成一个）超出本卡，未裁决。

### 3.3 `_PROFILE_KEYS_HINT` 由 `_PROFILE_LABELS` **生成**，不抄第二份

决策 #4 说「写死 7 个键名与含义（与 `_PROFILE_LABELS` 同源）」。落法是**真的同源**：`tools._PROFILE_KEYS_HINT = " / ".join(f"{k}（{v}）" for k, v in _PROFILE_LABELS.items())`——跨模块 import 私有名，范式同 `proposal_ops` 从 `sync.service` import 私有校验器（那里写着同一句理由：抄成第二份必然漂移）。于是「模型看到的键名」与「服务端渲染标签用的键名」**不可能**不一致；剩下的一条腿（服务端 ↔ 表单页 `FIELD_ORDER`）由新增的 `test_ai_profile_vocabulary.py` 钉住。

### 3.4 浅合并的三种输入，一宽容两严格

| 输入 | 处置 | 理由 |
| --- | --- | --- |
| 未知键 / 非字符串值 | **丢弃 + 记日志** | 决策 #4 的宽容档（推荐项）；写进去表单页也看不见（`parseStoredForm` 只认已知键的字符串），等于「写了个寂寞」 |
| **入参不是 JSON 对象** | **400** | 刻意**不**宽容：宽容只能落成「照收但什么都没改」，而卡片回执会说「已更新用户画像」——正是 T18-3 记的「回执说谎」。这段路在执行期、模型已不在回路里，报错（客户端显示执行失败）比吞掉诚实 |
| 存量值是脏值（非对象） | 按空对象合并 + warning | 那份内容按定义已经读不出来（表单页对它同样回退空表单），卡在这里会让用户永远改不动画像 |

**浅合并只给 `user_profile`**：`widget_config` 仍是整值替换（它是**整份**配置，「合并」没有意义）——`test_meta_set_still_replaces_widget_config_wholesale` 钉住口径没有扩散。**表单页那条路完全不受影响**：它走 sync push（`sync/service.py` 的 `user_preference` 分支仍是整值写 `value`），本卡一个字没动。

### 3.5 「清空画像」的已知边界（挂账，非缺陷）

浅合并下 `{}` = 「没有键在场」= **不改任何东西**。所以对话说「把我的用户画像清空」时，模型若回 `{}`，卡片会成功但库里不变。**单个字段**仍可清（写 `{"nickname": ""}` → 表单页显示为空 → 保存时该键被丢掉）。整份清空目前只有表单页那条路。归 T19-9 的挂账清单。
