## 二、取证与设计结论（本卡的第一交付物）

### 2.1 H3 在设备上被直接证实（v2 提案此前根本不进历史卡）

设备上原本就躺着一条真实会话（**修复前构建** `index-CBEINCG-.js`）。同刻对照：

| 判据 | 修复前 | 本卡构建后 |
| --- | --- | --- |
| 本地快照里的 v2 提案消息 | **2 条**（1 `pending` + 1 `committed`） | 同 2 条 + 新增 1 条 |
| 页面渲染出的 v2 卡 | **0 张** | **3 张** |
| 其中已执行那张的结果行 | （卡不存在） | `✓ 已执行 · 影响 1 项` |

即：**消息在、卡不在**——正是 H3 说的「v2 提案结构上不可能反映库」。v1 的历史卡同刻渲染出 3 张，
说明缺的不是渲染链路而是**判据**（`AssistantPage` 的 `!isV2Proposal(p)`）。

### 2.2 「回执」的数据源：两条链路、一个形状（这条决定了实现怎么摆）

卡面上的「执行结果」不能来自 `done.proposals`（那是**请求快照**，`transactionId`/`changes`/`version`），
也不该来自卡态。可用的**事实**只有服务端执行回执。而它在两条链路上的入口不同：

| 链路 | 何时发生 | 回执来源 | 与 `done.executions` 的关系 |
| --- | --- | --- | --- |
| **自动执行**（单 Step 高置信） | 一轮进行中，客户端**拿不到提案** | `done.executions` 逐条 | 就是它本身 |
| **用户确认后执行** | 用户点卡内「确认」→ `/ai/execute` | `bridge.executeProposal` 的返回 | **同形**（`stream.py:_done_payload` 原样透传 `result.executions`，字段 `transaction_ids` / `proposal_id` / `undo_window_seconds` 一致） |

**关键结构性事实**：服务端「已执行的提案不进 `proposals`」（`agent.py:AgentResult` 的 docstring），
所以**自动执行那一轮客户端手里没有卡**——有卡的那一轮，执行必然发生在确认之后、走的是上表第二行。
因此卡上的凭据语义上是 `done.executions` 的同一个东西，**取数点在 `/ai/execute` 的返回**。这一条
写进了 `ExecutionEvidence` 的 docstring，避免后人以为「凭据是从 done 帧搬来的」。

回执里的 `transaction_ids` 在 v2 车道承载的是**被影响的实体 id**（改 / 归档是同一个 id 的新版本，
新建是新 id；`service.py:788` 的注释），所以它只当**凭据与计数**用，不当交易 id 用。

### 2.3 为什么凭据必须是一个新字段，而不是复用 `proposalStatus`

`proposalStatus: 'committed'` 的含义是「**不在途**」——纯文本消息（`appendAssistantMessage`）也带它，
`settleStream` 的纯文本回执也带它。把它当回执，就是 REQ-67② 记的那个形态：**卡上说「已完成」，
但它只是一句话**。故新增 `AssistantMessage.executions?: ExecutionEvidence[]`：**有凭据才敢说已执行**，
没有就保守报「未执行 · 待确认」（与架构 §7.4「不确定时倾向拒绝」同一取向）。

**旧数据怎么办**：旧版本落盘的 v2 消息没有这个字段 → 历史卡显示「未执行 · 待确认」。
**这是如实，不是兼容性妥协**——那份快照里确实没有任何「写成功了」的事实。设备上两条老 v2 卡
现在就是这么显示的（§五）。

### 2.4 设备执行 op 的凭据

`DEVICE_OP_DISPATCH` 那四个 op 服务端**只挂起不执行**（`tools.DEVICE_EXECUTED_OPS`），没有服务端回执。
凭据是本机那次桥调用**成功返回**，`lane: 'device'`、`entityIds` 恒为空；卡上因此说
「✓ 已在本机执行」而不是「影响 0 项」（后者读起来像什么都没发生）。

## 六、发现并登记（本卡不修）

1. **混合轮里挂起的卡会被吞掉（结构性观察，未取证）**：`settleStream` 的
   `if (done.executions.length > 0) { …; return }` 在 `showPendingApproval` **之前**返回，而
   `enqueueApproval` 已经入队。若某一轮**既**在 Step 1 自动执行了 A、**又**在 Step 2 挂起了 B，
   B 会进队列但**永远不出卡**（用户看不见、也无法确认，直到下一次 `showPendingApproval`）。
   服务端的「互斥」是**逐提案**的（已执行的不进 `proposals`），不是逐轮的；R-PROD-27 又说明
   「Step 1 直接执行」是模型的常见形态。**需先取证**（造一轮混合真机现场）再决定修法，
   且它动的是确认门，本卡按红线未碰。
2. **v2 的 `undone` 没有生产者**：撤销入口仍只有 v1 卡的内存态通道（`activeTxIdsRef`），
   v2 消息不写 `transactionIds`，故 `undoExecution` 永远匹配不到它。本卡把渲染与用例就位，
   等撤销链路覆盖 v2 时不必再改卡。
3. **`error` 态原先指向一个不存在的按钮**（顺手如实化）：原话「可以拒绝这张卡后重说一次」，
   但拒绝按钮**只在待确认态存在**，失败态两边都没有按钮。改成「❌ 执行失败，请重说一次」——
   只陈述能确证的事实（桥调用没成功），**不声称「本轮没有写入」**：桥调用失败可能是超时，
   服务端那时可能已经写了。
4. **自动执行那一轮的回执文案对 v2 非记账 op 说谎（未修，登记）**：`settleStream` 对
   `done.executions` 一律渲染「已记录 N 笔交易」，而 v2 非记账 op（`account_create` /
   `budget_set` / `meta_set` …）的回执实体根本不是交易，N 取的是**实体数**——
   「把交行卡分类到储蓄卡」会被回执成「已记录 1 笔交易」。本轮**不改**：客户端在自动执行那一轮
   **拿不到 op**（提案不随 `executions` 下发），改文案需要先决定「回执要不要带 op」这个契约问题，
   属服务端面；且它不在本卡「卡上明示」的射程内。**建议**随 T18-6/T18-7（它们让非记账 v2 op 变常见）
   或收口卡一并裁决。
5. **T18-2 建议的收编项**（`AssistantPage.tsx:419` 图片链路仍是入队式 `bridge.triggerSync()`）：
   本卡**未做**——它既不在本卡改动清单里，也不是本卡独有的文件窗口（T18-1 已交付、T18-3 之后
   该文件仍由收口卡看管）。原样留给收口卡。
