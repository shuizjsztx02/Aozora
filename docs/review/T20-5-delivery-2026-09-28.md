## 三、设计决策（六条）

### 3.1 二级「先父后子」：`seedCategory` 回传 id

卡面①定死：父 id 是 `UUID.randomUUID()`，不能预置。故 `seedCategory` 的返回类型从 `Unit` 改为 `String`（新插入行的 id），`seedCategoryTree` 拿它作二级的 `parentId`：

```kotlin
private suspend fun seedCategoryTree(seed: SeedCategory, kind: String) {
    val parentId = seedCategory(seed.name, kind, seed.icon)
    seed.children.forEach { seedCategory(it.name, kind, it.icon, parentId) }
}
```

**入队顺序即父先子后**：`enqueueInsert` 是 FIFO，服务端 `SyncService.push` 按 `for mutation in mutations` 顺序逐条 apply（`sync/service.py:82`）→ 二级到达时父已落库，不会撞 `categories.parent_id` 的自引用 FK。

### 3.2 ★ 存量补齐：按「kind + name」diff，且二级挂到**已有的**那条一级上

决策 #9 定死「只增不改不删」。实现有**两个容易写错的点**，本卡都钉住了：

**（a）二级不能挂到新建的影子父上。** 存量账户已有「交通」（老 id），补齐时如果无脑新建一棵树，会造出**第二个「交通」**并把「打车」挂到它下面 —— 用户会看到两个「交通」，其中一个是空壳。修法：diff 命中已有一级时，用**已有那条的 id** 当 `parentId`：

```kotlin
val parentId = existing[kind to seed.name]?.id
    ?: seedCategory(seed.name, kind, seed.icon)
```

实测证据（模拟器 v1 存量账户）：5 个交通二级的 `parentId` 全部 = `ba91cc01-6cd8-44db-bf41-afadc380992f`，**与补齐前的「交通」id 逐字相同**。

**（b）已存在的分类不补 icon。** 老账户的 13 个分类 `icon` 全是 NULL；「只增不改」意味着**不给它们回填图标**——旧分类的图标由渲染层 `getCategoryEmoji` 兜底（这正是 ④ 要扩兜底表的理由）。实测确认：补齐后「餐饮 / 交通 / 工资」的 `icon` 仍是 NULL。

**幂等的实现**：版本键与分类同事务写（`db.withTransaction`），崩溃即整体回滚。分支结构：

- 分类表为空 → 全新种 + 写版本键（新账户 / 用户删光分类后的重置，与旧行为一致）
- 分类表非空且版本键落后 → 补齐 + 写版本键
- 分类表非空且版本键已是 `"2"` → **整段跳过**（零查询、零写入）

### 3.3 版本键走 Repository 自管，不进 meta 白名单

`category_seed_version` 照 `master_book_id` / `personas_seeded` / `cloud_entities_uploaded_v1` 的既有做法：只由 Repository 写，不进 `SyncablePreferenceKeys`，因此**不上云、也不在 `MetaWhitelist.KEYS`**。守护用例 `MetaWhitelistTest` 是**精确集合相等**断言，本卡未触碰 `KEYS` → 该用例一字未改即通过（即「meta 白名单仍 11 键」的机器化判据）。

选它而不选「每次冷启动都跑一遍 diff」的理由：diff 要读全表（60 行）再比 53 个名字，虽然小，但冷启动路径在 `Application.onCreate` 的 `runBlocking` 里，能省则省；更重要的是**语义**——「种子版本」是设备自管量，与 `personas_seeded` 同类。

### 3.4 ★ 新旧种子名并存的别名解析：`altNames` 候选机制

决策 #10 定死「两套名字并存是刻意接受的」。名字面没冲突（`uq_categories_scope_name` 含 `name`，且 NULL `book_id` 在 PG 里不参与唯一性判断），但**别名表**有：一条别名只能写一个 `categoryName`。

具体冲突点：老账户叫「红包收入」，新账户叫「收红包」，而用户打的是「红包 200」。若 `{ keyword: '红包', categoryName: '红包收入' }` 只写旧名，新账户（没有「红包收入」）会解析失败并回退到占位 id `cat-gift-income` —— 而占位 id 不在服务端授权的分类 UUID 集合内，发给 `/ai/execute` 会被判幻觉拒绝。

**修法**：`BuiltinAlias` 增可选 `altNames: readonly string[]`，解析时按「主名 → altNames」顺序在用户真实分类里找同名项，**谁在库里就用谁**：

```ts
function resolveAliasTarget(alias, categories) {
  for (const name of [alias.categoryName, ...(alias.altNames ?? [])]) {
    const hit = categories.find((c) => c.archivedAt === null && c.name === name)
    if (hit) return hit
  }
  return undefined
}
```

这样**两代账户都对**：老账户命中「红包收入」，新账户命中「收红包」，跳过补齐后的老账户（两套名都有）命中主名（旧名）——可接受。同类处理 11 条：`红包` / `奖金` / `房租` 等 7 条居住词 / `话费` `网费` / `药` `医院` `看病`。

**旧名条目一律保留**（决策 #10）：`娱乐` / `居住` / `通讯` / `学习` 相关的条目关键词一个字未动，只在其上加 `altNames`。

### 3.5 ★ 主动放宽一处：`altNames` 的引入是对卡面⑤的**结构扩展**

卡面⑤只写「补新名别名（旧名保留）」，没说可以改别名表的结构。本卡判断：**「旧名保留」与「新名可用」在单值 `categoryName` 下不可兼得**（见 3.4），故必须扩结构。选择「加可选字段」而非「把 `categoryName` 改成数组」，是为了让 34 条**不需要候选**的旧条目**一字不改**（diff 里它们不出现），把改动面压到最小。

这正是 CLAUDE.md「外科手术式改动」的口径：36 条老条目中 25 条零改动。

### 3.6 ★ 对卡面的一处**主动扩展**：bootstrap 清空实体时一并作废版本键

**这是本卡引入的缺陷，本卡自己收拾**（第二个提交 `e8050f9`）。

**问题**：`category_seed_version` 的存在，让「本地已补齐到 v2」成为一条**可被读到的断言**。而 `Repository.clearAllEntities()`（bootstrap 重建路径）会清空 `categories`、**却把 `sync_meta` 留着**（该文件的注释明写「bootstrap 重建实体不清 `sync_meta` → 跨重建存活」；它只把 `cursor` 置 0）。于是重建之后：

- 本地分类 = 服务端快照那一批（可能只有 13 个旧分类）；
- `category_seed_version` 仍是 `"2"` → 下次冷启动**跳过补齐**；
- 补齐的那几十条要靠 `pending_mutations` 的 push → pull 兜回来；**mutation 一旦进终态失败就长期缺失**。

**可达性**：不是理论问题。`SyncEngine.runBootstrapForced()` 由前端 `sync.trigger`（`forceBootstrap=true`）主动调用（`AozoraBridge.kt:1097`），**此时本地是有数据的**。自动路径（`needsBootstrap()`）要求 `cursor == 0` **且本地无 book**，那条路径下本地分类本就为空，会走「全量重种」分支，不受影响。

**修法**（与同函数里的 `cursor = 0` 同源）：

```kotlin
db.syncMetaDao().delete(SyncMetaEntity.KEY_CATEGORY_SEED_VERSION)
```

作废后冷启动重跑一次 diff —— 快照里已有的名字跳过、缺的补回，**幂等且自愈**。用例 `clearAllEntities_invalidatesCategorySeedVersion` 钉住。

**反方论点（供收口轮否决）**：卡面③只写「`ensureSeedDefaults` 段 1 改造 + 存量补齐」，`clearAllEntities` 不在卡面改动点上，此改动属**越出卡面**。本卡的判断依据是「这是本卡引入的新缺陷面（版本键以前不存在），不修则版本键在重建后**说谎**」，且修法只有一行、在独占文件内。若认为应当留给 T20-7，回退这个提交即可，不影响其余交付。

### 6.1 ★ 一条**无法**被变异捕捉的设计（诚实记录）

设计变异 ② 的初稿时发现：**版本键 `category_seed_version` 的「跳过」行为，与 `backfillSeedTree` 自身的 diff 幂等性在当前 v2 下不可区分**。

具体地：把段 1 的 `else if (版本键落后)` 改成无条件 `else`（即每次冷启动都跑补齐），结果**仍然是幂等的**——因为 `existingCats` 是当次快照，第二轮时所有名字都已存在，diff 全部跳过，不会插入任何行。所以「第二次冷启动后分类集合不变」这条断言**对这个变异不红**。

版本键在当前版本下的真实作用只有两条，都不是行为断言：

1. **冷启动短路**（性能）：键已是 `"2"` 时整段跳过，省掉「读 60 行 + 比 53 个名字」；
2. **v3 的挂钩**（语义）：将来种子再扩到 v3 时，靠这个键触发第三次补齐 —— 若无此键，v3 的新分类对已补齐到 v2 的账户**永远不会补**。

故本卡**没有**为版本键编造一条「变异后必红」的用例（那会是假绿的另一种形态：断言与触发点不匹配）。这一条作为设计说明记在此处，而非作为已验证项。

**副产物**：本轮把幂等用例的断言从「数量不变」升级为「**id 集合逐字相等**」——防的是「删了又建」式的假绿（数量相同但换了行）。

## 七、已知限制（挂账）

1. **多设备并发补齐的重复行**：两台设备各自对同一账户补齐时，会各自生成一套新分类（名字相同、UUID 不同）。服务端 `uq_categories_scope_name` 因 `book_id IS NULL` 在 PG 中不参与唯一性判断，**不会拒绝**，结果是库里出现两套同名分类。这与旧种子的既有行为**同源**（旧种子同样是「本机 UUID + 名字 diff」），本卡未引入新形态，但分类数量放大后触发面变大了。→ 建议归入 T20-7 收口时的风险册（决策 #10 的「新旧名并存」条目可合并写）。
2. **补齐会在首启产生 47 条 mutation**：存量账户第一次冷启动时，`pending_mutations` 会一次入队 47 条 `category.insert`。它们随下次 push 上行；服务端逐条 apply（每条一个 savepoint），不会毒丸整批。但**离线设备**上这 47 条会一直挂着——与既有种子的 13 条同源，只是量变大。
3. **`category-emoji.ts` 的兜底是「已知名穷举」**：86 键覆盖了新种子全部名字 + 旧名 + 一批高频自建名，但**用户自建分类名仍可能落回 💰**。这是该表的设计上限（按名映射），不是缺陷。
4. **旧分类的图标不会回填**：按决策 #9「只增不改不删」，老账户的「娱乐 / 居住 / 通讯 / 学习」等**永远**走兜底表而非实体 `icon` 列。若将来要回填，需要新的版本键语义（本卡刻意不做）。
