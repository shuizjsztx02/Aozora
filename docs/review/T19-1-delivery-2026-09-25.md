## 二、被改掉的现状（复核入库结论 + 三处入库未点名的实况）

入库已核实「服务端没有这一列、两个写入分支都不读、序列化也不出」（dev 库 `\d categories` 实测 10 列无 icon，对照 `books` / `accounts` 都有）。**修复前基线已复现**：本卡开工时该表仍是 10 列、alembic head = `0022_account_balance_type`。

三处**入库描述与代码实况不一致**的地方，本卡按实况落地：

1. **入库说「增量 pull 有保护（保留本地自定义图标，避免被 pull 冲刷）」——保护是真的，但它的成因不是「保留」，而是「读不到」。** `SyncModels.toCategory`（`SyncModels.kt:63`）**根本没有 icon 参数**，`entity.icon` 恒为 null，于是 `localIcon ?: entity.icon` 实际恒等于 `localIcon`。**这意味着两端化后如果不改这一处，服务端就算出了 icon 也永远下不来** —— 旧写法的语义是「无条件保留本地」，与 T19-2 的验收（「AI 改图标 → 设备同步一致」）正面冲突。
2. **入库说 bootstrap 走 `serverChangeMapToCategory` 让 `icon = map["icon"]` 恒为 null。** 实况是那一行**本来就写了** `icon = map["icon"]`（`Repository.kt:1928`）—— 它恒为 null 只是因为服务端不出该键。**两端化后它自动生效，无需改动**（见 §5.4）。
3. **照片图标的 wire 护栏在 book / account / savings / persona 都有，`categoryToJson` 是唯一无条件 `put("icon", …)` 的。** 这正是决策 #3 说的毒丸：服务端一开始 `_validate_name(icon, 64)`，一个用相册照片当图标的分类就会让**整批** push 422。

## 三、设计决策（四条）

### 3.1 服务端：加列 + 三处接线，逐字照 book / account 的现成写法

- 列：`VARCHAR(64) NULL`，无默认值（存量行保持 NULL），迁移 `0023` 只 `add_column` / `drop_column`。
- `_apply_insert`：`if payload.get("icon") is not None: _validate_name(payload["icon"], 64, "icon")`，然后 `icon=payload.get("icon")`（与 book / account 逐字同形）。
- `_apply_update`：`if "icon" in payload:` —— **键在场才改**，显式 `null` 可清。这条是给**尚未升级的旧客户端**的：它们的 payload 里没有 `icon` 键，无条件写入会把用户已有的图标清掉。
- `_serialize_entity` 的 Category 分支增 `"icon"`。**bootstrap checksum 不会失配**：客户端按**收到的原始 JSON**（`rawEntityMap`）重算，新增键两侧一致（与 T18-5 的 `account_type` 同一先例，注释已写在代码里）。

### 3.2 跨端只承载 ≤64 字符（ADR-014 决策 2）

护栏**必须与两端化同卡落地**（决策 #3），否则照片图标变整批 push 的毒丸。服务端 64 上限**不放宽** —— 放宽会让 48KB 的 data URI 灌进 change 表与每一份 bootstrap 快照；照片图标「仅本机可见」是 T9-6 / REQ-13 决策 #7 以来的既有口径，本轮无诉求推翻。

### 3.3 客户端 push 侧三分支（`categoryToJson`）

```
icon 为 null            → 显式 put JSON null（服务端「键在场才改」）
icon 长度 > 64          → 省略键（照片，防 422 毒丸）
其余                     → 原样上行
```

**`null` 之所以必须显式上行**：`IconPicker` 里有一个真实的「清除自定义图标」按钮（`IconPicker.tsx:75-80` 的 `onChange(null)`）。若沿用「省略键」的写法，服务端的「键在场才改」会让清除操作**静默失效** —— 保存后一切照旧，下次 pull 旧值又回来。

### 3.4 客户端 pull 侧三态合并（ADR-014 决策 4，本卡最容易抄错的地方）

| 本地 | 服务端 | 结果 | 理由 |
| --- | --- | --- | --- |
| `data:` 照片 | 任意 | 保留本地 | 照片仅本机可见（决策 3.2） |
| 任意 | 非 null | **服务端权威** | AI / 跨设备改图标**只走这条** |
| 任意 | null | 保留本地 | 服务端 NULL = 「无信息」：存量行全是 NULL，照单全收会在一次 pull 后抹掉本地 emoji。与 `accounts.account_type` 同口径（ADR-013 决策 4） |

实现在 `Repository.kt` 的 category 分支，形如 `savings_goal` 的 `if` + `account_type` 的 `?:` 组合。

**三条环境坑（供后续会话复用，均非本卡缺陷）：**

1. **模拟器网络缺 `VALIDATED`** → WorkManager 的同步任务永远 RETRY。**比入库配方更省的做法**：`settings put global captive_portal_mode 0`（禁用探测）+ `svc wifi disable/enable`。注意**不要**同时设 `captive_portal_https_url` 指向 HTTP 探针 —— 那会让网络停在 `PARTIAL_CONNECTIVITY` 而不是 `VALIDATED`。
2. **`adb shell cat` 拉 SQLite 会损坏文件**（换行转换）→ 必须用 **`adb exec-out`**；且要**连 `-wal` / `-shm` 一起拉**，否则读到的是落后于 WAL 的旧值（本次差点据此误判「cursor=0」）。
3. **★ 用桥命令注入测试数据时，`mutationId` 必须是合法 UUID**。本次用 `m-<epoch>` 注入 → FastAPI 的 `uuid_parsing` 校验直接 **422** → **整批 push 失败** → WorkManager 无限 RETRY，而客户端 `SyncHttpException` 分支**不打日志**（只有 emit），服务端 uvicorn 也**不输出 warning / access log** —— 表面症状与「本卡改动导致 push 失败」完全一样。真正的定位手段是**在 8000 上挂一个记录型代理**（本次用 8002 + 改 reverse，避开别的会话占用的长驻 uvicorn）。

> **设备侧的一次误判已排除**：本次一度怀疑「带 icon 的分类推不上去」，用**完全相同的 payload**（一字不改，含 `ownerId: "local"`、`version: 1`）对服务端复现 → **200 applied**，证明本卡改动与那次失败无关。

### 5.4 与卡面原文的两处偏离（均为落到实处的判断，非省略）

1. **卡面④「bootstrap 侧补本地 icon 保护（照增量 pull 的写法）」——不做，理由是它无事可做。** `applyBootstrap` 只在 `SyncEngine.runBootstrap` 里、且**紧跟在 `clearAllEntities()` 之后**调用（`SyncEngine.kt:280` → `:289`），本地此时已空，取不到旧值也无从保护；而它用的是 `serverChangeMapToCategory`，那一行**本来就写了** `icon = map["icon"]`，两端化后自动生效。**入口要的「bootstrap 不丢图标」由两端化本身达成**，不需要额外代码。真正的缺口在 `SyncModels.toCategory`（§2.1）。
2. **卡面②写「显式 null 可清」，客户端侧我选了「null 显式上行」而不是「省略键」。** 依据是 `IconPicker` 存在真实的「清除自定义图标」操作（§3.3）。若照「省略键」写，清除会在服务端静默失效。

## 六、已知限制与挂账（**交付面**，风险册落笔归 T19-9）

1. **照片图标不上云**：换机 / bootstrap 重建后丢失（服务端侧从来没有过它）。这是 T9-6 / REQ-13 以来的**既有行为**，本轮只是把它写成显式契约（ADR-014）。
2. **「清空图标」不能跨设备传播**：服务端 NULL 同时是「从未设置」与「他机清空」两种成因，而 pull 侧一律当「无信息」（否则存量 NULL 会大面积抹掉本地 emoji —— 两害相权）。A 机清空后，B 机 pull 到 NULL 仍保留自己的旧图标，直到 B 走一次 bootstrap。消除它需要显式哨兵值，本轮不做。
3. **bootstrap 会丢「从未上行过」的本地 emoji 图标**：`clearAllEntities()` 先清库，服务端仍是 NULL 的行随清空消失，随后由同一轮的 `migrateCloudEntitiesUp` 入队上行找回。与 ADR-013 后果 1 同形。
4. **`categories` REST 模块（`server/src/modules/categories/schemas.py`）仍不带 icon**：本卡只做同步面；AI 读工具 `category_list` 出 icon 归 **T19-2**。

> **给 T19-2 的输入**：列与同步已就位（PG 已迁移到 `0023`）；`category_list` 出 icon、工具增参、v2 payload、`proposal_ops` 落 icon 四处按卡面走即可；**注意 v2 payload 的 icon 同样受「键在场才改」约束**（未给 icon 时不得清空现有值，与 `account_update` 同口径）。
