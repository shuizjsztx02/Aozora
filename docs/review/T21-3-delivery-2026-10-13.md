## 二、设计决策与落地

### 2.1 文档先行：新增 `mergeKey` 列（`docs/architecture/data-model.md`）

**T21-1 写的表结构里没有 `mergeKey`。** 落地 L2（跨通道同笔）时发现它不可省，理由是两条，写进了 data-model 的列说明里：

1. L2 判据是 `hash(方向 + 金额分 + 分钟级时间桶)`（ADR-016 决策 5）。**采集层拿不到方向与金额**——那是解析才有的量，而 ADR-016 决策 4 明令采集层不做解析。若不在表里存这个键，L2 的候选查询就只能在读取路径上从 `rawText` 反解金额与方向，等于把解析器拖进读取路径，且**无法建索引**。
2. 它与 `dedupeKey` 是同一对称位：一个是 L1 的唯一键，一个是 L2 的查找键。

按 `AGENTS.md`「数据结构变更必须先改对应文档再动代码」与 `稳定性守则 §2.4`，**先改 `docs/architecture/data-model.md` 再动 entity**。同时把两处口径补齐：`mergeKey` 的**写入时机**（解析后回填）与 `multi_source` / L3「疑似重复」是**派生量、不另设列**（原文只写了"标 `multi_source`"，没说到哪儿标）。

### 2.3 去重（`DedupeKeys.kt`）

★ **L1 的时间输入只进到分钟桶，不进毫秒。** 这是本卡唯一一处"卡面没写、但不做就会失效"的判断：通知重复回调的 `postTime` 本来就是同一个值，**但无障碍每次 `TYPE_WINDOW_CONTENT_CHANGED` 的 `eventTime` 都不同**——用毫秒当输入等于没去重，而这一级恰恰是 ADR-016 决策 5 专门点名的必需品。代价（跨分钟边界的一次重复会漏过 L1）记在 §五挂账，交 T21-4 侧页面签名防抖兜底。

`eventIdentity` 由调用侧给：通知通道传 `StatusBarNotification.key`；无障碍通道传窗口/页面标识。

### 2.4 通知通道（`NotificationFilter` + `AutoBookNotificationListener`）

预筛是**纯函数**，判据顺序 = 先排除再取字段：来源集合 → 空文本 → 验证码 → 广告 → 金额 → 方向。

两处判断值得记下来（都是"不这么做就会静默出错"）：

- **方向取自事件词，不取品牌词。** "微信支付-退款到账"里的"支付"是品牌构件；据此判成支出会把**退款记成消费**。故支出表只收 `支付成功 / 已支付 / 已成功付款 / 扣款 / 消费 / 支出 …`，"支付"单字不入表。
- **广告守卫要留豁免口。** 营销文案爱写"消费满 100 元可用"这类带金额的句子（既有"消费"又有金额），但真交易里也会出现"优惠券已核销"。故判据是「命中广告标记 **且** 未命中**支付完成类**强事件词」——强事件词表刻意**不含**"消费/支出"，否则营销句会给自己豁免。

服务本体只做"extract extras → 预筛 → 落库"，**不做网络、不做解析**；两道闸门（总开关 → 来源集合）在协程里先过，原文**不写任何日志**（`security.md`）。

### 2.5 开关与来源清单（设备本地自管键）

决策 #9 说开关与配置走 Repository 自管 meta 键。**键常量与读写在本卡落地**（`SyncMetaEntity.KEY_AUTOBOOK_ENABLED` / `KEY_AUTOBOOK_SOURCE_PACKAGES` + `AutoBookRepository` 的四个方法），T21-5 的 `set_enabled` 与 T21-7 的来源清单直接消费——因为 `db/` 簇归 T21-3 独占，那两卡加不了键。**`MetaWhitelist.KEYS` 仍 11 键**（不碰）。

### 3.3 设备取证（Pixel_7_API_36 · Android 16 / API 36 模拟器）

**取证通道的说明（重要）**：模拟器上无法让 `com.tencent.mm` 真的发通知，故用 `adb shell cmd notification post` 注入，并把发通知的 `com.android.shell` 作为**用户勾选来源**写进 `KEY_AUTOBOOK_SOURCE_PACKAGES`——走的正是 T21-7 将来要写的那条路径（"从已安装应用添加"）。**不是**改代码放宽来源。落库读数一律经 `run-as com.aozora.app sqlite3`。

## 五、已知限制与挂账（交下游）

1. ★ **L1 的分钟桶边界**：跨分钟边界的一次重复投递会漏过 L1（见 §2.3）。**交 T21-4**：无障碍侧建议在服务内保留"上次页面签名 + 时间"，同页一分钟内不重复投递；通知侧无此问题（同一通知的 `postTime` 稳定）。
2. **`mergeKey` 由解析侧回填**：本卡只提供 `mergeIfSameTransaction(captureId, direction, amountCents, merchantKey)` 与 DAO 的候选查询。**T21-6 必须在每行解析完成后都调用它**（即使当时没有候选——回填本身是后到者能找到先到者的前提）。
3. **DAO 一次给齐了下游所需的 13 条查询**，其中 `applyResolution` / `lastCommittedByMerchant` / `listSameWindowOtherChannel` 在本卡**没有调用方**（分别对应 T21-6 的状态推进、商户记忆、L3 提示）。它们不是投机代码：`db/` 簇归 T21-3 独占，下游卡加不了。
4. **未走真机**：取证在模拟器上完成。T21-3 卡面要求的是"真机/模拟器"，且通知通道与机型无关；**真机取证留 T21-9 收口**（与无障碍通道一并做，那时才需要微信/支付宝真支付）。
5. **`isOngoing` 的通知被跳过**：正在进行的通知（下载/导航/播放）不可能是支付事件，这是刻意收窄——若将来发现某渠道的支付通知带 ongoing 标记，需回来改这一条。
6. **来源清单里的"短信通知来源"**：勾选的是**发通知的银行 App**，与申请短信权限无关（`<uses-permission>` 集合零增长由用例钉住）。这一口径在 T21-7 的 UI 文案里必须写清，否则用户会以为勾了就等于授权短信。
7. **服务被系统停用**（授权仍在、服务被 kill）这一态**本卡未处理**：Listener 被系统重新绑定是系统行为；"已授权但服务停用"的三态判定归 T21-7（决策 #10）。
8. **并发合并的守护已下沉到 DAO**：`markMergedInto` 是**条件更新**（`WHERE mergedInto IS NULL`）并返回受影响行数，`mergeIfSameTransaction` 在返回 0 时让路（`NoCandidate`）。这条本卡先加了——"两条通道同时抓到同一笔"是本表最核心的场景，若 T21-6 的编排是**逐行并行**（而不是串行循环），不加这一条就会让两行互相指向、谁也没真合并掉，且**不留任何报错**。DAO 那一层有确定性用例；仓库层「让路」分支只在真并发下可达，**故没有确定性用例**（不伪造并发绿）。**T21-6 侧仍建议顺序处理**，条件更新只是兜底。
