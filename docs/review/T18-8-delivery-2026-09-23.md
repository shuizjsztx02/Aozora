## 三、改动清单（逐条对卡）

### 3.1 在线判定加固（卡 ②）

**新增** `app/src/platform/cloud-reachability.ts`（唯一新代码模块）：

- **判据分两层**：①`navigator.onLine === false` → 直接判不可达，**不做探测**（省掉必然白等的一轮超时）；②否则**真打一次 `auth.me`**。
- **失败语义**：`auth_lost` / `server_error` 都算**可达**——服务端答复了，只是这次请求不被接受（那属于 AI 链路的报错文案，不该被译成「离线」）；只有 transport 层（`network_error` / `timeout` / 无 code 的异常）才算不可达。
- **短超时**：`PROBE_TIMEOUT_MS = 4000`，经 `getMe({timeoutMs})` 下发。桥默认 10s 会把冷启动第一次输入拖到十秒。
- **缓存 + 三个失效时机**：TTL 30s；云端调用失败时 `invalidateCloudReachability()`（一次失败即说明这次的「可达」不作数了）；系统 `online`/`offline` 事件（用户插拔网络立刻纠正）。
- **`bridge.isAvailable()` 已从「在线判据」里剥离**（卡 ② 要求）：它现在只是一条**环境前置**（纯浏览器开发态 / JS 与旧 APK 不同步时，云端不可达），不再冒充网络状态。

### 3.2 落点判据（卡 ③⑤）

`use-assistant.ts` 删 `needsAiRouting`（四条启发式：操作句式 / 置信度 / warnings / chat 兜底）与 `CONFIDENCE_THRESHOLD`，**新增导出纯函数**：

```ts
export function routeInput(text: string, cloudReachable: boolean): 'cloud' | 'local' | 'offline-canned'
```

`submitInput` 的新形态：`await isCloudReachable(bridge)` → `routeInput` → 三条路各自就地收尾。**离线时连 `parseInput` 都不调用**（「关闭 NLU」按字面落地）；在线时一律走 agent/单发，**本地解析结果完全不参与**。

### 3.3 失败口径统一（卡 ④ / 决策 #7）

| | 改前 | 改后 |
| --- | --- | --- |
| 单发链路 | 一次性轻提示 + **`finalProposal = localProposal` 回落本地写库**（操作句例外：canned） | **中断 + 重发入口 + 零写入**（与 agent 流转同形态） |
| agent 流转 | 中断 + 重发（`settleStream` 的 `error` 分支，未变） | 同左 |

统一到**后者**。理由：诉求逐字要求「在线时关闭 NLU」，回落等于把它又打开；而本地解析恰好在复合句 / 操作句上会记错（R-PROD-28 的两种形态），那正是本轮要拆的东西。设备侧已实测该结局（§五.4）。

**连带修正（同源、必须一起改）**：`settleProposal(proposal, fromCloud)` 抽出两条路共用的落库尾部；`fromCloud=true` 时服务端校验判无效**不再换成本地结果**，而是返回 false 交 `failCloudTurn` 收尾——服务端契约本就是「verdict 非 accepted/rejected_low_confidence 的提案，客户端**不得执行**」（`routes.py:157`），原先那行「换成本地解析继续写」既违反契约，在线时也**无本地结果可换**（NLU 已关）。

## 五、设备走查（模拟器 `Pixel_7_API_36` + CDP 驱动真实输入）

**环境**：debug 包（`AI_AGENT_CLIENT_ENABLED=true`，桥具备流式能力）+ 本机 uvicorn（`AI_AGENT_ENABLED=true`，provider `deepseek-flash`，库 `aozora` on `native-bills-postgres-1`）。驱动脚本 `.scratch/t18-8.mjs`（未提交）。
**判别手段**：①UI 形态（`step-stream`/`streaming-bubble` = agent；`confirmation-card` 秒出 = 本地快路径）；②服务端行的 **`source` + `note` 对**——`ai`/`咖啡` = 服务端执行，`nlu_ai`/`记一笔咖啡` = 本地执行。

| # | 状态 | 操作 | 实测 |
| --- | --- | --- | --- |
| 1 | **在线（可达）** | 「记一笔咖啡 25」 | **走 agent**：`streaming-bubble` + `step-stream`，**首帧 920ms**；收尾「记好了：今天咖啡 25 元，归到餐饮。已记录 1 笔交易」；服务端行 `2500 / 咖啡 / source=ai`。**这是本轮修好的那一格**——旧判据下这句会被本地 NLU 直接记账，AI 根本看不到 |
| 2 | **离线（判据层）** | 渲染进程断网（`Network.emulateNetworkConditions{offline}`，`navigator.onLine=false`）→「记一笔咖啡 25」 | **本地快路径**：152ms 出 v1 卡、**无**步骤卡/流式；另发「把咖啡那笔改成 30 元」→ 原文回 `断网时我只能记新账哦，查询、修改、删除和闲聊要联网后再试试`（`AI_OFFLINE_CANNED`）。**判别力**：该断网只影响 WebView，**Kotlin 侧照样能打到服务端**——若代码仍走云端会拿到模型答复，实际没有 |
| 3 | **系统误报在线 + 服务端不可达** | `navigator.onLine=true`（模拟器网络正常），把 debug 包的 base URL 指向**黑洞监听**（`10.0.2.2:8001`：accept 后不回应）→「记一笔咖啡 25」 | **卡在 4031ms 出现**（= 探测的 4s 短超时命中）且落点是**本地快路径**（无步骤卡）；其本地行随后被推上服务端（`source=nlu_ai`）。**这一条同时证明**：在线判据真的做了网络往返（否则不会等 4s）、短超时确实生效（不是桥默认 10s）、判决方向正确 |
| 4 | **在线 + 云端失败** | 把设备用户置 `frozen`（`/me` 故意不受冻结守卫 → 探测**通过**；`/ai/*` 返 403 → **云端失败**）→「记一笔咖啡 25」 | **统一结局成立**：流式中断 → 消息「⚠️ 连接中断，本轮未完成」+ 横幅「⚠️ 连接中断，这一步没做完」+「重发」按钮；**零写入**（冻结窗口内服务端无新行）。走查后已把用户 `status` 还原为 `guest` |

## 七、已知限制与挂账

1. **`OP_SENTENCE_RE` 没有整体下线，只砍了它在线的职责**（偏离卡 ⑤ 的字面）。卡片写的下线理由是「它们存在的理由正是『在线分流不准』」——这对**在线**成立，但**离线**时它仍是必需品：离线没有云端可去，少了这道守卫，「把昨天的午饭改成15块」会被本地解析成新账**直接落库**。故保留为**离线守卫**并在代码里写明了理由；`needsAiRouting`（在线分流那套）已如期删除。
2. **离线的误记是已知代价**：语料 97 条里，离线态有 **7 条非记账意图会被真写成一笔账**（快照在 `ai-tool-matrix-device-gate.test.ts` 的 `OFFLINE_MISPARSE`）。**这不是本轮引入的**——旧代码离线同样落到本地写（`needsAi` 只在在线时才起作用），只是以前没人量过。本地解析器本身的缺陷（「N 号」当金额、复合句丢字段）仍归 `domain/nlu/*`，本轮不动。
3. **单发链路的失败结局只有单测证据**（§五 末），设备侧构造性不可达。
4. **首次输入多一次探测往返**：缓存冷时 `GET /me` 最坏 4s。未做「进页面预热」（那要动 `AssistantPage.tsx`，属别的卡的串行文件）。在线态实测首帧 920ms（缓存冷），可接受。
5. **`AI_INTERPRET_ERROR_ZH.no_ai_provider` 那条运维文案仍在**，且现在会出现在中断提示的括号里。桥的 `ai.interpret` 从不下发该 code（它只发 timeout/network/429/503/auth_lost），故**当前不可达**；但若将来透传子码，它会以新形态复现 REQ-66 那类「暴露服务商细节」。T18-1 已把该预留分支判给「另案」，本卡未动，**建议并入 REQ-66 的后续**。
6. **建议给 T18-9 的 R-PROD-28 落笔文本**：`R-PROD-28「复合句被本地 NLU 直接消费、附加字段静默丢弃」——**在线侧已消除**（T18-8：在线一律走云端，本地 NLU 仅离线启用）；**离线侧仍在**，7 条语料快照见 `ai-tool-matrix-device-gate.test.ts`。`
7. **并发会话（本卡的实操记录）**：实施期间 T18-6 正在改**同两个文件**（`use-assistant.ts` 的 `formatSigned` 与 v1 config 车道的余额落库、`use-assistant-config.test.ts` 的两条新用例）。两条纪律因此生效：①**提交面分离**——本卡备好了按 hunk 过滤的补丁（丢弃对方 hunk），**恰好在其 `6b276f2` 入库后**才提交，于是无需拆分即天然只含本卡改动（提交前已逐文件核验：9 个改动文件里 `formatSigned`/`balanceCents`/`accountType`/`initBalance` 的残留均为 **0**）；②**板要重测**——T18-6 入库使 HEAD 前移、pytest 基线随之变化，故四板在 `6b276f2` 之上**重跑**（而非沿用实施中期的读数）。
