## 二、契约变更（三处，全部有测试钉住）

### 2.1 `accountType`：`income|expense` 二值 → 自由分类名（与设置页同值域）

- **为什么必须改**：旧口径执行时把二值折成「收入账户 / 支出账户」写入。用户说「把交行卡分类到储蓄卡」，落的却是「支出账户」——**分类信息在写入那一刻就丢了**（REQ-69 现状第 5 条）。
- **落点**：`ai-proposal-builder.ts` 的 `parseAiConfig` 与 `buildConfigPreview`、`use-assistant.ts` 的 `confirmConfig`、服务端 `prompts.py` 的 v1 契约串。
- **一个刻意的放宽**：旧口径 `accountType` **必填**——模型给不出分类时整条 config 回落 chat（开不出卡）。新口径**可省略**（省略 = 不填分类），与设置页「取消选择即不填」同值域。理由：分类是用户没提就不该由模型编的字段，而「必填」会把它逼成猜。
- **长度上限 64** = 服务端 `accounts.account_type` 列宽。超长按「可选字段坏 → 丢该字段」处理，**不截断用户原话**。

### 2.2 `initBalance`：只进回执 → 真落库

- 旧口径执行时明确不落库，回执里写「期初余额 … 请再记一笔写入（账户暂无期初字段）」——**该引导随本卡下线**，改为直接落库并回报「当前余额 ¥5000.00」。
- 语义从「期初」转为「当前余额」（`AccountEntity.balanceCents` 是存量字段，不是流水），预览行标签与回执文案同步改。
- **允许负值**（信用卡欠款）：`toSignedNum` 取代 `toNonNegativeNum`；显示统一走既有 `formatSigned`（`-¥2000.00`，不是 `¥-2000.00`）。

### 2.3 服务端工具：放开「改不动账目余额」

- 删掉 `account_update` 描述里写死的「**改不动账目余额——本工具只改账户自身的名字与图标**」（`tools.py:3428-3431`，卡面点名的那处）。
- `account_create` 增 `accountType` + `balanceCents`；`account_update` 增 `accountType` + `balanceCents`；`proposal_ops` 两个执行体把四字段透传给 T18-5 已备好的 `AccountCreate` / `AccountUpdate`。
- **与卡面文字的一处差异（有意）**：卡面 ② 写「`account_create` 增 `balance`、`account_update` 增 `balance` 与 `accountType`」——本卡给 **create 也加了 `accountType`**。依据是 REQ-69 的用户原话「对话**创建**和修改账户的时候支持修改账户的分类」；只给 update 会让「建一个储蓄卡账户，里面有五千」这一句话变成两步操作，其间还会出现一个既无分类也无余额的中间态。
- **字段名用 `balanceCents` 而非卡面的 `balance`**：注册表里金额参数一律「分 + `Cents` 后缀」（`amountCents` / `targetCents` / `currentCents`），沿用即可让模型复用同一条「元→分」换算指令，也避免与实体字段名分叉。
- **余额恒传绝对值**（决策 #4 的幂等铁律）：参数描述里明写「必须填更新后的绝对值，不要填增减量」。执行体侧 `None = 不修改` 是 `AccountUpdate` 既有的局部合并语义——**0 是合法值（清零），不是「不改」**，这一条有专门用例。

## 三、实现要点与两个坑

### 3.1 `account_balances` 改外连接（口径对齐的代价）

输出改为「期间净额 + 存量余额」双出（决策 #3），并把**所有未归档账户**都列出（原口径只列有流水的账户）。理由：账户可能有**手动校准过的余额却一笔流水都没有**，漏掉它，用户问「新建那张卡里有多少钱」时模型只能回「没有流水」，与账户页显示的数字自相矛盾——这正是决策 #3 要消掉的那类「两个答案」。`note` 随之改写为「净额是所选期间的流水；balanceCents 是当前余额，不随期间变化；两者不等是正常的（差额来自手动校准与期间之外的流水）；问账户有多少钱用 balanceCents」。

### 3.2 坑一：外连接的 ON 必须带关联条件（本卡实施期实现失误，被既有用例当场抓住）

`join(Transaction, and_(*tx_conditions), isouter=True)` 时我把期间/账本条件搬进了 ON，**却漏了 `Transaction.account_id == Account.id`**——原查询这层关联是由 `join(Account, ...)` 提供的，改外连接后没人再提供它。结果是 **Account × Transaction 的笛卡尔积：每个账户都汇总了全部流水**（既有的 `test_account_balances_spans_history_by_default` 等 3 条用例立刻报 3250 → 6250）。教训：搬 JOIN 条件时，**关联条件本身也是 ON 的一部分**，不能只搬过滤条件。

### 3.3 坑二：外连接后 `Account.owner_id` 必须显式过滤（新增用例守护）

账户是**用户级**实体（流水才是账本级）。原查询的归属限定是**间接**的——靠 JOIN 流水（流水挂在账本上，账本挂在用户上）。改外连接后这层间接限定消失，别人的账户会被列出来。本卡显式补上 `Account.owner_id == ctx.user_id`，并新增 `test_another_users_account_is_absent` 守住它（反向验证已确认：删掉这一行该用例立刻红）。

## 七、已知限制与挂账

1. **真机验收未做（本卡的唯一缺口）** — 卡面验收要求「真机账户页设余额 → 列表与明细反映该值；AI 对话改分类/余额 → 库内变更且同步后保持」。交付时设备（`emulator-5554`）**正被另一并发会话占用**（app 在前后台活跃、CDP 9222 开着、`adb reverse` 为空），按并发纪律不抢占；且见第 2 条的**结构性原因**——AI 那一半在设备上目前走不到。**归 T18-9 的真机回归**，配方：
   - 构建安装：`./gradlew :app:assembleDebug` → `adb -s emulator-5554 install -r <apk>`；`adb -s emulator-5554 reverse tcp:8000 tcp:8000`（**新增 reverse 只影响新连接**，改完重启 app）。
   - 客户端半：账户页设余额（含负值）→ 列表行显示 → `adb root` 后经 `sqlite3` 查 `accounts.balance_cents` → force-stop 重启后仍在 → 触发同步后仍在（服务端 `docker exec … psql` 对照 `accounts.balance_cents`）。
   - 网络前提（**本轮踩过的坑**）：WorkManager 同步要求网络为 `VALIDATED`，模拟器默认卡在未验证态 → 宿主机起 204 探针 + `captive_portal_http_url` 指向它 + 重启 wifi。
2. **★ AI「一句话改分类/余额」在设备上暂不可达（结构性，非本卡缺陷）** — 服务端侧（工具 + 执行体 + 授权面）已就位并被 v2 执行面用例覆盖，但客户端当前**不声明 `contractVersion`**（T-M7-05 收口对 R-PROD-31/37/38 的裁决：不开 v2 车道），故设备上的对话仍走 v1 车道，而 v1 可注入的写 op 只有 `transaction_add`（`V1_LANE_OPS`）。**这意味着本卡的 AI 半只有测试面证据，没有设备面证据**——直到尾卡开启 v2 车道；T18-9 的真机回归若发现「AI 改分类没反应」，先核这一条，而不是怀疑本卡的服务端改动。同一形态 T-M7-05 收口时已抓到过一次（生产 compose 未接线 AI Agent → `/ai/agent` 恒 404）。
3. **v1 config 车道放宽了 `accountType` 的必填** — 旧口径下模型给不出 `income|expense` 时整条 config 回落 chat；新口径下缺这个字段仍开卡（只是不填分类）。这是有意的（见 §2.1），但确实改变了「回落 chat」的触发面，登记备查。
4. **`account_balances` 的账户集合变了** — 从「有流水的账户」变为「所有未归档账户」。这是决策 #3 口径统一的必需（否则无流水但有余额的账户问不出答案），但模型可见的行为面确实扩大；`note` 已同步改写，避免模型把 0 流水的账户说成「没有这个账户」。
5. **账户页余额输入未做 UI 打磨** — 无千分位、无货币符号、无 +/- 步进；只做「留空 = 0、格式非法报错不静默改值」。不在卡内。
6. **CI 未能确认（非代码原因）** — 见 §八。
7. **`balanceCents` 未做「手动校准量」的独立呈现** — 决策 #3 只要求口径不矛盾，故 `account_balances` 给「净额 + 余额」两项而未给「差额」字段（差额在期间限定下不等于手动校准量，见 §3.1）。若后续模型仍在此处打转，可考虑补 `adjustmentCents`（仅在全量区间下有意义）。
