## 三、设计决策（三条，均在卡面既定口径内落地）

### 3.1 复用现成机制，不另造订阅（决策 #5 定死）

`useRefreshOnSync`（`app/src/platform/hooks/use-refresh-on-sync.ts`）已同时覆盖「同步轮完成（`lastSyncedAt` 前进）」与「页面重新可见（`visibilitychange` → visible）」。三数据页（HomePage / DetailPage / ReportsPage）自 T18-2 起就在用。**本卡零新增机制**，与决策 #5「复用，不得另造一套订阅」逐字一致。

一处与三数据页的差异：那三处传的是「静默重取」的数据加载函数（`loadData(true)`），本卡传的是一个**带判据的重取**——因为表单页有「用户正在输入」这一态。`refresh` 保持稳定（`useCallback([bridge, applyRemote])`），故 `useRefreshOnSync` 的两条 effect 都不会因 state 变化而重挂监听；`dirty` 与 `savedJson` 的「此刻值」经 `stateRef` 读取。

### 3.2 dirty 保护的判据与**比较归一化**

决策 #6 定死：非 dirty → 静默重取；dirty → 不覆盖、给提示。落地时多了一道卡面没写、但不做就会出错的工序——**比较前先归一化**：

```
nextJson = normalizeProfile(云端 raw)      // = serializeForm(parseStoredForm(raw))
nextJson === savedJson ? 不打扰 : (dirty ? 提示 : 重取)
```

- **为什么必须归一化**：`savedJson` 是 `serializeForm` 的产物（键序固定、空值剔除、未知键丢弃），而云端 raw 是**字节**。两者直接比，键序差异或一个 AI 写的未知键就会被判成「云端变了」→ 反复弹「载入最新」。归一化后比的是**同一口径**的语义值。
- **为什么要有 `nextJson === savedJson → return` 这一条**：`lastSyncedAt` 前进只说明**某一轮同步完成了**，不代表这一轮动过 `user_profile`（记账写入同样会推进它）。没有这条判据，用户每记一笔账、只要表单开着且 dirty，就会看到一次「云端已更新」的假提示。用例「同步轮跑完但这个键没变 → 不打扰」钉住它。

### 3.3 「载入最新」不写回；保存成功清除提示

- **载入最新 = 单向读**：云端与 `sync_meta` 已经是这个值，`applyRemote` 只把表单与 `savedJson` 对齐——**不调 `setMeta`**。写回不仅多余，还会把「用户点了载入」变成一次上行写入（多余的网络与版本推进）。
- **保存成功清除提示**：用户选择继续编辑并保存后，本次保存内容已成本机与云端的权威值，此前暂存的「云端旧值」随之失效——不清掉的话，用户再点「载入最新」会把**已被自己覆盖的旧值**载回表单（数据回退）。用例「保存成功清除待载入提示」钉住它。

## 六、已知限制与挂账

1. **dirty 期间的云端更新只提示一次、不排队**：若用户始终不点「载入最新」而云端又改了两次，提示条上是最新的那个值（后到的覆盖先到的）——用户看到的仍是「有更新」，不丢信息。不做版本队列（一份 7 字段画像不需要）。
2. **提示条不区分来源**：文案写「对话 AI 或其它设备改动」，不区分究竟是哪一侧（云端 `sync change` 不带这个信息）。如实措辞，不猜测。
3. **`pendingRemote` 在「用户改回原值」后不会自动消失**：dirty 由 `currentJson !== savedJson` 判定，用户手动撤销回原值即非 dirty——但提示条要等**下一次** refresh 才会走静默重取分支而消失（不点它也不会误覆盖，因为 `savedJson` 才是覆盖对象）。属可接受的粗糙边，未登记 R-PROD 号。
4. **未登记任何 R-PROD 号**：本轮风险册落笔统一归 T19-9（红线 §5.3），中间卡只在交付记录里描述。
5. **跨端闭环（AI 写入 → 表单可见）的验证欠账**转 T19-9 的真机回归清单。
