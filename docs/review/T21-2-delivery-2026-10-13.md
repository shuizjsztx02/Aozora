## 二、判据先行：数字与结论

### 2.1 四格对照（真实模型调用，非 Mock）

语料 21 条：**凭证正例 12 条**（微信支付页/微信通知、支付宝账单页/支付宝通知、云闪付页/通知、银行 App 页/通知、银行短信通知 × 收支两向）、**四类反例 8 条**、**边界 1 条**（有"支付成功"无金额）。探针 `server/scripts/probe_autobook_text_parse.py` 内置语料与判据，可随时重跑。

| 入口 / 模型 | 凭证正例 | 四类反例（退款 / 转账含还款 / 理财 / 红包） |
| --- | --- | --- |
| `/ai/interpret` + `qwen3.7-flash`（当时默认） | 金额与方向 **12/12** | **0/8 —— 全部记成账目** |
| `/ai/interpret` + `qwen-max` | 未跑（结论已由反例决定） | **0/8** |
| `/ai/parse-notification` + `qwen3.7-flash` | 10/12 | **0/8** |
| `/ai/parse-notification` + `qwen-max` | **12/12** | **8/8（类目 8/8 精确）** |

四类反例被误记的具体形态（第 1、2 格逐条实测）：退款 → `bookkeeping/income`、转账 → `expense/人情`、**信用卡还款 → `expense` 分类「其他」**（直接污染收支统计）、理财买入 → `income`、红包 → `expense` 或 `income`。

### 2.2 两个独立因素（这是本卡最有价值的产出）

1. **表达位（与模型无关）。** 口述模板的意图空间是 `bookkeeping / edit / delete / query / config / chat`——**没有「不是消费」的位置**。退款只能落成 `income`、还款只能落成 `expense`。换 `qwen-max` 依旧是 0/8，证明这一格**不是模型能力问题**，再强的模型也无处表达。→ 解法：`CAPTURE_PARSE` 引入 `kind`（`transaction` / `not_transaction`）与 `reason`（六值白名单）。
2. **模型能力（与提示词无关）。** 同一条新提示词，flash 级把四类**全部**判成账目（且 `confidence` 0.95–1.0，**会走自动入账**——因为高置信快速通道正是按置信度放行的）；max 级 8/8 判对且类目精确。而 `ai_provider_model` 的**默认值正是 flash 级**。→ 解法：`CAPTURE_PARSE` 用既有机制钉 `model="qwen-max"`（`PromptTemplate.model` 就是为此存在的字段），并由用例守护（见 §3.2）。

**旁证（复用直觉为什么是对的）**：`/ai/interpret` 下凭证正例的金额与方向本来就 12/12 全对——所以「够用就复用」的直觉并不荒谬，拦住它的只有反例那一格；而反例恰恰是最不能出错的一格（记错一笔退款＝凭空多一笔收入）。但反例一错，账目就被污染，故判据仍是「不够用」。

### 2.3 落地的端点

`POST /ai/parse-notification`：请求 `{text ≤2000, source_channel, context?}`，响应 output 形状 `{kind, reason, type, amountCents, category, note, bizDate, confidence}`。

- **提示词独立**（`prompts.CAPTURE_PARSE`）：凭证是**事实陈述**，与用户口述是两种输入。旧模板下实测出现的两个形态——把整段通知塞进 `note`、把账单页的「-32.00」读成**负金额**——在新提示词下都未复现（负金额另由消毒函数兜底）。
- **注入面与流程全复用**：`today` / `categories` 两段注入面走既有的 `render_messages_with_context`；限流、guest 日配额、重试、`ai_usage` 记账抽成 `AIService._run_json_task`，`interpret` 与 `parse_capture` 共用同一份实现（复制一份的代价是两条入口的约束慢慢漂开）。
- **四类之外**：其余非交易（余额提醒、账单汇总、验证码、广告）走 `reason="other"`。
- **离线语义**：本端点只做在线解析；本地规则先行、未命中才上行，是 T21-6 的编排。

### 2.4 形状消毒（`normalize_capture_output`）

解析结果**直接喂自动入账**（高置信自动写库），比 `/ai/interpret`（客户端还要自行组装 + validate）更需要服务端先钉死形状。消毒只做形状、不做语义再判断，四条不变量：

| 不变量 | 处置 |
| --- | --- |
| `kind` 非法 | **归为 `transaction` + `confidence=0`**——刻意**不**归 `not_transaction`：后者意味着「丢弃」，而把坏输出静默丢掉正是本仓反复出现的丢账形态（REQ-72），低置信进待确认箱才是「不产生不知情账目、也不静默丢」 |
| `not_transaction` | 其余字段**一律清空**（`reason` 走白名单，坏值 → `other`）——模型即使同时给了金额也不放行 |
| 金额 | 非负整数分（NFR-7）；文本里的负号只表示方向，取绝对值 |
| `confidence` / `bizDate` / `note` | clamp [0,1]；只收 `YYYY-MM-DD`；`note` 截 100 字符（模型照抄整段文本的护栏，实测出现过） |

## 五、已知限制与挂账（交下游）

1. **模型钉在模板里**（`CAPTURE_PARSE.model = "qwen-max"`）：换 provider 时这一行要跟着改，且有用例守护。这是刻意的取舍——默认配置是 flash 级，不钉就等于把四类反例放回生产；而单行常量是**显式可见**的，比静默用错模型好。
2. **成本抬升**：max 级 935 tokens / 2.26s 每次调用。缓解在客户端侧：本地规则（T21-6）先行命中就不上行；四类反例的文案有强特征（"退款/还款/转入/红包"），本地规则应优先识别。
3. **语料是构造的代表性样本**，非设备实拍；真实文案漂移由 T21-4 现场走查与 T21-6 本地规则共同兜底。语料在探针脚本里，随实测修订。
4. **无金额捕获的归属**：实测 max 级把「支付成功 / 查看账单详情」判成 `not_transaction/other`（丢弃）。若该页面其实有商户名，用户可能希望进待确认箱补金额——这条留给 T21-6 的本地规则与编排决定（服务端只如实报告它看到了什么）。
5. **未跑 `--bare`（无 context）对照**：分类注入面对 `category` 有作用、对 `kind` 判定无作用，本轮未取该对照数字。补跑成本约 2 分钟，需要时随时可跑。
6. **四类之外的长尾**（如「分期付款」「话费充值」是否算消费）未列反例；若 T21-4/T21-6 走查发现误记，先加语料再决定是否扩 `reason` 枚举——**枚举扩张要先改 ADR-016**。
