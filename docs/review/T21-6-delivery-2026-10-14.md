## 二、设计决策与落地

### 2.1 文档先行：`auto_captures` 的三条编排口径（`docs/architecture/data-model.md`）

先改文档再写码（`稳定性守则` §2.4）。补的三条都属"卡面没写、但不写清就会被下一个人推成别的结论"：

1. ★ **`parsing` 不落地**：解析在一次编排里跑完，行**不会停在 `parsing`**。持久化它需要在每次失败时回退，而它没有读侧消费者（待确认箱只读 `pending_confirm`）；更要紧的是——**崩溃后停在 `parsing` 的行会被"只扫 `captured`"的编排永久跳过**，那才是静默丢账。未定论的行一律留在 `captured`。
2. ★ **`ignored` 是「不是一笔账」的落点，两种成因**：① 引擎判定为四类「不是消费」或其余非交易文本（`reason` 留在 `parsedJson`）；② 被 L2 合并掉的**留痕行**。两者都保留 `rawText` 与 `parsedJson`——**不是删除**。强制理由：待确认箱按 `status` 取列表（T21-3 的 `listByStatus`），留痕行若停在 `pending_confirm` 会跟保留行一起出**两张卡**。
3. **上行失败 ≠ 写库失败**：上行（网络 / 服务端）失败 → 留在 `captured` + `error` 记原因码（下次再试）；解析成功但**落账写入**抛错 → `failed`（保留原文与解析结果）。

### 2.2 `LocalCaptureParser`（纯函数，离线兜底）

- **判据顺序**：四类「不是消费」→ 金额 → 方向 → 商户名 → 分类提示。**四类排在最前**是刻意的：它们都带金额、都像一笔收支，晚判就会被记成账目（T21-2 实测 `/ai/interpret` 下 8/8 误记，信用卡还款还被记成支出分类「其他」）。**类目顺序也有依赖**：红包 → 信用卡还款 → **退款 → 理财 → 转账**。
  - ★ 顺序里的 `退款 → 理财` 是实测逼出来的：语料 `支付宝 / 退款成功 32.00元 / 已退至余额宝` 同时含"退款"与"余额宝"，理财在前就会把一笔**退款**归成**理财买入**（两个 reason 都属"不是消费"，但成因报表失真）。
  - ★ 同一轮实测还挖出**理财判据的假阳性**：`付款方式：余额宝` 是"用哪儿的钱付"，不是理财买入——裸 `余额宝` 入表会把每一笔"余额宝付款"判成理财买入。故理财只认**动作**（`余额宝 转入/转出`、`转入余额宝`、`理财/基金/定投/朝朝宝/份额/证券/股票`）。这条由语料 `ali-notif-pay` 与 `ali-notif-yuebao-in` 一正一反钉住。
- **金额口径与两个预筛过滤器逐字一致**（复用 `NotificationFilter.extractAmountCents`，**货币标记必需**、整数分）。这不是省事：能走到解析层的文本必然已经过一次同样的判定，两处口径漂开就会出现"过滤器认了、解析器不认"的静默失配。
- **商户名**：先按来源文案的显式模板（`收款方：` / `付款给` / `在X消费` / `商户 X` / 收款人），取不到再退到**无障碍结果页形态**——金额那一行的下一行常常就是商户名（`支付成功 / ¥32.00 / 星巴克(北京国贸店) / 零钱 / 账单详情 / 完成`）。噪音行（`零钱`/`账单详情`/`完成`/`付款方式`/App 名…）一律不得当选，宁可为空交给上行通道。
- **分类提示只用种子分类里确实存在的名字**（餐饮 / 交通 / 购物 / 住房 / 买菜 / 爱车 / 休闲娱乐 / 生活服务 / 工资 / 报销），命中不了给空。提示最终要在**本地真实分类**上解析一次，用户改过名字就自然退化——不会写错分类。
- **不解析日期**：形态多、易错；日期由设备侧用**捕获时刻**折算（见 §2.3），与服务端提示词"绝不臆造日期"同口径。

### 2.3 `AutoBookEngine` 编排

流程（每条 `captured` 行）：

```
本地规则 ─┬─ 四类「不是消费」 → ignored（不上行：文案特征强，别白花一次调用）
          ├─ 高置信且字段完整 → 快速通道落账（立即可见 + 可撤销）
          └─ 其余 → 上行服务端 ─┬─ 高置信完整 → committed（来源记 nlu_ai）
                                ├─ 低置信 / 缺字段 → pending_confirm（进待确认箱）
                                └─ 上行失败 → 留在 captured（★ 断网不丢）
```

- ★ **可自动入账的判据 = 金额 + 方向 + 分类三者齐备，且置信度 ≥ 0.9**。**0.9 不是新发明的数**：客户端既有判据 `ai-proposal-builder.ts` 的 `requiresConfirmation = confidence < 0.9 || warnings.length > 0 || !categoryId` 就是它——自动记账只是多了一个提案来源（ADR-016 决策 8：不新造卡片类型）。缺任何一项进待确认箱（**宁低置信，不猜字段**）。
- **分类解析顺序 = 商户记忆 → 解析提示**。记忆优先是决策 #11 的原文（"取其**最近一次**的分类"）——用户自己上次的选择比模型的猜测更可靠。记忆读的是同 `merchantKey` 最近一条 **`committed`** 行的 `parsedJson.category`（T21-3 的 `lastCommittedByMerchant`）。
- **商户记忆的落点**（决策 #11，不开新表）：**只补分类，不抬置信度**。就是说——本地规则没给出分类提示时置信度只有 0.6，记忆能帮它补上分类，但不改变"这笔是不是真的"的判断。记忆真正的用处在**上行路径**：服务端从注入的分类名单里挑不出分类时（`category` 为空），记忆补上它，于是一笔本来要进待确认箱的账直接入账。
- **落账一律走 `Repository.insertTransaction`**（与 `pending_mutations` 同事务，决策 #16）。来源如实标注：本地规则认得的那笔 = `nlu_local`，服务端解析的 = `nlu_ai`（两个值都已在服务端 `TxSource` 并集内，越界即 push 422 毒丸）。
- **账本未就绪不硬写**（首启未播种 / 用户删光账本）：转待确认箱 + `error = book_not_ready`，比造一个"孤儿账本"诚实。

#### 2.3.1 L2 的两处守护（都是"不这么做就会静默出错"）

仓层的 `mergeIfSameTransaction` 按通道优先级（无障碍 > 通知）选保留行，**但它看不到候选的解析状态**。这留了一个真实的坑，本卡补了两道：

1. ★ **已落账的候选优先，且优先级规则只在"两边都还没落账"时适用。** 否则：通知那条先落账 → 无障碍那条（优先级更高）后到 → 按优先级把保留位挪到无障碍行 → 那一行也落账 = **同一笔写两条分录**。做法是在调用仓层方法前先查候选，只要有一个已 `committed` 就直接把本行作留痕并过去。
2. ★ **让位：优先级低的那条发现"同窗同笔、更高优先级、且刚刚捕获"的孪生行还没解析时，本轮不定论。** 否则信息更全的那条只能当留痕，**商户名落不到账目上**（决策 #5「保留信息最全的一份」、决策 #19 ④「合并为一条且保留商户名」）。让位有两道边界：用 `listSameWindowOtherChannel`（**不能用 `mergeKey` 查**——孪生行的 `mergeKey` 要等它自己被解析才回填，用键查永远查不到正是要防的那一条），并且带 **120 s 止损窗**（孪生行因断网长期停在 `captured` 时，本行最多等这么久就自己入账，不让位变成饥饿）。
3. **L3（同额不同商户）不合并**，也不预选删除：待确认箱用 `listSameWindowOtherChannel` 自己派生"疑似重复"提示（T21-8 消费，T21-3 的查询本卡未改写）。

### 2.4 触发面：本地档与在线档（**本卡不新增调度器**）

| 触发面 | 谁触发 | 档位 | 为什么 |
| --- | --- | --- | --- |
| 采集侧落行后 | `AutoBookNotificationListener` / `AutoBookAccessibilityService` | `allowRemote = false`（**只跑本地档**）+ `SyncScheduler.enqueue` | 本地规则认得出的那一笔**离线也能入账**（PR-3、T21-6 验收）；未定论的行交给同步任务在联网时上行 |
| 同步任务跑一轮 | `SyncWorker`（放在 `SyncEngine.runOnce()` **之前**） | `allowRemote = true`（在线档） | 复用 `SyncScheduler` 的既有形态（联网约束 + 唯一任务 + 指数退避），**不新造调度器**；放在同步之前 → 本轮自动入账的账目被同一轮同步推给服务端 |

- ★ **与 ADR-016 决策 4 的关系（如实记录，供 T21-9 判定）**：决策 4 写的是"采集层只做预筛 + 落库，不做网络、不做解析"。本卡的实现是：**采集回调本身仍只做预筛 + 落库**，它只是**触发**了一次异步编排，而那次编排被 `allowRemote = false` 钉死为**不做网络**（在线档只存在于 `SyncWorker`）。也就是说决策 4 的实质（网络不进后台服务）在两条通道上都被守住了，唯一的新增是"采集侧触发一次纯本地编排"。之所以必须这么做：**没有它，"本地规则命中的一笔离线也能入账"这条验收无从成立**（联网约束下的 `SyncWorker` 永远跑不起来）。**这是本卡唯一的解释性偏离，建议 T21-9 在收口时于 ADR-016 决策 4 补一句口径**（或裁定为不需要）。
- 两个触发面共用 `AozoraApp.autoBookEngine` **同一个实例**（同一个 `drainMutex`）；一轮编排用**非阻塞**互斥，重叠触发时后来者直接返回，不排队（采集回调可能连续触发，排队只会堆积）。
- 本地入账会改变今日 / 本月聚合，两个采集服务在推进后刷新桌面组件（与桥的记账路径同口径）。

### 2.5 在线解析入口（T21-2 结论的接线）

`AiGatewayClient.parseNotification(text, sourceChannel, contextJson)`——**`AiGatewayClient` 此前没有这个方法**，T21-2 只落了服务端端点，其 §五明确把"本地规则先行、未命中才上行"的编排判给 T21-6，故本卡补上这一处客户端接线（与 `interpret` 同口径：同一套 token 注入、25 s 预算、同样的错误映射与降级契约）。

- **注入面 = `today` + `categories` 两段**（与 `use-assistant` 的 `aiContext` 同键同口径）：分类名单**来自本地真实分类**（去重、≤16 字、≤120 条），否则模型会挑出一个本地不存在的分类名，最后只能进待确认箱。
- **适配器 `AiCaptureRemoteParser`**（与 `AutoBookEngine` 同文件）把服务端响应映射成**与本地规则同一个 `Draft`**——在线与离线同形状，编排段零分支。服务端已做形状消毒（T21-2），故这里只读字段；**读不出 `output` 一律抛异常**（行留在 `captured` 下次再试），而不是造一份空草稿——空草稿会被当成"解析成功但缺字段"进待确认箱，**掩盖真因**。
- **成本口径**：本地规则完整命中就**不上行**（省一次调用，T21-2 §五.2 点名的缓解手段）；未命中或字段不完整才上行。本地判出四类「不是消费」同样不上行。

## 五、已知限制与挂账（交 T21-9 收口落笔）

1. ★ **与 ADR-016 决策 4 的解释性偏离**（见 §2.4）：采集侧触发了一次**不做网络**的本地编排。实质口径（网络不进后台服务）仍然成立，但按字面与决策 4 有出入——建议 T21-9 在 ADR-016 补一句，或裁定为不需要。
2. ★ **`ignored` 承担了两种成因**（引擎判定"不是账" / L2 留痕），`parsedJson.reason` 与 `mergedInto` 可反查。若后续要按成因分列（例如"被合并的留痕不计入捕获统计"），需要新列或新查询——**那要改 `db/` 簇与 data-model**，本卡不做。
3. ★ **"两条通道各自的失效面"在编排层的落点**：同一笔若两条通道**被两次编排分开处理**（先到的那条已落账），保留行是**先落账**的那一条——若它没有商户名，商户名只留在留痕行的 `merchantKey` 上。**不重复入账优先于信息最全**（写两条分录是数据错误，商户名缺失只是体验上限）。让位规则把这条压到"仅跨编排"的窄缝里。
4. **商户记忆只记分类，账户取 `default_account_id`**：决策 #11 原文是"取其最近一次的分类/账户"，本卡只落了分类——账户有用户级偏好（T9-5a 的 `default_account_id`）且 `parsedJson` 的形状与服务端 output 对齐（无 account 字段），扩它要动跨层形状。够用就停。
5. **本地规则不解析日期**：`bizDate` 用**捕获时刻**在 `Asia/Shanghai` 折算（与 `WidgetDataHelper` / 前端 `todayBizDate` 同口径）。银行短信里的"10月13日"这类显式日期只有**上行路径**能算对（服务端提示词规则 5）。
6. ★ **一处 T21-4 侧的过滤器观察（不属于本卡，供收口判定）**：支付宝**账单详情页**的金额是 `-32.00`（**无货币标记**），而 `AccessibilityFilter` 的金额判据要求货币标记（与 `NotificationFilter` 同口径）→ **这一页形态会被无障碍预筛拦掉**，根本到不了解析层（语料 `ali-a11y-bill` 即此形态）。本卡的金额判据与过滤器保持一致（不制造"过滤器认了、解析器不认"的失配），但这条缺口值得在真机走查时专门看一眼是否影响支付宝通道的覆盖率。
7. **`reason` 枚举未扩**：长尾（分期付款 / 话费充值是否算消费）未列反例。实测出现的形态若确认误记，**先加语料、再决定是否扩 `reason`**——**枚举扩张要先改 ADR-016**（T21-2 §五.6 同口径）。
8. **`error` 字段是原因码不是文案**：`remote_failed` / `book_not_ready` / `commit_failed`（+ 写库异常时的异常消息）。**不含任何原文**（原文是敏感数据，`security.md`）。
9. **本卡未做真机 / 模拟器取证**：全部为 JVM（Robolectric + fake 上行通道）。决策 #19 的 ④⑤⑥ 与"断网 → 联网自动推进"现场走查 defer 到 **T21-9 收口**（与 T21-3 / T21-4 同处置）。
