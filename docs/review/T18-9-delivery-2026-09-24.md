## 四、收口期发现与处置

### 4.1 新发现①：图片提案的幂等键由模型生成（P1，**本卡已修**）

- **现象**：同一张小票第二次「确认 3 笔」，界面走完整套成功流程（清草稿、关面板），**服务端零写入、无任何提示**。
- **根因**：`prompts.py` 要求模型输出 `"proposalId": "img-<uuid4>"`，而 **LLM 无法真正生成随机 UUID**——实测它照抄训练数据里的经典示例值 `123e4567-e89b-12d3-a456-426614174000`，也曾产出含 `g/h/i/j` 等非十六进制字符的伪 UUID。该值被 `service.py` 原样用作**执行幂等键** → 撞历史键时 `execute_proposal` 命中缓存直接返回，本笔静默丢弃。
- **取证**：dev 库 `proposal_idempotency` 里那条 `img-123e4567-…`（2026-09-23 10:01:12）的 `transaction_ids` 正是**首次**图片记账的 3 笔；第二次确认时服务端日志出现 `AI proposal idempotent hit`、交易数不变。
- **反差**：agent 路径早已确立「幂等键不接受外部输入」的原则（`tests/test_ai_agent_approval.py` 断言攻击者指定的 id 被忽略），**只有图片路径漏了**。
- **修法**：`service.py` 恒用服务端自生成的 `img-{uuid4()}`；`prompts.py` 的示例由 `"img-<uuid4>"` 改为 `""`。
- **验证**：新增守护用例（模型反复给同一值 → 两次解析必须得到**不同**幂等键）；**变异验证**（还原修复 → 用例转红，断言直接打印两个相同的示例 UUID）；**端到端复验**（同一张小票连续两次识别 + 确认，两次都记账：服务端交易数 15 → 18 → 21，`idempotent hit` 0 次）。
- **影响面**：用户可见的数据丢失路径，且**部分解释了 REQ-72 的用户报告**（那一次服务端写下的 3 笔，正是这条路径首次、也是唯一一次成功的结果）。

### 4.2 新发现②：WebView 未实现 `WebChromeClient` → 删除操作静默无效（P1，**登记 R-PROD-45，未修**）

- 前端 5 处以 `window.confirm()` 作删除确认门，而全仓 `app/src/**` **无任何 `WebChromeClient` / `onJsConfirm` / `onJsAlert` 实现** → 默认 `onJsConfirm` 返回 `false` → 删除全部短路。
- **取证（差值实验）**：同一按钮，先在页面内覆写 `window.confirm = () => true` 再点 → **立即生效**（`deletedAt` 写入、余额按不变量④回补）。
- **影响**：删除交易 / 预算 / 角色 / 定时任务**四条用户功能在真机上完全不可用**且无反馈。
- **未修的理由**：非本轮引入（Android 层历史缺口），修复要在 `MainActivity` 新增 `WebChromeClient`（原生 AlertDialog）或把这 5 处改成应用内确认组件，且不能只靠 JVM 单测覆盖——按收口卡红线**登记待决策**。
- ★ **走查副作用声明**：本卡为验不变量④**在页面内覆写过 `window.confirm`**，该覆写只存在于当次页面上下文、随 App 重启消失，**未进入任何源码或提交**。

### 4.3 新发现③：服务端 `icon` 列可存裸词且可达 + 两处 fallback 不一致（P3，**登记 R-PROD-46**）

- REQ-68 当初的推断（「中毒客户端上行即把 `"default"` 存进服务端」）本轮**意外实证**：设备侧改 `icon='default'` 后下一次同步把它推上了服务端，再下发回设备——容错是唯一防线。
- 同一「图标未设置」的账户，账户页显示 `💰`、记账面板选择器按钮显示 `💳`（`entry-controls.tsx` 的 `fallback="💳"` 与 `DefaultIcons.ACCOUNT="💰"` 不同源）；都不是裸词、不影响功能，修法一行，未做。
