## 三、设计决策（四条）

### 3.1 两段式，上段逐字不动

卡面①定的形态：上段 = 现有 `CategoryEditor` 的名称 / 上级 / 图标（**一行未改**，包括 `IconPicker` 与「上级分类」按钮组），下段 = 新增的二级分类段。这样做的好处是**零回归面**：既有的一级编辑能力完全不受影响，`CategoriesPage.test.tsx` 原有的两条 REQ-12 字段顺序用例**一字未改即通过**。

子类段的位置在 `IconPicker` **之后**（卡面写明「自身配置」三项含图标，故图标属上段）。

### 3.2 ★ `key` 强制重挂载——本卡发现并修复的一处真缺陷

**问题**：弹层内从「一级编辑器」点进「其二级编辑器」时，React 会**复用同一个 `CategoryEditor` 实例**（同类型、同位置、无 key），而 `CategoryEditor` 的 `name` / `icon` / `parentId` 都是 `useState(editing.base.xxx)` 惰性初值——**只在首次挂载时生效**。结果：点进二级分类，表单里显示的还是**父级**的名称。

这不是本卡引入的（现状下弹层内无法切换编辑目标，所以暴露不出来）；是本卡新增「弹层内切换」能力后才可达的。修法是一行：

```tsx
key={editing.base.id || 'new'}
```

**反向验证**：把 key 固定成常量（模拟复用实例），用例 2、3 立刻双红（§5.3 变异 ①）。

### 3.3 无子类的一级分类：也给空态段 + 新建入口（**对卡面字面的一处主动放宽**）

卡面④只说「无子类的一级分类：点击行为回落到**直接编辑**（与现状一致，零回归）」。本卡按字面保住了**点击行为**（点一级格就是打开它自己的编辑器，没有变成「先展开再编辑」的两步交互），但在**弹层内容**上做了放宽：**无子类的一级分类也显示子类段（空态「暂无二级分类」+「＋ 新建二级分类」）**。

理由：卡面②要求给「新建二级分类」入口，而若只对**已有**子类的一级显示该入口，则「给一个从没有子类的分类添加第一个子类」将**无路可走**（只能绕到底部的「＋ 新建支出分类」再手动挑上级）。放宽后的实际差异只有一处：无子类一级的弹层里多了一行空态文案与一个按钮，**原字段与保存行为逐字不变**（用例 4 逐项钉住）。

判断口径：④ 约束的是「**点击行为**」，本卡未触碰该行为；内容增量属于②的必然连带面。

### 3.4 弹层可达性加固（本卡引入的连带面，自己收拾）

新增的子类段客观上增加了弹层高度（原有内容已含 emoji 宫格，本就接近一屏）。给 sheet 容器加 `max-h-[85vh] overflow-y-auto`，使**无论子类多长，底部「保存」都可达**——把「真机上会不会顶出屏幕」这个只能靠走查发现的风险，转成**结构上不可能发生**。

段内的子类列表另加 `max-h-48 overflow-y-auto`（沿用本仓既有写法，见 `entry-controls.tsx:281` / `OpPreviewCard.tsx:159`）。

## 六、已知限制与挂账

1. **未做「在弹层内从二级返回父级」**：保存或关闭后直接回到列表页（与现状编辑一级的行为一致）。卡面未要求，故不做。
2. **一级降级为二级时的既有语义问题（本卡不引入、未处理）**：编辑一个有子类的一级分类时，「上级分类」按钮组仍可把它改成别人的二级（现状行为），此时其子类会变成三级并被 `RepositoryCategoryTest.threeLevel_rejected` 拒绝、保存报错。**本轮不动**（改它会改既有交互契约），登记供收口决策。
3. **真机走查用的是模拟器不是用户手头真机**：卡面验收提到「债券」（附件 #149 里那个「2 个子类」的分类）——设备上并无该数据（用户数据在另一台机器），故走查改用**现场自建**的父/子分类完成同一路径。收口卡 T19-9 可在用户真机上按原样复走。
4. **本次走查在设备与 dev 库留下了测试数据**（「T19-6走查父」/「子A改」，设备 + 服务端各一份）。与 T19-1 的「T19-1取证」/「T19-1照片图标」同类，**未清理**（App 无删除分类功能）；收口时可视需要一并清。
