# Aozora · AI 协作稳定性守则

**建立：** 2026-09-19 | **状态：** 生效 | **上游依据：** `AGENTS.md`

**定位：** 本守则回答一个工程问题——**在由 AI 承担主要编码工作的前提下，如何让系统在持续加功能的同时不退化**。它不重复 `通用任务执行规范.md`（执行流程）、`需求变更规范.md`（变更分级）和 `testing.md`（测试分层）的既有内容，只补齐三者共同依赖、却此前无处安放的**稳定性原理与护栏**。

**适用范围：** 仓库中所有由 Agent 执行的改动。L1 局部改动可简化记录，但不得跳过第 2.1 节（事实层）与第 6 节（交付前清单）。

---

## 一、第一原则：让破坏可见

不能通过要求 Agent「谨慎」来获得稳定性——不确定性不会因为被叮嘱而消失。可依赖的做法只有一种：**让任何一次破坏都变成一次可观测的失败**。

由此推出三条推论，本守则其余章节都是它们的展开：

1. **能被自动发现的问题，才是已被防御的问题。** 口头约定、代码注释、记忆中的默契，都不构成防线。
2. **限制爆炸半径比限制行为更有效。** 与其要求「不要改错」，不如让单次改动小到改错了也容易回退。
3. **失败必须廉价。** 小提交、可回滚、门禁快，试错才是可持续的。

---

## 二、四层防线

按可靠性从高到低排列。上层失守时下层兜底；下层缺失时，上层无法单独成立。

### 2.1 事实层：测试与门禁

唯一不需要人盯着的防线。

- **钉关键不变量，不追求覆盖率数字。** 判据是「这条业务等式被破坏时会不会红」，不是百分比。本仓库的范式是 `testing.md` 的对账不变量 fuzz（一票否决项）。
- **回归集合来自真实咬痕。** 贯彻 `testing.md` 验收五原则第 5 条「一个 bug 一条守护」——每修复一个缺陷，就把它变成一条自动用例。这样累积的是**历史上真出过的问题**，而不是凭想象编写的用例。
- **门禁以 `.github/workflows/ci.yml` 为事实源。** 本地必须执行与改动相关的 CI 等价命令（`通用任务执行规范.md` 二.8）。远端 CI 未覆盖的模块，执行其本地门禁并在交付报告中注明「本地验证、远端未覆盖」。

### 2.2 范围层：限制爆炸半径

不阻止犯错，只让错误的代价可控。

- 单次改动只触及任务范围内的文件，不顺手重构无关模块（`通用任务执行规范.md` 二.5）。
- 暂存与提交使用**精确路径**，不得使用会批量纳入无关文件的 `git add -A` / `git add .`；提交前核对 `git diff --cached`（同规范 五.4）。
- 改动前记录 `git status` 基线，不覆盖、不暂存、不提交范围外的已有改动（同规范 一.5）。
- 涉及 `.yml` 时只改目标节点，完成后必须做 YAML 语法校验（`AGENTS.md` 关键工程约束）。

### 2.3 上下文层：消除「不知道已经有了」

Agent 闯祸的一大来源不是改错，而是**重新实现一个已经存在的东西**——同一概念出现两份实现后各自演化，这是屎山的胚胎。

- 开工前按 `AGENTS.md` 的路由加载文档，**不要预加载全部文档**。
- 写新函数、新命令、新组件之前，先确认仓库中是否已有等价物；判据见第 4.3 节。
- 上下文中的状态描述必须与仓库事实一致。**过期的状态描述不报错，只会让 Agent 在错误前提下做判断**——其危害高于信息缺失。

### 2.4 决策层：文档前置与 ADR

「先改文档再改代码」的价值不在文档本身，而在于**把隐含决策变成显式决策**。编码过程中 Agent 会顺手定下大量无人注意的选择（字段命名、重试次数、旧数据处置）；写进文档，才有机会在上线前被否决。

- 架构、协议、数据结构、安全边界或产品规则变化时，先更新对应文档再动代码（`需求变更规范.md` 三）。
- 关键取舍写入 `docs/adr/`，避免同一问题被反复推翻。

## 三、防止「老功能被改坏」

按杀伤力排序。

### 3.1 跨层契约必须逐处守护

本仓库历史上最严重的回归都属于这一类：**同一契约在多个位置必须保持一致，改动任一处就会静默失配**。

- 已知实例：JS Bridge 命令计数需在 Kotlin / TypeScript / 服务端三处同步；工具名必须使用下划线（点号会让 provider 返回 400）；Kotlin 块注释可嵌套，KDoc 中书写路径字面量会吞掉整个文件。
- 要求：此类契约**每一处都要有测试钉住**，且改动任一处即使测试变红。只在一处设防等于未设防。

### 3.2 反向验证测试本身

一个永远不会失败的断言比没有断言更糟，因为它提供虚假的安全感。

- 新增回归用例后，**先把它打回缺陷形态，确认它确实变红**，再恢复。
- 变异必须打在**真实可达路径**上；打在不可达分支上的变异证明不了任何事（本仓库已有此类「假绿」教训）。
- 禁止通过降低断言强度、跳过用例或删除 fixture 换取通过（`通用任务执行规范.md` 五.3）。

### 3.3 证据纪律

- **不采信「已完成」这类自我报告**，只采信命令与输出。
- 只有获得证据的检查才能标记为通过；无法确认时写「未能确认」，不得写成通过（同规范 二.12、五.5）。
- 本地全绿不等于远端全绿。本仓库出现过两类情况：一是 **JVM 单测全绿但 `androidTest` 源码集根本编不过**（`testDebugUnitTest` 不覆盖 androidTest 源码集）；二是 **HEAD 不自洽**——本机绿是因为工作区存在未提交的依赖，CI 上必红。**改动主源码后必须显式编译 androidTest 源码集。**

## 四、防止「屎山」

### 4.1 「最小改动」的副作用

「最小改动、不顺手重构」是对的，但它本身会催生屎山：Agent 会退化为只敢「加」不敢「改」——旧函数不动、旁边新写一个，旧路径不清、加开关绕过去。**因此最小改动必须与定期清理配对，缺一不可。**

### 4.2 清理通道

三条通道同时存在才有效：

| 通道 | 作用 | 载体 |
|---|---|---|
| 挂账表 | 该清理而未清理的必须记账，不许口头放过 | 各期实施推进计划的挂账项小节 |
| 清理轮次 | 专门为合并重复、删除死代码而开，不为加功能；此轮内「最小改动」原则暂停 | 里程碑级专项轮次 |
| 审查与简化 | 独立环节，专找重复实现与多余抽象 | Review 模式；`/code-review`、`/simplify` |

### 4.3 单一实现判据

- 判据：**同一个业务概念，仓库里有几处实现？超过一处即为债。**
- 交付前自查：本次新增的实现是否与既有实现语义重叠；若重叠，是合并，还是明确了分工并把原因记录在案。

## 五、多会话并行纪律

本仓库常以多个会话并行推进不同子卡，由此产生三类特有故障：

1. **HEAD 不自洽。** 依赖了尚未提交的改动的任务，本机绿、CI 红。**开工前确认所依赖的产物已提交**；跨卡依赖未落地时，不得据其宣称完成。
2. **提交夹带。** 并行工作区中执行范围外的全量提交，会把其他会话的在途改动一并带走。**一律使用精确路径暂存。**
3. **看板与工作区不同步。** 看板状态可能落后于工作区，反之亦然。**以 `git log` 与工作区事实为准**，不单凭看板下结论。

## 六、检查清单

### 开工前

- [ ] 任务编号、范围、非目标、验收标准已确认（`通用任务执行规范.md` 二.1）
- [ ] 按 `AGENTS.md` 路由只加载相关文档；其中的状态描述与仓库事实一致
- [ ] 已确认要新增的能力在仓库中确实不存在，或已明确与既有实现的分工
- [ ] 已记录 `git status` 基线；所依赖的产物已提交
- [ ] 影响契约、数据结构或安全边界的改动，文档 / ADR 已先行更新

### 交付前

- [ ] 改动范围与任务范围一致，未顺手重构无关模块
- [ ] 新逻辑有自动化测试；缺陷修复有回归用例，且**已反向验证它确实会红**
- [ ] 受影响的跨层契约每一处都有守护
- [ ] 已运行本地 CI 等价命令；改动主源码后已显式编译 androidTest 源码集
- [ ] 涉及金额 / 统计 / 导出 / 同步时，对账不变量全绿
- [ ] 暂存区仅含本次任务文件，`git diff --cached` 已核对
- [ ] 远端 CI 状态已确认，或如实记录「未能确认」
- [ ] 风险登记册与任务状态按事实更新
