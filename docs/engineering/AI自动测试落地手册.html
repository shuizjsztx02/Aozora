AI 自动测试落地手册

把「AI 自动测试」拆成三层可测量的面，用同一份语料库驱动三种执行器。日常只需要更新测试需求——加一条 JSON，不用碰任何脚本。

模拟器 + 安卓真机双端 Aozora · T17–T20 实战 2026-09-29
〇

这套方法在测什么

它不是「用 AI 代替人点按钮」。让 AI 去点按钮，反而比传统 UI 自动化更贵、更不稳定——模型每次点哪里是随机的，脚本不可复现，失败无法归因。

真正有价值的是把测试拆成三层测量面，每层各测一件事，而判据是数据，不是脚本：

corpus.json  ·  测试需求 96 条  唯一需要日常维护的文件
▼
离线执行器秒级 · 0 模型调用
路由词表覆盖、客户端闸门、链式依赖——量确定性的东西
服务端执行器全量约 25 分钟
直打 POST /ai/agent，绕开客户端——量模型层：选对工具没有、写操作落库没有
设备执行器每条 30–60 秒
经 CDP 驱动真实 WebView UI——量可达性：这句话能不能走到 AI、确认卡渲染没有
▼
判据 · hit / landing / also / device_expect
为什么必须分三层

同一句话在三个面上量到的可能是三件事。举例：「刚收到工资 12000 到卡里」——

  • 服务端面：失败。单字信号「卡」把整句路由进账户域，记账工具根本不在注入面，模型只能反问「记到哪个账户？」这是真缺陷。
  • 设备面：成功。因为客户端本地快路径先把句子接走了，用户看到的是正确结果。

所以：只看服务端会高估危害，只看设备会漏掉缺陷。

一

六条第一性原理

1.1语料库驱动：测试需求是数据，不是代码

一条用例就是一段 JSON：

{ "id": "TX-ADD-01", "domain": "transaction", "layer": "core",
  "kind": "write", "text": "记一笔 12.5 元的早餐",
  "expect": ["transaction_add"], "landing": "landed",
  "note": "最直白形态；「记一笔」是路由强信号" }

加测试需求 = 往数组里加一条 JSON。三个执行器共用同一份语料，量的永远是同一批需求。

层条数写什么
core59每个工具的主干说法，直白式
para15同一工具的换说法（口语、省略、中文数字、相对日期）
boundary15负例与能力边界（不该写 / 该澄清 / 高风险该出卡）
gate4客户端快路径闸门的对照样本
device3设备能力通道（单向 / 需结果 / 副作用断言）

para 层是中文产品独有的价值：「记一笔早餐 12.5」「早饭花了十二块五」「刚吃早饭 12.5」是三种说法，模型准确率在这三种之间会差很多——这是传统自动化测不到的。

1.2判据与执行分离

判据变了不重跑模型：run.py --rejudge report.json 直接对已存的报告重算。这一条把「改判据」的成本从 25 分钟降到 0。

判据含义
hit期望工具出现在本轮工具调用里（近义工具分属两域时任一都正确）
landing写操作的产出形态。landed 真落库 / produced 落库或出确认卡有其一 / proposal 只挂起（设备 op 与高风险 op 的预期形态）/ forbidden 一条写路径都不该有 / na
also附加断言（如记账后应刷新小组件）
device_expect设备能力看的是 device_request 帧的 capability 名
三个判据陷阱

不搞清楚这三条，量到的全是假数据。

  • done.writes 不是落库数。它是「写工具的调用次数（含只产出提案的）」。当成落库用，会把设备 op 与高风险 op 一律误判成「已执行」。落库只看 executions。
  • 落库还是出卡由模型行为决定，不是用例的固定属性。confirm_reason 规定：step ≥ 2 或低置信 → 强制确认。同一个工具，直接写就落库、先查再写就出卡，两者都对。真正的失败形态是两者皆无。
  • 前置数据必须覆盖用例点名的每一个名字。点名不存在的分类会让创建工具回 unknown_category，模型转去读工具——看起来像「读后不落子」，实际量到的是环境不是模型。

1.3闸门思维：逐级排查，不要跳着猜

一个功能在设备上不通，按三道闸门逐级查。端到端不通时，先问「走到哪一道了」：

闸门不通的后果怎么开
① 客户端 JS本地快路径把句子吞了，云端 AI 根本看不到这句输入在线态一律走云端；离线态是设计内的快路径
② 客户端 Kotlin整条退回旧单发链路客户端 feature flag
③ 服务端POST /ai/agent 恒 404两个服务端开关置 true

第一道闸最隐蔽：它不报错、不留痕，用户只看到「AI 好像变笨了」。为它付过一次大代价——怀疑了模型、prompt、桥命令，最后发现是客户端开关默认关，agent 路径编译期就不存在。

1.4归因顺序：先查环境与前置，再谈模型行为

这条最反直觉

测试集自身的缺陷会伪装成模型缺陷，而且伪装得很像。「读了就收尾」与「对象不存在」在工具调用序列上完全一样——都是一串读工具、零写操作。

第一个案例里有 6 条「读后不落子」，逐条核对后全是模型的正确行为：上一轮的创建用例先读了一次，提案落在 step 2，按审批策略只出确认卡不落库，于是对象从未存在。

  • 凡被「改 / 删 / 归档 / 切换」引用的对象一律直接播种，创建用例改用全新名字、作为终点，不与改/删目标重叠。
  • 加一道离线守卫：改/删用例必须点得到一个播种名，且不得指向一个已被更早用例改名的对象（改名链必然「找不到 X」）。守卫现在是 0 条违规——改了语料先跑 --dry-run，它把问题挡在花模型调用之前。

1.5判据必须能被反向验证（假绿识别）

一个永远不会失败的断言比没有断言更糟，因为它提供虚假的安全感。五种实际踩过的假绿形态：

形态反例修法
变异打在不可达分支用例被投影层的同 id 去重先挡住了，改坏代码仍绿变异必须打在真实可达路径
自反断言用被测代码自己的输出当期望值期望值必须来自独立来源
触发点早于被测行为断言在真正那行代码之前就通过了让失败必须发生在被测行之后
环境替身不真推jsdom 里 scrollTo 不真的推 scrollTop，判据永远成立让替身真的改变状态
断言的是事实源的抄写某用例名叫「所有命令都已定义」，实际断言一个手写列表有 45 项——真实命令集从 45 涨到 83 期间它一直绿断言必须读规范清单本身并交叉核对

纪律：新增回归用例后，先把它打回缺陷形态，确认它确实变红，再恢复。

1.6证据纪律

  • 不采信「已完成」这类自我报告，只采信命令与输出。
  • 只有获得证据的检查才能标记为通过；无法确认时写「未能确认」，不得写成通过。
  • 「用例绿」≠「代码对」；「本地绿」≠「HEAD 绿」≠「CI 绿」。
  • 上报缺陷必须带：复现命令 / 设备与 APK 版本 / 实际观察 / 是否跨轮一致。单轮不足以定性——至少两轮一致，或对可疑用例单独复跑。

三

启动步骤

前提：仓库已 clone，app/ 下已 npm ci——Gradle 的 preBuild 会自动跑 Vite 构建并把产物同步进 APK assets，缺了会失败。

1

起数据库并跑迁移

docker compose up -d db && docker compose ps
cd server && alembic upgrade head && alembic current

迁移配置里的 URL 是留空的，运行时从环境变量注入。报 "invalid URL" 是环境变量没设，不是配置写错。

2

配 .env 并起服务端

cd server && cp .env.example .env      # 首次
uvicorn src.main:app --reload --host 127.0.0.1 --port 8000
curl http://127.0.0.1:8000/api/v1/health/ready   # 含 DB 探活
每次开工必做

确认 uvicorn 跑的是当前 HEAD 代码。沿用几天前的旧进程会让整轮结论建立在旧代码上——本项目为此付过两次代价。多实例并存时，旧进程还会让设备结果反向。

3

先跑离线面（0 成本）

cd server && python scripts/ai_tool_matrix/run.py --dry-run

不花任何模型调用，秒级返回，直接给出路由漏注入与链式依赖违规两个核验。改完语料第一件事就是跑它——把问题挡在花钱之前。

4

起设备、装 APK

adb devices -l
adb -s emulator-5554 install -r app/build/outputs/apk/debug/app-debug.apk
adb -s emulator-5554 reverse tcp:8000 tcp:8000
adb -s emulator-5554 shell am start -n com.aozora.app/.MainActivity

命令一律带 -s。同时插着真机时，裸 adb install 会误装到真机。

5

建 CDP 通路（设备自动化的入口）

# ① 找 WebView 的 devtools socket（PID 每次启动都会变）
adb -s emulator-5554 shell "cat /proc/net/unix | grep webview_devtools_remote"
# ② 转发到本机端口
adb -s emulator-5554 forward tcp:9222 localabstract:webview_devtools_remote_<pid>
# ③ 验证：应返回 JSON 数组，其中一项 title 为 "Aozora"
curl http://127.0.0.1:9222/json/list
实测确认 · 2026-09-29

本项目源码里没有任何 setWebContentsDebuggingEnabled(...) 调用（全仓 grep 零命中），但通路照常可用。原因是 dumpsys package 显示 debug 包带 flags=[ DEBUGGABLE ]——WebView 远程调试对可调试的包是自动开启的。

两条推论决定了适用边界：release APK 走不通这条路；如果哪天 /json/list 连不上，先查 flags= 里有没有 DEBUGGABLE，而不是去改脚本。

四

日常运转：只更新测试需求

这是整套配置存在的目的。一轮完整回归只有四步：

① 改 corpus.json          ← 唯一需要人写的东西
② run.py --dry-run         ← 秒级，核验路由与链式依赖
③ run.py（服务端全量）       ← 量模型层
④ device_flow.mjs <子集>   ← 量可达性与渲染

4.1加一条用例的三条自检

对应 1.2 的三个陷阱，逐条问自己：

  1. 这条用例点名的名字，在播种数据里存在吗？（点名不存在的对象 → 量到的是环境）
  2. 这是写用例吗？判据该是 produced 而不是 landed——除非它是「单发、无前置读取」的快路径用例。
  3. 它跟更早的用例撞名字吗？撞名会被模型正确地拒绝，然后被记成失败。

4.2加一个工具时的连带面

工具注册表是权威源。加工具时这几处要一起改，而且很容易漏一处：注册表本身（含参数 schema）→ 域路由词表 → Skill 文档（漏写是静默的） → 执行器接线（服务端 or 设备端）→ 语料加至少一条 core 用例 → 契约 fixture 两套。

单域上限 8 个工具——超过 8 个，模型的选择准确率显著下降。这条是实测结论，不是经验之谈。

4.3一轮回归的产出

  • report.json：逐条明细（这是交付物，不是中间产物）
  • 通过率 + 按域拆解
  • 未通过逐条：输入 / 实际 / 判定 / 归属（客户端 or 服务端）
  • 跨轮一致性：哪些结论跨轮稳定，哪些是波动
一条容易犯的错

缺陷清单必须合并三个测量面。只看服务端那几条会严重低估问题——因为设备上还有一道闸门挡在 AI 前面，那里的问题一次都没进过服务端测试集。合并后才是完整清单。

五

双端走查配方

5.1页面内注入 JS 的六条配方

配方为什么
点击必须走 Input.dispatchMouseEvent，不要用 el.click()el.click() 在 WebView 里触发不了某些合成事件（React 合成事件、hover 态）；CDP 的 Input 域走 Chromium 真实输入管线，等价于一次真触摸
点击前先 scrollIntoView({block:'center'})视口外的元素坐标算出来在屏幕外，事件直接打空
React 受控 input 必须用 native setter直接 el.value = x 不会触发 React 的 onChange（React 在 value 上装了 descriptor 做劫持）。要用原型上的 setter 调用，再手工派发 input 事件
路由是 hash 路由，用 location.hash 导航不能用路径导航；视觉基线就因为用路径导航，导致认证页 20 张基线全是首页
reload 后页内记录器全丢注入的全局变量、事件钩子在 reload 后不存在。曾有整轮误判「没走 agent」，就是踩了这条
断言优先读 localStorage，不要读 DOM持久化中间件把 store 序列化到存储里。DOM 是视图投影，存储是事实源。前端打的 data-testid 则是 UI 与测试的解耦契约
测量学：让判据能区分两种可能

验证「进入会话即在最新消息、无滚动动画」时，用 requestAnimationFrame 采样 scrollTop：36 条消息的会话下第 1 帧即底（scrollTop = scrollHeight − clientHeight），其后 89 帧恒定、无中间值。

再做一次灵敏度对照：手动触发平滑滚动，采样到 43 个不同值。两种行为在采样上截然可分，才排除了「测量方法本身分辨不出」的假绿。

5.2绕过 UI 直调原生桥

有些东西不必走 UI——直接调原生桥更快、更稳。关键难点是桥的响应是多路复用的：所有响应都走同一个回调，所以必须按 requestId 过滤，并链式保留原有回调（否则会冲掉前端自己注册的那个）。注入一个 Promise 包装：命中的 resolve 并还原，未命中的透传给原回调，超时也要还原。

备用通道：debug 构建里还有一个只走 adb、完全不依赖 WebView 的桥入口——

adb shell am broadcast -a com.aozora.app.BRIDGE_COMMAND \
  --es command "bridge.getVersion" --es payload "e30="

它比 CDP 稳但更粗（拿不到页面上下文）。两条通道互为兜底：CDP 拿不到结果时，先用广播确认「桥本身是好的」，就能立刻把问题二分到「桥坏了」还是「页面驱动坏了」。

5.3两条取证通道

通道抓到的层次什么时候用
CDP Network 域Chromium 网络栈层，含 SSE 帧看流式响应、看真实请求体
页内 monkey-patch fetch应用层，即状态机处理后的形态看业务错误最直接；注意要 clone 响应才能取正文而不消费掉流

抓不到或数据不对时，先确认服务端日志里到底有没有你这次的请求——多实例并存时，你打到的可能不是你以为的那个实例。

5.4模拟器 vs 真机

维度差别影响
网络模拟器可能缺 VALIDATED同步静默不跑，UI 却说「已同步」
连通方式真机必须 adb reverse端口不一致 → 全部同步失败
装包小米/HyperOS 拒 adb install改 push + pm install
稳定性真机 USB 会中途掉线走查优先模拟器，真机只做最终确认
字体度量Android 的 tabular-nums 比桌面宽 4.6–6.3%（中文≈一致）桌面视觉基线不能代替设备侧布局判定
渲染桌面是 Chromium 渲染，设备是 WebView两者互补而非等价——逐页主题覆盖靠桌面，字体与光栅靠设备

5.5真机专项：设备内数据取证

  • 设备上 sqlite3 被禁 → 用 run-as 把库文件读出来
  • Room 的列名是 camelCase（不是 SQL 惯用的 snake_case），查库时别写错
  • 清数据造「新账号」：adb shell pm clear com.aozora.app——会清掉本地库与偏好设置，动手前先确认不是别人的真机

边界与坑清单

6.1先划清边界，避免过度承诺

边界说明
release APK 不可自动化CDP 需要可调试的包；设备自动化只覆盖 debug 构建
物理真机未全覆盖本项目多轮设备回归实际在模拟器完成，触屏手感差异未覆盖
无人值守的环境限制提醒类能力在无人值守下只能验到第一步（系统权限框会超时），完整路径只能人工验
模型有非确定性单轮结果不足以定性；稳定结论至少两轮一致
视觉基线 ≠ 设备渲染桌面基线是 Chromium，设备是 WebView，两者互补
环境替身测不到布局时序「有没有机会先画出那一帧」的差别只有设备侧证据——已在测试文件头写明

6.3三条不变量：每次改动必核

判断「我这次动没动到跨层契约」，看这三个数——任一变化都要在交付记录里显式声明：

不变量为什么危险
桥命令集前后端两侧各自维护，漏改一侧即静默失配
本地库版本版本没升就改表 → 老用户升级后崩
偏好白名单键数多一个键 = 多一条能被 AI 改写的偏好
不要相信文档里的计数

本项目这个数字从 85 漂到过 83，两份不同时期的文档各写着一个数。要实测，并至少三处同步：Kotlin 侧命令表 / TypeScript 侧客户端 / 桥测试里的白名单断言。

6.4跨层契约：改一处必须同时改

契约同步点与事实源
JS 桥命令集Kotlin 命令表 / TS 客户端 / 白名单 / 漂移检测用例——规范清单是唯一的权威源，检测用例必须读它并与另一侧交叉核对
AI 工具名必须下划线不能点号——点号会让 provider 返回 400，整轮请求死掉
金额符号收入 +、支出 −，是隐性跨端契约
契约 op 注册表两套版本 fixture 都要加
一个现成的反面教材

某个用例名叫「所有命令都已定义」，但它实际断言的是一个手写字面量列表有 45 项，不读规范清单。于是真实命令集从 45 涨到 83 的过程中，它一直是绿的。

两个教训：断言的必须是事实源本身，不是事实源的一份抄写（抄写会漂移，且漂移时不报错）；测试的名字是对读者的承诺——名不副实比不写这个测试危害更大，它让后来的人以为这块已经被守住了。

七

迁移到你自己的项目

7.1第一周：最小可运行版本

不必一次建成三层测量面。先做服务端面 + 离线面，它们成本最低、收益最大。

  • 写语料库：先覆盖主干说法，20–30 条即可开工
  • 写服务端执行器：一个函数发请求、一个函数判结果。判据与执行分离（支持重判）
  • 加离线核验：把「前置数据是否齐」「链式依赖是否自洽」做成 0 成本检查
  • 建开关表：把所有 feature flag 列成一张表，写清「不开的症状」——这张表能省掉大量「功能没反应」的排查时间
  • 建四板基线：定下你的四个数字与命令，每次交付都报

7.2第二周：加上设备面

  • 确认你的 App debug 包能开 WebView 调试，拿到调试端点列表返回你的页面
  • 把「找 socket → 转发 → 连 WS → 求值 → 截图」抽成一个零依赖脚本
  • 封装四个原语：按文本点击 / 输入（native setter）/ 导航（hash）/ 等待
  • 让设备执行器读同一份语料库，只跑「必须真机才能验」的子集

7.3持续：立纪律

  • 每修一个缺陷 → 变成一条自动用例（回归集合来自真实咬痕，不是凭想象编写）
  • 每个新用例先反向验证它确实会红
  • 每轮收口记下「今天有什么值得记的」：真实踩过的坑 / 反直觉的发现 / 会重犯的错
  • 失败归因先分三层：前置阻塞 → 环境不稳定 → 代码回归；不要默认「红 = 回归」

交接给同事的一句话

你只需要会两件事：往语料库里加一条 JSON，和看懂报告里的判定。环境怎么起、探针怎么打、判据怎么算，都已经固化成命令了。

命令速查、语料模板与术语对照见下方附录。首个完整案例见 docs/testing/T-M7-ai-tool-matrix-2026-09-21.md；本页与仓库内 docs/engineering/AI自动测试落地手册.md 同源。
