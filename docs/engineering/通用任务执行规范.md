# Aozora 通用任务执行规范

**治理任务：** T-M0-10 执行治理与长期规划

**适用范围：** Aozora 仓库中的开发实现、代码审查和审查问题修复。

**目标：** 用户用简短任务指令即可触发稳定、可验证、可追溯的完整工作流。

## 一、触发与优先级

下列是执行型口令。用户明确使用后，Agent 应执行对应模式的完整流程，不要求用户再次列出计划、测试、文档、提交或推送等步骤。

| 指令示例 | 执行模式 |
|---|---|
| `开发实现 T-M3-02`、`执行 T-M3-02` | 开发实现模式 |
| `审查 T-M3-02`、`Review T-M3-02，范围为……` | Review 模式 |
| `修复 R-M3-01`、`修复 T-M3-review 中全部 P1/P2`、`bug-fix` | Bug-fix 模式 |

执行规则：

1. 用户当前指令的范围和限制优先于本规范。
2. 用户明确要求“不要提交”“不要推送”“只分析”时，跳过对应默认步骤。
3. 用户仅询问方案、解释、状态、可行性或建议时，不进入执行模式。
4. 任务编号、审查范围或问题来源缺失且无法从仓库唯一确定时，先完成安全的只读定位，再向用户确认，不得猜测。
5. 开始前记录 `git status` 基线；不得覆盖、删除、暂存或提交任务范围外的已有改动。
6. 提交只包含当前任务文件。推送前再次核对暂存区和提交内容，禁止夹带密钥、环境文件、签名材料、构建产物或其他任务改动。

## 二、开发实现模式

### 固定流程

1. **确认任务：** 从权威文档确认 Task ID、目标、范围、非目标、依赖、验收标准和当前状态。
2. **加载上下文：** 按 `AGENTS.md` 和 `docs/APP-CONTEXT.md` 的路由只读取相关专题文档；需求变更遵循 `docs/engineering/需求变更规范.md`。
3. **制定计划：** 在动代码前给出可验证的实施计划，每一步写明产物和验证方式；复杂任务同步维护任务计划文档，简单任务可在执行消息中简写。
4. **文档前置：** 架构、协议、数据结构、安全边界或产品规则变化时，先更新对应文档和必要 ADR，再修改代码。
5. **最小实现：** 只修改任务范围内的代码和配置，不顺手重构或清理无关内容。
6. **补充测试：** 新逻辑添加自动化测试；Bug 修复先建立可复现的回归用例。根据影响范围补充契约、迁移、离线、同步、权限、安全或对账测试。
7. **任务级验证：** 先运行与改动直接相关的最小测试集，失败时定位并修复，禁止降低断言、跳过用例或删除 fixture 换取通过。
8. **CI 等价检查：** 运行 `.github/workflows/ci.yml` 中与改动相关的本地等价命令，并运行仓库文档规定但尚未纳入远端 CI 的必要门禁。所有结果必须如实记录。
9. **更新文档状态：** 按真实完成情况更新任务计划、里程碑状态、风险登记和相关专题文档。验证未通过或仍有阻塞时不得标记完成。
10. **交付前检查：** 检查 `git diff`、`git diff --check`、未跟踪文件、敏感信息和改动范围；确认文档描述与实际实现一致。
11. **提交与推送：** 仅暂存当前任务文件，提交信息包含 Task ID，并推送当前分支。不得把工作区中的其他改动带入提交。
12. **确认 CI：** 推送后检查对应远端 CI。若当前环境无法访问远端 CI，应明确记录“未能确认”，不得写成通过；若 CI 失败，在任务范围内修复后重新验证、提交和推送。
13. **最终交付：** 汇报任务编号、改动范围、验证命令与结果、提交哈希、推送分支、远端 CI 状态、已知风险及回退方式。

### 完成门禁

只有同时满足以下条件，才能宣布开发任务完成：

- 任务范围内的实现和测试已完成。
- 相关本地测试、构建和 CI 等价检查通过。
- 必要文档与任务状态已更新且与仓库事实一致。
- 当前任务改动已单独提交并推送。
- 远端 CI 已通过，或因客观条件无法确认且已清楚说明。
- 不存在未记录的阻塞风险。

## 三、Review 模式

### 只读边界

Review 的目标是发现、验证和记录问题，不实施修复：

- 不修改项目代码、测试、配置、依赖、迁移或生成物。
- 不通过格式化、自动修复工具或更新快照改变项目文件。
- 可以运行只读检查、测试、构建、静态分析和安全探针。
- 只允许修改本次审查文档以及为反映审查结果所必需的里程碑、任务状态和风险文档。
- 审查文档变更默认需要单独提交、推送，并确认远端 CI 状态。

### 固定流程

1. **确认范围：** 明确审查 Task、提交或文件范围、基线、包含项和排除项。范围未明确时不得擅自扩大为全仓库审查。
2. **读取依据：** 读取 Task 目标、验收标准、实现记录、相关需求/架构/测试规范及已有 review 文档。
3. **检查仓库事实：** 对照代码、测试、配置、文档和 git 状态验证交付声称，不以已有完成标记代替实测。
4. **运行验证：** 按审查范围运行相关测试、构建、静态检查和必要探针，记录实际命令、通过数、失败数及环境限制。
5. **登记问题：** 使用对应里程碑的连续编号 `R-Mx-nn`；已有问题沿用原编号，禁止为同一问题重复建项。
6. **写入审查文档：** 优先更新用户指定的 review 文档；未指定时使用现有的 `docs/review/T-Mx-review.md`，存在多个轮次时选择当前有效文档并说明依据。
7. **更新状态文档：** 仅依据审查证据更新问题、Task、里程碑或风险状态。存在阻塞项时不得维持与事实冲突的“已完成”状态。
8. **复核只读边界：** 提交前确认除允许的文档外没有产生任何本次 Review 修改；不得处理或提交工作区已有代码改动。
9. **提交与推送：** 仅暂存本次审查与状态文档，提交信息包含审查范围或 Task ID，推送当前分支。
10. **确认 CI 与交付：** 检查远端 CI；最终汇报审查范围、基线、问题数量和优先级、门禁结果、文档路径、提交哈希、推送分支与 CI 状态。

### 问题记录最低字段

每个问题至少包含：

```text
ID：R-Mx-nn
级别：P1 / P2 / P3
类别：正确性 / 安全 / 可靠性 / 性能 / 测试 / 流程 / 文档等
状态：未修复 / 部分修复 / 已修复 / 挂账 / 无法复现
文件与位置：
问题与触发条件：
证据或复现命令：
影响：
修复建议：
复验方法：
```

没有可定位证据的问题不得写成确定性缺陷；应标明推断、待验证条件或环境限制。

## 四、Bug-fix 模式

### 固定流程

1. **确定问题源：** 读取用户指定的 review 文档和问题编号，形成当前修复清单；不得顺手修复清单外问题。
2. **逐项核验现状：** 对每个问题检查当前代码、提交和测试，标记“仍存在、已修复、部分修复、无法复现或超出范围”。禁止依据旧审查结论直接修改。
3. **复现与定位：** 对仍存在的问题建立稳定复现，定位根因和影响边界；多个问题根因相同时仍分别保留状态和证据。
4. **回归用例：** 在实现修复前或同时补充能暴露原问题的回归测试。无法自动化时，记录可重复的人工复验步骤和原因。
5. **最小修复：** 只改解决根因所需内容，不扩展需求，不混入无关重构。
6. **逐项复测：** 每修复一项即运行其回归用例，并记录命令与结果。未通过的项目不得标记已修复。
7. **关联回归：** 全部单项通过后运行受影响模块测试、构建、对账/同步/迁移等专项门禁及 CI 等价检查。
8. **更新 review 历史：** 在原问题下或文档的修复记录区追加“根因、修复内容、回归测试、复验结果、提交信息和日期”；保留原始问题与证据，不覆盖审查历史。
9. **更新项目状态：** 根据实际结果更新问题汇总、Task/里程碑状态和风险登记。部分修复、环境受限或验证失败必须如实保留。
10. **交付前检查：** 检查 diff、格式、敏感信息、文档一致性及暂存范围，确保不包含其他任务改动。
11. **提交与推送：** 仅暂存本轮修复和对应文档，提交信息包含 Task ID 或主要 Review ID，推送当前分支。
12. **确认 CI：** 检查远端 CI；失败则在本轮范围内继续定位、修复、复测并重新推送，无法处理时记录阻塞。
13. **最终交付：** 按问题编号逐项汇报最终状态、根因、修复文件、验证证据，并附提交哈希、推送分支、CI 状态、遗留项和风险。

### 状态判定

| 状态 | 判定标准 |
|---|---|
| 已修复 | 根因已处理，回归用例和关联门禁通过，证据已写回 review 文档 |
| 部分修复 | 只关闭部分触发路径、验证不完整或仍有明确残余风险 |
| 无法复现 | 已记录环境、命令和观察结果，但没有足够证据证明问题已修复 |
| 挂账 | 明确不在本轮范围，并记录原因、风险和建议承接任务 |
| 阻塞 | 缺少必要权限、环境、外部依赖或关键决策，无法安全继续 |

## 五、CI 与提交的共同规则

1. 以 `.github/workflows/ci.yml` 为远端 CI 事实源；工作流变化时以最新文件为准，不在本规范复制易过期的命令清单。
2. 远端 CI 尚未覆盖的模块仍必须执行其项目测试规范规定的本地门禁，并在交付报告中注明“本地验证、远端未覆盖”。
3. 测试失败不得通过修改测试期望、跳过用例或缩小测试范围掩盖，除非需求本身明确改变，且对应文档先完成更新。
4. 工作区存在其他任务改动时，使用精确路径暂存并检查 `git diff --cached`；不得执行会批量纳入无关文件的提交操作。
5. 推送失败、远端 CI 失败或无法访问时必须如实报告。只有获得证据的检查才能标记为通过。
6. 禁止强制推送，除非用户在当前任务中明确授权且目标分支已核实。

## 六、最短可用指令

规范生效后，用户可以直接使用：

```text
开发实现 T-Mx-xx
审查 T-Mx-xx，范围为……
修复 T-Mx-review 中全部 P1/P2
```

Agent 应自行加载本规范、执行相应完整流程，并在出现真正需要用户决策的阻塞项时再提问。
