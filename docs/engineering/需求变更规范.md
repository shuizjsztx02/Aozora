# Aozora 需求变更规范

**适用范围：** 新增需求、已有功能修改、跨模块调整、视觉改版，以及涉及数据、同步、AI 协议或 Dify 工作流的改动。

**目标：** 让每项变更都可追溯、可验证、可兼容，并在出现问题时可控回退。

## 一、开始前：建立需求卡

每项需求必须有任务编号（例如 `T-M2-03`），并在任务描述、PR 或对应需求文档中写清以下内容：

| 项目 | 要求 |
| --- | --- |
| 目标 | 要解决的用户问题和预期结果。 |
| 范围 | 明确包含项与不包含项，避免实现中扩张。 |
| 验收标准 | 可观察、可测试的完成条件。 |
| 影响范围 | 涉及的客户端、服务端、数据、同步、AI、UI 或 Dify 工作流。 |
| 风险与兼容 | 新旧版本、旧数据、离线场景及回退风险。 |

小改动（单点文案、常量、明确根因的局部修复）可在任务描述中简写；其余需求应完整记录。

## 二、按变更级别选择流程

| 级别 | 典型情况 | 进入实现前必须完成 |
| --- | --- | --- |
| L1：局部改动 | 单文件小修改、明确单点修复 | 任务编号、验收标准、相关回归验证。 |
| L2：功能变更 | 新页面、新交互、跨模块功能 | 需求说明、影响分析、任务拆分、测试方案。 |
| L3：关键改动 | 数据模型、API、同步、AI 协议、权限、架构或大改版 | 更新对应架构/设计文档；必要时新增 ADR；补齐兼容、迁移、灰度和回退方案。 |

边界不清时，按更高一级处理。

## 三、先更新文档，再改代码

下列变更必须先更新对应文档，文档评审结论明确后才进入实现：

| 变更内容 | 必须更新的位置 |
| --- | --- |
| 用户需求、产品规则、指标 | `docs/product/` |
| 架构、接口协议、数据模型、同步、安全 | `docs/architecture/`；关键取舍另建 `docs/adr/` 记录 |
| 页面、视觉令牌、组件和交互 | `docs/design/` |
| 测试、构建、发布或工具链 | `docs/engineering/` |
| 里程碑范围和任务状态 | `docs/milestones/` 与 `docs/APP-CONTEXT.md` 的相关任务 |

不改变既有契约的 L1 局部改动无需补充设计文档，但仍须保留任务编号和验证结果。

## 四、关键影响检查

只要命中以下任一项，需求卡中必须写明结论和处理方式：

- **金额与账本：** 金额以分存储和运算；对账不变量不得被破坏。
- **离线与同步：** 断网可用性、离线队列、重试、幂等和冲突处理。
- **AI：** JSON 动作协议、异常输出拦截、本地 NLU 兜底；金额和统计仍由确定性业务代码执行。
- **兼容与迁移：** 旧客户端、旧接口、旧数据和历史数据键的兼容期限与迁移策略。
- **安全与隐私：** 服务商密钥不得进入前端或 APK；权限和敏感数据暴露面必须评估。
- **WebView 边界：** Android 壳、React 页面和 `AozoraBridge` 的契约是否同步变更。

## 五、实现与拆分原则

1. 按“文档/协议 → 数据与服务 → 客户端能力 → UI → 联调与灰度”拆成独立可验收的任务；不在一个改动中混合无关重构。
2. 每一处代码或配置变更都应能对应需求卡中的范围或验收标准；遵循最小改动原则。
3. 影响线上数据、关键流程或接口契约时，实施前必须明确：新旧共存方式、数据迁移步骤、失败处理、功能开关/灰度范围和回退步骤。
4. 修改 Dify `.yml` 时只改目标节点；完成后必须执行 YAML 语法校验和 Dify DSL 结构校验。

## 六、验证与交付门禁

交付前，根据变更范围完成并记录验证结果：

| 变更类型 | 最低验证 |
| --- | --- |
| 所有实现改动 | 构建、相关单元测试或回归用例通过。 |
| 金额/账本改动 | 对账不变量测试（含必要的 fuzz）通过。 |
| 同步/离线改动 | 断网、重连、重试、冲突和重复提交场景验证。 |
| AI/协议改动 | 正常、异常、缺字段和本地兜底用例验证。 |
| 数据结构/迁移 | 新旧数据兼容、迁移成功与迁移失败恢复验证。 |
| UI 改版 | 关键页面和状态（空、加载、失败、离线）回归验证。 |
| Dify `.yml` 改动 | YAML 语法与 Dify DSL 结构校验均通过。 |

交付说明必须包含：任务编号、改动范围、验证命令/结果、已知风险，以及灰度或回退方式（如适用）。风险未消除时，更新 `docs/risk-register.md`，不得仅口头记录。

## 七、固定执行清单

```text
需求卡（编号、范围、验收）
  → 判断 L1 / L2 / L3
  → 更新需求、设计、架构或 ADR（需要时）
  → 影响分析与兼容/回退方案
  → 拆分实施任务
  → 最小改动实现 + 对应回归用例
  → 按影响范围验证
  → 交付记录、灰度观察与风险沉淀
```

## 八、变更后观察

上线或灰度后关注错误率、同步失败率、AI 动作失败率、关键流程完成率和用户反馈。若结果改变了长期技术取舍、产品规则或风险判断，及时补充 ADR、产品文档或 `docs/risk-register.md`。
