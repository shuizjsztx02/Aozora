### REQ-83: 全应用——新增「自动记账」：支付发生后系统自动捕获并入账，用户不必手动记（用户第 1 项）

- **诉求**: 「给 aozora 新增一个自动记账功能……探索一下市面上安卓环境下的 app 都怎么实现自动记账功能，然后对需求尽可能的探究和挖掘找出一个效果较为理想且稳定的方案」（用户原话）。拆成四个子诉求：①**支付发生后不用手动记**（微信/支付宝等渠道的消费自动进入账本）；②**效果理想**（金额准、商户认得出、分类选得对）；③**稳定**（不因第三方 App 改版失败、不被系统省电策略杀掉、不漏记不重记）；④**方案要有调研依据**，不拍脑袋。

- **现状（已核实）**: 分三段——**A 是市面事实（外部调研，2026-10-13）**，**B 是本仓库可复用面与缺口（逐条给 文件:行号）**，**C 是与既有约定的冲突点（必须先解决，否则动工即违规）**。

  **A. 市面方案调研（2026-10-13，安卓环境）**

  | 通道 | 原理 | 代表产品 | 优点 | 硬伤 |
  |---|---|---|---|---|
  | **无障碍服务** `AccessibilityService` | 读屏；用户处于支付成功页/账单页时抓 UI 文本 | 钱迹、一木记账、iCost、小星记账、小花记账、指尖管家、Billbook | 信息最全（金额/时间/商户/订单号），能自发弹窗 | ★ **审核风险最高**：中国软件行业协会 2025-04 发布标准明确禁止智能助手滥用无障碍服务、要求双重授权；Google Play 政策禁止用 `AccessibilityService` 自主发起/规划/执行操作；**维护成本最高**——依赖微信/支付宝的 UI 结构，对方一改版即批量失效，需持续跟进多版本；**FLAG_SECURE / 支付保护页读不到**；需常驻后台，易被厂商省电策略杀；需悬浮窗权限 |
  | **通知监听** `NotificationListenerService` | 读通知栏文本（微信支付公众号消息、支付宝消息、云闪付/银行 App 消费提醒） | 记花（自述 6 类模板 / 20+ 条规则）、chaoxi-jizhang、小星记账（银行短信靠**通知**而非 READ_SMS） | 不依赖第三方 UI 结构 → **不随 App 改版失效**；**无需悬浮窗**；不动第三方 App；`<uses-permission>` **零新增**（通知使用权是系统设置授权，不是 manifest 权限） | ①**部分通知不含商户名**（只有金额），分类准确率受限；②用户可关闭该来源的通知 → **应收不到**；③通知格式仍可能变（但比 UI 结构稳得多）；④Android 15+ 起「不可信 listener」的**敏感通知内容被抹除**（实测口径针对 OTP 类；支付通知是否受影响需本机取证） |
  | **读取短信** `SMS_RECEIVED` / `READ_SMS` | 读银行短信 | 早期方案、部分产品作为可选 | 银行短信格式稳定、金额准 | ★ **基本不可得**：`READ_SMS` 仅默认短信应用可申请，第三方上架各商店均严审；**且与本仓库隐私政策直接冲突**（见 C ②）→ **本轮排除**。**但银行短信的「通知」走通知监听即可，不需要 READ_SMS**——这是关键区分 |
  | **截图 / 分享识别** | 用户分享支付截图 → 视觉模型结构化 | iCost「截图分享识别」、飞鸭 | 零权限风险、准确率高 | 需用户**主动**分享（不「自动」） |
  | **账单文件导入** | 导出微信/支付宝 CSV/XLSX 再解析 | 几乎所有记账 App | 权威（平台原始账）、可月度补漏 | 需用户定期手动导出，实时性差 |
  | **系统级 / 官方 API** | OS 厂商或支付平台直供 | 小米澎湃 OS 钱包「AI 自动记账」 | 体验最好 | ★ **第三方不可得**：系统级只有手机厂商能做，且**小米钱包的微信自动记账内测已于 2026 年终止**（官方称「探索更稳定方案」）；支付宝/微信的账单接口只对**商户**开放，个人开发者无接口 |
  | **Xposed / Hook** | 注入第三方进程 | 开源 AutoAccounting 等 | 可拿到最细数据 | 需 root / LSPosed，受众极小，**不做** |

  **调研结论（三条）**：① **没有任何单一通道能同时做到「全自动 + 稳定 + 合规」**——市面产品的真实形态一律是**多通道组合 + 待确认/补录**，没有例外。② **「稳定」与「合规」指向同一个答案**：**离第三方 UI 越远越稳**（无障碍是反面），**离敏感权限越远越合规**（`READ_SMS` 是反面）。③ 通知监听是唯一「零 manifest 权限 + 不碰第三方进程 + 不随 UI 改版失效」的通道，代价是**覆盖率受用户通知设置制约、部分通知缺商户名**——这个代价只能用**解析能力**和**补漏入口**去补，而不是用更激进的采集去补。

  **B. 本仓库可复用面与缺口（逐条实证）**

  1. **可复用的地基（四项，都是现成的）**：① **服务端 AI 能力**——`/ai/interpret`（`server/src/modules/ai/routes.py:70`）、`/ai/parse-image`（`:211`，服务端 vision 模型解析小票/账单图，`service.py:1375-1451`）与 agent 车道（`:407`），v1/v2 提案骨架、分类注入面（`prompts._render_categories_section`）齐备——**这意味着「解析」这一层不必从零造，而且可以把别的记账 App 只能本地写死的脆弱正则，换成服务端模型 + 本地规则双引擎**，这正是 PR-3「本地优先、云端是增强」的既有形态，也是本产品**唯一的差异化机会**。② **离线队列与同步**——`pending_mutations`（`db/entity/PendingMutationEntity.kt:19-33`）+ 契约「每次本地写入必须与对应 pending mutation 在同一 Room 事务内完成」（同文件 `:8`）+ `Repository.enqueueInsert`（`Repository.kt:590`）统一入口；`SyncScheduler.enqueue()`（`sync/SyncScheduler.kt:32-46`）已具备「写后触发 + 联网约束 + 指数退避」。③ **确认卡与撤销**——v1 `ConfirmationCard` / v2 `V2ConfirmationCard`、审批四值、撤销窗 `activeTxIdsRef` 均已定型；**PR-2 是现成的准绳**：「高置信快速通道自动入账但必须立即可见、带撤销按钮可随时撤销；低置信一律出确认卡。**永不产生用户不知情的账目**」（`docs/product/principles.md:10`）。④ **权限状态机与引导**——`PermissionManager`（`permission/PermissionManager.kt`，四态 `NOT_REQUESTED/GRANTED/DENIED/PERMANENTLY_DENIED`）+ 桥命令 `permissions.get_status` / `permissions.request` / `permissions.open_settings`（`BridgeProtocol.kt:141-143`）+ `requestDevicePermission`（`AozoraBridge.kt:2459`），**跳系统设置页的通道已有**；设备能力通道（ADR-010）`handleDeviceExecute`（`AozoraBridge.kt:2336-2355`）的分派表也易扩展。

2. ★★ **文档先行是硬门禁（本轮第一原则）**：REQ-83 正面冲撞 `APP-CONTEXT.md:97` 的非目标条目与 `privacy-policy-v1.md:23-25` 的「不收集」条款。按 `需求变更规范.md` 三与 `稳定性守则.md` §2.4，**T21-1（文档与 ADR）必须先交付并落笔，未落笔前 T21-2…T21-7 一律不得开工**。这不是流程洁癖：**非目标与隐私政策是能被外部核对的公开承诺**，代码先行会让仓库在一个「自己文档说不能做」的状态下运行。
3. ★★ **采集通道只允许通知监听（本轮最不可退让的一条）**：**不引入 `AccessibilityService`、不引入悬浮窗、不申请 `READ_SMS` / `SMS_RECEIVED`、不使用 Xposed/Hook**。可被守住的自证量：**`AndroidManifest.xml` 的 `<uses-permission>` 集合逐条不变**（本轮只增一个 `<service>` 声明，`SecurityConfigTest.kt` 的既有 manifest 守卫用例应扩展一条「不得出现上述权限」的反向断言）。理由见 REQ-83《方案选型》——**无障碍是「高风险 + 高维护 + 收益可被替代」的组合，在本产品不成立**；`READ_SMS` 是**审核不可得 + 与自家隐私政策打架**，无讨论空间。
4. ★ **去重分两级，且跨源永不自动合并（定死）**：① **同源 `dedupeKey`**（`hash(sourcePackage + 通知 key/postTime + 归一化文本)`）——**唯一索引 + 自动丢弃重复回调**（`NotificationListenerService` 会重复回调 `onNotificationPosted`，不同步去重必重复入账）。② **跨源 `crossKey`**（`hash(方向 + 金额分 + 分钟级时间桶)`）——微信绑卡支付时「微信支付通知」与「银行 App 通知」会**同时到达**，这是**最大的重复来源**；但**同额消费是日常**（两杯 18 元咖啡），**自动合并会吃掉真实账目**。故跨源命中**只在待确认箱里标一句「疑似与某笔重复」，由人决定**——对齐 PR-2「永不产生用户不知情的账目」，宁可多问一句，不可默默吞掉一笔。
5. ★ **幂等键由客户端确定性生成，禁止任何 LLM 参与**：`dedupeKey` / `crossKey` 一律是**确定性 hash**（来源包名、时间、金额、归一化文本的纯函数）。本仓已有惨痛先例——**LLM 生成 UUID 当幂等键 → 照抄训练示例值 → 撞键 → 静默丢弃**（T18 收口实证）。任何「让模型给这笔账编个 id」的形态**一律禁止**。
6. ★ **新增 `auto_captures` 表（Room v11 → v12）是不可回避的**：「一条被捕获、尚未解析/确认的原始通知」有独立生命周期与唯一性约束，`pending_mutations`（装已定型的写操作）语义不符、**不得挪用**。迁移必须走 `MIGRATION_11_12`（**不开启 `fallbackToDestructiveMigration`**，`AozoraDatabase.kt:40` 的既有取向不变），并导出 `12.json`。**除此之外不得再加第二张表**——商户记忆第一期复用本表内同 `merchantKey` 的已 committed 记录（决策 #9）。
7. **开关与配置走 Repository 自管 meta 键，meta 白名单保持 11 键**：自动记账开关是**每台设备独立**的（系统的通知使用权本就是按设备授予的），**不上云、不进 `MetaWhitelist.KEYS`**——照 `master_book_id` / `personas_seeded` / 分类种子版本键的既有做法。→ **本轮 meta 白名单零增键**，收口核验 = `MetaWhitelist.KEYS` 仍是 11 项。
8. ★ **通知使用权不是运行时权限，`PermissionManager` 要扩新形态（定死口径）**：`NotificationListenerService` 的授权**查不到也申请不到**——判定只能用 `NotificationManagerCompat.getEnabledListenerPackages()`（是否含 `com.aozora.app`），引导只能跳 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`。**不得**试图用 `permissions.request` 走运行时权限弹窗（那条路对这个授权无效，会产出一个永远 `DENIED` 的假状态）。**UI 要给三种态**：未授权 / 已授权 / 已授权但服务被系统或用户停用（用 `getEnabledListenerPackages` 与「服务是否在跑」两个信号区分），三种态各自一句人话解释。
9. **商户记忆第一期不开新表**：判据是「同 `merchantKey` 的已 committed 记录，取其最近一次的分类/账户」。够用就停（最小改动）；若实测证明跨账本/跨时间的记忆需求更复杂，**再开卡**，本轮不预设。
10. **桥命令四条、四处同步（含两处子集口径）**：`autobook.get_status` / `autobook.set_enabled` / `autobook.list_captures` / `autobook.resolve_capture`。**83 → 87**，四处 = `BridgeProtocol.kt`（常量 + `ALL`）/ `SecurityConfigTest.kt` 断言 / `bridge-types.ts` / `native-bridge.ts`；**另两处口径一并同步**：`BridgeProtocolTest.kt` 的清单与 `native-bridge.test.ts` 的分组描述串（`it(...)` 标题里逐段列了各轮增量，**新增四条必须补进去**，否则下一个读它的人会以为计数不对）。
11. ★ **「非支付类通知不落库、不上行」必须有守护用例（隐私承诺的兑现点）**：预筛是**纯函数**（`NotificationFilter`），用例必须覆盖——验证码 / 聊天消息 / 系统通知 / 广告推送**不得**产生 `auto_captures` 行；且**反向验证**（把预筛的 keyword 判断打回缺陷形态，确认用例变红——`稳定性守则.md` §3.2）。**这条是本轮唯一「隐私面」的自动化防线**，缺了它就只剩口头承诺。
12. ★ **断网不得静默丢失（对齐 REQ-72 的教训）**：捕获一律**先落本地** `auto_captures`（状态 `captured`），联网后再解析、再入账。**禁止**「网络失败就丢弃」——REQ-72 的实证是「**丢弃后游标照常推进＝静默永久丢失**」，同类事故不得重演。守护用例：断网状态下捕获一笔 → 本地有行 → 联网后能走到 `committed` 或 `pending_confirm`。
13. **服务端解析入口用「判据先行」决定是否新增（判据先行的既有范式）**：先用既有 `/ai/interpret` 直接喂真实通知原文取一轮命中率实测；**够用就复用、不新增端点**（最小改动优先）；不够才新增 `POST /ai/parse-notification`。无论走哪条：**必须计入 `ai_usage`**（成本可观测），**guest 日配额照常生效**，且提示词必须显式处理四类「**不是消费**」的语义——**退款 / 转账（含信用卡还款）/ 理财基金买入 / 红包收发**（否则会把这些记成消费，污染收支统计）。**判据与实测数字必须写进交付记录**，不得以「反正是必要的」免测。
14. **不动共享层（本轮红线）**：不改 `Money` 与交易金额链路（金额一律整数分，NFR-7）、不动 `pending_mutations` 的语义与契约、不动同步协议与 `SyncEngine` 编排、不动预算聚合口径、不动 v1/v2 提案与确认卡的既有形状（自动记账**只是新增提案来源**，不新造卡片类型）、不引入前台服务、不为自动记账新增账本/账户维度。**写库一律走 `Repository.enqueueInsert`**，与 `pending_mutations` 同事务——这是离线语义不被破坏的前提。
15. **轮内文件串行**：`app/src/main/java/com/aozora/app/db/` 簇（`AozoraDatabase.kt` / `Migrations.kt` / 新 entity+dao）归 **T21-3 独占**；`bridge/{BridgeProtocol.kt,AozoraBridge.kt}` + 四处同步文件归 **T21-4 独占**（T21-6 / T21-7 只消费、不改桥）；`AndroidManifest.xml` 归 **T21-3 独占**（T21-4 因 Kotlin 侧有桥常量需要读它，**只读不写**）；`PermissionManager.kt` 归 **T21-6 独占**；`docs/` 区归 **T21-1 独占**。
16. **真机复测口径（jsdom / JVM 单测无验证力的部分，实施卡必须走）**：**通知监听的授权与投递只能在真机/模拟器上验**——① 授予通知使用权后，用真实微信/支付宝（或构造的等价通知）触发一笔，看是否落 `auto_captures`；② **验证码类通知不产生任何行**（隐私面现场取证）；③ **同一条通知重复投递只产生一行**（去重现场取证）；④ **断网捕获、联网补解析**（决策 #12 现场取证）；⑤ **撤销授权后服务停用、不再捕获**（用户可撤销的承诺兑现）。**JVM 侧只能验纯函数**（`NotificationFilter` / `LocalNotificationParser` / 去重键），**不得用 Robolectric 的「伪造通知投递」冒充真机验收**。
17. **`NotificationListenerService` 的系统层约束登记为已知限制（收口落笔）**：Android 13+ 对**侧载**应用授予通知使用权需在应用详情页先「允许受限设置」，Android 15+ 会**抹除「不可信 listener」的敏感通知内容**（实测口径针对 OTP 类，**支付通知是否受影响必须在 T21-3 本机取证**）。这两条直接影响走查步骤与「覆盖率」的宣传口径，**不得等收口才发现**——T21-3 卡内取数，收口卡写入已知限制。
18. **用户可见的诚实口径（文案红线）**：自动记账**不得宣传成「全自动、零遗漏」**。通知通道的覆盖率**受用户自己的通知设置制约**——用户关掉了微信通知，就收不到那部分。故对用户的话只有两句是对的：「支付类通知到了就会自动记」+「没记上的可以一键补」。**禁止**出现「100% 自动」「绝不遗漏」类表述（这与 T20-9「回执文案必须诚实」是同一种纪律）。
