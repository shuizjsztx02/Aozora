### REQ-83: 全应用——新增「自动记账」：支付发生后系统自动捕获并入账，用户不必手动记（用户第 1 项）

- **诉求**: 「给 aozora 新增一个自动记账功能……探索一下市面上安卓环境下的 app 都怎么实现自动记账功能，然后对需求尽可能的探究和挖掘找出一个效果较为理想且稳定的方案」（用户原话）。拆成四个子诉求：①**支付发生后不用手动记**（微信/支付宝等渠道的消费自动进入账本）；②**效果理想**（金额准、商户认得出、分类选得对）；③**稳定**（不因第三方 App 改版失败、不被系统省电策略杀掉、不漏记不重记）；④**方案要有调研依据**，不拍脑袋。
- **同日澄清（2026-10-13，用户对首版登记的订正）**: 「修改一下，**可以通过无障碍服务这个渠道来实现自动记账的功能**」（用户原话）。→ **首版「第一版明确不做无障碍」的取向作废**，采集层改为**双通道：无障碍服务 + 通知监听**。这条澄清与市面调研是同向的——**效果最好的那批产品（钱迹 / iCost / 小星记账 / 一木）恰恰都以无障碍为主通道**，因为它是唯一能拿到「商户名 + 订单号」的通道；本卡的方案选型、去重口径、合规面、任务拆解均按双通道重写。

- **现状（已核实）**: 分三段——**A 是市面事实（外部调研，2026-10-13）**，**B 是本仓库可复用面与缺口（逐条给 文件:行号）**，**C 是与既有约定的冲突点（必须先解决，否则动工即违规）**。

  **A. 市面方案调研（2026-10-13，安卓环境）**

  | 通道 | 原理 | 代表产品 | 优点 | 硬伤 |
  |---|---|---|---|---|
  | **无障碍服务** `AccessibilityService` | 读屏；用户处于支付成功页/账单详情页时抓 UI 节点的**文本** | 钱迹、一木记账、iCost、小星记账、小花记账、指尖管家、Billbook | 信息最全（**金额 + 商户/对方 + 时间 + 订单号 + 收支方向**），能覆盖「通知没推」的情形，不依赖用户的通知设置 | ★ **代价三条（必须写进口径）**：①**审核与合规成本**——中国软件行业协会 2025-04 标准要求为 AI 开通无障碍须**用户明确授权 + 提供便捷撤销**，Google Play 政策要求**显著披露与用途限定**（本产品须声明 `isAccessibilityTool="false"` 并做卡内说明）；②**维护成本**——依赖微信/支付宝的页面文案与结构，对方改版可能导致规则失效，**须持续适配**；③**FLAG_SECURE / 支付保护页读不到**。**另有一条本产品可以规避的**：市面产品普遍另配**悬浮窗**弹确认——**本产品不引入悬浮窗**，改用已有 `POST_NOTIFICATIONS` 通知触达（决策 #3） |
  | **通知监听** `NotificationListenerService` | 读通知栏文本（微信支付公众号消息、支付宝消息、云闪付/银行 App 消费提醒） | 记花（自述 6 类模板 / 20+ 条规则）、chaoxi-jizhang、小星记账（银行短信靠**通知**而非 READ_SMS） | 不依赖第三方 UI 结构 → **不随 App 改版失效**；**无需悬浮窗**；不动第三方 App；`<uses-permission>` **零新增**（通知使用权是系统设置授权，不是 manifest 权限） | ①**部分通知不含商户名**（只有金额），分类准确率受限；②用户可关闭该来源的通知 → **就收不到**；③通知格式仍可能变（但比 UI 结构稳得多）；④Android 15+ 起「不可信 listener」的**敏感通知内容被抹除**（实测口径针对 OTP 类；支付通知是否受影响需本机取证） |
  | **读取短信** `SMS_RECEIVED` / `READ_SMS` | 读银行短信 | 早期方案、部分产品作为可选 | 银行短信格式稳定、金额准 | ★ **基本不可得**：`READ_SMS` 仅默认短信应用可申请，第三方上架各商店均严审；**且与本仓库隐私政策直接冲突**（见 C ②）→ **本轮排除**。**但银行短信的「通知」走通知监听即可，不需要 READ_SMS**——这是关键区分 |
  | **截图 / 分享识别** | 用户分享支付截图 → 视觉模型结构化 | iCost「截图分享识别」、飞鸭 | 零权限风险、准确率高 | 需用户**主动**分享（不「自动」） |
  | **账单文件导入** | 导出微信/支付宝 CSV/XLSX 再解析 | 几乎所有记账 App | 权威（平台原始账）、可月度补漏 | 需用户定期手动导出，实时性差 |
  | **系统级 / 官方 API** | OS 厂商或支付平台直供 | 小米澎湃 OS 钱包「AI 自动记账」 | 体验最好 | ★ **第三方不可得**：系统级只有手机厂商能做，且**小米钱包的微信自动记账内测已于 2026 年终止**（官方称「探索更稳定方案」）；支付宝/微信的账单接口只对**商户**开放，个人开发者无接口 |
  | **Xposed / Hook** | 注入第三方进程 | 开源 AutoAccounting 等 | 可拿到最细数据 | 需 root / LSPosed，受众极小，**不做** |

  **调研结论（三条）**：① **没有任何单一通道能同时做到「全自动 + 稳定 + 合规」**——市面产品的真实形态一律是**多通道组合 + 待确认/补录**，没有例外；**「效果理想」的那批产品清一色是「无障碍（拿全字段）+ 通知（补漏、免 UI 依赖）」的组合**。② **两条通道的失效面几乎不重叠**，这是双通道能成立的根本原因：无障碍**怕 UI 改版、怕 FLAG_SECURE/支付保护**，但不依赖用户的通知设置；通知**不随 UI 改版失效**，但**缺商户名、且用户关掉通知就收不到**。二者互补 → **互为兜底**，这比单独任何一条都稳。③ **代价是明确的、必须写进口径的两条**：无障碍带来**审核与维护成本**（用途申报、版本适配），通知带来**覆盖率上限**（受用户通知设置制约）——**都不许宣传成「100% 自动」**（决策 #20）。

  **B. 本仓库可复用面与缺口（逐条实证）**

  1. **可复用的地基（四项，都是现成的）**：① **服务端 AI 能力**——`/ai/interpret`（`server/src/modules/ai/routes.py:70`）、`/ai/parse-image`（`:211`，服务端 vision 模型解析小票/账单图，`service.py:1375-1451`）与 agent 车道（`:407`），v1/v2 提案骨架、分类注入面（`prompts._render_categories_section`）齐备——**这意味着「解析」这一层不必从零造，而且可以把别的记账 App 只能本地写死的脆弱正则，换成服务端模型 + 本地规则双引擎**，这正是 PR-3「本地优先、云端是增强」的既有形态，也是本产品**唯一的差异化机会**。② **离线队列与同步**——`pending_mutations`（`db/entity/PendingMutationEntity.kt:19-33`）+ 契约「每次本地写入必须与对应 pending mutation 在同一 Room 事务内完成」（同文件 `:8`）+ `Repository.enqueueInsert`（`Repository.kt:590`）统一入口；`SyncScheduler.enqueue()`（`sync/SyncScheduler.kt:32-46`）已具备「写后触发 + 联网约束 + 指数退避」。③ **确认卡与撤销**——v1 `ConfirmationCard` / v2 `V2ConfirmationCard`、审批四值、撤销窗 `activeTxIdsRef` 均已定型；**PR-2 是现成的准绳**：「高置信快速通道自动入账但必须立即可见、带撤销按钮可随时撤销；低置信一律出确认卡。**永不产生用户不知情的账目**」（`docs/product/principles.md:10`）。④ **权限状态机与引导**——`PermissionManager`（`permission/PermissionManager.kt`，四态 `NOT_REQUESTED/GRANTED/DENIED/PERMANENTLY_DENIED`）+ 桥命令 `permissions.get_status` / `permissions.request` / `permissions.open_settings`（`BridgeProtocol.kt:141-143`）+ `requestDevicePermission`（`AozoraBridge.kt:2459`），**跳系统设置页的通道已有**；设备能力通道（ADR-010）`handleDeviceExecute`（`AozoraBridge.kt:2336-2355`）的分派表也易扩展。
  2. ★ **缺口一：客户端没有任何常驻采集能力**。`AndroidManifest.xml` 实测**无任何 `<service>` 声明**；全仓 `grep` **零命中** `NotificationListenerService` / `AccessibilityService` / `ForegroundService` / `JobScheduler`。现有后台只有 WorkManager（同步，`SyncWorker` + `SyncScheduler`）与 AlarmManager（提醒/定时规则，`ReminderScheduler.kt:103-122` / `ScheduledTxReceiver.kt:82-99`）。→ **通知监听服务与无障碍服务都是全新引入的组件**，且**都只能通过系统设置页授权**（不是运行时权限）。
  3. ★ **缺口二：「其他应用的支付事件」在数据模型里没有落点**。Room **v11** 的 12 张实体表（`TransactionEntity` / `BookEntity` / `CategoryEntity` / `AccountEntity` / `BudgetEntity` / `PendingMutationEntity` / `SyncMetaEntity` / `UserConsentEntity` / `SavingsGoalEntity` / `ScheduledRuleEntity` / `ChatPersonaEntity` / `UserPreferenceEntity`）**没有任何一张能承载「一条被捕获、尚未解析/尚未确认的原始事件」**——它有独立生命周期（captured → parsed → pending_confirm → committed / ignored / failed）、需要**去重键唯一索引**、需要**原文留档**、且**双通道会写同一张表**（靠 `sourceChannel` 区分）。`pending_mutations` 装的是**已定型的写操作**，语义不符，**不得挪用**。→ 这是**「REQ-69 的 `account_type`」同款形态**：新能力需要的字段，底层没有落点 → **必然新增一张 Room 表 → Room v11 → v12**（本轮唯一的红线变动，必须在设计决策里显式声明，见决策 #6）。
  4. ★ **缺口三：两类授权都没有走查路径**。`PermissionManager` 只覆盖 `CAMERA` / `READ_MEDIA_IMAGES` / `POST_NOTIFICATIONS` 三种**运行时权限**（`PermissionManager.kt` 类注释自述）；而**通知使用权**与**无障碍服务**都**不是运行时权限**，`checkSelfPermission` 查不到——前者只能靠 `NotificationManagerCompat.getEnabledListenerPackages()` 判定 + `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS` 跳转，后者只能靠 `AccessibilityManager.getEnabledAccessibilityServiceList()` / `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` 判定 + `Settings.ACTION_ACCESSIBILITY_SETTINGS` 跳转。→ 权限状态机**要扩一种「设置页授权」的形态，且要支持两个授权目标**。
  5. **缺口的量级**：桥命令 83 **必然增加**（状态要能同时反映两个授权 + 待确认箱要可读可操作）；Room **必然 v12**（缺口二）；meta 白名单 **可以不变**（开关走 Repository 自管键，见决策 #7）。

  2. ★★ **隐私政策正面冲突（双通道下更重）**：`docs/legal/privacy-policy-v1.md:23` 明写「**不收集通讯录、短信、通话记录**」、`:25`「不收集其他应用的使用数据」。**两条通道读的都是其他 App 的内容**——通知监听读通知文本，无障碍服务读**第三方支付页面的屏幕文本**，后者更敏感。即便我们只在用户选定的支付类来源上工作、且**绝不上行原文以外的任何东西**，也必须**改写隐私政策**：新增「自动记账」专节，按**通道分别**明示——读取范围（通知：仅用户选定来源的支付类通知；无障碍：**仅在用户选定的支付类应用处于支付/账单相关页面时**读取该页面的文本）、处理位置（预筛在设备内完成、非支付类内容当场丢弃不落库）、上行范围（仅疑似交易文本，且可整体关闭）、以及**用户可随时撤销**。`app/src/main/java/com/aozora/app/consent/` 侧的 `consent.record` / `UserConsentEntity`（桥命令 `BridgeProtocol.kt:145-146`）是现成的同意面基座。
  3. **PR-2 是硬约束不是参考**：「**永不产生用户不知情的账目**」→ 自动记账**不得**做成「静默写库、事后才在某个角落露面」。凡自动入账，**必须立即可见 + 可撤销**；凡识别有疑，**必须进待确认箱**。
  4. **PR-3 的离线口径**（`principles.md:11`，M7 收窄后）：离线面 = 本地规则 NLU 覆盖的记账。→ 自动记账在**断网时不得静默丢失**：捕获必须落本地、排队，联网后补解析、补入账。这条与 **R-PROD 系列既有教训**同源——REQ-72 的「丢弃后游标照常推进＝静默永久丢失」是同一类事故，**不得重演**。
  5. **权限红线（双通道下的新口径，收窄但不放手）**：**`READ_SMS` / `SMS_RECEIVED` 不申请**（银行短信的**通知**走通知监听即可，不需要短信权限）、**悬浮窗不申请**（`SYSTEM_ALERT_WINDOW`——市面无障碍方案普遍要它，本产品用已有 `POST_NOTIFICATIONS` 通知触达替代）、**不使用 Xposed/Hook**、**不自动点击或操作第三方 App**（无障碍**只读不写**：`AccessibilityService` 只订阅窗口事件并读取节点文本，**不执行任何 `ACTION_CLICK` 等手势**——这是与「AI 智能体操作第三方 App」的分界线，也是 2025 软协标准与不正当竞争判例的落点）。**`AndroidManifest.xml` 的 `<uses-permission>` 集合逐条不变**——两条通道都**不通过 `<uses-permission>` 授权**（`NotificationListenerService` 与 `AccessibilityService` 都是 `<service>` + `android:permission` 声明，授权在系统设置页），故「零新增 manifest 权限」这条**在双通道下依然成立**，且必须由 `SecurityConfigTest.kt` 的反向断言钉住（决策 #3）。

     - **L2 跨通道同笔** → `mergeKey`（`hash(方向 + 金额分 + 分钟级时间桶)`）命中**且**「两边都无商户名 **或** 商户名相同」→ **合并为一条**（`mergedInto` 留痕），**保留信息最全的那份**（`sourceChannel` 优先级 无障碍 > 通知），标 `multi_source`。★ **合并只解决「不重复入账」，不改变「要不要问用户」**——合并后的条目仍按置信度走，且**在待确认箱与交易详情里可见来源数**（不静默）。
     - **L3 同额但不可判定** → 商户名不同、或时间窗外的同额 → **不合并**，只标「疑似与其他一笔重复」的**提示**。理由：同额消费是日常（两杯 18 元咖啡），**自动合并会吃掉真实账目**；但**两条通道同时抓到同一笔**是强信号（两个独立来源印证），故 L2 允许自动合并、L3 不允许。
  4. **解析与编排层（两条通道共用一条链）**：新增 `autobook/AutoBookEngine.kt` 编排：**采集（两条通道）→ L1/L2/L3 去重 → 本地规则解析 → 高置信直接成草稿 / 其余排队 → 联网上行服务端 → 落 `committed` 或 `pending_confirm`**。① **本地规则**（`autobook/LocalCaptureParser.kt`，纯函数 + 用例集）：**输入统一是文本**（无障碍把页面文本按行拼装、通知取标题+正文），故**两条通道共用同一套模板**——微信支付页/微信通知、支付宝支付页/支付宝通知、云闪付、银行 App、银行短信 各若干条，**离线可用**。② **服务端**：**判据先行**——先用 `/ai/interpret` 直接喂文本取一轮命中率实测，**够用就不新增端点**（最小改动），不够再新增 `POST /ai/parse-notification`（复用 v1 proposal 骨架与 `_render_categories_section` 分类注入面，提示词独立——**页面/通知文案与用户口语差异大**，且必须显式处理**退款 / 转账（含信用卡还款）/ 理财基金买入 / 红包收发**四类「**不是消费**」的语义）。无论走哪条，**都要计入 `ai_usage`**（成本可观测；guest 日配额 `check_daily_quota` 照常生效）。③ **商户记忆**：第一期**不开新表**——用 `auto_captures` 表内同 `merchantKey` 的已 `committed` 记录回查上次分类（零新表，最小改动；若后续证明不够再开卡）。★ **无障碍通道的存在让商户记忆真正可用**——通知通道常常拿不到商户名，无障碍拿得到，两者进同一张表后记忆的命中率显著提高。
  5. **桥与交互层**：新增 **`autobook.*` 四条桥命令**——`autobook.get_status`（开关 / **两个授权各自的态** / 今日捕获数 / 待确认数）、`autobook.set_enabled`、`autobook.list_captures`（待确认箱分页）、`autobook.resolve_capture`（确认 / 改后确认 / 忽略）。**桥计数 83 → 87**，**四处同步铁律照旧**（`BridgeProtocol.kt` + `SecurityConfigTest.kt` + `bridge-types.ts` + `native-bridge.ts`，另 `BridgeProtocolTest.kt` 的子集口径与 `native-bridge.test.ts` 的分组描述同步）。UI 三块：① **设置页新增「自动记账」区块**——开关 + **两条授权各自的引导与状态**（无障碍：`AccessibilityManager.getEnabledAccessibilityServiceList()` 判定 + 跳 `Settings.ACTION_ACCESSIBILITY_SETTINGS`；通知：`NotificationManagerCompat.getEnabledListenerPackages()` 判定 + 跳 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`；**两种都是「设置页授权」，不是运行时权限**，故 `PermissionManager` 要扩出这种形态并支持两个目标，决策 #8）+ **来源清单**（内置三项 + 「从已安装应用添加」）+ **用途说明**（读什么、不读什么、**不操作什么**、上不上行）+ **撤销入口**。② **捕获后的即时触达**：★ **不用悬浮窗**——用已有 `POST_NOTIFICATIONS` 发一条通知「已记一笔 ¥32.00 · 星巴克 · 点击确认」，点进待确认箱（这是对市面「悬浮窗弹确认」的低权限替代，决策 #3）。③ **首页「待确认」入口**（仅当有待确认项时出现；自动入账的账目走既有「立即可见 + 撤销」通道，不新造组件）。**不做什么**：**不做悬浮窗**、**不申请 `READ_SMS`**、**无障碍只读不写（禁止 `performAction`）**、不使用 Xposed/Hook、**不做「静默写库、事后不露面」的任何形态**、不改 `Money` 与交易金额链路、不动 `pending_mutations` 的语义、不动同步协议、不为自动记账新增账本/账户维度。

2. ★★ **文档先行是硬门禁（本轮第一原则）**：REQ-83 正面冲撞 `APP-CONTEXT.md:97` 的非目标条目与 `privacy-policy-v1.md:23-25` 的「不收集」条款。按 `需求变更规范.md` 三与 `稳定性守则.md` §2.4，**T21-1（文档与 ADR）必须先交付并落笔，未落笔前 T21-2…T21-8 一律不得开工**。这不是流程洁癖：**非目标与隐私政策是能被外部核对的公开承诺**，代码先行会让仓库在一个「自己文档说不能做」的状态下运行。**无障碍通道还多一层**：用途说明与商店申报口径属**上架前置物料**，必须在写码前定稿（决策 #18）。
3. ★★ **采集通道＝双通道（无障碍 + 通知），红线收窄但不放手**：**两条通道都要**——无障碍拿全字段（商户/订单号）且不依赖用户通知设置，通知不随 App 改版失效，**二者失效面几乎不重叠、互为兜底**。**仍然禁止的四项**：**`READ_SMS` / `SMS_RECEIVED` 不申请**（银行短信的**通知**走通知监听即可）、**悬浮窗 `SYSTEM_ALERT_WINDOW` 不申请**（用已有 `POST_NOTIFICATIONS` 通知触达替代，见决策 #4）、**Xposed/Hook 不用**、★ **无障碍只读不写**（决策 #5）。可被守住的自证量：**`AndroidManifest.xml` 的 `<uses-permission>` 集合逐条不变**——两条通道都靠 `<service>` + `android:permission` 声明、授权在系统设置页，**都不走 `<uses-permission>`**；`SecurityConfigTest.kt` 应扩展反向断言钉住「不得出现 `READ_SMS` / `SYSTEM_ALERT_WINDOW`」。
4. ★ **不用悬浮窗，用通知触达（对市面方案的刻意偏离）**：市面无障碍方案几乎都配悬浮窗来弹确认窗；本产品**不申请 `SYSTEM_ALERT_WINDOW`**——捕获后用已有 `POST_NOTIFICATIONS` 发一条「已记一笔 ¥32.00 · 星巴克 · 点击确认」。**少一个高危权限，UX 不减**；这也是 `APP-CONTEXT.md:97` 新口径要写清的一条。
5. ★★ **无障碍只读不写（本轮的合规分界线）**：`AccessibilityService` **只订阅窗口事件 + 读取节点文本**，**禁止调用任何 `performAction`（`ACTION_CLICK` / `ACTION_SET_TEXT` / 手势派发一律禁止）**。这是「读屏记账」与「AI 智能体操作第三方 App」的分界线——2025 软协标准与不正当竞争判例的落点都在后者。守护方式：配置 XML 里**不声明 `canPerformGestures`**，并在 `SecurityConfigTest.kt` 加反向断言；用例层面**断言服务代码中不存在 `performAction` 调用**（可用 grep 式守护）。
6. ★ **去重分三级（定死）**：① **L1 同通道同事件** → `dedupeKey`（`hash(sourceChannel + sourcePackage + 事件 key/postTime + 归一化文本)`）**唯一索引 + 自动丢弃**。★ 这一级**在无障碍通道上是必需的**——`TYPE_WINDOW_CONTENT_CHANGED` 在一个页面上会**高频抖动**，不按事件去重必然重复入账。② **L2 跨通道同笔** → `mergeKey`（`hash(方向 + 金额分 + 分钟级时间桶)`）命中**且**（两边都无商户名 **或** 商户名相同）→ **合并为一条**，保留信息最全的那份（无障碍 > 通知），标 `multi_source`。**两条通道同时抓到同一笔 = 两个独立来源印证**，这是允许自动合并的依据。③ **L3 同额但不可判定**（商户名不同 / 时间窗外）→ **不合并**，只标「疑似重复」提示。理由：同额消费是日常（两杯 18 元咖啡），**自动合并会吃掉真实账目**。★ **合并只解决「不重复入账」，不改变「要不要问用户」**——合并后仍按置信度走，且**在待确认箱与交易详情里可见来源数**（不静默）。
7. ★ **幂等键由客户端确定性生成，禁止任何 LLM 参与**：`dedupeKey` / `mergeKey` 一律是**确定性 hash**（通道、包名、时间、金额、归一化文本的纯函数）。本仓已有惨痛先例——**LLM 生成 UUID 当幂等键 → 照抄训练示例值 → 撞键 → 静默丢弃**（T18 收口实证）。任何「让模型给这笔账编个 id」的形态**一律禁止**。
8. ★ **新增 `auto_captures` 表（Room v11 → v12）是不可回避的**：「一条被捕获、尚未解析/确认的原始事件」有独立生命周期与唯一性约束，且**两条通道要写同一张表**（靠 `sourceChannel` 区分）；`pending_mutations`（装已定型的写操作）语义不符、**不得挪用**。迁移必须走 `MIGRATION_11_12`（**不开启 `fallbackToDestructiveMigration`**，`AozoraDatabase.kt:40` 的既有取向不变），并导出 `12.json`。**除此之外不得再加第二张表**——商户记忆第一期复用本表内同 `merchantKey` 的已 committed 记录（决策 #10）。
9. **开关与配置走 Repository 自管 meta 键，meta 白名单保持 11 键**：自动记账开关是**每台设备独立**的（两类授权本就是按设备授予的），**不上云、不进 `MetaWhitelist.KEYS`**——照 `master_book_id` / `personas_seeded` / 分类种子版本键的既有做法。→ **本轮 meta 白名单零增键**，收口核验 = `MetaWhitelist.KEYS` 仍是 11 项。
10. ★ **两类授权都是「设置页授权」，`PermissionManager` 要扩出新形态并支持两个目标（定死口径）**：**无障碍**——判定用 `AccessibilityManager.getEnabledAccessibilityServiceList()`（或 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`），引导跳 `Settings.ACTION_ACCESSIBILITY_SETTINGS`；**通知**——判定用 `NotificationManagerCompat.getEnabledListenerPackages()`，引导跳 `Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`。**两者都查不到、也申请不到**——**不得**试图用 `permissions.request` 走运行时权限弹窗（那条路对这些授权无效，只会产出一个永远 `DENIED` 的假状态）。**UI 每类要给三种态**：未授权 / 已授权 / 已授权但服务被系统或用户停用，各自一句人话解释。**两个授权可各自独立开关**（只授一个也应有可用的一半能力）。

18. ★ **无障碍通道的系统层与审核约束，登记为已知限制（T21-4 卡内取数，收口落笔）**：① **Android 13+ 侧载应用授予无障碍需先在应用详情页「允许受限设置」**（Android 15+ 更严）——直接影响走查步骤；② **`FLAG_SECURE` / 支付保护页读不到**——必须在真机上确认微信/支付宝的**支付结果页**在常见机型的支付保护开启与否两种状态下**是否可读**；③ **商店审核**——国内商店须做无障碍权限申报（钱迹 / iCost / 小星记账均有在架先例，口径可参考），Google Play 须声明 `isAccessibilityTool="false"` 并做显著披露。**这三条不得等收口才发现**。
19. **真机复测口径（jsdom / JVM 单测无验证力的部分，实施卡必须走）**：**两类授权与两条通道的投递都只能在真机/模拟器上验**——① 分别授予无障碍/通知使用权后各触发一笔，看是否落 `auto_captures` 且 `sourceChannel` 正确；② **验证码类通知与「非支付页面的浏览」不产生任何行**（隐私面现场取证，两条通道各一次）；③ **同一条事件重复投递只产生一行**（L1 去重现场取证）；④ **两条通道抓到同一笔时合并为一条且保留商户名**（L2 现场取证）；⑤ **两笔同额不同商户不合并**（L3 现场取证）；⑥ **断网捕获、联网补解析**（决策 #14）；⑦ **撤销任一授权后对应通道停用、另一条仍工作**（用户可撤销的承诺兑现）。**JVM 侧只能验纯函数**（两个过滤器 / `LocalCaptureParser` / `DedupeKeys`），**不得用 Robolectric 的「伪造通知投递」或「伪造节点树」冒充真机验收**。
20. **用户可见的诚实口径（文案红线）**：自动记账**不得宣传成「全自动、零遗漏」**。两条通道都有各自的失效面（无障碍怕改版与支付保护，通知怕用户关通知），故对用户的话只有两句是对的：「支付类通知到了、或在支付页上，就会自动记」+「没记上的可以一键补」。**禁止**出现「100% 自动」「绝不遗漏」类表述（这与 T20-9「回执文案必须诚实」是同一种纪律）。

### 5. 已知限制（本轮挂账，后续轮可升级为 REQ）

1. **无障碍的第三方改版维护成本**（R-PROD-58）：关键词集是粗筛、成本在页面文本拼装形态；每次第三方改版需真机回归一次。
