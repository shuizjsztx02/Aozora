## 🔴 P0 — 功能 Bug

### Bug-1: 聊天页面确认记账无响应

## 第四轮问题（2026-09-07 补充 · 真机复测）

### Bug-3: 数据管理子页（账本/账户/预算）点击"添加"完全无反应
- **现象**: 「我的 → 数据管理」下的 账本 / 账户 页，填写名称、选图标后点"添加"按钮无任何反应——表单不关闭、不出现新记录、也没有任何错误提示（截图 #15 / #16）
- **预期**: 创建成功后关闭表单并刷新列表；失败时给出明确提示
- **根因（已确认为代码缺陷，双层）**:
  1. **payload 契约不匹配**：页面绕过 NativeBridge 封装方法，直接 `bridge.call('book.insert', { id, ownerId, name, icon, version })` 传**扁平** payload；而原生 `AozoraBridge.handleBookInsert`（AozoraBridge.kt:265）期望 `p.getJSONObject("book")` + `p.getString("mutationId")` 的**包裹结构**。缺 `book`/`account`/`budget` 外层与 `mutationId` → Kotlin 抛 `JSONException` → 返回 error 响应 → 前端 promise reject。此外 AccountsPage 还漏传 `ownerId`（`handleAccountInsert` 需要 `aObj.getString("ownerId")`）。
  2. **错误被静默吞掉**：`handleAdd` 的 `catch (err) { console.error(...) }` 只打 console，不反馈到 UI——所以用户只看到"点了没反应"。
  - 对照：`native-bridge.ts` 已有正确封装 `insertBook/insertAccount/insertBudget/deleteBudget`（215 / 232 / 247 / 255 行，均传 `{book, mutationId}` 形状），但 UI-12 新建页没走它们。CategoriesPage 只读，不受影响。
- **修复方案**:
  1. 三页改调用 NativeBridge 封装方法，补齐 `mutationId`（生成 uuid，与交易写入同源）与 `ownerId`
  2. `catch` 里把错误提示到 UI（toast 或表单内错误条），不静默吞掉；失败时保留表单内容供用户改后重试
- **涉及文件**: BooksPage.tsx、AccountsPage.tsx、BudgetPage.tsx（预算页同为 `bridge.call('budget.insert',{...})` 扁平调用，命中同一缺陷，需一并修）

### UI-14: "更多设置"子页（数据导出 / 提醒设置）顶部内容仍顶到状态栏
- **现象**: 打开 ExportPage、ReminderSettingsPage，首屏内容（"选择账本…"、"通知权限未开启"）与系统状态栏时间/信号图标重叠，顶部安全区不足（截图 #17 / #18）
- **预期**: 子页内容顶部留出安全区，不被状态栏遮挡
- **根因**: `.safe-top { padding-top: max(env(safe-area-inset-top, 0px), 24px) }`（index.css:253）——Android WebView 中 `env(safe-area-inset-top)` 返回 0，回退到 24px，低于本机状态栏实际高度（约 35–45px）；且原生侧（MainActivity / themes.xml 为 `Theme.AppCompat.DayNight.NoActionBar`，无 edge-to-edge / WindowInsets 注入逻辑）未把真实状态栏 inset 传给页面。UI-13 的"已统一"结论对本机不成立。
- **修复方案（择一）**:
  1.（推荐）MainActivity 监听 `WindowInsets` → 取 statusBars 顶部 inset，注入 CSS 变量（如 `--safe-top-px`），`.safe-top` 改为 `padding-top: max(env(safe-area-inset-top, 0px), var(--safe-top-px), 24px)`
  2. 临时：`.safe-top` 回退值 24px 提到 44px+（覆盖主流机型，非像素级精确）
  3. 或让 WebView 非沉浸式（容器 fitsSystemWindows），内容整体下移到状态栏下方（但背景月亮/星星将不再延伸到顶部）
- **待真机确认**: BooksPage / FeedbackPage 是否同样偏高不足——它们顶部留白看着更大，可能只是内容首块高度不同造成视觉差异，同一 safe-top 代码路径下应统一修复

### Bug-4: 意见反馈无法确认是否真正提交成功
- **现象**: 填写反馈点提交后，页面停在"提交中…"，用户无法确认最终是否成功（截图 #19）
- **链路（已核查完整）**: FeedbackPage.submitFeedback → `call('feedback.submit')`（10s 超时，native-bridge.ts:663）→ 原生 `handleFeedbackSubmit`（AozoraBridge.kt:1270）→ `FeedbackClient.submit` → 服务端 `POST /telemetry/feedback`。前端**已有**成功页（✅ 感谢你的反馈）与错误条（rate_limited / auth_lost / network_error / server_error / timeout 均有对应文案）
- **可能原因**:
  1. **服务端不可达 / 未部署**：dev 环境 `/telemetry/feedback` 若未部署或 `FeedbackClient.baseUrl` 不对 → 最终失败（network_error/server_error），但在 10s 超时前用户一直看到"提交中…"，误以为卡住
  2. **截图取于超时窗口内**：正常等待 10s 后应转错误提示，用户可能没看到最终结果
  3. **原生未 respond**：若 `FeedbackClient.submit` 阻塞或异常未落入已 catch 的分支，promise 会挂到 10s 超时才 reject（非永久挂起，但体验差）
- **修复方案**:
  1. 端到端验证：真机构建下 `FeedbackClient.baseUrl` 是否指向可达 server，`POST /telemetry/feedback` 是否返回 200
  2. UI 明确化：提交后展示结果态——成功后显示反馈 ID 并停留/自动返回；失败给原因 + "重试"按钮，让用户能确认
  3. 检查 `FeedbackClient.submit` 是否存在长时间不返回路径，确保 10s 超时兜底能触发到错误提示
- **涉及文件**: FeedbackPage.tsx、FeedbackClient.kt、AozoraBridge.kt、server `/telemetry/feedback`

### 本轮新发现并修复
1. **NSC 阻断真机通路（阻塞 Bug-5.3，已修复）**：debug 构建的 `network_security_config.xml` 明文白名单只有 `localhost`/`10.0.2.2`，**缺 `127.0.0.1`**；而 `adb reverse` 方案下手机连的正是 `http://127.0.0.1:8000` → `CLEARTEXT communication to 127.0.0.1 not permitted` → 记账必失败。修复：向 debug overlay 与 base 的 `<domain-config>` 各补 `<domain>127.0.0.1</domain>`（release 的 HTTPS-only 策略不动）。修复后真机成功注册并同步（上条证据即来自修复后）。
2. **NLU 别名输出占位 id 致聊天记账被拒（属 Bug-5.2 同类，已修复）**：本地 NLU `matchCategory` 命中内置别名（如"午饭/咖啡"→餐饮）时返回**硬编码占位 id `cat-food`**，非真实 UUID；离线/未配 AI provider 时聊天走本地 NLU，确认卡带 `cat-food` 发 `/ai/execute` → 服务端 `rejected_hallucination`（403）。修复 `category.ts`：别名命中后用目标分类名在用户真实分类中查同名项，取其 UUID，查不到才回退占位（保持空分类兼容）。新增 2 个 `category.test.ts` 用例复现→转绿；vitest **585/585**、tsc 干净。

### 本轮新发现（尚未修复，需决策）— 交易 sync push 恒 422
真机记一笔后，交易 mutation **始终无法上行**（server `transactions=0`，`/sync/push` 返 **422**，SyncWorker 陷入 RETRY 循环，pending_mutations 卡住）。根因（已定位）：
- 交易 mutation 的 payload 由 `Repository.transactionToJson` 输出为 **camelCase**（`bookId/amountCents/categoryId/bizDate/occurredAt`）；
- 但服务端 `_apply_insert` 对 transaction 用**直接下标读 snake_case**（`service.py:241-265`：`payload["book_id"]`/`["amount_cents"]`/`["category_id"]`/`["biz_date"]`/`["occurred_at"]`）→ **KeyError → 422**；
- 且 `occurred_at` 客户端为 epoch 毫秒整数，服务端 `_to_datetime` 用 `fromisoformat`（需 ISO 串）→ 即便字段名对上仍会二次失败；
- 分类/账本因服务端读 `.get()` 未报错，但把 `bookId` 静默丢弃 → server 侧分类 `book_id` 全为 **NULL**（数据完整性缺陷）；
- 权威 wire 格式为 **snake_case + ISO datetime**（pull 方向 `_serialize_entity` 输出即 snake，客户端 `snakeToCamelMap` 反向证实）；push 方向缺 camel→snake + epoch→ISO 的转换。`SyncPayloadMapperTest` 现有断言 `assertEquals(pm.payload, wire.payload)` 把 camelCase 原样透传写进了测试，属错误契约。

> 此为**独立于第六轮清单之外的既有契约 bug**（第六轮 5.2 只覆盖"实体 id 用 UUID"，未涉及 push payload 字段命名/日期格式）。涉及跨模块 wire 契约变更（客户端 push 5 类实体 payload 字段名 + datetime 格式 + 更新测试 + 可能需服务端容忍 epoch + 回填已产生的 NULL-book_id 分类），影响面较大，**待用户确认修复方向后再实施**。临时规避：beta 单机场景下本地记账与首页展示不受影响，仅上行备份/多端一致性受影响。

## 第七轮设计决策（所有任务卡必须遵循，勿重新发明）

> 以下结论来自本轮代码勘察，实施前无需重复调研。

1. **总账本标记方式**：不给 books 表加列，在 `sync_meta` 表写键 `master_book_id`（值 = 总账本 UUID）。
   - 理由：`clearAllEntities()`（bootstrap 重建）不清 sync_meta，且账本 UUID 经 push/pull 稳定 → 标记跨重建存活；服务端 sync/ai 契约零改动；总账本作为普通 book 行照常上行（服务端只存 name/icon，无感知）。
   - `AozoraBridge.handleBookList` 比对 `master_book_id` 输出 `isMaster: Boolean`；`ensureSeedDefaults` 幂等补种（见 T7-1 卡）。
2. **必踩坑：`BookDao.listActive()` 是 `ORDER BY name`**，UTF-8 字节序下"总账本"（总=U+603B）排在"默认账本"（默=U+9ED8）**之前**。凡是 `books[0]` 当记账/展示目标的调用点必须改为"第一个非 master 账本"：
   - Kotlin：`WidgetDataHelper.loadData`（69 行）
   - 前端：HomePage(111)、QuickEntrySheet.getBookId(57)、ReportsPage(40)、AssistantPage(38)、ExportPage(64)、BudgetPage(32)、DetailPage(68)
   - 前端统一走新增 helper `pickEntryBook()`（见 T7-2 卡），禁止各处手写 filter
3. **账户分类存储**：Room `accounts` 新增 `accountType TEXT`（nullable，旧行 NULL）。迁移 `MIGRATION_3_4`。服务端 `MutationItem.payload` 为 `dict[str, Any]`（已核实，server/src/modules/sync/schemas.py:30），push 时 `account_type` 未知字段被服务端忽略——**已知限制：bootstrap 重建后 accountType 丢失**，写入本轮修复说明即可，不改服务端。
