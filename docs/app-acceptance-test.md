# Aozora 端到端验收集划

> 定位：跨模块联合测试 + 用户场景验收的完整指南。
> 适用阶段：T-M5 收尾后，全功能集成验证。

---

## 一、核心目标

1. 验证前端（RN）→ 后端（FastAPI）→ AI（DashScope LLM）→ 数据库（Postgres）全链路打通
2. 验证 T-M0 ~ T-M5 各模块在真实联调场景下无冲突
3. 覆盖核心用户旅程的 Happy Path + 关键异常路径
4. 产出一份可重复执行的验收清单，供发版前跑一遍

---

## 二、联调环境搭建

### 2.1 服务依赖全景

```
┌──────────────┐     HTTP      ┌──────────────┐     SQL      ┌──────────┐
│  React Native │ ◄──────────► │  FastAPI      │ ◄──────────► │ Postgres │
│  (Expo Go /   │              │  :8000        │              │ :5432    │
│   模拟器)      │              │              │              └──────────┘
└──────────────┘              │              │     HTTP      ┌──────────┐
                              │  AI Gateway   │ ◄──────────► │  Redis   │
                              │  (DashScope)  │              │ :6379    │
                              └──────────────┘              └──────────┘
```

> AI 调用链路：RN → FastAPI `/api/ai/*` → `server/src/modules/ai/provider.py`（DashScopeProvider，OpenAI 兼容模式）→ 阿里云 DashScope API（模型 `qwen3.7-flash`）。
> 后端是唯一持有 provider key 的组件，客户端不直接调用模型。

### 2.2 启动顺序

| 步骤 | 操作 | 验证方式 |
|------|------|----------|
| 1 | Docker 启动 Postgres + Redis | `docker compose ps` 全部 healthy |
| 2 | 启动 FastAPI 后端 | `curl http://localhost:8000/health` 返回 200 |
| 3 | 启动 RN 前端 | Metro bundler 正常运行，设备/模拟器能访问 |

### 2.3 环境配置检查清单

- [ ] `.env` 文件中 `DATABASE_URL` 指向正确的 Postgres 实例
- [ ] `.env` 中 `REDIS_URL` 指向正确的 Redis 实例
- [ ] `.env` 中 `AI_PROVIDER_API_KEY` 已配置有效的 DashScope API Key
- [ ] `.env` 中 `AI_PROVIDER_BASE_URL` 指向 DashScope OpenAI 兼容端点
- [ ] 后端 `alembic upgrade head` 已执行，数据库 schema 最新
- [ ] RN 的 API base URL 指向后端地址（模拟器用 `10.0.2.2:8000`，真机用局域网 IP）

## 三、核心用户旅程（E2E 场景）

### 场景 1：新用户首次使用（冷启动 → 记账）

**覆盖模块：** T-M0（登录UI）+ T-M1（AI对话）+ T-M3（后端+DB）+ T-M5（认证）

| 步骤 | 用户操作 | 预期结果 | 验证点 |
|------|----------|----------|--------|
| 1 | 打开 App | 显示登录页 | UI 渲染正常 |
| 2 | 点击「注册」，输入邮箱+密码 | 注册成功，自动登录 | 后端 `/auth/register` 返回 token；数据库 `users` 表新增记录 |
| 3 | 进入首页（Me 页面） | 显示空状态或引导 | 前端渲染正常 |
| 4 | 点击记账入口，进入 AI 对话页 | 对话页加载，显示输入框 | 前端路由正常 |
| 5 | 输入「午饭花了 35 元」 | AI 返回结构化记账结果：category=餐饮, amount=35, currency=CNY | DashScope LLM 正确解析；后端 AI 模块返回结构化数据 |
| 6 | 确认记账 | 交易记录写入数据库；首页余额/统计更新 | 数据库 `transactions` 表新增记录；前端状态同步刷新 |

**验收标准：**
- [ ] 注册到记账全链路 < 3 分钟
- [ ] AI 解析结果准确（金额、分类、货币）
- [ ] 数据库中有正确的交易记录

---

### 场景 2：多账本 + 多币种

**覆盖模块：** T-M0（账本切换UI）+ T-M1（多币种解析）+ T-M2（本地持久化）+ T-M3（账本API）

| 步骤 | 用户操作 | 预期结果 |
|------|----------|----------|
| 1 | 创建第二个账本（如「旅行账本」，USD） | 账本列表更新，可切换 |
| 2 | 切换到旅行账本，输入「Hotel $120」 | AI 识别 USD，amount=120 |
| 3 | 切回默认账本 | 交易列表只显示 CNY 的交易 |
| 4 | 再切回旅行账本 | 交易列表显示 USD 的交易 |

**验收标准：**
- [ ] 账本间数据隔离，无串账
- [ ] 切换账本后 UI 状态正确刷新
- [ ] 本地缓存按账本隔离

### 场景 3：离线记账 → 联网同步

**覆盖模块：** T-M2（本地持久化）+ T-M3（同步模块）+ T-M4（冲突解决）

| 步骤 | 用户操作 | 预期结果 |
|------|----------|----------|
| 1 | 断开网络（飞行模式） | App 不崩溃，显示离线状态 |
| 2 | 离线记一笔「早餐 15 元」 | 交易写入本地 SQLite，pending 状态 |
| 3 | 再离线记一笔「咖啡 28 元」 | 同上，本地两条 pending |
| 4 | 恢复网络 | 自动触发同步，两条交易上传到后端 |
| 5 | 检查后端数据库 | 两条交易记录存在，version 正确 |

**验收标准：**
- [ ] 离线操作不丢数据
- [ ] 恢复网络后自动同步
- [ ] 同步后本地和远端数据一致

### 场景 4：多设备冲突场景

**覆盖模块：** T-M3（同步）+ T-M4（冲突解决）

| 步骤 | 操作 | 预期结果 |
|------|------|----------|
| 1 | 设备 A 离线，修改交易 X 的分类为「餐饮」 | 本地保存，version 不变 |
| 2 | 设备 B 在线，修改同一交易 X 的分类为「交通」 | 后端 version +1 |

| 4 | 选择「使用远程版本」 | 交易 X 分类 = 「交通」 |
| 5 | 选择「使用本地版本」 | 交易 X 分类 = 「餐饮」，后端 version +1 |

**验收标准：**
- [ ] 冲突被正确检测到
- [ ] 两种解决策略都能正常工作
- [ ] 解决后两端数据最终一致

**验收标准：**
- [ ] 备份文件可正常导出

### 场景 6：AI 对话边界场景

**覆盖模块：** T-M1（AI 模块）+ T-M5（异常处理）

## 四、模块间接口验证矩阵

> 重点验证模块之间的"接缝"，这是集成问题最高发的地方。

### 4.1 前端 → 后端 API 接口

| 接口 | 方法 | 验证要点 |
|------|------|----------|
| `POST /auth/register` | 注册 | 返回 access_token + refresh_token；重复注册返回 409 |
| `POST /auth/login` | 登录 | token 有效；错误密码返回 401 |
| `POST /auth/refresh` | 刷新 token | 旧 token 过期后能刷新；refresh token 过期后需重新登录 |
| `GET /accounts` | 获取账本列表 | 返回当前用户的所有账本 |
| `POST /accounts` | 创建账本 | 新账本出现在列表中 |
| `POST /ai/chat` | AI 对话 | 返回结构化 JSON（amount, category, currency, description） |
| `GET /transactions?account_id=` | 查询交易 | 按账本过滤，分页正确 |
| `POST /transactions` | 创建交易 | 写入数据库，返回带 id 的记录 |
| `PUT /transactions/:id` | 更新交易 | version 乐观锁检查生效 |
| `DELETE /transactions/:id` | 删除交易 | 软删除 or 硬删除符合设计 |
| `POST /sync/pull` | 拉取变更 | 返回 last_sync_version 之后的变更 |
| `POST /sync/push` | 推送变更 | 冲突检测正确；返回冲突项 |
| `POST /backup/export` | 导出备份 | 文件完整可解析 |
| `POST /backup/import` | 导入备份 | 数据完整恢复 |

### 4.2 后端 → DashScope LLM 接口

| 验证点 | 方法 |
|--------|------|
| LLM 调用成功 | 发一条正常记账指令，检查 DashScope 返回有效结果 |
| 返回格式正确 | 验证 AI 模块解析后的 JSON 包含 amount, category, currency, description |
| LLM 超时处理 | DashScope 响应慢（>25s），后端返回 503 + 用户友好提示 |
| API Key 无效 | 配置错误 key，后端返回 4xx 错误，不暴露 key 到日志 |
| 限流处理 | 触发 429，后端自动重试或返回友好提示 |
| Token 用量 | 检查 DashScope 控制台的 token 消耗记录是否合理 |

### 4.3 后端 → 数据库接口

| 验证点 | 方法 |
|--------|------|
| Schema 版本 | `alembic current` 显示最新版本 |
| 外键约束 | 删除账本时关联交易的处理（级联/拒绝） |
| 事务一致性 | 创建交易 + 更新余额在同一事务中 |
| 乐观锁 | 并发更新同一交易，第二个请求返回 409 |
| 索引性能 | 大量数据下查询仍快速（见性能章节） |

## 五、非功能性验收

### 5.1 性能

| 指标 | 目标值 | 验证方式 |
|------|--------|----------|
| 冷启动到可交互 | < 3s（模拟器）/ < 5s（真机） | 手动计时 |
| AI 对话响应 | < 5s（含网络延迟） | 从发送到显示结果 |
| 列表滚动 | 60fps，无明显卡顿 | 100+ 条交易记录下滚动 |
| 同步延迟 | < 2s（局域网） | 从操作到另一端可见 |
| 数据库查询 | 单表 < 100ms（1000 条数据） | `EXPLAIN ANALYZE` |

### 5.2 安全

| 检查项 | 验证方式 |
|--------|----------|
| Token 过期自动刷新 | 手动过期 token，观察是否自动刷新 |
| 未认证访问 | 不带 token 调 API，返回 401 |
| 跨用户数据隔离 | 用户 A 无法访问用户 B 的账本/交易 |
| SQL 注入 | 输入 `' OR 1=1 --` 类文本，不触发注入 |
| API Key 不泄露 | 检查后端日志中不出现 DashScope API Key |
| HTTPS（生产） | 生产环境强制 HTTPS |

### 5.3 兼容性

| 平台 | 验证方式 |
|------|----------|
| Android 模拟器 | API 33/34 各跑一遍场景 1 |
| iOS 模拟器 | 场景 1 完整跑通 |
| 不同屏幕尺寸 | 小屏（iPhone SE）+ 大屏（iPad/平板）布局正常 |

## 六、回归测试策略

### 6.1 每次发版必跑的 Smoke Test（~15 分钟）

```
1. 启动所有服务 → 健康检查全通过
2. 注册新用户 → 登录成功
3. 记一笔账 → AI 解析正确 → 数据库有记录
4. 查看交易列表 → 数据正确显示
5. 切换账本 → 数据隔离正确
6. 退出登录 → 重新登录 → 数据还在
```

### 6.2 完整回归（~2 小时）

Smoke Test + 场景 2~6 全部跑一遍。

### 6.3 探索性测试

- 随机操作顺序，不按脚本走
- 快速点击、重复提交、中途退出
- 网络波动下操作（Chrome DevTools 模拟慢速 3G）
- 大数据量下的表现（导入 1000+ 条交易后操作）

## 八、自动化演进路线

当前阶段以手动验收为主，后续可按以下优先级逐步自动化：

| 优先级 | 范围 | 工具 | 投入 |
|--------|------|------|------|
| P0 | 后端 API 集成测试 | pytest + httpx | 低，已有基础 |
| P1 | AI 模块回归测试 | pytest + MockTransport | 中，provider.py 已有测试桩 |
| P2 | 前端关键路径 E2E | Detox / Maestro | 高 |
| P3 | 全链路自动化（CI） | GitHub Actions + 模拟器 | 高 |

**建议第一步：** 把场景 1~4 的后端 API 调用写成 pytest 集成测试脚本，不依赖前端，先保证后端链路没问题。
