### REQ-57: 报表页——每日趋势点击即整页渲染失败（用户第 1 项）
- **诉求**: 「每日趋势」图任意位置都应可点击查看某日数据；当前**经常一点就渲染失败**（用户原话）。
- **现状（已核实，根因已实证）**: 崩溃链 = ①趋势卡内建 recharts `<Tooltip>`（ReportsPage.tsx:485-488 曲线 / :503-507 柱状）的 `formatter={(value) => formatCents(Number(value))}`；②`formatCents`（:29-31）= `Money.formatDisplay(Money.cents(cents))`；③`Money.cents`（domain/money.ts:15-22）**断言入参为「非负安全整数」，负数直接 throw**；④`daily` 每日含 `balance = income − expense`（:113），**任何支出日结余为负**（默认图例三系列全开、柱状默认为 expense）→ 鼠标/手指划过或点击图上任意点，recharts 渲染 tooltip 内容时对负 balance 调 formatter → throw → 冒泡到全局 `ErrorBoundary` → **整页**「出了点问题」（不是图表局部降级）。实测异常原文：`cents: expected non-negative safe integer, got -800`（见节首实证①）。**补充**：卡内自绘浮层（:523-555）已正确处理负数（`Math.abs` + 手拼负号，:541/:549），崩溃只来自 recharts 内建 Tooltip；柱状 onClick 取 `state.activeTooltipIndex`（:497-499）在触摸环境不可靠，也是「点了没反应/响应位置飘」的次因。
- **修复设计**: ①**删两条内建 `<Tooltip>` 组件**（曲线 + 柱状各一），把「点了没反应」的解一并交给卡内自绘浮层——`LineChart/BarChart onClick` 取点逻辑保留并改为**按点击坐标反推最近数据点**（比 `activeTooltipIndex` 在触屏下可靠；`Bar` 的 `payload` 分支可留作兜底）；②浮层数值展示复用现有 `Math.abs` + 负号口径，零格式化改动；③**不做什么**：不改 `Money.cents` 的非负契约（它保护的是金额主链路）、不改饼图（其值恒为正、Tooltip 安全）、不引第三方 tooltip 库、不重排版式。
- **涉及文件**: ReportsPage.tsx、ReportsPage.test.tsx

### REQ-58: 聊天页——已记账单卡需作为消息永久留在历史中（用户第 2 项）
- **诉求**: 聊天里记了一笔后，那张账单卡必须留在聊天历史里；不能记完就消失。
- **现状（已核实，根因）**: messages **已持久化**（zustand persist → localStorage，assistant-chat-store.ts:55-70，T14-4），且消息对象**本就带 `proposal` 与 `proposalStatus`**（use-assistant.ts:61-70，写入点 :731-740）。但：①消息渲染循环（AssistantPage.tsx:494-522）**只渲染 `msg.text` 文本气泡**，对 `msg.proposal` 不做任何卡片渲染；②卡片唯一的渲染点由**瞬时内存态** `activeProposal`（:559-575）门控——它在下一次输入（:568-571 清 pendingOp/config，新提交另起）即被替换/清空，撤销后更是显式置 null（use-assistant.ts:827-828）。所以账单一记完、再聊下一句，卡片就从页面消失（历史里只剩「已记录 N 笔交易」文本）。测试注释如实记录了现状：`assistant-chat-persistence.test.ts:97`「历史气泡只读渲染：proposalStatus 不影响 ConfirmationCard（其门控为内存态）」。
- **修复设计**: ①消息流中，凡 `msg.proposal?.transactions` 非空的消息，在气泡下渲染**只读账单卡**（新增轻量组件或给现卡加 `readonly` 态）；②只读态展示内容 = 现展示态四行（分类/收支/金额/日期/备注/账本/状态徽标），**隐藏「编辑」「撤销」**（撤销依赖 `activeTxIdsRef` 内存态，切页/重启后不可用）；③`proposalStatus` 文案沿用现语义：`committed`=已记录、`undone`=已撤销（灰化）、`error`=记账失败；④会话重载（remount）后历史卡照常渲染，**不复活**任何可写按钮；⑤**不做什么**：不动 `activeProposal` 现链路（当轮那张卡仍可编辑/撤销）、不改消息存储结构（`proposal` 已在 persist 内）、不清理历史文本气泡。
- **涉及文件**: AssistantPage.tsx、ConfirmationCard.tsx、对应测试（confirmation-card.test.tsx / assistant-chat-persistence.test.ts / assistant-page-*.test.tsx）

### REQ-59: 聊天页——改账单需展示新旧卡片对照 + 确认/取消（用户第 3 项）
- **诉求**: 修改账单时要同时看到**旧账单完整卡片**与**修改后的卡片状态**，有「确认」「取消」按钮，确认后才生效。
- **现状（已核实）**: 会话卡编辑态（ConfirmationCard.tsx:403-547）**每个字段改完即写库**——`commit()`（:118-161）在点选/失焦时立刻调 `onEditCommit` → `use-assistant.editProposal` 执行「softDelete 旧笔 + insert 新笔」替换写（use-assistant.ts:766-813）。即：没有「改完先看对照、再确认」的环节，取消只能靠事后撤销（且撤销是软删该笔、丢失全部修改）。语音/文字路径的 `OpPreviewCard`（edit/delete 意图）确有确认卡，但它只显示**摘要行**、不显示完整新旧卡片。
- **修复设计**: ①会话卡编辑态改「**草稿态**」：字段改动只更新本地草稿（现 `CommittedSnapshot` 语义复用），**不再即时调 `onEditCommit`**；②底部「完成」钮改为「确认修改」：点击后**展开新旧对照区**（旧 = 进入编辑前的快照卡，新 = 当前草稿卡，逐字段差异高亮；未变更字段可弱化）；③对照区两钮：「确认」→ 调 `editProposal` 执行替换写（口径不变：softDelete 旧 + insert 新 + triggerSync）、「取消」→ 放弃草稿退回展示态（**不写库**）；④`pending-category` 态（未写库首提）同走此流，确认后才触发首写；⑤**不做什么**：不改 `editProposal` 的写入语义与错误本地化、不改 `TxEditSheet`（首页/明细的编辑弹层是另一路径，本轮不碰）、`OpPreviewCard` 保持现状。

### REQ-65: 聊天页——从「＋」进入时不再从第一条滚到最后一条（用户第 3 项）
- **诉求**: 每次点底部中间的「＋」进聊天页，聊天记录都会从顶部第一条**快速滚到**最新一条；希望**取消这个滚动动作**，打开即停在最新一条（尾部）的历史页面。
- **现状（已核实，根因）**: `AssistantPage.tsx:425-428` 的自动滚动 effect **在挂载时首跑**就用 `behavior: 'smooth'`：`scrollRef.current?.scrollTo({ top: scrollHeight, behavior: 'smooth' })`。新挂载的滚动容器（`ref={scrollRef}` 的 `flex-1 overflow-y-auto`，:614-617）初始 `scrollTop = 0` = 列表顶部 = 最早那条消息，于是**每次进入都必然演一遍「从第一屏滚到底」的平滑动画**。入口链见节首实证③（BottomNav「＋」→ `/assistant` 路由 → 卸载重挂），故与用户「每次」的观察一致；dev 库现存 71 条消息（T16-7 记录），滚动距离客观很长。
- **修复设计**: ①该 effect 改 `useLayoutEffect`（在**布局阶段**就定位，不给浏览器画出「顶部第一条」那一帧的机会）；②按「是否首帧定位」+「跳得远不远」选行为：首帧（`useRef` 标记的首次执行）**或**剩余距离 > 一屏（`scrollHeight - scrollTop - clientHeight > clientHeight`）→ `'auto'`（瞬移），只有尾部小增量（会话中追加新消息）才 `'smooth'`——后者顺带覆盖「服务端会话正文异步补进来」的场景（那会儿 messages 二次变更、距离可能很大，同样不该演动画）；③`resize`（键盘顶起）那条 effect（:432-438）保持 `'smooth'` 不动。**不做什么**：不上 `flex-direction: column-reverse`／虚拟列表／分页等会翻转消息 DOM 顺序的方案（会牵动 T16-2 的历史卡顺序断言与全部聊天用例）、不改消息存储与持久化、不动 `Router.tsx:75-82` 的 `window.scrollTo(0,0)`（那是文档级滚动复位，与本容器无关）。

### REQ-66: 账单图片识别——报「AI 服务未配置：需在服务器 .env 填 AI_PROVIDER_API_KEY 并重启」（用户第 1 项，附件 #39）
- **诉求**: 「我点击上传一张账单图片的时候，报错 AI 服务未配置，需要在 .env 文件配置服务」（用户原话）。要的是**这个功能能用**，且不该被暴露服务端运维细节。
- **现状（已核实，根因已实证）**: 四层事实——
  1. **文案是前端选的，且是错误归因**：服务端在 provider 不可用时只回 HTTP **503** + `{code:"ai_unavailable", message:"AI service is temporarily unavailable"}`（`server/src/modules/ai/service.py:1285-1290`），**从不下发这句话**；桥在 503 分支**不读 body**、按状态码映射（`ai/AiGatewayClient.kt:350` → `AiError.Unavailable(httpCode)`，该错误类只带 httpCode，`:79-80`），再由 `AozoraBridge.kt:1805-1807`（`handleImageParse`）**一律压成桥码 `no_ai_provider`**；前端据此命中 `AssistantPage.tsx:79` 的运维文案。服务端**三种不同情况都回 503**：provider 为 None（`:1285-1290`）、provider 调用失败/输出非法（`:1374-1384`）、图片解析被配置关闭（`:1324-1327` `image_parsing_disabled`）——**三者被桥译成同一句话**，于是 provider 只是临时抽风时，用户也会读到「请去改服务器 .env」。
  2. **用户环境其实配好了 key**：`server/.env` 的 `AI_PROVIDER_API_KEY` **非空**（与文本快路径共用同一把）。故用户这次看到的报错**极可能是误译**（调用失败/超时/输出非法），而不是真没配。旁证：`ENV=production` 缺 key **直接拒绝启动**（`common/config.py:388` `_check_production_safety`，`:414-418`）——这句文案在正常生产部署下只可能来自误译。
  3. **图片链路无任何降级**：全仓 grep `mlkit|tesseract|ocr` **零命中**；图片 100% 走云端视觉模型（`AI_VISION_MODEL` 默认 `qwen-vl-max`，`config.py:195-197`，与文本共用一把 key），**没 key / 不可用即死路**。而文本没 key 可降级到本地 NLU。这与 `APP-CONTEXT.md:384`（§6.4）的既定承诺「**无法处理图片时保留草稿并提示联网后继续**」**不符**——承诺有降级，实现没有。
  4. **同码两套用户可见文案**：`AssistantPage.tsx:79`（图片链路，**可达**，用户看到的就是它）暴露运维细节；而走**同一桥命令**的 `QuickEntrySheet.tsx:684` 写的是「识别失败（AI 服务不可用）」。另有一处 `use-assistant.ts:472` 是**文本 interpret 链路**的预留分支（该链路桥压成 `'503'`，`:465-470` 注释自认不可达），与图片链路无关——**第十二轮决策 #9（v1 文档 :1357）立下该文案时，无人注意到图片链路让它真的可达**；而「不暴露服务商错误」是 `APP-CONTEXT.md:389`（§6.4）的既定原则，本条是表外例外。
- **修复设计**: 三项，可独立落地——①**文案收口**（最小）：删掉运维细节，图片链路与 `QuickEntrySheet` **共用同一份文案常量**，统一为「AI 服务暂时不可用，请稍后重试」（对齐 §6.4「不暴露服务商错误」）；②**归因分层**：`handleImageParse` 不再把任意 503 压成 `no_ai_provider`——服务端 body 里已有 `code`，桥现在**丢弃**它；透传或至少降级为「暂时不可用」，让「真未配置」与「暂时抽风」在 UI 上可分；③**退路**：按 §6.4 承诺，图片失败时给用户明确的下一步（现状只有 `QuickEntrySheet` 的「手动记账」）。**不做什么**：不引入本地 OCR（超出本轮，属产品决策）、不改图片大小上限与 provider 选型、不动文本 interpret 链路的预留分支（另案）、**不把这项写成「改文案即完事」**——真因多半在服务端侧（见任务卡的判据先行）。

## 第十八轮设计决策（所有任务卡必须遵循，勿重新发明）

1. **编号与占用**：REQ 起点 **66**（本轮 66–71）；任务卡 `T18-1…T18-9`（T18-9 为收口卡）。**Room v10 → v11**（REQ-69 加列，收口核验 = `schemas/…/11.json` 存在且只此一个新版本）；**meta 白名单 11 键不变**；**桥命令计数 85 → 由 T18-8 定夺**（REQ-71 若以「新增可达性探测命令」实现则 85→86，若复用现有 `sync.getStatus`/`auth.triggerSync` 语义则**保持 85**——**开工前必须先定死**，定了就锁；变更则三处同步：`BridgeProtocol.kt` + `SecurityConfigTest.kt:55-62` + TS 契约）。四板基线以本轮盘点为准：tsc 0 / vitest **1361** / JVM **468**（1 skip）/ pytest **1596 + 37s**，各卡验收 =「领取时工作树全绿 + 本卡增量」。
2. **REQ-69/70 的余额 = 存量字段，这是对既有产品口径的显式推翻**：`APP-CONTEXT.md:274`「仅支付渠道标记，**不维护真实余额**」与 `:464` 验收项「**账户不计算余额**」是**当前在册口径**，本轮作废。理由：用户要的是「**手动设置**账户当前余额」——而"由交易推导"方案（现有 `account_balances` 就是这种）**只能算净额、无法承载人为校准**，诉求在推导式下不可表达。落地 = 两端各存一列（客户端 `AccountEntity.balanceCents` + 服务端 `accounts.balance_cents`），**允许负值**（信用卡欠款是常态），**不加非负 CHECK**（与 `savings_goals.current_cents` 的 `>= 0` 语义刻意不同）。**该条属 L3 变更**（数据模型 + 同步契约 + AI 工具面）：必须同步更新 `docs/APP-CONTEXT.md:274/:464`、`docs/architecture/data-model.md`，并新增 ADR 记录取舍。
3. **余额与交易净额不保证相等（差额口径必须写进文档与工具描述）**：存量余额允许被手动校准，故「余额 ≠ 该账户交易净额」是**正常状态**，差额 = 手动校准量。AI 只读工具 `account_balances`（`tools.py:1664-1712`）现算的是**净额**——**必须给它统一口径**（建议工具输出同时给「净额」与「当前余额」两项，并在描述里说明差额来源），否则模型会对同一问题给出两个答案。
4. **余额更新的幂等铁律：写绝对值，不写增量**：记账联动时，account 的 mutation 携带**更新后的余额绝对值**，而非「+100」这样的增量——这是**重放安全的关键**（离线队列重试、pull/push 重放都不会重复累加）。冲突以**服务端为权威**（客户端本地乐观更新，pull 覆盖）。**已知代价**：多设备各自离线记账后同步会互相覆盖（后到者胜）→ 登记新风险 **R-PROD-43**，并在收口写入已知限制。
5. **`accountType` 必须两端化（否则 REQ-69 会复制 REQ-67 的症状）**：AI 改账户分类是在**服务端执行**的；服务端当前**不存 `account_type`**（`models/ledger.py:114-129`），pull/bootstrap 会冲刷（只保护 `icon`）。若只改 AI 工具不改存储，用户会看到「AI 说改好了 → 同步回来又变回去」——**与 REQ-67 同源**。故 `account_type` 与 `balance_cents` **必须同批两端化**（同一张卡，见 T18-5）。
6. **REQ-67 判据先行，禁止不取证就改**：该条有 6 个根因假设——**H1** 写操作压根没落库（卡在确认门）、**H2** 服务端写了但客户端无写后刷新、**H3** 聊天历史卡结构上不可能反映库（v2 提案被 `!isV2Proposal` 排除，**必然成立**）、**H4** 设备执行 op 无落点、**H5** 被本地快路径吞掉、**H6** 同步链路整体停摆。实施卡**第一步必须先在真实环境定性**（看 `done.executions` 是否为空、服务端该行 `version` 是否 +1、有没有 `SyncChange`、切页与 force-stop 重启的对照），**据实修对应的那一层**。H3 与 H1/H2 相互独立，H3 无论写没写都要修。
7. **REQ-71 换的是「谁决策走哪条路」，不是改解析器**：`parseInput` 的规则本轮**一律不动**；改的是 `submitInput` 的落点判据。但**「在线」的判据本身不可信**（`navigator.onLine` + 桥接口存在性 ≠ 云端可达；captive portal / 未 VALIDATED 网络 / 服务端 `AI_AGENT_ENABLED=false` 都会被误判为在线）——**加固在线判定是本卡的组成部分，不是可选项**。另**两条链路的失败结局当前不一致**（单发回退本地 `:1427` vs agent 流转 `interrupted` `:1074`）：**必须在设计里二选一并统一**，否则「在线走云端」会让同一句话有时有结果、有时没有。
